What is application server?

An application server provides a managed runtime for business logic, handling connection pools, JMS, JTA, and EJB alongside its servlet container.

Definition

Implements Java EE/Jakarta EE specs: Servlet container, EJB container, JTA, JNDI, JMS — e.g., Oracle WebLogic, IBM WebSphere, JBoss.

Differs from a plain web server (Apache HTTP, Nginx) which only serves static content and proxies HTTP.

Banking angle

FLEXCUBE runs on Oracle WebLogic; admin server manages domain configuration while managed servers host the banking application.

DB connection pools are configured on WebLogic and looked up by the app via JNDI names like jdbc/flexDS.

Now coming to conclusion.

App servers are the backbone of enterprise banking deployments providing HA clustering and transactional resource management.

Web server vs application server.

A web server handles HTTP and static content; an application server adds full Java EE services like EJB, JTA, JMS, and connection pooling.

Differences

Web server (Apache HTTP, Nginx): static files, SSL termination, reverse proxy — no EJB or JTA support.

App server (WebLogic, JBoss): web container PLUS EJB, JMS, JTA, JNDI, connection pooling.

In banking: Nginx sits in front of WebLogic for SSL offloading and load balancing.

Now coming to conclusion.

Modern deployments combine both: web server for SSL/static, app server for dynamic banking business logic.

What is WAR file?

A WAR (Web Application Archive) is a JAR-formatted archive containing servlets, JSPs, HTML, and WEB-INF/web.xml for deployment to a servlet container.

Structure

Contains: /WEB-INF/web.xml (deployment descriptor), /WEB-INF/classes (compiled bytecode), /WEB-INF/lib (JARs), static resources.

Deployed to Tomcat or embedded in an EAR for deployment to a full app server.

Banking angle

FLEXCUBE web layer (REST controllers, JSF screens) is typically packaged as a WAR inside an EAR on WebLogic.

What is EAR file?

An EAR (Enterprise Application Archive) bundles multiple Java EE modules (WAR + EJB JARs) with a META-INF/application.xml descriptor for app-server deployment.

Structure

Contains: one or more WAR modules, EJB JARs, application-scoped lib/, and META-INF/application.xml.

Supports shared class loader across modules enabling cross-module JNDI lookups and transactions.

Banking angle

FLEXCUBE ships as an EAR combining the web WAR and EJB module; single deployment unit ensures consistent versioning on WebLogic.

WAR vs EAR.

A WAR packages a single web application; an EAR packages multiple Java EE modules (WAR + EJB) as one deployable unit with shared class loading.

Key differences

WAR: servlet/JSP apps, deployed to servlet container or app server web container.

EAR: enterprise apps with EJBs + WARs bundled, deployed to full app server; supports cross-module JTA transactions.

EAR has application-scoped class loader shared across modules; WAR has isolated web class loader.

Now coming to conclusion.

Use WAR for Spring Boot microservices; use EAR for legacy enterprise apps with EJBs like FLEXCUBE.

What is admin server and managed server?

In Oracle WebLogic, the admin server is the central management node while managed servers run the actual deployed applications.

Admin server

Hosts WebLogic Admin Console (port 7001); manages domain config, deployments, data sources, JMS servers.

Single point of configuration — changes pushed to managed servers via Node Manager.

Managed servers

Run deployed applications (EAR/WAR); grouped into clusters for load balancing and session failover.

In banking: separate managed server clusters for FLEXCUBE OLTP, OSB integration, and batch processing.

Now coming to conclusion.

Never run production applications on the admin server — reserve it for management only.

How does session replication work?

Session replication copies HTTP session state across cluster members so any server can handle a user request if another node fails.

Mechanisms

In-memory replication (WebLogic cluster default): each server holds replica of peer sessions via multicast/unicast heartbeat.

Database-backed sessions: session serialized to DB — survives full cluster restart but adds DB I/O per request.

Sticky sessions (no replication): load balancer always routes user to same node — simple but no failover.

Requirements

Session objects and all attributes must implement Serializable; non-serializable attributes cause replication failures.

Prefer stateless JWT-based auth in REST APIs to eliminate session replication overhead entirely.

Now coming to conclusion.

Banking apps should use stateless JWT tokens or serializable sessions with a configured replication group.

How do you configure connection pool?

A connection pool pre-creates and reuses DB connections, configured on WebLogic as a Data Source with JNDI name, driver URL, and pool size parameters.

WebLogic steps

Admin Console → Services → Data Sources → New Generic Data Source; set JNDI name (jdbc/oracleDS), driver, URL, credentials.

Set InitialCapacity, MaxCapacity, MinCapacity, TestConnectionsOnReserve=true, TestTableName='SQL SELECT 1 FROM DUAL'.

Key parameters

ConnectionReserveTimeoutSeconds: how long a thread waits for connection before throwing exception — prevents starvation.

StatementCacheSize: caches prepared statements per connection for Oracle performance improvement.

Banking angle

FLEXCUBE uses multiple data sources: OLTP DS (max 50 connections), batch DS (max 20), reporting DS (max 10) — each sized per workload.

Now coming to conclusion.

Always configure test-on-reserve and connection timeout to detect stale connections and prevent thread starvation.

How do you troubleshoot deployment failure?

Deployment failures on WebLogic require checking server logs, class-loading order, and descriptor validation to identify the root exception.

Steps

1. Check AdminServer.log and managed server log under domain/servers/<name>/logs/ for the root cause exception.

2. Look for ClassNotFoundException (missing JAR), version conflicts, or deployment descriptor validation errors.

3. Verify EAR/WAR structure is valid; use jar -tf app.ear to inspect contents.

Common causes

Missing JARs in EAR/lib, wrong context-root in application.xml, port already in use.

Java EE spec version mismatch — app compiled with newer APIs than server supports.

Now coming to conclusion.

Always deploy to staging managed server first and compare logs; never deploy directly to production cluster.

How do you check server logs?

WebLogic server logs reside under domain/servers/<name>/logs/ and are also accessible via the Admin Console Diagnostics tab.

Log locations

AdminServer.log: domain-wide events; <ServerName>.log: per-server runtime events including deployment and JTA.

wls-domain.log: aggregated domain log; access.log: HTTP access log with request/response details.

Useful commands

tail -f <ServerName>.log | grep -i ERROR to watch live errors on Unix.

Admin Console → Diagnostics → Log Files for browser-based log viewing with severity and time filters.

Now coming to conclusion.

Set log rotation and retention policies to prevent disk exhaustion on long-running banking production servers.

What is thread stuck issue?

A thread stuck alert in WebLogic fires when an execute thread is occupied beyond the configured stuck-thread-max-time (default 600 seconds), indicating blocking or deadlock.

Causes

Infinite loop, deadlock, or blocking I/O — waiting for slow DB query, external API timeout, or lock contention.

Connection pool exhaustion: thread waits indefinitely for a DB connection when pool is at MaxCapacity.

Resolution

Take thread dump (Admin Console → Servers → Monitoring → Threads or jstack <pid>) to identify blocked stack trace.

Fix the underlying slow query, add connection/read timeout on external calls, or increase pool size.

EOD batch holding row locks can cause stuck threads on OLTP server — isolate batch to a dedicated managed server.

Now coming to conclusion.

Take 3 thread dumps 10 seconds apart — truly stuck threads appear BLOCKED at the same frame in all dumps.

How do you troubleshoot high CPU in app server?

High CPU on an app server is diagnosed by combining OS thread identification (top) with Java thread dumps (jstack) to pinpoint the hot stack.

Steps

1. Run top -H -p <pid> (Linux) to find the OS thread ID with highest CPU; convert tid to hex.

2. Run jstack <pid> and find the thread whose nid matches the hex tid; examine its stack trace.

3. Look for RUNNABLE threads in tight loops, excessive GC (jstat -gcutil), or busy XML parsing.

Banking causes

Poorly written PL/SQL returning millions of rows processed in a Java loop; unbounded cache causing frequent full GC.

DEBUG-level logging in production; repeated XML parsing for high-volume SOAP messages.

Now coming to conclusion.

Fix GC-caused CPU by tuning heap and GC algorithm; fix logic CPU by profiling with async-profiler or JProfiler.

How do you tune JVM for app server?

JVM tuning for an app server involves setting heap size, GC algorithm, thread stack, metaspace, and enabling GC logging for ongoing analysis.

Heap and GC

-Xms4g -Xmx4g (equal to avoid resize pauses); typical banking servers: 4–16 GB depending on session load.

-XX:+UseG1GC for balanced throughput/latency; -XX:MaxGCPauseMillis=200 to cap STW pauses.

Enable GC log: -Xlog:gc*:file=gc.log:time (JDK 9+); analyze with GCEasy or GCViewer.

Other parameters

-Xss256k: reduce thread stack size to fit more threads in available memory.

-XX:MaxMetaspaceSize=512m: cap metaspace growth from dynamic class generation (e.g., Spring proxies).

Now coming to conclusion.

Always baseline before tuning, change one parameter at a time, and validate with a realistic load test.
