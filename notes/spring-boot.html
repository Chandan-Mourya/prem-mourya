Fundamentals
What is Spring Boot? must

Spring Boot is an opinionated layer on top of the Spring Framework that lets you build production-ready Java apps with minimal boilerplate. The big ideas:

  • Auto-configuration — sensible defaults based on what's on the classpath.
  • Starters — curated dependency bundles (spring-boot-starter-web, -data-jpa, etc.).
  • Embedded servers — Tomcat/Jetty/Undertow built in; deploy a fat JAR with java -jar.
  • Externalized config via application.yml + profiles + environment variables.
  • Actuator for production endpoints (health, metrics, info).

Before Spring Boot we spent days on XML config and packaging. Today I bootstrap a new service from start.spring.io in 10 minutes. It's the standard for Java microservices.

Auto-Configuration in Spring Boot — how it works internally must

Auto-configuration is the feature that makes Spring Boot feel like magic — drop a library on the classpath and Spring Boot automatically creates and wires the beans you need for it (DataSource, DispatcherServlet, ObjectMapper, EntityManager, etc.). It's the reason you can go from an empty pom.xml to a running REST API in 30 seconds.

CORE IDEA Spring Boot ships hundreds of pre-written auto-configuration classes. At startup, @EnableAutoConfiguration walks through them and asks: "Are the right libraries on the classpath? Has the user already defined this bean? Is this property enabled?" If yes → it creates the bean. If no → it backs off silently.

The end-to-end mechanism — what happens when you start a Spring Boot app:

1. @SpringBootApplication includes @EnableAutoConfiguration
↓
2. Spring loads the list of auto-config classes from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
↓
3. Each auto-config class is evaluated against its @Conditional* rules
↓
4. Spring checks the classpath, existing beans, and properties
↓
5. Conditions met → the auto-config's @Bean methods run and register beans
↓
6. Conditions not met → Spring silently skips that auto-config

The conditional annotations you need to know:

AnnotationTriggers when…Typical use
@ConditionalOnClassA class is on the classpath.Configure JPA only if Hibernate jar is present.
@ConditionalOnMissingBeanThe user hasn't already defined a bean of that type.Provide a default that the user can override.
@ConditionalOnBeanSome other bean already exists in the context.Configure something only after its prerequisite bean is there.
@ConditionalOnPropertyA specific property is set in application.yml.Enable a feature only when app.feature.x=true.
@ConditionalOnMissingClassA class is not on the classpath.Fall back when an optional dep is absent.
@ConditionalOnWebApplicationRunning in a servlet / reactive web context.Skip web beans for non-web apps.
@ConditionalOnResourceA given resource is on the classpath.Configure something only if a file exists.
@ConditionalA custom Condition class returns true.Anything else you can imagine.

A real Spring Boot auto-config class — simplified:

@AutoConfiguration
@ConditionalOnClass(DataSource.class)            // only if JDBC API is on classpath
@EnableConfigurationProperties(DataSourceProperties.class)
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                    // back off if user defined their own
    public DataSource dataSource(DataSourceProperties props) {
        return DataSourceBuilder.create()
            .url(props.getUrl())
            .username(props.getUsername())
            .password(props.getPassword())
            .build();
    }
}

That's literally what makes "drop a JDBC driver, get a working DataSource" happen. Same pattern for WebMvcAutoConfiguration, JacksonAutoConfiguration, RedisAutoConfiguration, KafkaAutoConfiguration, etc.

How to inspect or control auto-configuration:

  • --debug startup flag — prints the full auto-configuration report: which configs matched, which were negative-matched (and why), and which are unconditional.
  • Actuator /actuator/conditions — same report exposed over HTTP for production introspection.
  • Exclude an auto-config at the source: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class).
  • Exclude via property in application.yml: spring.autoconfigure.exclude=....
  • Override a bean — just declare your own @Bean; @ConditionalOnMissingBean means Spring will use yours.
  • Order — control evaluation order with @AutoConfigureBefore, @AutoConfigureAfter, @AutoConfigureOrder.

Writing your own auto-configuration (for a custom starter):

// 1) Auto-config class
@AutoConfiguration
@ConditionalOnClass(GreeterClient.class)
@EnableConfigurationProperties(GreeterProperties.class)
public class GreeterAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public GreeterClient greeterClient(GreeterProperties props) {
        return new GreeterClient(props.getUrl());
    }
}

// 2) Register it for Spring to discover
// src/main/resources/META-INF/spring/
//   org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.example.greeter.GreeterAutoConfiguration

Pack this into a JAR, add it to pom.xml, and any Spring Boot app that includes it gets the GreeterClient bean automatically — same way Spring Boot's own auto-configs work.

Why auto-configuration matters:

Without auto-configuration
  • Hundreds of lines of XML or @Bean methods.
  • Wire DispatcherServlet, message converters, view resolvers manually.
  • Hand-code DataSource, EntityManager, TransactionManager.
  • Library upgrades require config rework.
With auto-configuration
  • Drop a starter; the beans appear.
  • Sensible defaults; override only what's different.
  • Library upgrades carry config along automatically.
  • Same app code works in dev, test, prod with profile-specific overrides.

Common interview gotchas:

  • Auto-configs are conditional, not unconditional — they only kick in when their conditions match.
  • User beans win — @ConditionalOnMissingBean is the standard pattern, so your @Bean overrides the default cleanly.
  • Use --debug or /actuator/conditions when something is or isn't wiring as expected.
  • Not every starter has its own auto-config — some just bring deps; the real auto-configs are inside spring-boot-autoconfigure.
  • Order matters for plug-ins — use @AutoConfigureBefore/After when your custom config depends on Spring's defaults.
  • It's evaluated at startup — auto-configuration decisions are final; you can't add/remove beans dynamically based on runtime state.

Interview one-liner: Spring Boot auto-configuration automatically creates and wires beans based on what's on the classpath, what beans the user has already defined, and what properties are set. @SpringBootApplication includes @EnableAutoConfiguration, which loads dozens of auto-configuration classes from META-INF/spring/...AutoConfiguration.imports. Each class uses conditional annotations — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty — to decide whether its @Bean methods run. So adding spring-boot-starter-data-jpa with a JDBC driver triggers DataSourceAutoConfiguration, HibernateJpaAutoConfiguration, etc., and you get a working DataSource + EntityManagerFactory + TransactionManager without writing any XML. Your own @Bean always wins because the defaults back off via @ConditionalOnMissingBean.

Spring Boot Starters — what they are and why they exist must

Spring Boot Starters are curated dependency bundles — pre-packaged POMs that pull in everything you need for a specific use case (web, JPA, security, testing, monitoring), with all the version compatibilities pre-resolved by the Spring team. Add one starter and you skip the painful "which version of Spring + Jackson + Tomcat works together" research.

CORE IDEA A starter is just a POM that depends on other POMs. Add spring-boot-starter-web and you get Spring MVC + embedded Tomcat + Jackson + Validation, all at versions that have been tested together. Combined with @EnableAutoConfiguration, those libraries also wire themselves up automatically.

Why starters matter — the benefits at a glance:

  • Reduced dependency management — one line in pom.xml instead of 8.
  • No version conflicts — Spring Boot's BOM pins every transitive dependency to a tested version.
  • Faster project setup — you go from start.spring.io to "hello world REST API" in minutes.
  • Auto-configuration synergy — adding the starter is enough; you don't write XML or @Beans for the typical case.
  • Predictable upgrades — bump Spring Boot version → all your starters move together.

Common interview gotchas:

  • Starter ≠ runtime magic — a starter just adds JARs to the classpath. The actual wiring is done by @EnableAutoConfiguration.
  • Starters carry no business logic — they're empty POMs that depend on other POMs.
  • You can exclude transitive deps if a starter brings in something you don't want (e.g., exclude Tomcat to use Undertow instead).
  • Tests should use spring-boot-starter-test only with <scope>test</scope> — it's a heavy umbrella dep.
  • Version is managed by the BOM — never put a version on a starter; the parent POM (spring-boot-starter-parent) controls it.

Starters reduce dependency management, avoid version conflicts, speed up setup, and enable auto-configuration — and large orgs often build internal starters to standardise observability, security, and config across all microservices.

Custom Spring Boot Starter — how to design one for your organization must

A custom Spring Boot starter is an internal library that packages your organisation's common cross-cutting concerns — logging, audit, security, exception handling, tracing, Redis, REST client defaults — into a single, auto-configured Maven dependency. Instead of copy-pasting the same @Configuration classes, filters, and YAML across 30 microservices, every service gets the standard setup by adding one line to its pom.xml.

CORE IDEA Package common org-wide functionality as an auto-configured dependency. The starter brings the JARs; an @AutoConfiguration class wires the beans via conditional annotations; @ConfigurationProperties exposes toggles. Add the dependency — features turn on automatically. Override safely via properties or by defining your own bean.

What typically goes inside an org-level starter:

Logging
Structured JSON layout, correlation IDs, MDC propagation, standard log fields.
Security
JWT / OAuth2 resource-server filter, common auth rules, CORS defaults.
Audit
Request/response capture filter, who-did-what records, PII masking.
Exception handling
Global @ControllerAdvice + standard error JSON envelope.
REST client
RestTemplate / WebClient with timeouts, retries, interceptors.
Distributed tracing
Micrometer / Sleuth + OpenTelemetry exporter wiring.
Redis / cache
Common RedisTemplate, serializer, cache manager defaults.
Metrics & Actuator
Standard Actuator endpoints, tags, Prometheus registry config.

How a starter is structured — the two-module pattern:

ModulePurpose
xxx-spring-boot-autoconfigureHolds the actual @AutoConfiguration classes, @ConfigurationProperties, conditional beans, and the AutoConfiguration.imports file. All real code lives here.
xxx-spring-boot-starterThin module — empty JAR with a pom.xml that depends on the autoconfigure module plus any required transitive deps (e.g. spring-boot-starter-web). Consumers add only this.

Splitting them lets a consumer depend on -autoconfigure alone (e.g. to opt into beans without forcing transitive deps), while the -starter is the convenient one-line "just give me everything" entry point.

Step-by-step design:

Identify common functionality repeated across microservices (logging, audit, security, tracing...)
↓
Create the xxx-spring-boot-autoconfigure module — this is where real code lives
↓
Define @ConfigurationProperties classes for toggles & tunables (prefix per feature)
↓
Write the auto-configuration class with @AutoConfiguration + conditional annotations (@ConditionalOnClass, @ConditionalOnProperty, @ConditionalOnMissingBean)
↓
Register it via META-INF/spring/...AutoConfiguration.imports (Boot 3) or META-INF/spring.factories (Boot ≤ 2.7)
↓
Wrap it into the thin xxx-spring-boot-starter module that just declares the autoconfigure dep + required transitive deps
↓
Publish both artifacts to internal Nexus / Artifactory (semantic version pinned to a Spring Boot line)
↓
Other services add the starter as a single dependency — features are auto-enabled, override via application.yml when needed

1) Define your @ConfigurationProperties:

@ConfigurationProperties(prefix = "org.audit")
public class AuditProperties {
    private boolean enabled = true;
    private String logLevel = "INFO";
    // getters/setters
}

2) The auto-configuration class — conditionals are the whole game:

@AutoConfiguration
@EnableConfigurationProperties(AuditProperties.class)
@ConditionalOnClass(AuditFilter.class)
@ConditionalOnProperty(
    name = "org.audit.enabled",
    havingValue = "true",
    matchIfMissing = true)
public class AuditAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean
    public AuditFilter auditFilter(AuditProperties props) {
        return new AuditFilter(props.getLogLevel());
    }
}

The combination is deliberate: @ConditionalOnClass guards classpath presence, @ConditionalOnProperty lets a service opt out with one line of YAML, and @ConditionalOnMissingBean means a consuming service can override the filter by simply defining its own AuditFilter bean.

3) Register the auto-config so Spring Boot discovers it:

# src/main/resources/META-INF/spring/
#   org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.acme.audit.AuditAutoConfiguration

On Spring Boot 2.x the equivalent lived in META-INF/spring.factories under the org.springframework.boot.autoconfigure.EnableAutoConfiguration key — Boot 3 deprecated that in favour of the cleaner AutoConfiguration.imports file.

Conditional annotations — the key building blocks:

AnnotationPurpose
@ConditionalOnClassOnly activate the config when a given class is on the classpath — gate features by JAR presence.
@ConditionalOnMissingBeanOnly register the bean if the consumer hasn't defined one — makes your starter override-safe.
@ConditionalOnPropertyToggle the bean via a property (org.audit.enabled=false) — clean opt-in / opt-out.
@ConditionalOnBeanOnly register when another required bean already exists (e.g. a MeterRegistry before adding tracing).
@ConditionalOnWebApplicationActivate only for Servlet / Reactive web apps — skip in CLI / batch services.
@AutoConfigureBefore / @AutoConfigureAfterOrder one auto-config relative to another when bean dependencies require it.

4) How a consuming microservice uses it — one Maven dep:

<dependency>
    <groupId>com.acme</groupId>
    <artifactId>audit-spring-boot-starter</artifactId>
    <version>1.2.0</version>
</dependency>

Override defaults from application.yml — no Java config required:

org:
  audit:
    enabled: true
    log-level: DEBUG

Design principles for a good starter:

  • Opt-in by default vs opt-out — pick consciously per feature; expose a single enabled property either way.
  • Sensible defaults — a fresh consumer should get useful behaviour with zero configuration.
  • Never override user beans — every @Bean should carry @ConditionalOnMissingBean.
  • Fully configurable via properties — typed @ConfigurationProperties, not scattered @Value lookups.
  • Don't leak required deps — only declare the minimum transitive deps; let consumers bring their own web / JPA / Redis starter.
  • Semantic versioning + Spring Boot alignment — keep a BOM or pin tightly to a Spring Boot minor line.
  • Ship additional-spring-configuration-metadata.json — so IDEs autocomplete your custom properties just like Spring's own.

Real-world example:

Picture a fictional acme-audit-spring-boot-starter. A team adds it to their pom.xml. On startup the auto-config sees AuditFilter on the classpath and org.audit.enabled defaulting to true — so it registers an AuditFilter in the servlet chain, wires a JSON logger with correlation IDs, and exposes /actuator/audit-events. Zero Java config in the consuming service; if they need to disable it temporarily for a load test, one line in application-perf.yml (org.audit.enabled: false) is enough.

Common interview gotchas:

  • Forgetting to register the auto-config class in AutoConfiguration.imports — Spring silently never loads it; no error, just "why aren't my beans wired?".
  • Using @Configuration instead of @AutoConfiguration on Spring Boot 3+ — works partially, but auto-config ordering and conditional resolution misbehave.
  • Overriding user beans because you forgot @ConditionalOnMissingBean — consumers can't replace your defaults.
  • Heavy transitive deps leaked from the starter (e.g. dragging in spring-boot-starter-web when not needed) — bloats every consumer.
  • Single module vs two — the official convention is two: -autoconfigure (code) + -starter (thin pom). Single-module starters work but break consumer flexibility.
  • Versioning misalignment with Spring Boot — a starter built for Boot 2.7 can break on Boot 3 (Jakarta namespace, removed APIs). Keep a BOM or pin tightly.
  • No additional-spring-configuration-metadata.json — IDE autocomplete doesn't work for your custom properties; consumers hit typos at runtime instead of compile-time.

Interview one-liner: Building a custom Spring Boot starter for your organisation is a five-step recipe — identify the common functionality (logging, audit, security, tracing), create an -autoconfigure module with @ConfigurationProperties + conditional beans, register the auto-config in META-INF/spring/...AutoConfiguration.imports (or spring.factories on Boot 2.x), wrap it in a thin -starter module that just declares the autoconfigure dep, and publish to your internal Maven repo (Nexus / Artifactory). Conditional annotations — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty — make the starter flexible, override-safe, and opt-in: every consuming microservice gets the standard org behaviour with one Maven dependency, and can still override any bean or toggle any feature from application.yml.

Spring Profiles — managing configs across dev / qa / prod must

Spring Profiles let one codebase run with environment-specific configuration — a different DB in dev vs prod, different log levels, different API keys, even different beans — without changing a single line of business code. You pick the profile at startup, Spring loads the matching configuration and beans, and the same JAR works everywhere from your laptop to production.

CORE IDEA One JAR, many environments. A profile is a label (dev, qa, prod); Spring loads application-{profile}.yml and any @Profile("…") beans for the active profile(s). Change the environment by changing one flag — not by rebuilding.

Why profiles exist — the problem they solve:

  • Different DB URLs — local H2 vs AWS RDS in prod.
  • Different secrets / API keys — sandbox vs live payment gateway.
  • Different log levels — DEBUG everywhere in dev, INFO/WARN in prod.
  • Different infrastructure — in-memory message broker locally, real Kafka in prod.
  • Different caches — Caffeine in dev, Redis in prod.

Hardcoding any of these makes the JAR environment-specific; profiles keep the build environment-agnostic.

Profile-specific config files:

src/main/resources/
├── application.yml          # base config — loaded ALWAYS
├── application-dev.yml      # only when 'dev' is active
├── application-qa.yml       # only when 'qa' is active
└── application-prod.yml     # only when 'prod' is active

Example contents:

# application.yml — common defaults
spring:
  application:
    name: order-service
  jpa:
    hibernate:
      ddl-auto: validate

# application-dev.yml
spring:
  datasource:
    url: jdbc:h2:mem:dev

  level:
    root: DEBUG

# application-prod.yml

  datasource:
    url: jdbc:postgresql://db.prod.internal:5432/orders

How Spring picks up the active profile — internal flow:

1. Application starts → SpringApplication.run(...)
↓
2. Spring reads spring.profiles.active from env var / CLI / system property / YAML
↓
3. Loads application.yml (base defaults)
↓
4. Loads application-{active}.yml on top — keys override the base
↓
5. Component scan + @Profile filter — only beans matching the active profile(s) are registered
↓
6. App is ready with the right config + right beans

@Profile annotation — profile-scoped beans:

// Only in dev
@Configuration
@Profile("dev")
public class DevConfig {
    @Bean
    public DataSource dataSource() {
        return new EmbeddedDatabaseBuilder().setType(H2).build();
    }
}

// Only in prod
@Configuration
@Profile("prod")
public class ProdConfig {
    @Bean
    public DataSource dataSource(@Value("${db.url}") String url) {
        return DataSourceBuilder.create().url(url).build();
    }
}

Other useful patterns:

  • @Profile("!prod") — load when prod is not active.
  • @Profile({"dev", "qa"}) — load in dev or qa.
  • @Profile("dev & debug") — load only if both are active (Spring 5.1+).

Property resolution order — later wins:

  1. application.yml (base)
  2. application-{profile}.yml
  3. Config in external locations (--spring.config.location=...)
  4. OS environment variables
  5. Command-line arguments (highest precedence)

This ordering is what lets prod override the YAML defaults using just env vars — perfect for containers.

Best practices — production checklist:

  • Never check in secrets — use placeholders (password: ${DB_PASSWORD}) backed by env vars / AWS Secrets Manager / Vault.
  • Don't hardcode spring.profiles.active=prod in YAML — set it via env var in the deployment.
  • Keep base config minimal — only truly shared defaults belong in application.yml.
  • One profile = one concern — prod, aws, kafka-enabled compose better than prod-aws-kafka.
  • Default profile — Spring uses default if none is active. Don't rely on it in prod.
  • Use @Profile sparingly — for radically different beans (stub vs real, in-memory vs Redis). For simple value changes, properties are cleaner.

Common interview gotchas:

  • Default profile — if you don't set one, Spring uses default. Logs always show the active profile at startup; grep "The following profiles are active".
  • Beans not loading? — check the profile filter; @Profile mismatch means the bean isn't even registered.
  • YAML key conflicts — profile-specific keys override base; same key in two active profiles → later in the comma list wins.
  • @Profile on tests — use @ActiveProfiles("test") in JUnit; the Spring TestContext loads the matching config.
  • Profiles ≠ feature flags — profiles are a startup decision; feature flags can change at runtime. Don't abuse profiles as toggles.
  • Secrets in YAML — never. Use env-var placeholders or external config services.

Interview one-liner: Spring Profiles let one codebase carry environment-specific configuration for dev, QA, prod, and beyond. Spring loads application.yml first, then layers application-{profile}.yml on top based on spring.profiles.active — set via environment variable, CLI argument, or property. Beans can be scoped with @Profile("…") so different implementations load per environment — e.g. an in-memory broker in dev vs Kafka in prod. The same JAR runs everywhere; only the active profile changes. Combined with secret managers and env-var placeholders, profiles give clean, maintainable, environment-aware configuration without rebuilding the app.

@Value — injecting properties / env vars into beans must

@Value is a Spring annotation that injects values into bean fields, constructor parameters, or setter parameters — values pulled from application.properties/.yml, environment variables, system properties, or computed from SpEL expressions. It's how configuration becomes code at runtime.

CORE IDEA Don't hard-code config (URLs, ports, API keys, feature flags) inside Java classes. Declare a placeholder with @Value("${...}"), and Spring resolves it from the property sources at bean creation time. Same code, different config per environment.

Basic example:

// application.properties
app.name=MyApplication
server.port=8080

// Java
@Component
public class AppInfo {

    @Value("${app.name}")
    private String appName;

    @Value("${server.port}")
    private int port;
}

Spring injects "MyApplication" into appName and 8080 into port when the bean is constructed.

Default values — never crash on a missing property:

@Value("${server.port:8080}")        // default 8080 if not set
private int port;

@Value("${feature.dark-mode:false}") // default false
private boolean darkModeEnabled;

@Value("${app.greeting:Hello}")
private String greeting;

Inject environment variables and system properties:

@Value("${JAVA_HOME}")           // env var
private String javaHome;

@Value("${user.timezone:UTC}")   // JVM system property with default
private String timezone;

Spring's ${...} placeholder resolves against all property sources in priority order — command-line args > env vars > application-{profile}.yml > application.yml.

Lists, maps, and SpEL expressions:

// Comma-separated list
@Value("${app.allowed-origins}")              // app.allowed-origins=a.com,b.com
private List<String> allowedOrigins;

// SpEL — Spring Expression Language
@Value("#{T(java.lang.Math).random() * 100}")
private double random;

@Value("#{systemProperties['user.home']}")
private String home;

@Value("#{otherBean.someProperty}")           // read from another bean
private String fromAnotherBean;

Use it on a constructor parameter (preferred — same reasoning as DI):

@Service
public class PaymentService {
    private final String apiKey;
    private final Duration timeout;

    public PaymentService(@Value("${payment.api-key}") String apiKey,
                          @Value("${payment.timeout:5s}") Duration timeout) {
        this.apiKey = apiKey;
        this.timeout = timeout;
    }
}

Constructor injection of @Value keeps fields final and makes unit-testing trivial — no Spring context, just pass strings.

Where @Value is commonly used:

Configuration values
App name, server port, base URLs, timeouts, retry counts.
API keys & credentials
Externalised secrets read from env vars or Vault — never in source.
Database / broker configs
JDBC URL, username, Kafka bootstrap servers.
Feature flags
@Value("${feature.new-search:false}") — flip behaviour by env.
Environment variables
JAVA_HOME, HOSTNAME, region info for cloud apps.
Defaults for safe fallback
Keep apps booting even if a property is missing.

How Spring resolves @Value internally:

1. Spring loads all PropertySources at startup — application.yml, profile files, env vars, command-line args.
↓
2. When a bean is being created, Spring scans its fields/constructors for @Value.
↓
3. The PropertySourcesPlaceholderConfigurer resolves ${...} placeholders against the loaded sources.
↓
4. The raw String value is converted to the target type (int, boolean, Duration, List<String>) via Spring's ConversionService.
↓
5. Typed value is injected into the field/parameter — bean is now usable.

@Value vs @ConfigurationProperties — which to use:

@Value("${...}")
  • One value at a time — quick and direct.
  • Supports defaults and SpEL.
  • No type safety beyond Spring's conversion.
  • Best for: a few stand-alone properties, env vars, feature flags.
@ConfigurationProperties
  • Binds a whole group of properties to a typed POJO/record.
  • Built-in validation (@Validated, @NotNull, @Min).
  • IDE autocomplete with spring-boot-configuration-processor.
  • Best for: large, grouped configs like app.* or payment.*.

Best practices and gotchas:

  • Always provide defaults (${...:default}) for non-critical config — your app should boot even with a missing property.
  • Prefer constructor injection of @Value over field injection — final fields, no reflection in tests.
  • Use @ConfigurationProperties for grouped config instead of scattering 20 @Values across a class.
  • Never put secrets in application.yml — reference an env var or Vault: ${DB_PASSWORD}.
  • Watch out for ${...} vs #{...} — ${} is property placeholder, #{} is SpEL (totally different resolution rules).
  • @Value doesn't work on static fields — use a setter on an instance field or a static @PostConstruct hack (don't).
  • It only works on Spring-managed beans — using @Value on a class you instantiate with new does nothing.

Interview one-liner: @Value is the Spring Boot annotation used to inject values from application.properties/.yml, environment variables, or system properties into Spring beans — with support for defaults (${key:default}) and SpEL expressions (#{...}). It's commonly used for configuration values, API keys, DB configs, feature flags, and per-environment tuning. Spring resolves the placeholder against all loaded PropertySources during bean creation and converts the raw string to the target type. For a few stand-alone properties, use @Value; for a whole group of related properties, prefer @ConfigurationProperties — it's type-safe, validatable, and IDE-friendly.

Reading values from application.yml — @Value vs @ConfigurationProperties must

Spring Boot loads externalized configuration from application.properties / application.yml at startup. There are two main ways to read those values into your beans: @Value for individual properties, and @ConfigurationProperties for whole groups of related, type-safe configuration.

CORE IDEA @Value — quick, one property at a time, string-based. @ConfigurationProperties — declarative, binds an entire prefix to a typed POJO with validation and IDE autocomplete. Use the first for one-off values, the second for grouped config.

Same YAML, two reading styles:

# application.yml
app:
  name: MyApp
  port: 8080
  admin-email: ops@example.com
  retry:
    max-attempts: 3
    backoff: 500ms
1) With @Value — one property at a time
@Component
public class AppInfo {
    @Value("${app.name}")
    private String name;

    @Value("${app.port:8080}")    // default
    private int port;

    @Value("${app.admin-email}")
    private String adminEmail;
}
  • Fine for 1–2 fields.
  • No type safety beyond Spring's conversion.
  • Default values via ${key:default}.
  • Supports SpEL: #{T(Math).random()}.
2) With @ConfigurationProperties — grouped, typed
@ConfigurationProperties(prefix = "app")
@Component                // or use @EnableConfigurationProperties
public class AppConfig {

    private String name;
    private int port = 8080;     // default
    private String adminEmail;
    private Retry retry = new Retry();

    // getters & setters (or use Lombok @Data / record)

    public static class Retry {
        private int maxAttempts = 3;
        private Duration backoff = Duration.ofMillis(500);
        // getters & setters
    }
}
  • Binds the whole app.* tree in one shot.
  • Type-safe — int, Duration, List, nested POJOs.
  • Supports validation and IDE autocomplete.
  • Cleanest for large/nested configs.

Validation — a big @ConfigurationProperties win:

Common interview gotchas:

  • Relaxed binding — @ConfigurationProperties accepts app.adminEmail, app.admin-email, APP_ADMIN_EMAIL for the same field. Very forgiving with env vars.
  • Need setters (or constructor binding) — POJO style needs getters/setters; record / Lombok handles it for you.
  • Activate the bean — either annotate the class with @Component + @ConfigurationProperties, or use @EnableConfigurationProperties(AppConfig.class) on a config class.
  • Don't mix excessively — once you have more than ~3 @Values pointing at the same prefix, switch to @ConfigurationProperties.
  • Secrets — store in env vars / Vault / AWS Secrets Manager, then reference with placeholders: password: ${DB_PASSWORD}.

Use @Value for one-off values; use @ConfigurationProperties for any non-trivial grouped configuration. The general rule: more than a couple of related properties → switch to @ConfigurationProperties.

@SpringBootApplication — what does it do internally? must

@SpringBootApplication is the single annotation that turns a plain Java class into a Spring Boot application. It's a convenience meta-annotation that bundles three foundational Spring annotations together — replacing what used to be dozens of lines of XML configuration in old-school Spring.

CORE IDEA @SpringBootApplication = @Configuration + @EnableAutoConfiguration + @ComponentScan. Mark one class with it, run SpringApplication.run(...), and Spring Boot handles bean discovery, auto-configuration, and embedded-server startup for you.

What the annotation actually looks like under the hood:

@Retention(RetentionPolicy.RUNTIME)

public @interface SpringBootApplication { ... }

Why it matters:

  • Zero XML — replaces hundreds of lines of applicationContext.xml from old Spring.
  • Convention over configuration — sensible defaults; you only override what's different.
  • Auto-wiring of infrastructure — DataSource, web server, security, message brokers configured automatically when their libs are present.
  • One-class bootstrap — every Spring Boot app starts the same way: one annotated class + SpringApplication.run(...).
  • Conditional & overridable — define your own bean and Spring Boot will back off (@ConditionalOnMissingBean) — you get the default unless you override it.

Common interview gotchas:

  • Main class must be in the root package — otherwise @ComponentScan misses your beans.
  • Auto-configuration is conditional — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty. Use --debug or check /actuator/conditions to see which were applied.
  • Excluding auto-configs — use exclude = ... or set spring.autoconfigure.exclude property.
  • You can have only one main class with @SpringBootApplication per Spring Boot app — but you can split config into multiple @Configuration classes if needed.
  • @SpringBootApplication is also a @Configuration — meaning you can put @Bean methods directly in the main class.

Interview one-liner: @SpringBootApplication is a meta-annotation that combines @Configuration (marks the class as a Spring config), @EnableAutoConfiguration (auto-wires beans based on what's on the classpath — DB, web server, security, etc.), and @ComponentScan (discovers @Component/@Service/@Repository/@Controller beans from the package of the main class and below). When SpringApplication.run(...) is called, Spring Boot loads properties, scans for beans, applies conditional auto-configurations, wires dependencies, and starts the embedded server — replacing hundreds of lines of XML with a single annotation and a 5-line main class.

Embedded server — Tomcat, Jetty, Undertow?

Spring Boot ships Tomcat by default — battle-tested, well-documented, fine for most loads. Jetty is the long-standing alternative — slightly lower memory, used historically by Eclipse and many cloud platforms. Undertow (Red Hat) is the most performant and lowest memory of the three, especially for high-concurrency workloads with many idle connections.

Switching is one dependency change:

<exclusion>spring-boot-starter-tomcat</exclusion>
<dependency>spring-boot-starter-undertow</dependency>

I've defaulted to Tomcat in every prod service I've shipped — its tooling and observability story is best. With Spring Boot 3 + Virtual Threads on Tomcat, the throughput is excellent and I don't feel the need to switch. For reactive workloads, Spring WebFlux uses Netty by default instead.

Testing in Spring Boot — @WebMvcTest vs @SpringBootTest (and friends) must

Spring Boot ships a family of test slice annotations so you don't have to spin up the entire application context just to verify a controller, a JPA repository, or a JSON serializer. Each slice loads only the beans relevant to that layer, which makes tests dramatically faster and more focused — leaving full @SpringBootTest for true end-to-end integration tests.

CORE IDEA @WebMvcTest loads only the web layer (controllers, filters, MockMvc) — it's a fast slice test. @SpringBootTest loads the full application context (every bean, real DB, embedded server) — it's an integration test. Pick the smallest slice that proves what you need; reach for the full context only when you must.

@WebMvcTest vs @SpringBootTest at a glance:

@WebMvcTest — slice test
  • Loads: only MVC infrastructure — @Controller/@RestController, @ControllerAdvice, filters, MockMvc, Jackson converters.
  • Mocked: @Service, @Repository, DataSource — provide them with @MockBean / @MockitoBean.
  • Use for: controller routing, request validation, status codes, JSON shape, exception handling.
  • Speed: very fast (~1 s) — tiny context, no DB, no embedded server.
@SpringBootTest — integration test
  • Loads: the full ApplicationContext via @SpringBootApplication — every @Service, @Repository, configuration, and auto-config.
  • Real beans: real services, real JPA repositories, real (or in-memory / Testcontainers) DB.
  • Use for: end-to-end flows — HTTP → controller → service → DB → response.
  • Speed: slow (5–30 s startup) — share the context across tests where possible.

@WebMvcTest example — controller with a mocked service:

@WebMvcTest(UserController.class)              // load ONLY UserController
class UserControllerTest {

    @Autowired
    private MockMvc mockMvc;                    // auto-configured by @WebMvcTest

    @MockBean                                   // Spring Boot 3.4+: prefer @MockitoBean
    private UserService userService;            // service layer is MOCKED

    @Test
    void getUser_returns200_andUserJson() throws Exception {
        when(userService.findById(42L))
            .thenReturn(new User(42L, "Prem", "prem@example.com"));

        mockMvc.perform(get("/users/{id}", 42L)
                    .accept(MediaType.APPLICATION_JSON))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.id").value(42))
               .andExpect(jsonPath("$.name").value("Prem"))
               .andExpect(jsonPath("$.email").value("prem@example.com"));

        verify(userService).findById(42L);
    }

    @Test
    void getUser_unknownId_returns404() throws Exception {
        when(userService.findById(99L))
            .thenThrow(new UserNotFoundException(99L));

        mockMvc.perform(get("/users/{id}", 99L))
               .andExpect(status().isNotFound());
    }
}

Notice: no UserService implementation, no DB, no embedded Tomcat — just the controller + MockMvc + a Mockito mock. Fast, focused, deterministic — exactly what's needed to assert the HTTP contract.

@AutoConfigureTestDatabase                     // swap real DB for in-memory H2

Common interview gotchas:

  • @WebMvcTest doesn't load @Service or @Repository beans — provide them with @MockBean (or @MockitoBean in 3.4+) or the context will fail to start with "bean not found".
  • @SpringBootTest is slow because it spins up the entire context — share it across tests (Spring caches contexts by configuration), and use @DirtiesContext sparingly since it forces a rebuild.
  • Use @AutoConfigureMockMvc when you need MockMvc inside a @SpringBootTest — @WebMvcTest auto-configures it for you, but the full integration test does not.
  • In Spring Boot 3.4+ prefer @MockitoBean over the deprecated @MockBean — same idea, but it's part of Spring Framework directly and is the going-forward API.
  • For DB integration use @Testcontainers + a real DB image (PostgreSQL, MySQL) instead of H2 to catch dialect-specific bugs your prod DB would hit.
  • Test classpath must contain spring-boot-starter-test — it brings JUnit 5, AssertJ, Mockito, MockMvc, Hamcrest, and JSONassert in one curated bundle.
  • @SpringBootTest(webEnvironment = ...) modes: MOCK (default — no port, mocked servlet env), RANDOM_PORT (real embedded server on a random port), DEFINED_PORT (use the configured port), NONE (no web env at all).

Interview one-liner: @WebMvcTest is a Spring Boot slice test that loads only the web layer (controllers + MockMvc) and forces you to mock services with @MockBean / @MockitoBean, while @SpringBootTest boots the full application context for end-to-end integration testing, typically with RANDOM_PORT + TestRestTemplate and a real (or Testcontainers-managed) database. The broader Spring Boot philosophy is "pick the smallest slice that proves what you need" — @DataJpaTest for repositories, @JsonTest for serialization, @RestClientTest for outbound HTTP, @WebFluxTest for reactive controllers — and only fall back to @SpringBootTest when the test genuinely needs the whole app wired together.

Liveness vs Readiness — Kubernetes integration:

Liveness — /health/liveness

"Is the app alive?"

  • If DOWN → K8s restarts the pod.
  • Should check only fatal in-process state (OOM, broken internal threads).
  • Never check downstream services — a flaky DB shouldn't restart the pod.
Readiness — /health/readiness

"Is the app ready to serve traffic?"

  • If DOWN → K8s removes the pod from the Service endpoints (no restart).
  • Should check critical dependencies (DB, downstream service).
  • Use during slow JVM startup so traffic doesn't hit a half-ready pod.

Debugging a memory leak in Spring Boot production — heap dumps, GC logs, common causes hot

Production memory leaks rarely crash the app immediately — they degrade it gradually. Heap usage drifts up, Full GC fires more often, pauses get longer, response times climb, and eventually the JVM dies with OutOfMemoryError: Java heap space. The mistake people make under pressure is restart first, investigate later — but a restart wipes the only evidence you have. Unless the app is genuinely unstable, collect data before restarting: a heap dump, GC logs, and Actuator metrics.

CORE IDEA Symptoms → snapshot the heap → analyse dominators in MAT → identify retained roots → fix the source in code. Don't restart blindly — every restart costs you the dump that would have told you what was wrong.

Symptoms — how a leak looks in production:

  • Heap usage continuously rising over hours/days, not stabilising after Full GC.
  • GC frequency increasing — Young GC every few seconds, Full GC every few minutes.
  • Longer GC pauses — Full GC takes hundreds of ms or seconds.
  • Response times degrading as the JVM spends more wall-clock time in GC.
  • Eventually OutOfMemoryError: Java heap space in the logs and the pod gets restarted by K8s.

The investigation flow:

1. Confirm symptoms via metrics — Actuator /actuator/metrics/jvm.memory.used, Grafana, CloudWatch, Datadog/New Relic APM.
↓
2. Pull GC logs — does heap drop back down after Full GC? If not, it's a real leak (vs high allocation churn).
↓
3. Take a heap dump (snapshot 1) — via /actuator/heapdump or jcmd.
↓
4. Let the app run / apply load → take heap dump 2 some time later.
↓
5. Compare the two dumps in Eclipse MAT — which class instance count or retained heap grew?
↓
6. Find the GC roots holding the suspect objects — static field? Thread? Classloader?
↓
7. Identify the leak in code — cache, static collection, ThreadLocal, listener, executor.
↓
8. Reproduce in a lower env with a load test (JMeter / Gatling / k6) so you can verify the fix.
↓
9. Fix and verify — heap is now stable across hours under sustained load.

What to look for in Eclipse MAT:

  • Dominator Tree — which single objects retain the most heap? The top of this list is almost always your culprit.
  • Leak Suspects Report — MAT runs this automatically when you open a dump; it names probable offenders.
  • Retained heap column — not shallow size, but everything that would be freed if this object disappeared.
  • GC Roots — "Path to GC Roots" tells you why an object isn't being collected (static field, thread, classloader).
  • Class histogram — count of instances per class; a class with a million instances is suspicious.
  • Compare two heap dumps — MAT shows which classes grew between snapshots; this is the smoking gun.

GC logs — what they tell you:

A single line of GC log shows you whether memory is actually being reclaimed. Look at the heap usage after Full GC: if Full GC runs and heap doesn't come down, that's a real leak; if heap drops but climbs again over time, that's probably a slow leak; if heap fluctuates around a stable baseline, the JVM is healthy.

   Heap: 3712M(4096M)->3690M(4096M)   <-- before -> after Full GC
   3.214s

# Healthy:  3712M -> 480M    (heap recovers)
# Leaking:  3712M -> 3690M   (Full GC freed almost nothing — leak confirmed)

Most common leak causes in Spring Boot apps:

Spring-specific patterns that leak:

Leaks easily
  • Singleton bean holding a Map keyed by request data (userId, sessionId) with no eviction.
  • @Cacheable without a TTL or size limit (default cache is unbounded ConcurrentHashMap).
  • @Scheduled task that keeps adding to an in-memory queue faster than it drains.
  • Prototype bean injected into a singleton without ObjectFactory / Provider — Spring retains each prototype forever.
Safer alternatives
  • Bounded Caffeine cache with maximumSize + expireAfterWrite.
  • Redis (or another external cache) for shared state — moves the memory out of the JVM.
  • Request-scoped beans (@Scope("request")) for per-request state, not singletons holding maps.
  • Explicit cleanup hooks — @PreDestroy to shutdown() executors, close clients, deregister listeners.

Taking the heap dump in production:

# via Actuator (recommended — works through the app, no shell access needed)
curl -o heap.hprof http://localhost:8080/actuator/heapdump

# via jcmd (server access required — modern, low overhead)
jcmd <pid> GC.heap_dump /tmp/heap.hprof

# automatic on OOM — set these JVM flags so the next OOM gives you a free dump
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/dumps

Quick stabilisation moves while you investigate:

  • Bump -Xmx temporarily to buy time — doesn't fix the leak, but pushes out the next OOM.
  • Rolling restart with a heap-usage threshold — restart pods when heap stays above ~85% after Full GC.
  • Route traffic away from the leaky pod via readiness probe failure (drains it without killing it).
  • Ensure -XX:+HeapDumpOnOutOfMemoryError is set in the manifest so the next OOM hands you a dump for free.

Common interview gotchas:

  • "Memory leak" in Java doesn't mean unfreed C-style memory — it means objects unintentionally reachable from GC roots.
  • The heap dump itself causes a STW pause — schedule for low-traffic windows; live mode also filters unreachable objects.
  • High memory ≠ leak. The JVM is allowed to grow up to -Xmx; only worry when heap fails to drop after Full GC.
  • Different memory regions matter — an Old Gen leak looks different from a Metaspace leak or a direct/off-heap leak (e.g. Netty DirectByteBuffer).
  • Use JFR (Java Flight Recorder) in production — almost zero overhead, much better signal than periodic heap dumps.
  • In containers, set -XX:+UseContainerSupport (default in Java 11+) and use -XX:MaxRAMPercentage rather than a fixed -Xmx.
  • GC logs are gold — turn them on by default in prod: -Xlog:gc*,gc+heap=info:file=gc.log:time,uptime,level,tags.

Interview one-liner: My approach is methodical — verify symptoms via Actuator/APM, take heap dumps via /actuator/heapdump or jcmd, analyse in Eclipse MAT, compare two snapshots, find the GC roots, identify the source (almost always an unbounded cache, static state, a ThreadLocal not cleared, or unclosed resources), reproduce the issue in a lower env with sustained load, fix, and verify heap stays flat for hours. Never restart blindly — you lose the only evidence you have.

Liveness vs readiness vs startup probes

These map directly to Kubernetes probes. Spring Boot Actuator's /health exposes them as /actuator/health/liveness and /actuator/health/readiness by default since Spring Boot 2.3.

Liveness: is the app alive? If this fails, K8s restarts the pod. Should check only fatal in-process states (e.g., out-of-memory flag) — not downstream dependencies.

Readiness: is the app ready to serve traffic? If this fails, K8s removes it from the load balancer but doesn't restart it. Should check downstream dependencies (DB, Kafka, ES) so we don't route traffic to a partially-broken instance.

Startup: a one-shot probe for slow-to-start apps so K8s doesn't kill them during boot. Once it passes, liveness takes over.

Getting these wrong causes restart loops or routing failures — a common production incident.

REST & Web
@RestController vs @Controller — what's the difference?

Both register the class as a Spring MVC handler. The difference: @Controller + @ResponseBody tells Spring to serialize the return value (typically to JSON via Jackson) instead of resolving a view name. @RestController is shorthand for both — every method implicitly returns the body directly.

@RestController
@RequestMapping("/api/users")
public class UserController {
    @GetMapping("/{id}")
    public User get(@PathVariable Long id) { ... }
}

Use @Controller only when you serve server-rendered views (Thymeleaf, JSP) and need to return view names. For JSON APIs — which is 99% of what I write — always @RestController.

Path variable vs request param vs request body

Three ways to read input in Spring MVC:

  • @PathVariable — part of the URL path: /users/{id} → @PathVariable Long id. Use for resource identifiers in REST.
  • @RequestParam — query string: /users?status=active&limit=10. Optional with defaults: @RequestParam(defaultValue = "20") int limit. Use for filters and pagination.
  • @RequestBody — deserialize the HTTP body (JSON) into an object. Use for POST/PUT/PATCH payloads. Pair with @Valid for Bean Validation.

Idiomatic REST: identify resources by path, filter/paginate by query params, send payloads in the body. Headers via @RequestHeader when you need them.

Global / Custom Exception Handling in Spring Boot (@ControllerAdvice + @ExceptionHandler) must

Custom Exception Handling means creating your own exception classes for business-specific errors (UserNotFoundException, InvalidAmountException, OrderNotFoundException) and handling them centrally so every endpoint returns the same, meaningful error shape — instead of leaking raw Java stack traces to clients.

CORE IDEA Throw domain-specific exceptions from the service layer, map them once in a global handler (@RestControllerAdvice), and return a consistent JSON error response with the right HTTP status. Controllers stay clean; clients get predictable errors.

Why custom exceptions instead of generic ones?

  • Better error handling — the type itself carries meaning (UserNotFoundException → 404).
  • Meaningful messages — clients see "User 42 not found", not NullPointerException.
  • Cleaner controllers — no try/catch noise in every endpoint.
  • Business-specific validation — encode rules like "insufficient balance" or "duplicate order" as exception types.
  • Consistent API contract — all errors share the same shape.

Step 1 — Create the custom exception class.

public class ResourceNotFoundException extends RuntimeException {
    public ResourceNotFoundException(String message) {
        super(message);
    }
}

public class InvalidAmountException extends RuntimeException {
    public InvalidAmountException(String message) {
        super(message);
    }
}

Extend RuntimeException (unchecked) for almost all REST API exceptions — they don't pollute every method signature with throws declarations and they work cleanly with streams, lambdas, and JPA repositories.

Checked vs Unchecked — which to use:

TypeExtendsUse for
UncheckedRuntimeExceptionProgramming/business errors a caller can't usefully recover from — preferred in Spring Boot APIs.
CheckedExceptionTruly recoverable conditions (rare in modern apps). Forces caller to handle or declare.

Step 2 — Throw the exception from the service layer.

public Employee getById(Long id) {
    return employeeRepository.findById(id)
        .orElseThrow(() ->
            new ResourceNotFoundException("Employee " + id + " not found"));
}

public void withdraw(Long accountId, BigDecimal amount) {
    if (amount.signum() <= 0) {
        throw new InvalidAmountException("Amount must be positive");
    }
    // ...
}

Step 3 — Handle it globally with @RestControllerAdvice.

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
            .body(new ErrorResponse("NOT_FOUND", ex.getMessage(), Instant.now()));
    }

    @ExceptionHandler(InvalidAmountException.class)
    public ResponseEntity<ErrorResponse> handleBadRequest(InvalidAmountException ex) {
        return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ErrorResponse("INVALID_AMOUNT", ex.getMessage(), Instant.now()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
        String details = ex.getBindingResult().getFieldErrors().stream()
            .map(f -> f.getField() + ": " + f.getDefaultMessage())
            .collect(Collectors.joining(", "));
        return ResponseEntity.badRequest()
            .body(new ErrorResponse("VALIDATION_FAILED", details, Instant.now()));
    }

    @ExceptionHandler(Exception.class)         // fallback for anything unmapped
    public ResponseEntity<ErrorResponse> handleAny(Exception ex) {
        log.error("Unhandled error", ex);
        return ResponseEntity.status(500)
            .body(new ErrorResponse("INTERNAL_ERROR", "Something went wrong", Instant.now()));
    }
}

public record ErrorResponse(String code, String message, Instant timestamp) {}

HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "code": "NOT_FOUND",
  "message": "Employee 42 not found",
  "timestamp": "2026-05-15T15:53:00Z"
}

AnnotationPurpose
@RestControllerAdviceGlobal handler class — applies to all @RestControllers. Combines @ControllerAdvice + @ResponseBody.
@ControllerAdviceSame idea, but for MVC (HTML views).
@ExceptionHandler(SomeEx.class)Maps a specific exception type to a handler method.

Modern alternative — ProblemDetail (Spring Boot 3, RFC 7807):

@ExceptionHandler(ResourceNotFoundException.class)
public ProblemDetail handleNotFound(ResourceNotFoundException ex) {
    ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
    pd.setTitle("Resource Not Found");
    pd.setProperty("traceId", MDC.get("traceId"));
    return pd;
}

ProblemDetail is a standardised error format (type, title, status, detail, instance) — I prefer it for new services since clients across teams understand it without docs.

Why global handling beats per-controller try/catch:

Without @ControllerAdvice
  • Every controller method ends up with try/catch blocks.
  • Different endpoints return different error shapes.
  • Stack traces leak to clients on missed exceptions.
  • Logging is scattered and inconsistent.
With @ControllerAdvice
  • Controllers contain only happy-path code.
  • Every error returns the same JSON shape.
  • Status codes mapped centrally — easy to audit.
  • Logging and trace-ID propagation happen in one place.

Best practices from production:

  • One exception type per business meaning — OrderNotFoundException, InsufficientBalanceException, etc. Don't reuse RuntimeException.
  • Map each to the right HTTP status — 404 for not-found, 400 for validation, 409 for conflicts, 403 for forbidden, 500 only as fallback.
  • Don't leak internals — clients should never see SQL errors, package names, or stack traces. Log them server-side, return a sanitised message.
  • Always include a fallback @ExceptionHandler(Exception.class) that returns a generic 500 and logs the real error.
  • Include a traceId in the error body (from MDC) so support can correlate the user's screenshot to logs.
  • Keep the handler stateless — no business logic, only translation from exception → HTTP response.

Interview one-liner: Custom Exception Handling means defining business-specific exception classes (e.g., UserNotFoundException, InvalidAmountException) by extending RuntimeException, throwing them from the service layer, and handling them centrally with @RestControllerAdvice + @ExceptionHandler. This gives meaningful error messages, cleaner controllers, consistent API responses, and the right HTTP status for each business condition — and in Spring Boot 3, ProblemDetail (RFC 7807) is the recommended standard error body.

Validation — Bean Validation + @Valid

Bean Validation (JSR-380, Jakarta Validation) lets you annotate fields with constraints — @NotNull, @Size(min=1, max=100), @Email, @Min, @Pattern — and Spring runs them when you annotate the parameter with @Valid.

public record CreateUserRequest(
    @NotBlank String name,
    @Email String email,
    @Min(18) int age) {}

@PostMapping
public User create(@RequestBody @Valid CreateUserRequest req) { ... }

Violations throw MethodArgumentNotValidException, which your @ControllerAdvice converts to a 400 response with field-level errors. For service-layer parameters use @Validated on the class plus @Valid on params. Custom constraints are easy: write a @Constraint annotation and a ConstraintValidator. I always validate at the API boundary — defense in depth.

WebFlux — when would you use it over MVC?

Spring WebFlux is the reactive alternative to MVC — non-blocking, built on Project Reactor (Mono/Flux), running on Netty by default. Threads aren't blocked on I/O; they're parked and resumed when data arrives.

Use it when: you handle many concurrent slow connections (server-sent events, WebSockets, streaming responses), or when downstream calls are mostly I/O and you've hit thread-pool ceilings on MVC.

Costs: reactive code is harder to read, debug, and trace; you can't use blocking JDBC; learning curve for the team. Many "WebFlux for performance" projects end up slower because of code complexity and bugs.

My current take in 2026: with Virtual Threads (Java 21 + Boot 3.2+), MVC gives you reactive-like scaling without reactive code complexity. I'd reach for WebFlux today only for streaming use cases.

Caching in Spring Boot — @Cacheable, Redis, EhCache, Caffeine must

Caching means storing frequently accessed data temporarily in memory so subsequent reads return instantly — without hitting the database, an external API, or doing expensive computation again. It's one of the cheapest, highest-impact performance optimisations in any backend.

CORE IDEA Check the cache first. On a hit → return immediately. On a miss → compute / fetch from the source, store the result in the cache, and return it. The next request for the same key is microseconds instead of milliseconds.

Why we cache:

  • Improve performance — in-memory reads are 100–1000× faster than a DB call.
  • Reduce DB / API load — fewer connections, less CPU pressure on the source.
  • Lower latency — instant responses for repeat queries.
  • Cost savings — fewer paid API calls, smaller DB instances.
  • Resilience — serve degraded data when the source is down (with appropriate TTL).

The classic cache-aside flow:

Request arrives for key K
↓
Look up K in the cache
↓
HIT → return cached value   |   MISS → fetch from DB / API
↓
On miss: store result in cache with TTL
↓
Return the value

Enabling caching in Spring Boot — 3 lines:

@SpringBootApplication
@EnableCaching
public class App { ... }

The three caching annotations everyone needs:

AnnotationPurposeTypical use
@CacheableRead-through — check cache; if missing, run method & cache the result.Heavy GETs — findById, product details, user profiles.
@CachePutAlways run the method and update the cached value.After an update — refresh the cached version with new data.
@CacheEvictRemove entries from the cache.After delete / bulk update — invalidate stale entries.

Practical example — product service:

@Service
public class ProductService {

    @Cacheable(value = "products", key = "#id")
    public Product findById(Long id) {
        // only called on cache MISS
        return productRepository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Product " + id));
    }

    @CachePut(value = "products", key = "#product.id")
    public Product update(Product product) {
        return productRepository.save(product);
    }

    @CacheEvict(value = "products", key = "#id")
    public void delete(Long id) {
        productRepository.deleteById(id);
    }

    @CacheEvict(value = "products", allEntries = true)
    public void clearAll() { /* nightly cache refresh, for example */ }
}

Without vs With caching:

Without cache
  • Every request → DB call.
  • DB CPU and connections grow with traffic.
  • p99 latency dominated by DB query time.
  • Repeated reads of the same item waste resources.
With cache
  • First request → DB; subsequent → cache.
  • DB load drops dramatically (often 80–95%).
  • p99 latency tightens to microseconds for hits.

Common caching pitfalls and how to avoid them:

  • Stale data — pick a TTL, use @CacheEvict on updates, or use a message-driven invalidation event.
  • Cache stampede — many requests miss simultaneously and hammer the DB. Mitigate with request coalescing (Caffeine's refreshAfterWrite) or short jittered TTLs.
  • Caching null — by default a null result is cached too. Use unless = "#result == null" if that's not what you want.
  • Self-invocation — calling a @Cacheable method from another method in the same class bypasses the proxy. Same gotcha as @Transactional.
  • Big values — don't cache huge blobs in Redis; cache derived/summary data instead.
  • No monitoring — always track cache hit rate. If hits < 50%, the cache might be hurting more than helping.

Interview one-liner: Caching stores frequently accessed data temporarily so subsequent reads skip the database — improving performance, reducing DB load, and lowering latency. In Spring Boot, enable it with @EnableCaching and use @Cacheable (read-through), @CachePut (refresh on write), and @CacheEvict (invalidate). Pick Caffeine for single-instance apps and Redis for distributed microservices — shared, in-memory, sub-millisecond, with TTL and clustering support. Together with Spring Security, caching helps build applications that are both secure and fast at scale.

Distributed Caching using Redis in Microservices — design & production tips must

In a microservices architecture, every service runs as multiple instances for scalability and fault tolerance. A local in-JVM cache (like Caffeine) only helps one pod — every other instance is cold. The fix is a distributed cache: a single shared, network-accessible cache that all instances of all services can read and write to. Redis is the production default.

CORE IDEA Move the cache out of the JVM and into a shared Redis cluster. Every microservice instance does a cache-aside lookup against Redis before hitting the database. One write invalidates the cache for every consumer — no stale-per-pod surprises.

The problem local caches don't solve:

Local cache (Caffeine)
  • Each pod has its own copy of the cache.
  • Pod A updates DB + evicts its local cache → pods B, C, D still hold stale data.
  • Cold start = full DB load for every new pod.
  • Cache hit rate falls as you scale out.
  • Memory duplicated across every pod.
Distributed cache (Redis)
  • One shared cache across all pods of all services.
  • Update + evict happens once, every consumer sees it.
  • New pods start "warm" — cache already populated.
  • Hit rate stays high as you scale horizontally.
  • Memory used once, in Redis — not per pod.

The cache-aside flow in a microservices setup:

1. Client calls GET /products/123
↓
2. Product Service looks up key product:123 in Redis
↓
3a. HIT → return Redis value (~1 ms)  |  3b. MISS → fetch from DB
↓
4. On miss: SET product:123 {…} EX 600 (10 min TTL)
↓
5. Return response to client
↓
6. On update: DEL product:123 or @CachePut — every pod is consistent instantly

Common interview gotchas:

  • "Why Redis over a local cache?" — local caches don't share across instances; updates and evictions are per-pod.
  • "How do you keep caches consistent across services?" — event-driven invalidation via Kafka / Redis Pub/Sub, or short TTLs.
  • "What if Redis is down?" — circuit breaker + CacheErrorHandler fallback to DB. Cache is a performance layer, not a system of record.
  • "How do you avoid the thundering herd on a cold cache?" — jittered TTLs, distributed locks around DB refresh, or pre-warming on deploy.
  • "Cache vs DB consistency?" — cache is eventually consistent. If you need strict consistency, don't cache, or use @CachePut in the same transaction.
  • "How big should the cache be?" — Redis sizing depends on key count × value size × replication factor; monitor used_memory, set maxmemory-policy: allkeys-lru.
  • "Should every read go through cache?" — no. Strongly consistent reads (financial transactions, latest stock) often bypass the cache entirely.

Resilience & Observability
Circuit Breaker pattern with Resilience4j hot must

A circuit breaker protects a service from a failing downstream by short-circuiting calls when it detects systemic failure — instead of waiting for every call to time out, the breaker fails fast and lets the downstream recover. Resilience4j is the modern Java implementation (Hystrix is in maintenance mode); it's lightweight, functional, and integrates cleanly with Spring Boot.

CORE IDEA A state machine — CLOSED → OPEN → HALF_OPEN → CLOSED — wraps remote calls. Records success/failure in a sliding window; when the failure rate crosses the threshold, OPEN the breaker and fail fast for a wait period. After the wait, allow a few HALF_OPEN probes to test recovery, then close again.
1 The state machine
CLOSED — all calls pass; record success/failure in sliding window
↓
Failure rate ≥ threshold (e.g. 50%) over min sample size
↓
OPEN — calls fail immediately for waitDurationInOpenState (e.g. 30s); fallback returned
↓
Wait period elapses
↓
HALF_OPEN — allow N probe calls through
↓
Probes succeed → CLOSED. Probes fail → OPEN again.

@Service

    @CircuitBreaker(name = "paymentApi", fallbackMethod = "fallback")
    @Retry(name = "paymentApi")
    @TimeLimiter(name = "paymentApi")
    @Bulkhead(name = "paymentApi", type = Bulkhead.Type.SEMAPHORE)

        return webClient.post().uri("/v1/charges").bodyValue(req)
            .retrieve().bodyToMono(PaymentResult.class).toFuture();

    private CompletableFuture<PaymentResult> fallback(ChargeRequest req, Throwable t) {
        log.warn("Payment fallback for orderId={} cause={}", req.getOrderId(), t.toString());
        metrics.increment("payment.fallback");
        return CompletableFuture.completedFuture(PaymentResult.deferred(req.getOrderId()));
    }
}

The decorators stack: TimeLimiter caps each attempt, Retry runs N attempts, CircuitBreaker tracks failure rate, Bulkhead caps concurrency. The fallback method returns a degraded response so callers never see the upstream failure directly.

7 Common interview gotchas
  • Circuit breakers without timeouts don't help — slow downstreams still consume threads. Combine with @TimeLimiter.
  • Without minimum-number-of-calls, the breaker can trip on a tiny sample (3 fails out of 5 calls).
  • Per-instance state (Resilience4j is in-process) — for cluster-wide insight, aggregate via metrics.
  • Fallbacks must be cheap and side-effect-free; calling the same downstream from the fallback defeats the breaker.

  • Reactive vs annotation API — choose one style per service; mixing causes subtle bugs.

Retry strategies — when to retry?

Retries help with transient failures: network blips, 502/503, throttling. They hurt with permanent failures (validation errors, 404, business errors) or side-effect-causing calls that aren't idempotent.

Three rules I follow:

  • Retry only on retriable errors (timeouts, specific status codes). Don't retry 4xx.
  • Use exponential backoff with jitter: 100 ms, 200 ms, 400 ms + random — prevents thundering-herd reconnect storms.
  • Make the operation idempotent — use idempotency keys or natural keys so repeated requests don't double-charge or double-write.

With Resilience4j: @Retry(name = "paymentApi", fallbackMethod = "..."). Combine with circuit breaker — retry first, open the breaker on persistent failure. Bound the total time so we don't blow request timeouts.

Retry vs Circuit Breaker — when to use which? hot

Retry handles a blip; a circuit breaker handles a broken dependency. Use both, but never retry blindly into an open circuit.

Retry Same call may succeed on attempt 2–3 — for transient timeouts/503s on idempotent ops.

Async processing — @Async and TaskExecutor

@Async runs a method on a separate thread without blocking the caller. Enable with @EnableAsync on a config class. The method must return void, Future, or CompletableFuture — the caller gets the future immediately.

Two production gotchas. (1) Define a named TaskExecutor — the default is SimpleAsyncTaskExecutor which creates a new thread per call (bad). Inject a bounded ThreadPoolTaskExecutor sized for your workload. (2) Self-invocation doesn't trigger async — same proxy gotcha as @Transactional.

I use @Async for fire-and-forget side effects: sending welcome emails, recording analytics, writing to Elasticsearch. For more complex async pipelines I prefer explicit CompletableFuture chains or Kafka events for durability.

Scheduling — @Scheduled and pitfalls

@Scheduled runs a method on a schedule. Enable with @EnableScheduling. Three styles:

  • @Scheduled(fixedRate = 30_000) — every 30 s from start of last run.
  • @Scheduled(fixedDelay = 30_000) — 30 s after the last finish.
  • @Scheduled(cron = "0 0 2 * * *") — 2 a.m. daily.

Pitfalls in production:

  • By default Spring uses a single-threaded scheduler — long-running jobs block subsequent runs. Configure a ThreadPoolTaskScheduler with multiple threads.
  • If you run multiple instances of the service, every instance fires the job. Solve with leader election (ShedLock, Quartz cluster) or move to a real job scheduler.
  • Don't put heavy DB work in scheduled methods without proper transaction management.

For non-trivial workloads I use Quartz, Kubernetes CronJobs, or Spring Batch.

Overall structure — Job contains Steps, each Step contains the trio:

Job
 └── Step

Minimum working example (Spring Boot 3 / Spring Batch 5):

// ---- Reader ----
@Bean
public FlatFileItemReader<Employee> reader() {
    return new FlatFileItemReaderBuilder<Employee>()
        .name("employeeReader")
        .resource(new ClassPathResource("employees.csv"))
        .delimited().names("id","name","salary")
        .targetType(Employee.class)
        .build();
}

// ---- Processor ----
@Bean
public ItemProcessor<Employee, EmployeeDTO> processor() {
    return e -> {
        if (e.getSalary() < 0) return null;             // skip bad rows
        return new EmployeeDTO(e.getId(),
                               e.getName().toUpperCase(),
                               e.getSalary());
    };
}

// ---- Writer ----
@Bean
public JdbcBatchItemWriter<EmployeeDTO> writer(DataSource ds) {
    return new JdbcBatchItemWriterBuilder<EmployeeDTO>()
        .dataSource(ds)
        .sql("INSERT INTO employee(id,name,salary) VALUES (:id,:name,:salary)")
        .beanMapped()
        .build();
}

// ---- Step (chunk size = 100) ----
@Bean
public Step step1(JobRepository jobRepo,
                  PlatformTransactionManager tx,
                  ItemReader<Employee> reader,
                  ItemProcessor<Employee,EmployeeDTO> processor,
                  ItemWriter<EmployeeDTO> writer) {
    return new StepBuilder("step1", jobRepo)
        .<Employee, EmployeeDTO>chunk(100, tx)
        .reader(reader).processor(processor).writer(writer)
        .faultTolerant().skip(Exception.class).skipLimit(10)
        .build();
}

// ---- Job ----
@Bean
public Job employeeJob(JobRepository jobRepo, Step step1) {
    return new JobBuilder("employeeJob", jobRepo)
        .start(step1)
        .build();
}

What happens internally — chunk-oriented processing:

JobLauncher starts the Job
↓
Step opens a transaction
↓
Reader.read() called repeatedly — items added to chunk list
↓
Processor transforms each item (returning null = skip)
↓
Chunk size reached → Writer writes the whole chunk in one batch
↓
Transaction commits → metadata persisted
↓
Loop until Reader returns null

Why chunking matters:

  • Memory: only chunk size items live in memory at once — handles million-row imports comfortably.
  • Performance: writers use JDBC batch inserts → 10–100× faster than one row at a time.
  • Transactions: one commit per chunk — failure rolls back only the current chunk, not the whole job.
  • Restartability: metadata stored in BATCH_* tables means a failed job restarts from the last committed chunk, not the beginning.

Metadata tables Spring Batch creates (and uses for restartability):

TablePurpose
BATCH_JOB_INSTANCELogical Job identity (name + parameters).
BATCH_JOB_EXECUTIONEach execution attempt of a Job — status, start/end time.
BATCH_STEP_EXECUTIONPer-Step stats: read/write/skip counts, commit count, status.
BATCH_JOB_EXECUTION_CONTEXTPer-execution key-value context — used for restart state.

Fault tolerance — retry and skip:

.faultTolerant()
.retry(TransientDataAccessException.class).retryLimit(3)
.skip(ValidationException.class).skipLimit(100)
.listener(skipListener());   // log skipped items for audit

Use retry for transient failures (lock timeouts, network blips) and skip for bad data (validation, parsing). Always log skipped items — silent skips are how production data gets dropped.

Tasklet vs Chunk-oriented Step:

Tasklet Step

A single execute() method that does one task. Use for non-row work: archive old files, drop a temp table, send a notification, run a stored procedure.

Chunk-oriented Step

The Reader / Processor / Writer pipeline. The default and most common. Use whenever you're iterating over a dataset.

Common interview gotchas:

  • Why is Processor optional? Some jobs only move data unchanged (Reader → Writer). Skipping the Processor is fine.
  • Job vs Step? A Job is the whole batch process; a Step is one unit of work inside it. A Job can have many sequential or conditional Steps.
  • Why chunking over loading everything? Loading 10M rows into memory crashes the JVM. Chunks of 500–5000 give you streaming + batch inserts + per-chunk transactions.
  • Multiple instances? Use a single-instance scheduler (ShedLock, Quartz cluster, K8s Job) — or partitioned/parallel Steps for horizontal scale.
  • Restartability: rerun the same Job with the same parameters → Spring Batch resumes from the last committed chunk; new parameters = new JobInstance.

Interview-ready one-liner: Spring Batch is a framework for large-scale batch processing built around a simple model: a Job contains one or more Steps, and each Step runs a Reader → Processor → Writer pipeline over the data in chunks, each chunk wrapped in a transaction. The framework handles chunking, retries, skips, restartability, and metadata, so we just write business logic. It's used wherever you need to move or transform large datasets reliably on a schedule — banking EOD, payroll, ETL, data migration, reporting, insurance claims — and is the right choice over real-time streaming whenever the workload is scheduled, high-volume, and latency-tolerant.

How do you call another microservice from Spring Boot? must

In a microservices architecture, one Spring Boot service often needs to call another service over the network.

For example, an Order Service may call a Payment Service, or an Account Service may call a Customer Service.

The main idea is: the caller should not hard-code hostnames and ports. It should use a service name, apply timeouts, handle failures, and keep the call observable.

Now coming to the common ways to call another microservice.

In Spring Boot projects, we usually use one of these:

RestTemplate

WebClient

OpenFeign

All three make HTTP calls. The difference is style, blocking vs non-blocking, and how much boilerplate you write.

Now coming to the typical production flow.

First, the client sends a request to Service A.

Service A needs data from Service B.

Service A resolves Service B using service discovery (for example Eureka, Consul, or Kubernetes DNS).

Then Service A calls Service B over HTTP with a timeout.

If Service B is slow or down, Service A should fail fast or use a fallback — not hang forever.

In real projects, I also add:

correlation id in headers for tracing

authentication token propagation (JWT or internal token)

retry only for safe/idempotent calls

circuit breaker for unstable dependencies

Now coming to a simple RestTemplate example.

RestTemplate is synchronous and older, but still common in legacy code.

@Service
public class OrderClient {

    private final RestTemplate restTemplate;

    public OrderClient(RestTemplate restTemplate) {
        this.restTemplate = restTemplate;
    }

    public PaymentResponse charge(PaymentRequest request) {
        return restTemplate.postForObject(
            "http://payment-service/api/payments",
            request,
            PaymentResponse.class
        );
    }
}

In production, I never use a default RestTemplate bean. I configure:

connect timeout

read timeout

connection pool

error handler

Now coming to WebClient (recommended for new code).

WebClient is non-blocking and works well with reactive stacks, but you can also use it in blocking style.

It is the modern replacement for RestTemplate.

@Service
public class OrderClient {

    private final WebClient webClient;

    public OrderClient(WebClient.Builder builder) {
        this.webClient = builder.baseUrl("http://payment-service").build();
    }

    public PaymentResponse charge(PaymentRequest request) {
        return webClient.post()
            .uri("/api/payments")
            .bodyValue(request)
            .retrieve()
            .bodyToMono(PaymentResponse.class)
            .block();
    }
}

For high traffic services, non-blocking calls help use fewer threads.

Now coming to OpenFeign (declarative HTTP client).

Feign lets you define an interface; Spring generates the HTTP client implementation.

@FeignClient(name = "payment-service")
public interface PaymentClient {

    @PostMapping("/api/payments")
    PaymentResponse charge(@RequestBody PaymentRequest request);
}

This is clean when you have many downstream APIs and want less boilerplate.

In microservices, Feign is often combined with:

service discovery

load balancing (Spring Cloud LoadBalancer)

resilience4j for retry and circuit breaker

Now coming to important production concerns.

Timeouts are mandatory. Without timeout, one slow downstream service can block all threads.

Idempotency matters for POST in payments and transfers. Retries must not double-charge.

Error mapping — map downstream 4xx/5xx to meaningful API errors for the caller.

Observability — log service name, latency, status code, and correlation id.

Security — pass auth token or use service-to-service credentials (mTLS, client credentials in OAuth2).

In conclusion, I call microservices from Spring Boot using HTTP clients (WebClient or Feign in new projects), with service discovery, strict timeouts, retries only where safe, and circuit breakers for failure isolation.

All three are used to call external HTTP APIs from Spring Boot, especially other microservices.

But they are not the same. The choice affects threading, performance, readability, and maintainability.

Now coming to RestTemplate.

Pros:

Cons:

Now coming to what I would choose in an interview / real project.

For a new microservice in 2024–2026:

I prefer Feign when the team wants clean interfaces and many internal REST calls with Spring Cloud.

I avoid introducing new RestTemplate code.

Regardless of client, I always configure timeouts, logging, resilience (retry + circuit breaker), and secure token propagation.

How do you externalize configuration in Spring Boot? must

Externalizing configuration means keeping environment-specific settings outside the application JAR, so the same build can run in dev, UAT, and production without code changes.

This is one of the most important Spring Boot practices for real projects and banking implementations.

Now coming to where configuration is stored.

Spring Boot reads configuration from multiple sources, in a defined order of precedence.

Common sources are:

application.properties

application.yml

profile-specific files like application-prod.yml

environment variables

command-line arguments

external config server (Spring Cloud Config)

secrets manager (Vault, AWS Secrets Manager, Azure Key Vault)

In banking projects, sensitive values like DB passwords and API keys should never be committed to Git.

Now coming to profiles.

Profiles let one application behave differently per environment.

For example:

spring.profiles.active=dev

spring.profiles.active=uat

spring.profiles.active=prod

We keep separate YAML files:

application-dev.yml

application-uat.yml

application-prod.yml

Dev may point to a local database; prod points to the production datasource and real payment gateway URL.

Now coming to reading configuration in code.

There are two common approaches.

1. @Value for single properties

@Value("${payment.timeout-ms:5000}")
private int paymentTimeoutMs;

2. @ConfigurationProperties for a group of related settings

@ConfigurationProperties(prefix = "payment")
public record PaymentProperties(String baseUrl, int timeoutMs, int maxRetries) {}

In real projects, I prefer @ConfigurationProperties for anything non-trivial because it is type-safe and easy to test.

Now coming to environment variables in containers/Kubernetes.

In Docker/Kubernetes, we inject config as env vars:

SPRING_DATASOURCE_URL

SPRING_DATASOURCE_USERNAME

SPRING_DATASOURCE_PASSWORD

Spring Boot maps relaxed binding automatically.

This is how the same image runs in every environment with different secrets and endpoints.

Now coming to Spring Cloud Config (centralized config).

When you have many microservices, maintaining YAML in every repo becomes hard.

Spring Cloud Config Server stores configuration centrally (often in Git).

Each service pulls its config at startup.

Benefits:

single place to change URLs and feature flags

audit trail via Git history

refresh without redeploy (with @RefreshScope and actuator)

Now coming to best practices I follow.

Never hard-code environment-specific URLs in Java code.

Never commit secrets to source control.

Use meaningful property prefixes (payment.*, kafka.*).

Validate required properties at startup (fail fast if prod DB URL is missing).

Document every property in README or config metadata.

In conclusion, externalized configuration in Spring Boot means using YAML/properties, profiles, env vars, and optionally a config server — so the same application is portable, secure, and environment-aware.

What is IoC container?

The IoC (Inversion of Control) container in Spring manages bean creation, configuration, and lifecycle — injecting dependencies into objects rather than objects creating their own dependencies.

Implementations

BeanFactory: lazy initialization; minimal features. ApplicationContext: eager initialization, events, internationalization, AOP.

AnnotationConfigApplicationContext: for annotation-based Spring apps; WebApplicationContext: for Spring MVC/Boot.

How it works

Scans @Component, @Service, @Repository, @Controller; creates bean instances; injects @Autowired dependencies.

Dependency graph resolved at startup; circular dependencies detected; beans initialized in correct order.

Now coming to conclusion.

How do you handle exceptions globally in Spring Boot?

@ControllerAdvice with @ExceptionHandler methods provides centralized exception handling for all controllers — mapping exceptions to HTTP responses.

Implementation

@ControllerAdvice class with @ExceptionHandler(InsufficientBalanceException.class) → return ResponseEntity with 422 and error body.

@ExceptionHandler(MethodArgumentNotValidException.class) → return 400 with validation error details.

Benefits

No try-catch in controllers. Consistent error response format across all endpoints.

Add @ResponseStatus on exception class for simple status mapping without ControllerAdvice.

Banking

Map AccountNotFoundException → 404. InsufficientBalanceException → 422. DuplicatePaymentException → 409.

Now coming to conclusion.

@ControllerAdvice is the standard pattern — never scatter exception handling across individual controllers.

How do you implement retry in Spring Boot?

Retries in Spring Boot are implemented using Spring Retry (@Retryable annotation) or Resilience4j Retry with configurable attempts, delay, and backoff.

Spring Retry

@Retryable(value={ConnectException.class}, maxAttempts=3, backoff=@Backoff(delay=1000, multiplier=2))

@Recover method: fallback when all retries exhausted — log and return error response.

Resilience4j

RetryConfig: maxAttempts(3).waitDuration(Duration.ofMillis(500)).retryOnException(e -> e instanceof ConnectException).

@Retry(name='paymentGateway') on the method — configured in application.yml.

Banking caution

Never retry fund transfer without idempotency key — duplicate processing causes double debit.

Now coming to conclusion.

Combine retry with idempotency key for payment operations — retry safety requires server-side dedup.

What is dependency injection?

Dependency Injection (DI) is a design pattern where an object's dependencies are provided externally (by the IoC container) rather than the object creating them itself.

Types

Constructor injection: dependencies passed in constructor — preferred; enables immutability, easy testing.

Setter injection: @Autowired on setter method — for optional dependencies. Field injection: @Autowired on field — avoid (hard to test).

Benefits

Decoupling: depends on interface, not concrete class. Testability: inject mocks in unit tests. Reusability: swap implementations without changing consumers.

Now coming to conclusion.

Prefer constructor injection — forces required dependencies, enables final fields, and makes dependencies explicit.

Constructor injection vs field injection.

Constructor injection declares dependencies as constructor parameters (immutable, testable); field injection uses @Autowired on fields (convenient but hides dependencies and breaks testability).

Constructor injection

All required deps in constructor; class is immutable (final fields); easy to test with new Service(mockDep).

If constructor is long: signals SRP violation — too many dependencies.

Field injection

@Autowired on field: convenient but requires Spring container to test; cannot use final; dependencies hidden.

Now coming to conclusion.

Spring team recommends constructor injection — @Autowired on fields is legacy style, avoid in new code.

Bean lifecycle in Spring.

A Spring bean's lifecycle: instantiation → dependency injection → @PostConstruct → business use → @PreDestroy → destruction.

Lifecycle callbacks

@PostConstruct: called after all dependencies injected — use for initialization (DB connection validation, cache warm-up).

@PreDestroy: called before bean destroyed on context shutdown — use for cleanup (close connections, flush cache).

Interfaces

InitializingBean.afterPropertiesSet() and DisposableBean.destroy() — interface-based alternatives (less preferred than annotations).

Scopes

Singleton (default): one instance per context. Prototype: new instance per getBean(). Request/Session: per HTTP request/session.

Now coming to conclusion.

Use @PostConstruct for initialization and @PreDestroy for cleanup — they work with any IoC container, not just Spring.

Difference between `@Component`, `@Service`, `@Repository`, `@Controller`.

@Component is the generic stereotype; @Service, @Repository, and @Controller are specializations with semantic meaning and additional behavior.

Stereotypes

@Component: generic Spring-managed bean. @Service: business logic layer — no extra behavior, semantic clarity.

@Repository: DAO layer — adds persistence exception translation (converts JPA/JDBC exceptions to Spring DataAccessException).

@Controller: Spring MVC controller — enables request mapping. @RestController = @Controller + @ResponseBody.

Now coming to conclusion.

Use the most specific annotation — @Repository gets exception translation, @RestController gets response body serialization.

What is `@Transactional`? must

@Transactional wraps a method in a database transaction — commit on success, rollback on runtime exception.

Now coming to internals.

Spring AOP proxy starts transaction before method; one connection per thread.

Now coming to conclusion.

Use on service layer; avoid on controllers.

Transaction propagation types.

Spring transaction propagation defines how a transactional method behaves when called from within an existing transaction.

Common types

REQUIRED (default): join existing transaction, or create new if none. Most used for service methods.

REQUIRES_NEW: always start new transaction, suspend existing. Used for: audit logging that must commit independently.

SUPPORTS: join if exists, run non-transactionally if none. MANDATORY: must join existing or throw exception.

NOT_SUPPORTED: suspend existing, run non-transactionally. NEVER: throw exception if transaction exists.

Banking

Fund transfer service: REQUIRED. Audit log: REQUIRES_NEW (must persist even if outer tx rolls back).

Now coming to conclusion.

REQUIRED covers 90% of cases; use REQUIRES_NEW only for audit/error logging that must always commit.

Transaction isolation levels.

Spring's transaction isolation levels correspond to SQL isolation levels, controlling how concurrent transactions see each other's data.

Levels

DEFAULT: uses DB default (READ_COMMITTED for Oracle). READ_UNCOMMITTED: dirty reads possible (not in Oracle).

READ_COMMITTED: sees only committed data at each statement (Oracle default) — phantom reads possible.

REPEATABLE_READ: consistent reads within transaction — phantom rows still possible.

SERIALIZABLE: full isolation — highest consistency, lowest concurrency.

Banking

@Transactional(isolation=SERIALIZABLE) for balance verification before high-value transfer — prevents phantom balance change.

Now coming to conclusion.

READ_COMMITTED is the right default for banking OLTP; use SERIALIZABLE only for critical consistency checks.
