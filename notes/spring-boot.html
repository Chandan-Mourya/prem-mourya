Fundamentals
What is Spring Boot? must

Spring Boot is an opinionated layer on top of the Spring Framework that lets you build production-ready Java apps with minimal boilerplate. The big ideas:

  • Auto-configuration — sensible defaults based on what's on the classpath.
  • Starters — curated dependency bundles (spring-boot-starter-web, -data-jpa, etc.).
  • Embedded servers — Tomcat/Jetty/Undertow built in; deploy a fat JAR with java -jar.
  • Externalized config via application.yml + profiles + environment variables.
  • Actuator for production endpoints (health, metrics, info).

Before Spring Boot we spent days on XML config and packaging. Today I bootstrap a new service from start.spring.io in 10 minutes. It's the standard for Java microservices.

How does auto-configuration work?

Auto-configuration = conditional bean definitions that activate based on what's on the classpath and what's already configured.

Mechanically: @SpringBootApplication includes @EnableAutoConfiguration, which loads classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (formerly spring.factories). Each auto-config class uses @Conditional annotations:

  • @ConditionalOnClass(DataSource.class) — only if class is present.
  • @ConditionalOnMissingBean — only if user hasn't defined one.
  • @ConditionalOnProperty — only if config flag set.

Example: add spring-boot-starter-data-jpa and Hibernate, plus an H2 driver, and Spring auto-creates a DataSource, EntityManagerFactory, TransactionManager. You override any of them by declaring your own bean — your bean wins. Add --debug at startup to see the auto-configuration report.

What are starters and why do they exist?

Starters are curated POMs that pull in a set of compatible dependencies for a use case. spring-boot-starter-web brings in Spring MVC, Tomcat embedded, Jackson, Validation — everything you need for a REST API, with versions tested together.

Why they matter: in pre-Boot days, picking compatible versions of Spring + Hibernate + Jackson + Servlet API was a mini-project. Starters solve that. Common ones I use:

  • -starter-web — REST/MVC.
  • -starter-data-jpa, -data-mongodb, -data-elasticsearch.
  • -starter-security, -oauth2-resource-server.
  • -starter-actuator — production endpoints.
  • -starter-validation — Bean Validation.
  • -starter-test — JUnit, Mockito, AssertJ.

You can also build a custom internal starter for shared cross-team configuration.

application.properties vs application.yml — profiles

Both store externalized configuration; YAML is hierarchical and cleaner for nested config. Spring Boot loads in a precise order: application.yml, then profile-specific application-{profile}.yml, then environment variables, then command-line args — later wins.

Profiles partition configuration: application-dev.yml, application-staging.yml, application-prod.yml. Activate via SPRING_PROFILES_ACTIVE=prod environment variable.

Beans can also be profile-scoped: @Profile("prod") on a bean means it loads only in prod. I use this for in-memory message brokers in dev vs real Kafka in prod, or different log levels.

For secrets I never put values in YAML — placeholders only: password: ${DB_PASSWORD} sourced from env vars, AWS Parameter Store, or Vault.

@SpringBootApplication — what's inside it?

It's a composed annotation equivalent to three:

  • @SpringBootConfiguration — same as @Configuration but marks the class as the primary config.
  • @EnableAutoConfiguration — turns on Spring Boot's conditional auto-config.
  • @ComponentScan — scans the package of the annotated class and all sub-packages for @Component/@Service/@Repository/@Controller.

That's why your main class should be in the root package — scanning starts from there. You can customize: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) to opt out of auto-configuring a DB, or scanBasePackages = {"com.foo", "com.shared"} to scan additional packages.

Embedded server — Tomcat, Jetty, Undertow?

Spring Boot ships Tomcat by default — battle-tested, well-documented, fine for most loads. Jetty is the long-standing alternative — slightly lower memory, used historically by Eclipse and many cloud platforms. Undertow (Red Hat) is the most performant and lowest memory of the three, especially for high-concurrency workloads with many idle connections.

Switching is one dependency change:

<exclusion>spring-boot-starter-tomcat</exclusion>
<dependency>spring-boot-starter-undertow</dependency>

I've defaulted to Tomcat in every prod service I've shipped — its tooling and observability story is best. With Spring Boot 3 + Virtual Threads on Tomcat, the throughput is excellent and I don't feel the need to switch. For reactive workloads, Spring WebFlux uses Netty by default instead.

Actuator — production endpoints

Spring Boot Actuator exposes ops endpoints over HTTP (or JMX) for monitoring and management. Add the starter and key endpoints appear under /actuator:

  • /health — liveness/readiness for Kubernetes probes; aggregates health indicators (DB, Mongo, ES, custom checks).
  • /metrics + /prometheus — Micrometer metrics: JVM, HTTP, DB pool, custom.
  • /info — build info, git commit, custom info.
  • /env, /configprops — running configuration (lock these down).
  • /loggers — change log levels at runtime — invaluable for prod debugging.
  • /threaddump, /heapdump — diagnostics.

In prod I expose only health, info, prometheus publicly; everything else behind a management port and IAM rules.

Liveness vs readiness vs startup probes

These map directly to Kubernetes probes. Spring Boot Actuator's /health exposes them as /actuator/health/liveness and /actuator/health/readiness by default since Spring Boot 2.3.

Liveness: is the app alive? If this fails, K8s restarts the pod. Should check only fatal in-process states (e.g., out-of-memory flag) — not downstream dependencies.

Readiness: is the app ready to serve traffic? If this fails, K8s removes it from the load balancer but doesn't restart it. Should check downstream dependencies (DB, Kafka, ES) so we don't route traffic to a partially-broken instance.

Startup: a one-shot probe for slow-to-start apps so K8s doesn't kill them during boot. Once it passes, liveness takes over.

Getting these wrong causes restart loops or routing failures — a common production incident.

Logging — Logback, levels, structured logs

Spring Boot uses Logback behind SLF4J by default. logback-spring.xml in src/main/resources lets you customize appenders, levels, and patterns; Spring's variant supports profile-specific blocks.

In production I always log structured JSON using logstash-logback-encoder — one line per event with fields like level, logger, traceId, spanId, userId. Easy to ingest into ELK, Loki, or CloudWatch.

Practices:

  • Use SLF4J's parametrized form: log.info("user {} placed order {}", userId, orderId).
  • Don't log inside hot loops without rate-limiting.
  • MDC (Mapped Diagnostic Context) for request-scoped fields — traceId, userId.
  • Pair with Sleuth/Micrometer Tracing for distributed tracing.
  • Use the Actuator /loggers endpoint to bump log levels without redeploy.
Spring Boot 2 vs 3 — what changed?

Spring Boot 3 (and Spring Framework 6) released late 2022 introduced several breaking changes:

  • Java 17 baseline (Boot 2 worked on Java 8/11/17).
  • Jakarta EE namespace — every javax.servlet.* becomes jakarta.servlet.*. Big migration for code that uses Servlet API directly.
  • Native image support (GraalVM) is first-class — build truly small/fast-start images with -Pnative.
  • Observability overhaul — Micrometer Tracing replaces Spring Cloud Sleuth.
  • Virtual threads support (Boot 3.2+) — set spring.threads.virtual.enabled=true.

I once migrated a service to Boot 3 — most of the work was the Jakarta rename and a few deprecated APIs. Worth it for native image options and the cleaner observability story.

REST & Web
@RestController vs @Controller — what's the difference?

Both register the class as a Spring MVC handler. The difference: @Controller + @ResponseBody tells Spring to serialize the return value (typically to JSON via Jackson) instead of resolving a view name. @RestController is shorthand for both — every method implicitly returns the body directly.

@RestController
@RequestMapping("/api/users")
public class UserController {
    @GetMapping("/{id}")
    public User get(@PathVariable Long id) { ... }
}

Use @Controller only when you serve server-rendered views (Thymeleaf, JSP) and need to return view names. For JSON APIs — which is 99% of what I write — always @RestController.

Path variable vs request param vs request body

Three ways to read input in Spring MVC:

  • @PathVariable — part of the URL path: /users/{id} → @PathVariable Long id. Use for resource identifiers in REST.
  • @RequestParam — query string: /users?status=active&limit=10. Optional with defaults: @RequestParam(defaultValue = "20") int limit. Use for filters and pagination.
  • @RequestBody — deserialize the HTTP body (JSON) into an object. Use for POST/PUT/PATCH payloads. Pair with @Valid for Bean Validation.

Idiomatic REST: identify resources by path, filter/paginate by query params, send payloads in the body. Headers via @RequestHeader when you need them.

Global exception handling — @ControllerAdvice

I use @ControllerAdvice + @ExceptionHandler to centralize error handling and return consistent JSON error responses:

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(NotFoundException.class)
    public ResponseEntity<Problem> notFound(NotFoundException ex) {
        return ResponseEntity.status(404)
            .body(new Problem("NOT_FOUND", ex.getMessage()));
    }
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Problem> validation(...) { ... }
}

Spring Boot 3 also provides ProblemDetail (RFC 7807) for standardized error bodies. I prefer that for new services. The big benefit is consistency — every endpoint returns the same error shape, which makes client code much simpler. Pair with structured logging so we capture the traceId in every error response.

Validation — Bean Validation + @Valid

Bean Validation (JSR-380, Jakarta Validation) lets you annotate fields with constraints — @NotNull, @Size(min=1, max=100), @Email, @Min, @Pattern — and Spring runs them when you annotate the parameter with @Valid.

public record CreateUserRequest(
    @NotBlank String name,
    @Email String email,
    @Min(18) int age) {}

@PostMapping
public User create(@RequestBody @Valid CreateUserRequest req) { ... }

Violations throw MethodArgumentNotValidException, which your @ControllerAdvice converts to a 400 response with field-level errors. For service-layer parameters use @Validated on the class plus @Valid on params. Custom constraints are easy: write a @Constraint annotation and a ConstraintValidator. I always validate at the API boundary — defense in depth.

WebFlux — when would you use it over MVC?

Spring WebFlux is the reactive alternative to MVC — non-blocking, built on Project Reactor (Mono/Flux), running on Netty by default. Threads aren't blocked on I/O; they're parked and resumed when data arrives.

Use it when: you handle many concurrent slow connections (server-sent events, WebSockets, streaming responses), or when downstream calls are mostly I/O and you've hit thread-pool ceilings on MVC.

Costs: reactive code is harder to read, debug, and trace; you can't use blocking JDBC; learning curve for the team. Many "WebFlux for performance" projects end up slower because of code complexity and bugs.

My current take in 2026: with Virtual Threads (Java 21 + Boot 3.2+), MVC gives you reactive-like scaling without reactive code complexity. I'd reach for WebFlux today only for streaming use cases.

Resilience & Observability
Circuit breaker — what and why? hot

A circuit breaker wraps remote calls and short-circuits them when the downstream is failing — instead of waiting for every call to time out, we fail fast and recover quickly. States: CLOSED (all calls pass), OPEN (calls fail immediately for a wait period), HALF_OPEN (let a few probes through to test recovery).

In Spring Boot I use Resilience4j (the modern replacement for Hystrix):

@CircuitBreaker(name = "paymentApi", fallbackMethod = "fallback")
public PaymentResult charge(String id, BigDecimal amt) { ... }
public PaymentResult fallback(String id, BigDecimal amt, Throwable t) {
    return PaymentResult.deferred(id);
}

Configure failure-rate threshold, sliding window, wait duration. At Indus Net I wrapped the LLM API call with a circuit breaker — when the vendor had an outage, our service stayed up and returned cached / degraded results instead of cascading failures.

Retry strategies — when to retry?

Retries help with transient failures: network blips, 502/503, throttling. They hurt with permanent failures (validation errors, 404, business errors) or side-effect-causing calls that aren't idempotent.

Three rules I follow:

  • Retry only on retriable errors (timeouts, specific status codes). Don't retry 4xx.
  • Use exponential backoff with jitter: 100 ms, 200 ms, 400 ms + random — prevents thundering-herd reconnect storms.
  • Make the operation idempotent — use idempotency keys or natural keys so repeated requests don't double-charge or double-write.

With Resilience4j: @Retry(name = "paymentApi", fallbackMethod = "..."). Combine with circuit breaker — retry first, open the breaker on persistent failure. Bound the total time so we don't blow request timeouts.

Distributed tracing — Sleuth, Zipkin, OpenTelemetry

In microservices a single user request can touch 5+ services. Distributed tracing assigns a traceId at the edge that propagates through HTTP headers and message metadata to every hop. Each service adds spans; a collector reconstructs the timeline.

Spring Boot 2 used Spring Cloud Sleuth; Boot 3 uses Micrometer Tracing with bridges to Zipkin or OpenTelemetry. With one starter and management.tracing.sampling.probability=1.0 in dev, every log line gets traceId and spanId, and we ship spans to a backend like Jaeger, Zipkin, or commercial APM.

At Indus Net this saved hours during a latency investigation — we saw a request spend 4 s waiting on a sync call to an internal service that should've been async. Tracing made the bottleneck obvious.

Metrics — Micrometer + Prometheus + Grafana

Micrometer is a metrics façade (think SLF4J for metrics) — write to it once, switch backends. Spring Boot Actuator wires it up automatically: JVM metrics, HTTP request timings, DB pool sizing, Kafka consumer lag — all out of the box.

Custom metrics in code:

private final Counter charges = Counter.builder("payment.charges")
    .tag("provider", "stripe").register(registry);
charges.increment();
Timer.builder("payment.charge.latency").register(registry)
    .record(() -> paymentClient.charge(...));

Pair the /actuator/prometheus endpoint with Prometheus scraping, then dashboards in Grafana with alerts on p99 latency, error rate, and saturation. "RED" metrics (Rate, Errors, Duration) per endpoint is my baseline — if those four panels are healthy, the service is healthy.

Async processing — @Async and TaskExecutor

@Async runs a method on a separate thread without blocking the caller. Enable with @EnableAsync on a config class. The method must return void, Future, or CompletableFuture — the caller gets the future immediately.

Two production gotchas. (1) Define a named TaskExecutor — the default is SimpleAsyncTaskExecutor which creates a new thread per call (bad). Inject a bounded ThreadPoolTaskExecutor sized for your workload. (2) Self-invocation doesn't trigger async — same proxy gotcha as @Transactional.

I use @Async for fire-and-forget side effects: sending welcome emails, recording analytics, writing to Elasticsearch. For more complex async pipelines I prefer explicit CompletableFuture chains or Kafka events for durability.

Scheduling — @Scheduled and pitfalls

@Scheduled runs a method on a schedule. Enable with @EnableScheduling. Three styles:

  • @Scheduled(fixedRate = 30_000) — every 30 s from start of last run.
  • @Scheduled(fixedDelay = 30_000) — 30 s after the last finish.
  • @Scheduled(cron = "0 0 2 * * *") — 2 a.m. daily.

Pitfalls in production:

  • By default Spring uses a single-threaded scheduler — long-running jobs block subsequent runs. Configure a ThreadPoolTaskScheduler with multiple threads.
  • If you run multiple instances of the service, every instance fires the job. Solve with leader election (ShedLock, Quartz cluster) or move to a real job scheduler.
  • Don't put heavy DB work in scheduled methods without proper transaction management.

For non-trivial workloads I use Quartz, Kubernetes CronJobs, or Spring Batch.
