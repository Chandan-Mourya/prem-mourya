What happens in end-to-end implementation from requirement to go-live?

End-to-end banking implementation follows: requirement gathering → solution design → development → SIT → UAT → parallel run → go-live → hypercare.

Phases

Requirements: BRD/FRS from business; gap analysis against product capabilities; change request for gaps.

Design: solution design document, DB schema, API contracts, interface design — reviewed and signed off.

Development: customization, unit testing, code review; artifacts checked into version control.

Testing: SIT (IT team integration test), UAT (business acceptance), performance testing.

Go-live: data migration, cutover, parallel run, production support (hypercare).

Now coming to conclusion.

Each phase requires formal sign-off before proceeding — gate reviews prevent discovering issues too late.

Explain SDLC phases.

SDLC phases cover the complete software development lifecycle: planning, requirements, design, development, testing, deployment, and maintenance.

Phases

Planning: feasibility, resource estimation, timeline, risk assessment.

Requirements: gather BRD/FRS; create user stories; define acceptance criteria.

Design: system architecture, DB schema, API contracts, UI wireframes.

Development: coding, unit testing, code review, integration.

Testing: SIT, UAT, performance, security testing.

Deployment: release to production under change management.

Maintenance: production support, bug fixes, enhancements.

Now coming to conclusion.

SDLC phases are sequential in Waterfall, iterative in Agile — both cover the same concerns, differently paced.

Waterfall vs Agile. must

Waterfall — fixed phases (requirements → design → build → test → deploy). Agile — iterative sprints, frequent delivery.

Now coming to banking.

Waterfall for fixed-scope vendor implementations; Agile for in-house product teams.

When would you use Waterfall?

Use Waterfall when requirements are fixed, well-understood, and unlikely to change — such as regulatory compliance implementations or hardware-integrated banking systems.

Good fit

Fixed requirements: core banking product rollout with predefined FLEXCUBE configuration scope.

Contractual projects: fixed scope, price, and delivery date — Waterfall's documentation and sign-offs protect both parties.

Compliance projects: RBI mandate with specific requirements and deadline — no scope ambiguity.

Drawbacks

Inflexible to requirement changes mid-project. Testing at the end means late defect discovery.

Now coming to conclusion.

Waterfall suits compliance and large product rollouts; Agile suits evolving product development.

When would you use Agile?

Use Agile when requirements will evolve, early feedback is valuable, and the team can deliver incremental value in short iterations.

Good fit

Product development with evolving requirements: digital banking app features changing based on user feedback.

Long projects: 12+ month implementations where business needs evolve — Agile adapts vs. Waterfall's rigid scope.

Banking agile

Scrum sprints for microservice development: 2-week sprint delivers a working API endpoint end-to-end.

Product backlog prioritized by business value — highest ROI features delivered first.

Now coming to conclusion.

Agile does not mean no documentation — banking projects need architecture docs, API specs, and RCA reports regardless.

What is sprint planning?

Sprint planning is the Scrum ceremony where the team selects user stories from the product backlog for the upcoming sprint and defines how to deliver the sprint goal.

Activities

PO presents top backlog items; team estimates effort (story points); team commits to sprint goal.

Break stories into tasks: '5-point API story' → design DTO, implement endpoint, unit test, code review, SIT test.

Capacity

Team velocity (avg story points from last 3 sprints) guides how much to commit. Account for leave, meetings.

Now coming to conclusion.

Sprint planning commitment is a team promise — don't over-commit; under-deliver breeds distrust.

What is daily standup?

The daily standup is a 15-minute synchronization meeting where each team member answers: what I did yesterday, what I'll do today, and any blockers.

Purpose

Identify blockers early (dependency on another team, environment issue, unclear requirement).

Team coordination: who is working on what; avoid duplicate or conflicting work.

Anti-patterns

Status report to manager: standup is for the team, not management. Long discussions: take offline.

Now coming to conclusion.

Blockers raised in standup should be resolved the same day — unresolved blockers stall the sprint.

What is retrospective?

A sprint retrospective is the Scrum ceremony after each sprint where the team reflects on what went well, what didn't, and defines concrete improvements for the next sprint.

Format

What went well (keep doing), what didn't work (stop doing), what to try (start doing).

Each item gets an owner and action due by next sprint — tracked in Jira or action log.

Value

Continuous improvement: sprint-over-sprint, teams reduce waste and improve process.

Blameless: focus on process gaps, not individuals — psychological safety enables honest feedback.

Now coming to conclusion.

Retrospectives without action items are just conversations — each improvement must have an owner and due date.

What is backlog grooming?

Backlog grooming (refinement) is the ongoing process of reviewing, clarifying, estimating, and prioritizing product backlog items — ensuring the backlog is ready for sprint planning.

Activities

PO clarifies story requirements; team estimates story points; stories split if too large (> 8 points).

Acceptance criteria defined and agreed before sprint — prevents ambiguity during development.

Frequency

Typically mid-sprint (weekly for 2-week sprints) — ensures top 2 sprints of backlog are always ready.

Now coming to conclusion.

Well-groomed backlog enables efficient sprint planning — team spends less time in planning clarifying requirements.

What is user story?

A user story describes a software feature from the user's perspective: 'As a [user], I want [goal] so that [benefit]' — enabling team to understand purpose behind the requirement.

Format

'As a bank customer, I want to see my last 10 transactions so that I can monitor my spending.'

INVEST criteria: Independent, Negotiable, Valuable, Estimable, Small, Testable.

Banking examples

'As a teller, I want to place a hold on a cheque amount so that funds are blocked until clearance.'

'As a risk officer, I want to see AML flagged transactions so that I can investigate suspicious activity.'

Now coming to conclusion.

User stories focus on value and outcome — not implementation details, which the team decides.

What is acceptance criteria?

Acceptance criteria define the conditions that must be met for a user story to be considered done — specific, testable, and agreed between PO and team before development.

Format

Given-When-Then (Gherkin): 'Given account balance is ₹1000, When debit ₹500, Then balance shows ₹500 and SMS sent within 10 seconds.'

Good criteria

Specific: 'Transaction list shows last 30 days by default' — not 'shows recent transactions'.

Testable: QA can write a test case from the criterion without further clarification.

Now coming to conclusion.

Acceptance criteria prevent the #1 sprint failure: 'done' meaning different things to developer and product owner.

What is definition of done?

The definition of done (DoD) is the team's shared standard that a story must meet before it can be marked complete — ensuring consistent quality across all stories.

Typical DoD

Code complete and reviewed. Unit tests written and passing. Integration tests passing. SonarQube quality gate passed.

API documented (Swagger). Deployed to SIT and smoke-tested. No open blocker defects.

Banking DoD additions

Audit logging verified. Security checklist completed. Performance test passed (if applicable). Test evidence in Jira.

Now coming to conclusion.

DoD prevents 'it works on my machine' — every story must pass the same objective criteria before closure.

What is impact analysis?

Impact analysis assesses the full effect of a proposed change — which components, tests, databases, interfaces, and downstream systems are affected before proceeding.

Process

Identify the change: new field, logic change, DB schema change, API change.

Trace dependencies: which code uses this field/API/table? Which reports? Which interfaces? Which tests?

Banking

Adding a column to accounts table: impacts stored procedures, JPA entities, DTOs, reports, OSB transformations, migration scripts.

Changing business rule: which products/account types are affected? Are there regulatory implications?

Now coming to conclusion.

Incomplete impact analysis is the most common root cause of regression bugs — be thorough before estimating.

What is requirement traceability matrix?

A Requirements Traceability Matrix (RTM) maps each business requirement to its design artifact, code module, and test case — ensuring nothing is missed.

Contents

Columns: Requirement ID, Requirement Description, Design Document Reference, Code Module, Test Case ID, Test Status.

Each row traces one requirement through all phases — proves complete coverage.

Banking use

Mandatory for regulatory projects: auditors verify that RBI mandate requirements are implemented and tested via RTM.

Helps during UAT: each UAT test case linked to requirement — gaps in test coverage visible immediately.

Now coming to conclusion.

RTM is the audit evidence that all requirements were designed, built, and tested — keep it updated throughout.

What is technical specification document?

A Technical Specification Document (TSD) describes the detailed technical design: DB schema, API contracts, sequence diagrams, error handling, and performance considerations.

Contents

Architecture: component diagram, tech stack, integration points. DB design: tables, columns, indexes, sequences.

API design: endpoint URLs, request/response DTOs, error codes, authentication mechanism.

Sequence diagrams: end-to-end flow for each use case. Non-functional: performance targets, security controls.

Banking

TSD reviewed by solution architect and DBA before development — catch design issues early.

Now coming to conclusion.

A good TSD reduces development ambiguity and enables parallel work across team members.

What is release note?

A release note documents what is included in a release: new features, bug fixes, known issues, configuration changes, and deployment instructions for the operations team.

Contents

Version number, release date. What's new (features, enhancements). Bugs fixed (Jira IDs). Known issues.

Deployment instructions: DB scripts to run, config changes, WebLogic restart requirements, verification steps.

Banking

Distributed to: dev team, QA, operations, business stakeholders. Required before change management approval.

Now coming to conclusion.

Release notes are the operations team's deployment guide — incomplete notes cause deployment failures.

What is deployment document?

A deployment document provides step-by-step instructions for deploying a release to an environment — including pre-conditions, steps, verification, and rollback procedure.

Contents

Pre-conditions: environment health check, backup verification, maintenance window confirmation.

Steps: DB scripts (in order), application EAR deployment, config changes, WebLogic restart, smoke test.

Verification: list of health checks post-deployment. Rollback: steps to revert if deployment fails.

Importance

Reviewed and approved by CAB (Change Advisory Board) before production deployment window.

Now coming to conclusion.

A deployment without a document is a risk — ops team needs precise steps, not assumptions.

What is rollback plan?

A rollback plan defines how to revert a production deployment to the previous stable state if the new release causes critical issues.

Components

Decision criteria: what conditions trigger rollback (Sev1 issue within X hours of deployment, data corruption).

Steps: revert application EAR to previous version, run DB rollback scripts, restore config, verify.

Time estimate: rollback must complete before business impact exceeds reverting cost.

Banking

Test rollback in staging before production deployment — a rollback plan never tested is a plan that will fail under pressure.

Now coming to conclusion.

Every production deployment must have a tested rollback plan — this is non-negotiable in banking.

What is change request?

A change request (CR) is a formal document requesting a modification to an IT system — assessed for risk, impact, and approved by the Change Advisory Board before implementation.

Process

CR raised with: description of change, business justification, risk assessment, rollback plan, test evidence.

CAB review: assesses risk, scheduling conflicts, resources; approves or defers.

Post-implementation: verify change success; update CR status; post-implementation review for major changes.

Banking

Emergency CR: expedited approval for Sev1 hotfixes — not zero process, but faster (2-4 hours vs. 1 week).

Now coming to conclusion.

Change management prevents unplanned changes that cause incidents — no change to production without a CR.

What is defect lifecycle?

The defect lifecycle tracks a bug from discovery through triage, assignment, fix, re-test, and closure — ensuring no defect is lost or prematurely closed.

States

New → Assigned (to developer) → In Progress → Fixed → In Testing → Closed.

If re-test fails: Reopened → In Progress → Fixed → In Testing → Closed.

Deferred: valid bug, scheduled for future release. Rejected: not a bug or duplicate.

Banking specifics

Sev1 defects: bypass normal cycle with emergency fix path. All defects require test evidence for closure.

Now coming to conclusion.

A defect closed without verified test evidence will reappear in production — enforce the testing requirement.

How do you handle scope change?

Scope changes are managed through formal change control: document the change, assess impact on timeline/cost/resources, get stakeholder approval, then adjust the plan.

Process

Document: what is changing, why, and what was originally agreed.

Impact: estimate additional effort, timeline extension, resource needs, and risks.

Approval: stakeholder sign-off on the change and its implications before proceeding.

Banking

Regulatory scope change (new RBI mandate mid-project): mandatory — adjust timeline with regulator's deadline in mind.

Business-driven scope change: evaluate if it can wait for next phase vs. immediate priority.

Now coming to conclusion.

Never absorb scope changes silently — undocumented scope creep causes team burnout and project failure.
