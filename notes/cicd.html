CI vs CD vs CD — what each one means must

The three CI/CD terms are confusingly similar:

  • Continuous Integration — every commit triggers automated build + tests. Goal: catch breakage within minutes, not days. Requires good test coverage and a healthy main branch.
  • Continuous Delivery — every commit that passes CI is deployable — packaged and ready for staging/prod. Production deploys are a one-click manual gate.
  • Continuous Deployment — every commit that passes goes automatically to production. No human gate. Requires very strong tests, feature flags, canary rollouts, automated rollback.

Most teams aim for Delivery first; Deployment is for mature orgs with deep monitoring. At Indus Net we're at Delivery — staging deploys are auto, prod is one-click after a smoke check.

CI/CD Pipeline — step-by-step (with Jenkinsfile example) must

A CI/CD pipeline automates the entire path from code commit to production: pull the latest code → build → test → quality-check → package → deploy → verify. The goal is to make every push safely deployable with no manual SSH-ing into servers or hand-built JARs.

CORE FLOW Code Commit → Build → Test → Quality Check → Artifact → Deploy → Verify. Every CI/CD pipeline, no matter how big, is a chain of these stages — each stage fails fast and blocks the next.

The 9-stage pipeline at a glance:

1. Developer pushes code to main / opens a PR
↓
2. CI tool (Jenkins / GitHub Actions) triggers automatically via webhook
↓
3. Checkout latest code into a clean workspace
↓
4. Build — mvn clean package → produces target/app.jar
↓
5. Run automated tests — unit + integration. Failure = pipeline stops.
↓
6. Code quality & security scans — SonarQube, OWASP, Snyk
↓
7. Create artifact — JAR uploaded to Nexus, or Docker image pushed to ECR
↓
8. Deploy to AWS — EC2 / ECS / EKS via SSH, ECS update-service, or kubectl
↓
9. Verify — health check, smoke tests, CloudWatch alarms

Deploy stage — two common shapes:

JAR-based (EC2)
  1. scp the JAR to the EC2 instance.
  2. systemctl stop app (or kill the old process).
  3. Replace the JAR file.
  4. systemctl start app → new version live.

Simple, works for single-instance deployments. No zero-downtime by default.

Container-based (ECS / EKS)
  1. Build Docker image → tag with commit SHA.
  2. Push to ECR.
  3. Update ECS service / Kubernetes Deployment with the new image tag.
  4. Rolling deploy — drain old tasks, ramp up new ones, health-check gated.

This is what real production looks like — zero-downtime, auto-rollback, multi-instance.

Example Jenkinsfile (declarative pipeline):

pipeline {
    agent any

    tools {
        maven 'maven-3.9'
        jdk   'jdk-17'
    }

    stages {
        stage('Checkout') {
            steps {
                git branch: 'main',
                    url: 'https://github.com/user/app.git'
            }
        }

        stage('Build') {
            steps {
                sh 'mvn clean package -DskipTests'
            }
        }

        stage('Test') {
            steps {
                sh 'mvn test'
            }
            post {
                always {
                    junit '**/target/surefire-reports/*.xml'
                }
            }
        }

        stage('Quality Gate') {
            steps {
                withSonarQubeEnv('sonarqube') {
                    sh 'mvn sonar:sonar'
                }
            }
        }

        stage('Artifact') {
            steps {
                sh 'docker build -t my-app:${GIT_COMMIT} .'
                sh 'docker push my-registry/my-app:${GIT_COMMIT}'
            }
        }

        stage('Deploy') {
            steps {
                sh '''
                    scp -i $KEY target/app.jar ec2-user@$SERVER:/home/ec2-user/
                    ssh -i $KEY ec2-user@$SERVER "sudo systemctl restart app"
                '''
            }
        }

        stage('Verify') {
            steps {
                sh 'curl -f http://$SERVER:8080/actuator/health'
            }
        }
    }

    post {
        failure  { mail to: 'team@example.com', subject: 'Build failed', body: 'Check Jenkins.' }
        success  { echo "Deployed ${env.GIT_COMMIT} successfully." }
    }
}

Why CI/CD pipelines matter:

  • Faster delivery — minutes from merge to production, not days.
  • Fewer human errors — same script every time; no "forgot to update the env var".
  • Quality gates baked in — failing tests / vulnerabilities block bad code automatically.
  • Reproducible — every artifact is tied to a commit SHA; you can roll back to any past build.
  • Confidence to deploy small & often — small diffs are safer than monthly mega-releases.

Best practices I follow:

  • Keep CI fast — target < 10 min for a PR build. Cache Maven deps, parallelize tests, skip slow integration tests until merge.
  • Tag everything with commit SHA — JARs, Docker images, deploy metadata. Makes rollbacks one command.
  • Fail fast, fail loud — first stage that fails should stop the pipeline and ping the author.
  • Secrets in a vault — never echo them in build logs. Use GitHub Actions secrets / Jenkins credentials / AWS Secrets Manager.
  • Smoke tests after deploy — at minimum hit /actuator/health; ideally a few end-to-end API calls.
  • Automated rollback on health-check failure for prod — don't rely on humans during incidents.
  • Promote artifacts, don't rebuild — the same Docker image moves dev → staging → prod, eliminating "works on staging" surprises.

Interview one-liner: A CI/CD pipeline automates build → test → quality check → package → deploy → verify. When a developer pushes to GitHub, a webhook triggers Jenkins / GitHub Actions, which checks out the code, runs mvn clean package, runs all tests, scans for quality and vulnerabilities, builds a JAR or Docker image, pushes it to Nexus / ECR, and deploys it to EC2 / ECS / EKS. After deploy, health checks and CloudWatch alarms verify success; on failure the previous version is automatically rolled back. The result is faster, repeatable, error-free releases — small commits flow to production in minutes with full traceability back to the source commit.

What does a good CI pipeline look like?

For a typical Spring Boot service:

  1. Checkout + cache dependencies (Maven/Gradle, Docker layer cache).
  2. Lint / format check — Spotless, Checkstyle, EditorConfig. Fast, fails first.
  3. Unit tests — fast, isolated.
  4. Integration tests — with Testcontainers spinning up Postgres, Kafka, Redis. Production-like, slower.
  5. Static analysis — SonarQube/Codacy, dependency vulnerabilities (Snyk, OWASP, Dependabot), SAST (CodeQL).
  6. Build container image, push to registry tagged with commit SHA.
  7. Sign + SBOM for supply-chain security (sigstore/cosign).
  8. Auto-deploy to dev/staging.
  9. Smoke tests / health checks post-deploy.
  10. Manual approval + canary to production.

Total CI time target: <10 min for typical PR; <20 min for the full pipeline. Anything slower kills developer flow.

SonarQube — code quality & security scanning in CI/CD must

SonarQube is a static code analysis platform that scans your code for bugs, vulnerabilities, code smells, duplication, and test coverage — and enforces a Quality Gate in CI/CD that blocks bad code before it merges or deploys. It's the standard tool every Java/Spring Boot team I've worked with uses to keep technical debt and security issues from sneaking into production.

CORE IDEA Run the scanner on every PR / build → SonarQube analyses the diff → produces a Quality Gate verdict (PASS / FAIL) based on coverage, duplication, bug count, and security issues. Fail = pipeline stops. Quality stays high automatically.

What SonarQube checks:

BugsLikely runtime errors — NPEs, resource leaks, infinite loops.Unclosed InputStream, null dereference after a null check.
VulnerabilitiesSecurity issues that an attacker could exploit.SQL injection, hardcoded passwords, weak crypto (MD5).
Security HotspotsLines worth a security review (not always wrong, but worth a look).Random instead of SecureRandom, permissive CORS.
Code SmellsMaintainability issues — design / style problems.Methods over 100 lines, complex conditionals, dead code.
CoverageHow much of new code is covered by tests."80% coverage on new code" gate.
DuplicationCopy-pasted blocks across files.Same try/catch block in 5 services.
ComplexityCyclomatic complexity of methods/classes.Method with 20 nested if/else branches.

How SonarQube fits into a CI/CD pipeline:

Developer pushes code / opens a PR
↓
CI/CD pipeline (Jenkins / GitHub Actions) starts
↓
Pipeline runs build + tests + coverage (mvn verify)
↓
SonarQube scanner sends source + coverage + issues to the Sonar server
↓

  • Catches bugs & vulnerabilities early — before code review, before merge, before production.

  • Tracks technical debt — "debt ratio" trend over time keeps it from growing silently.

Common interview gotchas:

  • SonarQube doesn't run your tests — it consumes the JaCoCo/Surefire coverage report. Run mvn verify before the scan.
  • "New code" vs "Overall" — the Quality Gate is usually scoped to new code so you don't drown in legacy issues.
  • It's not a replacement for code review — it catches the boring stuff so humans can focus on design.
  • Pull request decoration — modern setups post Sonar issues as inline PR comments (GitHub/GitLab).
  • SonarLint — the IDE plugin (IntelliJ / VS Code) catches the same issues while you type, before push.

Interview one-liner: SonarQube is a static code analysis tool that scans every build for bugs, vulnerabilities, security hotspots, code smells, duplication, and test coverage. It's integrated into the CI/CD pipeline (Jenkins / GitHub Actions / GitLab CI), runs after build + tests, and enforces a Quality Gate that fails the pipeline if thresholds (e.g., 80% new-code coverage, zero new bugs, zero new vulnerabilities) aren't met. The result: code quality stays high automatically, security regressions don't ship, and teams have an objective baseline for technical debt.

Trunk-based vs Git Flow vs GitHub Flow

Three popular branching strategies.

Git Flow — long-lived branches: master, develop, feature/*, release/*, hotfix/*. Designed for versioned releases (installable software). Heavy for web/SaaS — too much branch ceremony.

GitHub Flow — one main branch + short-lived feature branches → PR → merge → deploy. Simple, works great for continuous delivery.

Trunk-based development — everyone commits to main multiple times a day; very short-lived branches. Relies on feature flags to hide incomplete work in production. Used by Google, Facebook, Meta. Fastest velocity.

For web services I prefer GitHub Flow with trunk-based principles: feature branches live <2 days, integrate often, use flags for unfinished features. Long-lived branches are where merge conflicts and bugs come from.

Merge vs rebase — which when?

Two ways to integrate one branch's changes into another.

Merge (git merge feature) creates a merge commit preserving full history. Pros: non-destructive, easy collaboration on a shared branch. Cons: history can get noisy.

Rebase (git rebase main) replays your commits on top of the target. Pros: linear history, easier to read. Cons: rewrites commit SHAs — dangerous on shared branches.

Rules I follow:

  • Rebase your local feature branch onto main before pushing to keep PR clean.
  • Never rebase commits that have been pushed and others may have pulled.
  • Use squash-and-merge on PRs — one logical commit per feature on main. Clean history without rewriting branches.
  • Reserve true merge commits for integrating long-lived release branches.
How do you handle hotfixes in production?

The playbook:

  1. Triage — confirm severity. If it's data loss or auth break, prioritize. Otherwise queue normally.
  2. Create a hotfix branch from the production tag (not main, in case main has unreleased changes).
  3. Minimal fix — smallest possible diff. Don't sneak unrelated changes in.
  4. Test — add a regression test that fails before the fix and passes after.
  5. Fast-track PR — same review standards, just expedited.
  6. Deploy — canary first if at all possible. Watch metrics.
  7. Cherry-pick / merge back to main immediately so the fix isn't lost on the next release.
  8. Post-mortem — what caused this? Add monitoring/tests/automation so the next one is caught earlier.

One Indus Net case: a JSON parsing bug caused 500s for some resumes. Hotfix shipped in 30 minutes; the regression test we added has caught two similar bugs since.

Feature flags — why and how?

Feature flags let you turn features on/off without redeploying. Code is shipped to production behind a flag, then enabled gradually for specific users.

Use cases:

  • Trunk-based development — merge unfinished work behind a flag; flip it on when ready.
  • Canary releases — enable for 5% of users, watch metrics, ramp up.
  • A/B testing — show variant A to half, B to the other.
  • Kill switches — disable a misbehaving feature without a deploy.
  • Per-customer features in B2B SaaS.

Tools: LaunchDarkly, Unleash, Split.io, Flagsmith, or roll your own. A simple FeatureService.enabled("new-search", userId) lookup with a config map and percentage rollouts gets you 80%.

Watch out for flag debt: clean up old flags monthly — they accumulate quickly.

What makes a good code review?

What I look for as a reviewer:

  • Correctness — does it do what the PR says? Edge cases?
  • Tests — meaningful coverage, including failure paths. Not just "happy path + 100% coverage".
  • Design fit — does it belong here, or does it deserve its own module/service? Are abstractions earning their keep?
  • Security — input validation, authz checks, secrets, SQL injection.
  • Observability — logs, metrics, tracing for the new code paths.
  • Performance — N+1 queries, missing indexes, hot-path allocations.
  • Readability — naming, comments where needed, no clever tricks.
  • Backward compatibility — DB migrations, API contracts.

What I value as an author: small PRs (<400 lines diff), clear description with context, screenshots/curl examples for API changes. Code review is mentorship — explain the "why", not just "no".

How do you manage database migrations?

Use a migration tool — Flyway or Liquibase — that versions schema changes as code in your repo, applied in order. V1__create_users.sql, V2__add_status_to_users.sql, etc.

Rules I follow for zero-downtime migrations:

  • Backward-compatible changes only. Old code must still work with the new schema for the duration of a deploy.
  • Two-phase for breaking changes: add column (nullable) → deploy code that writes both old and new → backfill → deploy code that reads new only → drop old column later.
  • Renames are two migrations + an interim code change.
  • Long migrations (large tables) — run online; use tools like pg_repack or gh-ost for big alters.
  • Apply migrations early in the deploy pipeline, before pod rollout — never on app startup in parallel.

Always test migrations on a staging snapshot. Test rollback. Migration mistakes cause the worst incidents.

GitOps — what and why?

GitOps declares infrastructure and app state as code in git, and a reconciler agent applies it. Git is the single source of truth — to change production, open a PR.

Tools: Argo CD and Flux for Kubernetes deploys. They watch a git repo containing manifests/Helm charts and continuously reconcile cluster state.

Wins:

  • Audit trail — every change is a commit by a named author.
  • Easy rollback — revert the commit.
  • Self-healing — if someone manually changes the cluster, the agent reverts it.
  • Disaster recovery — recreate a cluster by pointing Argo at the repo.
  • Separation of concerns — CI builds and tests; GitOps deploys. No CI agent has cluster credentials.

Pattern: app code repo → CI builds image → bumps image tag in deploy repo → Argo CD picks it up and rolls out. We use Argo CD at Indus Net — production is a git revert away if anything breaks.

Maven vs Gradle.

Maven uses XML-based declarative configuration with fixed lifecycle; Gradle uses Groovy/Kotlin DSL with flexible, incremental build and better performance.

Maven

pom.xml: declarative; strict lifecycle (validate→compile→test→package→install→deploy); wide enterprise adoption.

Convention over configuration: standard project layout, predictable behavior, strong plugin ecosystem.

Gradle

build.gradle: programmable DSL; incremental builds (skips unchanged tasks); build cache speeds CI significantly.

Android standard; gaining traction in Java microservices; steeper learning curve than Maven.

Banking context

Most banking projects use Maven for legacy codebases; new microservices projects increasingly adopt Gradle.

Now coming to conclusion.

Maven for stability and enterprise convention; Gradle for performance and flexibility in modern projects.

What is `pom.xml`?

A pom.xml (Project Object Model) is Maven's build descriptor defining project coordinates, dependencies, plugins, profiles, and build lifecycle configuration.

Key sections

groupId, artifactId, version: uniquely identify the artifact (e.g., com.bank:payment-service:1.0.0).

dependencies: list of library dependencies with scope (compile, test, provided, runtime).

build/plugins: Maven Surefire (test), Maven Compiler (Java version), Spring Boot Maven Plugin (fat JAR).

Banking usage

Parent POM defines common dependency versions (BOM) and plugin config shared across all microservices.

Profiles: -Pproduction activates production-specific settings (logging level, optimization flags).

Now coming to conclusion.

Use a parent POM with dependencyManagement to centralize version control across a multi-module banking project.

What is dependency management?

Dependency management in Maven centrally declares dependency versions in a parent POM's dependencyManagement section, ensuring consistent versions across all child modules.

How it works

Parent POM: dependencyManagement lists all dependencies with versions — child POMs inherit versions without specifying them.

Spring Boot BOM (Bill of Materials): import spring-boot-dependencies BOM to get tested, compatible library versions.

Benefits

Version consistency across all modules in a multi-module project; no version drift between services.

Upgrade: change version in one place (parent) — all children pick up the new version.

Now coming to conclusion.

Dependency management is essential in large banking projects with 20+ Maven modules sharing common libraries.

What is transitive dependency?

A transitive dependency is a library that your direct dependency depends on — Maven automatically includes it in the build classpath.

Example

Your project depends on spring-web; spring-web depends on jackson-databind — jackson-databind is a transitive dependency.

mvn dependency:tree shows the full transitive dependency tree including version of each resolved artifact.

Issues

Version conflicts: two different libraries depend on different versions of the same artifact — Maven picks nearest-wins version.

Exclusion: use <exclusions> to exclude a transitive dependency that conflicts or is unused.

Now coming to conclusion.

Always inspect the dependency tree when upgrading libraries — a transitive version change can break production.

What is Maven profile?

A Maven profile allows environment-specific build configuration (properties, dependencies, plugins) activated via -P flag or environment trigger.

Usage

Profiles: dev (H2 DB config, debug logging), sit (Oracle DB config), production (minified, optimized builds).

Activate: mvn package -Pproduction; or auto-activate based on OS, JDK version, or absence of a file.

Banking use

CI pipeline activates -Psit to use SIT database URL and credentials during integration testing.

Production profile enables dead-code elimination and disables actuator endpoints for security.

Now coming to conclusion.

Profiles keep environment-specific configuration out of the main build — critical for banking deploy pipelines.

What is snapshot version?

A SNAPSHOT version (e.g., 1.0.0-SNAPSHOT) in Maven indicates a development version that may change; Maven always downloads the latest snapshot from the remote repository.

Behaviour

Maven downloads SNAPSHOT artifact from Nexus on every build (or per update policy) — gets latest published development build.

Release version (1.0.0 without SNAPSHOT) is immutable once published — never changed after release.

Banking practice

Use SNAPSHOT versions during development and SIT; release (remove SNAPSHOT) before promoting to UAT/Production.

Never deploy SNAPSHOT artifacts to production — they are mutable and non-reproducible.

Now coming to conclusion.

SNAPSHOT in production is a red flag — always release a fixed version before production deployment.

How do you resolve dependency conflict?

Dependency conflicts are resolved using Maven's dependency:tree to identify conflicting versions, then adding explicit version declarations or exclusions to force the correct version.

Steps

mvn dependency:tree -Dincludes=groupId:artifactId shows which version is being pulled and by whom.

Add explicit <dependency> in your POM with the correct version to override Maven's nearest-wins selection.

Use <exclusion> in the conflicting dependency to remove the wrong transitive version.

Example

jackson-databind 2.9 (vulnerable) pulled transitively — add explicit 2.15.x dependency to override.

Now coming to conclusion.

Run OWASP dependency-check plugin in CI to detect known CVEs in transitive dependencies automatically.

What is Git branching strategy?

A Git branching strategy defines how branches are created, merged, and managed — common strategies are GitFlow, trunk-based development, and GitHub Flow.

GitFlow

main (production), develop (integration), feature/*, release/*, hotfix/* branches.

Feature branches merged to develop; release branch cut from develop; hotfix branches from main.

Trunk-based

All developers commit to main/trunk frequently; feature flags hide incomplete features; short-lived branches.

Better for continuous delivery; reduces merge conflicts from long-lived feature branches.

Banking practice

Most banking teams use GitFlow due to release management complexity; hotfix branches for production patches.

Now coming to conclusion.

Choose branching strategy based on team size and release frequency; document and enforce it via PR rules.

What is pull request?

A pull request (PR) is a proposal to merge code changes from a feature branch into a target branch, with code review, CI checks, and approval gate before merge.

Process

Developer pushes feature branch → opens PR → reviewers inspect code, leave comments → CI runs tests.

After review approvals and green CI: merge using merge commit (preserves history) or squash merge (clean history).

Banking practice

Require minimum 2 approvals for PRs touching financial calculation or security code.

Branch protection: no direct push to main/develop; all changes via PR with mandatory CI pass.

Now coming to conclusion.

PRs are the main quality gate — enforce code review, test coverage, and SonarQube pass before any merge.

How do you resolve merge conflicts?

Merge conflicts are resolved by identifying the conflicting changes, understanding both versions' intent, choosing the correct merge, and verifying the result with tests.

Steps

git pull origin develop; git merge or git rebase triggers conflict markers in affected files.

Open conflicting file: <<< HEAD shows your changes, >>> branch shows incoming; edit to correct combined version.

git add <resolved-file>; git merge --continue (or git rebase --continue); run tests to verify.

Prevention

Short-lived feature branches (< 1 week) reduce conflict probability significantly.

Rebase feature branch onto latest develop daily to incorporate others' changes incrementally.

Now coming to conclusion.

Never blindly accept 'ours' or 'theirs' in a merge — understand what both sides changed before deciding.

What is Git stash?

git stash temporarily shelves uncommitted working-directory changes so you can switch context (fix a bug, pull updates) then restore them later.

Usage

git stash (saves changes); git stash pop (restores and removes latest stash); git stash list (view all stashes).

git stash push -m 'WIP: interest calculation' to add a descriptive name for later identification.

Use case

Mid-feature when an urgent hotfix is needed: stash WIP, checkout hotfix branch, fix, merge, pop stash.

Now coming to conclusion.

Stash is a temporary shelf — don't leave stashes for days; commit or discard to keep the stash list clean.

What is cherry-pick?

git cherry-pick applies a specific commit from one branch to another — useful for backporting a hotfix to a release branch without merging the full feature branch.

Usage

git cherry-pick <commit-sha> applies that commit's changes on top of current branch.

Cherry-pick a range: git cherry-pick A..B applies commits A+1 through B.

Banking use case

Critical hotfix committed to main: cherry-pick to release/1.5 branch to include in next patch release without merging main.

Now coming to conclusion.

Cherry-pick creates a new commit with a different SHA — can cause confusion if the original is later merged; use carefully.

What is Jira workflow?

A Jira workflow defines the lifecycle states (To Do → In Progress → Code Review → Testing → Done) and transitions for issues in a project.

States

To Do → In Progress (dev starts) → Code Review (PR raised) → In Testing (in SIT) → Done (deployed and verified).

Defects: Open → In Progress → Fixed → In Testing → Closed (or Reopened if regression found).

Banking projects

How do you estimate story points?

Story points estimate relative effort and complexity using Fibonacci sequence (1, 2, 3, 5, 8, 13) — accounting for complexity, uncertainty, and effort.

Process

Planning poker: each team member independently estimates; discuss outliers to understand different assumptions.

Use a reference story as benchmark (e.g., account balance API = 3 points) to calibrate team's estimation scale.

Banking specifics

Banking stories have hidden complexity: regulatory checks, maker-checker flows, audit logging add points.

Integration stories get higher points due to external system dependency and testing complexity.

Now coming to conclusion.

Story points estimate complexity, not hours — they help the team understand capacity and spot under-estimated work.

What is sprint?

A sprint is a fixed time-box (typically 2 weeks) in Scrum during which a cross-functional team delivers a potentially shippable product increment.

Structure

Sprint planning: team selects stories from backlog fitting velocity; defines sprint goal.

Daily standup: what did I do, what will I do, any blockers — 15 minutes, standing.

Sprint review: demo completed work to stakeholders; sprint retrospective: improve team process.

Banking projects

Banking sprints must account for SIT/UAT cycles — delivery in sprint may mean 'dev complete + SIT pass'.

Now coming to conclusion.

A sprint's value is the working software delivered — not the number of story points completed.

What is bug lifecycle?

A bug lifecycle tracks a defect from discovery through triage, assignment, fix, testing, and closure — ensuring no defect is lost or prematurely closed.

States

New → Assigned → In Progress → Fixed → In Testing → Closed (or Reopened → In Progress if not fixed).

Deferred: valid bug but not fixed in current release — documented and scheduled for future.

Banking practice

P1/Sev1 bugs (financial data loss, security breach) bypasses normal cycle — immediate hotfix with emergency change request.

Bug closure requires test evidence (test case pass screenshot) and business sign-off for UAT defects.

Now coming to conclusion.

Never close a bug without verified test evidence — 'Fixed' without test leads to production regression.

What is release branch?

A release branch is cut from develop (GitFlow) when a version is feature-complete; it receives only bug fixes, doc updates, and release preparation — no new features.

Purpose

Allows new feature development on develop to continue in parallel while release branch is stabilized.

Hotfixes on release branch are cherry-picked back to develop to keep main branch in sync.

Banking naming

release/v1.5.0 branch: contains exactly the features going into the 1.5.0 production deployment.

After go-live: merge release branch to main, tag with version (v1.5.0), then delete the release branch.

Now coming to conclusion.

Tagging release branches in Git provides an immutable reference for any future hotfix baseline.

How do you manage hotfix?

A hotfix is an emergency fix for a critical production defect: branch from main/production, fix, test, deploy via emergency change process, and merge back to develop.

Process

git checkout -b hotfix/ORA-04091-trigger main — branch from the current production code.

Fix, unit test, deploy to SIT/staging for smoke test, raise emergency change request.

Merge to main (tag new patch version), cherry-pick to develop and any active release branches.

Banking constraints

Hotfixes require emergency CAB (Change Advisory Board) approval; cannot skip testing even under pressure.

Always have a rollback plan: if hotfix causes new issue, can revert to previous tagged version.

Now coming to conclusion.

Hotfix urgency must not eliminate testing — a bad hotfix in banking can cause worse damage than the original issue.
