What is an LLM, in one paragraph? must

A Large Language Model is a neural network — typically a transformer — trained on huge amounts of text to predict the next token. "Token" is roughly a word piece; for English ~4 characters on average. Predicting the next token over billions of examples gives the model statistical understanding of grammar, facts, reasoning patterns, code, and style.

At inference you give it a prompt; it generates tokens one at a time, conditioned on everything before. Context window limits how much it can see at once (commonly 8K–200K tokens today). Temperature controls randomness — 0 for deterministic outputs, >0 for creativity.

Common families: OpenAI GPT, Anthropic Claude, Google Gemini, Meta Llama (open weights), Mistral, DeepSeek. As an engineer I treat them like a remote service — call an API, handle latency, retries, cost, and safety just like any other dependency.

What is RAG (Retrieval-Augmented Generation)? hot

RAG grounds an LLM in your own data. Flow:

  1. Ingest — split documents into chunks, generate embeddings (vectors) for each, store in a vector DB.
  2. Query — embed the user's question, do a vector search (kNN) for the top-K most similar chunks.
  3. Generate — pass the question plus retrieved chunks as context to the LLM with a prompt like "Answer using only this context."

Why use it: LLMs have stale training data and hallucinate. RAG keeps answers grounded in your current docs without retraining.

On Punctuations.ai, I built RAG over a recruiter's candidate database — they can ask "show me Python developers in Bangalore with 3+ years of GenAI work" and the system retrieves matching resume chunks and generates a ranked summary. Tweaks that mattered: hybrid retrieval (BM25 + vector), reranking (cross-encoder on top 50), and careful prompt engineering with citations.

What are embeddings? Why do they work?

An embedding is a fixed-length vector (commonly 768 or 1536 floats) that represents text in a high-dimensional space. The crucial property: semantically similar texts produce vectors close together in that space, regardless of exact wording.

Examples: "Python developer" and "Pythonista" land near each other; "Java engineer" sits far from both but near "JVM developer". This is why kNN search on embeddings finds meaning, not just keywords.

Practical points:

  • Use a dedicated embedding model — OpenAI text-embedding-3, Cohere, BGE, all-mpnet, Gemini Embedding.
  • Stick to one model per index (different models produce non-comparable vectors).
  • Storage: Elasticsearch dense_vector, PGVector, Qdrant, Pinecone, Weaviate.
  • Normalize vectors and use cosine similarity (default for most embedding models).
Vector databases — when do you need one?

A vector DB stores embeddings and supports fast approximate nearest-neighbor (ANN) search. You need it when the dataset is too big or too slow for an exact scan — typically > ~100K vectors.

Options:

  • Elasticsearch / OpenSearch — kNN support (HNSW), great if you already use ES. My pick for Punctuations.ai since we needed hybrid search anyway.
  • PostgreSQL + pgvector — keep vectors next to relational data; simple ops; HNSW or IVFFlat.
  • Qdrant / Milvus / Weaviate — purpose-built, more advanced filtering and clustering features.
  • Pinecone — managed, popular for hosted RAG apps.
  • Redis Stack — vector + KV; latency wins for hot data.

For small datasets (<100K), a flat in-memory cosine search is fine and avoids extra infrastructure. Don't over-engineer.

Prompt engineering — what actually works

Practical techniques that I've found move the needle:

  • Be specific. "Summarize this resume in 3 bullet points, each ≤15 words, focused on backend skills" beats "summarize this resume."
  • Give examples (few-shot). Show 1–3 input/output pairs of the format you want. Often more reliable than instructions.
  • Role + task + constraints. "You are a senior recruiter. Given the JD and resume below, score 1–10 and list 3 strengths and 2 gaps."
  • Output format — request strict JSON with a schema, then parse. Use structured output (OpenAI JSON mode, Anthropic tool use) when available.
  • Chain of thought / "think step by step" for reasoning tasks.
  • Temperature 0 (or near) for deterministic / extraction tasks; higher only for creative work.
  • Test like code — keep a set of golden inputs and run prompts through an eval harness before changes.
How do you reduce LLM latency and cost?

LLM calls are both slow and expensive — these compound at scale. My toolkit:

  • Cache — semantic cache (vector similarity) for repeat or near-duplicate queries. On Punctuations.ai we cache JD embeddings and the matched-resume list keyed by JD hash.
  • Smaller models for easier sub-tasks — classification, extraction, reranking don't need GPT-4. Use Mistral 7B, Llama 3 8B, or a fine-tuned small model.
  • Streaming — improves perceived latency; users see output as it arrives.
  • Batch + parallelize — concurrent calls for unrelated sub-prompts.
  • Truncate context — don't pass the whole document if the model only needs a section.
  • Prompt caching (Anthropic, Gemini) for static system prompts.
  • Async pipelines — heavy LLM work in Kafka workers, not synchronous APIs.
  • Token quotas per user/tenant for cost protection.

Result on Punctuations.ai: dropped match latency from 4 s to ~600 ms and cut monthly token spend nearly in half.

Tool calling / function calling

Tool calling lets the LLM call external functions / APIs in a structured way. You describe tools with JSON schemas; the model decides when to invoke one and produces arguments.

tools: [
  { name: "lookupCandidate", parameters: { id: "string" } },
  { name: "sendInterviewInvite", parameters: { candidateId, slot } }
]
// Model returns: { tool: "lookupCandidate", args: { id: "C-123" } }
// Your code executes, returns result, model continues.

Builds agentic flows: the model decides which tool, you execute, feed the result back, loop until done.

On Punctuations.ai a recruiter assistant uses tool calling for: search_candidates, get_resume, send_invite, schedule_meeting. The LLM is the planner; tools are deterministic. Important: always validate tool arguments server-side — never trust the model to send safe inputs. Authorize like any other API call.

Hallucinations — what causes them, how to mitigate?

Hallucination = the model produces fluent text that's confidently wrong — fabricated facts, invented citations, made-up APIs. Root cause: an LLM optimizes for plausible-next-token, not truth.

Mitigations:

  • Ground with RAG — feed authoritative context; instruct the model to answer only from it; insist on citations.
  • Low temperature for factual tasks.
  • Structured output with schemas — harder to make up shape than free text.
  • Verify — when an answer matters (linking to a real candidate, real product), check IDs exist before returning.
  • Self-check / critique — a second model pass asking "is this fully supported by the context?"
  • Set user expectations — show sources, "AI-generated, verify before acting".
  • Eval harness with hallucination-specific tests so we catch regressions.

Can't be eliminated entirely; design around it.

How do you evaluate an LLM application?

Without evals, every prompt change is guesswork. My approach:

  • Golden set — 50–500 hand-curated input/expected-output pairs for the most critical paths. Stored in a repo, versioned.
  • Automated metrics where possible: exact-match for extraction, BLEU/ROUGE for short generations, custom rule checks for format.
  • LLM-as-judge — a stronger model scores outputs on rubric criteria (accuracy, helpfulness, format). Calibrate with human spot-checks; can be noisy.
  • Human eval on a sample — gold standard but expensive. Use for high-stakes flows.
  • Production telemetry — log queries + responses (with consent/privacy controls), thumbs-up/down feedback, drop-offs.
  • CI integration — block prompt changes that regress the golden set beyond a threshold.

Frameworks I've looked at: LangSmith, Braintrust, Promptfoo, Ragas (for RAG). The pattern matters more than the tool.

RAG vs fine-tuning — when which?

Different tools for different problems.

RAG adds knowledge — facts, docs, latest data. Best when:

  • The knowledge changes often (you can update without retraining).
  • You need citations / traceability.
  • You have a lot of grounding documents.

Fine-tuning adapts behavior or style — tone, format, domain jargon, specific tasks. Best when:

  • You need a specific output style or structure consistently.
  • You can produce high-quality training pairs (~1000+).
  • Latency/cost is critical — smaller fine-tuned model can beat a larger general one.

They combine well: fine-tune for style + RAG for knowledge. Start with RAG and prompting — 90% of use cases solved without fine-tuning. Reach for fine-tuning only when prompting plateaus.

Safety, PII, prompt injection — production concerns

Production LLM apps need a security mindset.

  • PII handling — don't send user PII to third-party APIs unless covered by your DPA. Mask or redact (regex + NER) before sending; log minimally.
  • Prompt injection — user input containing "ignore previous instructions and …" can hijack your prompt. Mitigations: separate system vs user roles, sanitize, never let model output drive privileged actions without authorization checks, isolate untrusted text in clearly tagged sections.
  • Tool authorization — every tool call goes through real RBAC, not "the model said it was OK."
  • Output filtering — content moderation APIs to catch unsafe outputs (toxic, harmful, leakage).
  • Rate limits + quotas per user — protect against abuse and runaway costs.
  • Logging + audit — keep prompts/responses for incident investigation; consider PII redaction in logs.
  • Vendor risk — multi-provider abstraction so you can fail over (Anthropic ↔ OpenAI ↔ Bedrock).
How would you architect a production AI feature?

My reference architecture for an LLM-powered feature in production:

  • Synchronous edge: API gateway → auth → rate limit → feature service.
  • Decide sync vs async: if >3 s expected, push to a Kafka topic and return a job ID; client polls or websocket.
  • Retrieval layer: ES + vector DB; hybrid retrieval; small cache for hot queries.
  • LLM gateway: a thin internal service that abstracts providers (OpenAI / Anthropic / Bedrock), with circuit breaker, retry, budget enforcement, and prompt caching.
  • Worker pool: scales on queue depth (Kafka lag based HPA).
  • State store: Mongo or Postgres for jobs and outputs; S3 for large artifacts.
  • Observability: log prompts + responses (with privacy controls), distributed tracing per request, dashboards for token usage, latency, error rate per model.
  • Evals in CI on the golden set before prompt changes ship.
  • Feature flags to switch models/prompts without redeploy.

This is roughly the shape of what we built for Punctuations.ai's match service.
