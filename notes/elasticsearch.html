What is Elasticsearch and where does it shine? must

Elasticsearch is a distributed, near-real-time search and analytics engine built on top of Apache Lucene. It stores data as JSON documents in indices, which are split into shards distributed across nodes for horizontal scaling and replicated for high availability.

It shines wherever you need full-text search, ranking, faceting, aggregations, or kNN vector search — use cases like log analytics (the ELK stack), product search, autocomplete, observability, and now AI semantic search. I've used it for resume search: keyword + filters for skill/location, plus dense_vector fields for semantic match between job descriptions and candidate profiles. Where a relational DB struggles (fuzzy match, scoring, faceted aggregations), Elasticsearch is purpose-built.

Explain index, shard, and replica

An index is a logical group of documents — think of it like a database in RDBMS. Each index is split into primary shards, which are independent Lucene indices physically holding the data. Shards let you spread an index across many nodes — that's how Elasticsearch scales horizontally.

Each primary shard has zero or more replicas — exact copies on other nodes. Replicas give you two things: fault tolerance (a node failure doesn't lose data) and read scaling (queries can hit replicas in parallel). Number of primary shards is fixed at index creation; replicas can be changed live. A common pitfall is over-sharding — too many tiny shards hurt cluster metadata. Rule of thumb: keep shards between 10 GB and 50 GB.

How does Elasticsearch actually search? Inverted index? hot

Underneath Elasticsearch is Apache Lucene, which uses an inverted index. When you index a document, the text is passed through an analyzer — tokenized, lowercased, optionally stemmed — and Lucene stores a mapping from each token to the list of documents (and positions) that contain it.

At search time the query is run through the same analyzer, tokens are looked up in the inverted index, posting lists are intersected, and matching documents are scored using BM25 (default since ES 5). Scoring rewards rare-term matches and shorter documents. That's why "java" matches "Java developer" — both produce the token java after the standard analyzer. For non-tokenized exact match you use keyword fields, which skip analysis.

match vs term vs match_phrase — when do you use each?

match is the most common full-text query — it analyzes the query string the same way as the field, so match: "spring boot" on an analyzed field finds documents containing either token, with BM25 ranking. Use it for human-typed search boxes.

term does not analyze — it looks up the literal token. It's the right choice for keyword fields, IDs, status codes, tags. term: "Spring Boot" on an analyzed field would almost never match because the indexed tokens are lowercased and split.

match_phrase matches only when tokens appear in the same order and adjacent. Useful for searching exact phrases like a name or a quoted query: match_phrase: "natural language processing".

Mappings — dynamic vs explicit. Why does this matter?

A mapping is the schema for an index — it declares fields and their types: text, keyword, integer, date, dense_vector, etc. With dynamic mapping, ES infers types from the first document. Convenient for prototypes but dangerous in production — a stringified number can lock the field to text and break aggregations later.

I always use explicit mappings in production, often via index templates. Key choices: text for searchable fields, keyword for exact-match/sortable fields like IDs or enums (or a multi-field combining both), and dense_vector with the right dimension and similarity for kNN. Changing a mapping usually requires reindex, so getting it right early saves a migration later.

Analyzers — what are they and have you customized one?

An analyzer processes text in three stages: char filters (e.g. strip HTML), a tokenizer (e.g. standard splits on whitespace and punctuation), and zero or more token filters (lowercase, stop words, stemming, synonyms, ngrams). The default standard analyzer works for most English text.

I once built a custom analyzer for resumes: standard tokenizer plus lowercase, plus a synonym filter mapping js → javascript, k8s → kubernetes, etc., and an edge_ngram tokenizer on a separate field for autocomplete. The synonym list was loaded from a file and reloadable without reindexing. That single change improved recall on tech-skill searches noticeably — recruiters typing "ML" started finding "Machine Learning" resumes.

kNN / vector search in Elasticsearch hot

Since ES 8 you can index dense_vector fields and run kNN search using HNSW, an approximate nearest-neighbor algorithm. You declare the dimension (e.g. 768 or 1536) and a similarity metric (cosine, dot product, L2), then store embeddings produced by an LLM or embedding model.

In one project I stored a 768-dim vector per resume (computed from a summary + skills). At query time we embed the job description, run a knn query with k: 50, then re-rank by combining vector score with BM25 on must-have skills using a function_score. This hybrid search gives much better results than pure vector or pure keyword: vector handles "Python developer" ≈ "Pythonista" while BM25 anchors hard requirements like "AWS".

How do you handle scaling and hot shards?

The first lever is shard sizing: target 10–50 GB primary shards and keep total shard count reasonable (per node). Then choose replicas based on read load — more replicas means more parallel query capacity. For time-series data (logs, events) use time-based indices (daily/weekly) with the data streams + ILM (Index Lifecycle Management) so old indices roll over, shrink, and eventually move to cold storage.

For hot shards — when one shard gets disproportionate traffic — you can change the routing key, increase shard count via reindex, or use the force_merge only on read-only indices. I monitor shard-level latency in Kibana and the _cat/shards API. When a shard's queries are 10× slower than peers, that's usually a routing-key or document-skew issue.

How do you keep MongoDB and Elasticsearch in sync?

In a project I worked on, MongoDB was the source of truth and Elasticsearch a read-optimized projection. We used an event-driven sync: the service writes to Mongo, then publishes a domain event (ResumeUpserted, ResumeDeleted) to Kafka. A small consumer reads those events and updates the ES index — bulk API in batches of 500 for throughput. Indexing is idempotent using the resume ID as the ES document ID, so retries are safe.

For initial loads and recovery we have a full-reindex job that streams Mongo via a change stream cursor and pushes everything through the bulk API. We also expose a small admin endpoint to reindex a single document on demand. With this pattern the lag is typically <500 ms and we never write to ES directly from request paths — that keeps API latency predictable.
