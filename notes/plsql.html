What is PL/SQL?

PL/SQL (Procedural Language/SQL) is Oracle's procedural extension to SQL — combining SQL DML/DQL with loops, conditions, cursors, exception handling, and modular programming constructs.

Key features

Block structure: DECLARE (variables), BEGIN (executable), EXCEPTION (error handling), END.

Tight SQL integration: SQL statements embedded directly in PL/SQL blocks — no connection overhead per statement.

Banking use

EOD batch interest accrual, charge posting, reconciliation checks — all implemented as PL/SQL packages.

Now coming to conclusion.

PL/SQL processes data close to the database, eliminating network round trips for batch operations on millions of rows.

Difference between SQL and PL/SQL.

SQL is a declarative query language for data manipulation; PL/SQL adds procedural constructs (loops, conditions, exception handling) to build complex business logic close to the data.

SQL

Set-based operations: SELECT, INSERT, UPDATE, DELETE, MERGE — one statement, one result set.

No variables, loops, or conditions — pure declarative.

PL/SQL

Procedural: variables, IF-THEN-ELSE, loops (FOR, WHILE, LOOP), cursors, exception handlers.

Can embed SQL statements; execute multiple SQL statements in sequence as a transaction.

Now coming to conclusion.

Use SQL for set-based data retrieval; PL/SQL when business logic requires iteration, conditions, or exception handling.

What is procedure?

A PL/SQL procedure is a named, stored, reusable block that performs an action — accepting IN, OUT, or IN OUT parameters but not returning a value via RETURN.

Syntax

CREATE OR REPLACE PROCEDURE calculate_interest(p_date IN DATE, p_count OUT NUMBER) IS BEGIN ... END;

Called with EXEC or from another block: calculate_interest(SYSDATE, v_count);

Banking use

EOD procedures: calculate_daily_interest(p_date), post_monthly_charges(p_month), generate_statements(p_date).

Now coming to conclusion.

Procedures encapsulate multi-step business operations; use packages to group related procedures.

What is function?

A PL/SQL function is a named block that returns exactly one value — can be called in SQL SELECT statements if it is a pure function.

Syntax

CREATE OR REPLACE FUNCTION calculate_emi(p_principal NUMBER, p_rate NUMBER, p_months NUMBER) RETURN NUMBER IS BEGIN ... RETURN v_emi; END;

SQL usage

SELECT account_id, calculate_emi(loan_amount, interest_rate, tenure) emi FROM loan_accounts;

Restriction for SQL usage: cannot use DML inside function (unless autonomous transaction), no OUT params.

Now coming to conclusion.

Use functions for calculations that return a single value and may be reused in SQL queries.

Procedure vs function.

A procedure performs an action with IN/OUT params and no RETURN; a function returns a single value and can be used in SQL expressions.

Key differences

Function has a RETURN clause (mandatory); procedure does not. Function can be called in SQL SELECT; procedure cannot.

Procedure can have multiple OUT parameters to return multiple values; function returns one value.

Banking choice

Procedure: post_emi_collection(p_account, p_date) — performs DML, has side effects.

Function: get_available_balance(p_account) RETURN NUMBER — pure calculation used in queries.

What is package?

A PL/SQL package groups related procedures, functions, variables, cursors, and exceptions into a named module — providing encapsulation and improved performance.

Benefits

Encapsulation: spec (public interface) vs body (private implementation) — callers only see the spec.

Performance: entire package loaded into shared memory on first call — subsequent calls use cached code.

Session state: package variables persist for the duration of the session — useful for caching lookups.

Banking

PKG_INTEREST_CALC: package with accrual procedures, interest functions, and shared constants for all interest-related logic.

Now coming to conclusion.

Prefer packages over standalone procedures/functions — they reduce recompilation dependencies and organize module logic.

Package specification vs package body.

The package specification declares the public interface (procedure/function signatures, public types/variables); the package body contains the implementation.

Specification

CREATE OR REPLACE PACKAGE pkg_account IS PROCEDURE open_account(...); FUNCTION get_balance(...) RETURN NUMBER; END;

Callers only need the spec; body can be changed without recompiling callers (if spec unchanged).

Body

CREATE OR REPLACE PACKAGE BODY pkg_account IS PROCEDURE open_account IS BEGIN ... END; ... END;

Can have private procedures/functions not declared in spec — internal helpers.

Now coming to conclusion.

Changing the body without changing the spec doesn't invalidate dependent objects — key for patching.

What is trigger?

A PL/SQL trigger is a named block that fires automatically in response to a DML event (INSERT, UPDATE, DELETE) or DDL/system event on a table or view.

Usage

BEFORE INSERT trigger: auto-populate created_by, created_date, generate sequence-based ID.

AFTER UPDATE trigger: write audit log entry to audit_trail table when sensitive field changes.

Banking use

Trigger on account_transactions: AFTER INSERT log every new transaction to audit_log with user, timestamp, amounts.

Trigger on account_master: BEFORE UPDATE validate status transitions (ACTIVE→DORMANT is OK; CLOSED→ACTIVE is not).

Now coming to conclusion.

Use triggers for cross-cutting concerns (audit, defaults) — avoid complex business logic in triggers.

Types of triggers.

Oracle triggers are classified by timing (BEFORE/AFTER/INSTEAD OF), level (row/statement), and event type (DML/DDL/system).

By timing

BEFORE: fires before the DML; can modify :NEW values. AFTER: fires after DML; cannot modify :NEW.

INSTEAD OF: fires on views that cannot be directly updated — redirects DML to base tables.

By level

Row-level (FOR EACH ROW): fires once per affected row; accesses :OLD and :NEW values.

Statement-level: fires once per DML statement regardless of rows affected; no :OLD/:NEW access.

Before trigger vs after trigger.

BEFORE trigger fires before the DML operation, allowing modification of :NEW values; AFTER trigger fires after the DML, useful for auditing the committed change.

BEFORE

Can modify :NEW.column_value before the row is inserted/updated — use for defaulting and validation.

Example: :NEW.created_date := SYSDATE; :NEW.created_by := SYS_CONTEXT('USERENV','SESSION_USER');

AFTER

DML is already applied; cannot modify :NEW. Ideal for audit logging, raising events, sending notifications.

Example: AFTER UPDATE OF status ON accounts — write status change to accounts_audit table.

Now coming to conclusion.

Use BEFORE for data defaulting/validation; AFTER for audit logging and cascading effects.

Row-level trigger vs statement-level trigger.

A row-level trigger fires once for each row affected by the DML; a statement-level trigger fires once per DML statement regardless of rows affected.

Row-level (FOR EACH ROW)

Has access to :OLD (original values) and :NEW (new values) for the current row.

Use for per-row audit logging, per-row validation, or computing derived values.

Statement-level

No access to individual row values; fires once even if DML affects 1000 rows.

Use for: logging the occurrence of a DML event, enforcing non-row-specific constraints.

Now coming to conclusion.

Row triggers are most common in banking for per-account audit; statement triggers for monitoring DDL events.

What is cursor?

A cursor is a named context area in the PGA that holds the result of a SQL query, allowing row-by-row processing.

Types

Implicit cursor: automatically created by Oracle for single-row DML and SELECT INTO; attributes: SQL%ROWCOUNT, SQL%FOUND.

Explicit cursor: declared by programmer with CURSOR c IS SELECT ...; controlled with OPEN/FETCH/CLOSE.

Best practice

Use cursor FOR loops: FOR rec IN cursor LOOP ... END LOOP — Oracle auto-opens, fetches, closes.

For large datasets, use BULK COLLECT + FORALL to avoid row-by-row context switching.

Now coming to conclusion.

Avoid fetching millions of rows in a cursor loop — use BULK COLLECT with LIMIT for batch processing.

Implicit cursor vs explicit cursor.

Implicit cursors are automatically managed by Oracle for DML and SELECT INTO; explicit cursors are declared and controlled by the programmer for multi-row queries.

Implicit

Created automatically for: INSERT, UPDATE, DELETE, SELECT INTO. Attributes: SQL%FOUND, SQL%NOTFOUND, SQL%ROWCOUNT.

SELECT INTO raises NO_DATA_FOUND if no rows, TOO_MANY_ROWS if multiple — must handle exceptions.

Explicit

CURSOR c IS SELECT account_id, balance FROM accounts WHERE status='ACTIVE'; OPEN c; FETCH c INTO v_id, v_bal; CLOSE c;

More control over fetch size; can use BULK COLLECT; can pass as parameter (ref cursor).

Now coming to conclusion.

Use explicit cursors for multi-row processing; use SELECT INTO with exception handling for single-row lookups.

Cursor vs ref cursor.

A static cursor has a fixed query defined at compile time; a ref cursor is a pointer to a cursor result set whose query is determined at runtime.

Static cursor

CURSOR c IS SELECT * FROM accounts WHERE status = 'ACTIVE'; — query fixed at compile time.

Ref cursor

TYPE ref_cur IS REF CURSOR; or SYS_REFCURSOR (weak); OPEN p_cur FOR SELECT * FROM accounts WHERE branch = p_branch;

Passed as OUT parameter from procedure; Java JDBC receives it as a ResultSet via CallableStatement.

Banking use

FLEXCUBE APIs: procedure takes parameters, opens ref cursor with dynamic query, Java layer fetches results.

Now coming to conclusion.

Ref cursors enable dynamic queries and result set return from procedures — standard pattern in FLEXCUBE API layer.

Strong ref cursor vs weak ref cursor.

A strong ref cursor is typed (bound to a specific row type); a weak ref cursor (SYS_REFCURSOR) is untyped and can be opened for any query.

Strong

TYPE account_cur IS REF CURSOR RETURN accounts%ROWTYPE; — compiler checks column compatibility.

Weak (SYS_REFCURSOR)

SYS_REFCURSOR can be opened for any SELECT query — flexible but no compile-time type checking.

Standard in FLEXCUBE API procedures — SYS_REFCURSOR OUT parameter passed back to Java.

Now coming to conclusion.

Use strong ref cursors when the query shape is known and fixed; SYS_REFCURSOR for flexible dynamic queries.

What is exception handling in PL/SQL?

PL/SQL exception handling catches runtime errors in the EXCEPTION section, allowing graceful error recovery, logging, and re-raising or converting to custom exceptions.

Structure

EXCEPTION WHEN NO_DATA_FOUND THEN handle; WHEN TOO_MANY_ROWS THEN handle; WHEN OTHERS THEN log and re-raise.

Best practices

Always include WHEN OTHERS THEN as last resort — log SQLCODE, SQLERRM, and re-raise with RAISE.

Never use WHEN OTHERS THEN NULL — silently swallowing exceptions hides critical errors in banking.

Now coming to conclusion.

Exception handling in banking PL/SQL must log error details (SQLCODE, SQLERRM, business context) before raising.

Predefined vs user-defined exceptions.

Predefined exceptions are Oracle's built-in named exceptions; user-defined exceptions are declared by the programmer and raised explicitly for business rule violations.

Predefined

NO_DATA_FOUND, TOO_MANY_ROWS, ZERO_DIVIDE, DUP_VAL_ON_INDEX, VALUE_ERROR — raised automatically by Oracle.

User-defined

DECLARE insufficient_balance EXCEPTION; ... RAISE insufficient_balance; EXCEPTION WHEN insufficient_balance THEN ...

PRAGMA EXCEPTION_INIT(my_exc, -20001) to associate with error number for RAISE_APPLICATION_ERROR.

Banking use

RAISE_APPLICATION_ERROR(-20100, 'Insufficient available balance for debit of '||p_amount) — meaningful error to caller.

Now coming to conclusion.

Use RAISE_APPLICATION_ERROR with specific error codes (-20000 to -20999) for business rule violations.

What is autonomous transaction?

An autonomous transaction (PRAGMA AUTONOMOUS_TRANSACTION) runs in a separate transaction context — commits or rolls back independently from the calling transaction.

Usage

PRAGMA AUTONOMOUS_TRANSACTION in procedure declaration; it commits/rollbacks without affecting caller's transaction.

Use case: error logging procedure that must commit the log even if the calling transaction rolls back.

Banking example

log_error() procedure: PRAGMA AUTONOMOUS_TRANSACTION; INSERT INTO error_log; COMMIT; — log persists even when caller rolls back on exception.

Caution

Autonomous transactions can see committed data from other sessions but not uncommitted data from caller — use carefully to avoid inconsistency.

Now coming to conclusion.

Autonomous transactions are essential for audit logging and error logging in PL/SQL — ensure log survives rollback.

What is pragma exception_init?

PRAGMA EXCEPTION_INIT associates a user-defined exception variable with a specific Oracle error number, enabling catching of named Oracle errors.

Syntax

DECLARE deadlock_err EXCEPTION; PRAGMA EXCEPTION_INIT(deadlock_err, -60); BEGIN ... EXCEPTION WHEN deadlock_err THEN ...

Allows catching specific ORA- errors by name rather than checking SQLCODE in WHEN OTHERS.

Banking use

PRAGMA EXCEPTION_INIT(dup_payment, -00001) — catches unique constraint violation when duplicate payment reference inserted.

What is dynamic SQL?

Dynamic SQL in PL/SQL builds and executes SQL statements whose structure is determined at runtime — using EXECUTE IMMEDIATE or DBMS_SQL.

EXECUTE IMMEDIATE

EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM ' || p_table_name INTO v_count; — simple dynamic queries.

With bind variables: EXECUTE IMMEDIATE 'SELECT balance FROM accounts WHERE id = :1' USING p_id;

Use cases

Dynamic table names, dynamic WHERE clauses, DDL in PL/SQL (CREATE, ALTER — cannot use static SQL for DDL).

Security

Always use bind variables (:1, :name) for values — concatenating user input into dynamic SQL causes SQL injection.

Now coming to conclusion.

Avoid dynamic SQL for simple cases — prefer static SQL. When needed, always use bind variables for user-supplied values.

Execute immediate vs DBMS_SQL.

EXECUTE IMMEDIATE is simpler for most dynamic SQL; DBMS_SQL provides advanced features like unknown column count at compile time and re-use of parsed cursors.

EXECUTE IMMEDIATE

Simpler syntax; supports bind variables; executes and fetches in one step for queries.

Limitation: column count and types must be known at compile time.

DBMS_SQL

Handles truly dynamic result sets (unknown columns); supports DESCRIBE_COLUMNS to discover column structure.

More verbose but powerful for generic report generators or schema-agnostic utilities.

Now coming to conclusion.

Use EXECUTE IMMEDIATE for 95% of dynamic SQL; DBMS_SQL only when column structure is completely unknown at runtime.

What is mutating table error?

ORA-04091 (mutating table error) occurs when a row-level trigger tries to query or modify the same table the triggering DML is currently changing.

Cause

Row-level AFTER UPDATE trigger on accounts tries to SELECT FROM accounts — table is mid-DML, inconsistent state.

Oracle prevents dirty reads within the same DML statement.

Solutions

Compound trigger (Oracle 11g+): use AFTER STATEMENT section for the query/DML, accumulating data in AFTER EACH ROW.

Autonomous transaction in trigger — reads committed state; use carefully (won't see uncommitted current changes).

Now coming to conclusion.

Compound triggers are the preferred Oracle solution — they handle accumulation and post-statement processing cleanly.

How do you avoid mutating table error?

Avoid ORA-04091 using a compound trigger that separates row-level accumulation from statement-level processing, or by moving logic out of triggers into the application layer.

Compound trigger

BEFORE EACH ROW: accumulate affected IDs in package-level collection.

AFTER STATEMENT: query/DML on the table using the accumulated IDs — table is stable at this point.

Application layer

Move business logic from trigger to stored procedure called explicitly — avoids trigger context entirely.

What are collections in PL/SQL?

PL/SQL collections are data structures storing multiple elements: associative arrays, nested tables, and varrays.

Types

Associative array (index-by table): indexed by VARCHAR2 or PLS_INTEGER; sparse; cannot be stored in DB.

Nested table: unordered, unbounded, can be stored in DB columns; supports SET operations.

Varray: ordered, bounded (max size fixed at declaration); stored in DB columns.

Banking use

BULK COLLECT INTO l_account_ids — collection holds fetched account IDs for FORALL DML.

Associative array for in-memory lookup: l_rate_map('SAVINGS') := 0.035 — avoids repeated DB queries.

Now coming to conclusion.

Use associative arrays for session-scoped caches; nested tables for BULK COLLECT and set operations.

Nested table vs varray vs associative array.

Associative arrays are sparse key-indexed PL/SQL-only; nested tables are unordered, DB-storable, unbounded; varrays are ordered, bounded, DB-storable.

Comparison

Associative array: best for in-memory lookup/cache; any key type; cannot store in DB column.

Nested table: best for BULK COLLECT, DB storage, set operations (MULTISET UNION); sparse after DELETE.

Varray: best when max size is known; stored inline in DB row (up to 4000 bytes) or out-of-line for larger.

Now coming to conclusion.

Use nested table for BULK COLLECT; associative array for in-memory dictionaries; varray for small ordered lists.

What is `%TYPE` and `%ROWTYPE`?

%TYPE anchors a variable's type to a column's datatype; %ROWTYPE anchors to a whole table or cursor row structure — both auto-adapt when the schema changes.

%TYPE

v_balance accounts.balance%TYPE; — if balance column changes from NUMBER(15,2) to NUMBER(18,4), code adapts automatically.

%ROWTYPE

v_account accounts%ROWTYPE; — v_account.account_id, v_account.balance etc. all available without individual declarations.

FETCH cursor_name INTO v_account — fetches entire row into the record variable.

Now coming to conclusion.

Always use %TYPE and %ROWTYPE — they prevent type mismatch bugs when the underlying table schema changes.

How do you optimize PL/SQL code?

Optimize PL/SQL by replacing row-by-row processing with BULK COLLECT+FORALL, avoiding context switches, using bind variables, and leveraging set-based SQL over procedural loops.

Key optimizations

BULK COLLECT with LIMIT 1000: fetch in batches, not row-by-row — reduces context switches dramatically.

FORALL: single round-trip for all DML operations instead of one per row.

Set-based SQL: replace cursor loop with single UPDATE/INSERT..SELECT — SQL engine processes in bulk.

Other tips

Cache frequently used lookups in package-level associative arrays — avoid repeated SELECT per row.

Use RETURNING clause: INSERT ... RETURNING id INTO v_id — avoids separate SELECT after INSERT.

Now coming to conclusion.

The biggest PL/SQL optimization gain is always replacing row-by-row loops with BULK COLLECT and set-based SQL.

How do you debug PL/SQL procedure?

PL/SQL debugging uses DBMS_OUTPUT for simple tracing, Oracle SQL Developer's debugger for step-through, and custom logging tables for production troubleshooting.

Tools

DBMS_OUTPUT.PUT_LINE('v_count='||v_count) — works in SQL*Plus/SQL Developer; disabled in production.

SQL Developer debugger: set breakpoints, step through, inspect variable values — development environment only.

Production logging

Log to debug_log table using autonomous transaction procedure: log_debug(p_proc, p_step, p_msg, p_data).

Enable/disable via a parameter: if get_param('DEBUG_INTEREST_CALC') = 'Y' then log_debug(...); end if;

Now coming to conclusion.

Production debugging should use parameterized logging tables — DBMS_OUTPUT is invisible in production.

How do you log errors in PL/SQL?

PL/SQL errors are logged using an autonomous transaction error-logging procedure that captures SQLCODE, SQLERRM, DBMS_UTILITY.FORMAT_ERROR_BACKTRACE, and business context.

Pattern

EXCEPTION WHEN OTHERS THEN log_error(p_proc_name, p_account, SQLCODE, SQLERRM, DBMS_UTILITY.FORMAT_ERROR_BACKTRACE); RAISE;

log_error() uses PRAGMA AUTONOMOUS_TRANSACTION — commits log entry even if calling transaction rolls back.

Log table

error_log(error_id, proc_name, account_id, error_code, error_msg, stack_trace, created_at) — query for post-incident analysis.

Now coming to conclusion.

DBMS_UTILITY.FORMAT_ERROR_BACKTRACE gives the exact line number of the error — essential for debugging complex packages.

What is commit and rollback?

COMMIT permanently saves all DML changes made since the last commit/rollback; ROLLBACK undoes all uncommitted DML changes back to the last commit point.

Behaviour

COMMIT: makes changes visible to other sessions; releases row locks; marks the transaction boundary.

ROLLBACK: undoes all changes in the current transaction; releases locks; used on exception.

ROLLBACK TO SAVEPOINT sp1: partial rollback to a named savepoint within the transaction.

Banking

Fund transfer procedure: COMMIT only after both debit and credit are posted — never commit partial transactions.

Now coming to conclusion.

In banking PL/SQL, COMMIT exactly once at the end of the complete business transaction — never mid-transaction.

Can we commit inside trigger?

A regular trigger cannot COMMIT — it is part of the triggering transaction. However, an autonomous transaction trigger can COMMIT its own work independently.

Regular trigger

COMMIT/ROLLBACK in a regular trigger raises ORA-04092 — the trigger cannot control the enclosing transaction.

Autonomous transaction trigger

PRAGMA AUTONOMOUS_TRANSACTION in the trigger enables its own COMMIT/ROLLBACK.

Use case: audit trigger that must persist its log even if the main transaction rolls back.

Now coming to conclusion.

Use autonomous transaction triggers sparingly — they can create data inconsistencies if not designed carefully.

What is savepoint?

A SAVEPOINT marks a point in a transaction to which you can partially rollback without rolling back the entire transaction.

Usage

SAVEPOINT sp_after_validation; ... ROLLBACK TO SAVEPOINT sp_after_validation; — undoes work after the savepoint.

Multiple savepoints: release or rollback to specific points for fine-grained transaction control.

Banking

EOD job with multiple accounts: SAVEPOINT before each account; if one account fails, ROLLBACK TO SAVEPOINT and continue with next account.

Now coming to conclusion.

Savepoints enable partial rollback — useful for batch processing where one failed record should not abort the entire batch.

How do you schedule PL/SQL jobs?

PL/SQL jobs are scheduled using DBMS_SCHEDULER (preferred, Oracle 10g+) or the legacy DBMS_JOB, defining programs, schedules, and job attributes.

DBMS_SCHEDULER

DBMS_SCHEDULER.CREATE_JOB(job_name=>'EOD_INTEREST', job_type=>'STORED_PROCEDURE', job_action=>'PKG_EOD.calculate_interest', start_date=>SYSDATE, repeat_interval=>'FREQ=DAILY;BYHOUR=22;BYMINUTE=0', enabled=>TRUE);

Banking use

EOD batch: schedule at 10 PM daily. Monthly fee posting: first day of month at midnight. NPA classification: nightly.

Now coming to conclusion.

DBMS_SCHEDULER provides logging, email notification on failure, and dependency chains — far superior to DBMS_JOB.

What is DBMS_SCHEDULER?

DBMS_SCHEDULER is Oracle's built-in job scheduler managing PL/SQL jobs, external programs, and job chains with logging, notification, and complex schedules.

Key objects

Program: defines what to run (stored procedure, external script). Schedule: when to run (calendar expression).

Job: combines program + schedule + attributes (logging level, email notification, priority).

Operations

DBMS_SCHEDULER.RUN_JOB('EOD_INTEREST') — run immediately on demand. DBMS_SCHEDULER.DISABLE('JOB_NAME') — temporarily disable.

DBA_SCHEDULER_JOB_RUN_DETAILS: query job history, status, actual start/end, error message.

Now coming to conclusion.

DBMS_SCHEDULER job run history is the first place to check when an EOD batch fails — shows exact error and timestamp.

What is DBMS_OUTPUT?

DBMS_OUTPUT is an Oracle built-in package that buffers text output during PL/SQL execution, displayed in SQL*Plus or SQL Developer after execution completes.

Usage

DBMS_OUTPUT.PUT_LINE('Processing account: '||v_account_id); — writes to output buffer.

Enable in SQL*Plus: SET SERVEROUTPUT ON SIZE UNLIMITED. In SQL Developer: View → DBMS Output panel.

Limitation

Not visible during batch execution or in production web apps — use logging tables for production diagnostics.

Buffer limited (default 1MB) — verbose output may truncate; set UNLIMITED for large outputs.

Now coming to conclusion.

DBMS_OUTPUT is for development/debugging only — use autonomous-transaction log tables for production diagnostics.

What is DBMS_LOB?

DBMS_LOB is Oracle's package for manipulating LOB (Large Object) values — CLOB, BLOB, NCLOB, BFILE — enabling read, write, append, copy, and search operations.

Common operations

DBMS_LOB.READ(clob_col, amount, offset, buffer) — read portion of CLOB into buffer.

DBMS_LOB.WRITEAPPEND(clob_col, amount, buffer) — append text to CLOB.

DBMS_LOB.GETLENGTH(blob_col) — get length in bytes/chars.

Banking use

FLEXCUBE stores SWIFT XML messages and document scans as CLOB/BLOB; DBMS_LOB used to extract or append XML content.

Now coming to conclusion.

Use DBMS_LOB for programmatic LOB manipulation; for simple reads, direct SQL or SUBSTR on CLOB may suffice.

What is DBMS_ALERT / DBMS_PIPE?

DBMS_ALERT provides asynchronous database event notification between sessions; DBMS_PIPE provides synchronous inter-session message passing within the same database.

DBMS_ALERT

Session A: DBMS_ALERT.SIGNAL('EOD_COMPLETE', 'date=2024-01-15'); Session B: DBMS_ALERT.WAITONE('EOD_COMPLETE', msg, status, timeout);

Alert is transaction-based — signaled on COMMIT; used to notify downstream processes after batch completion.

DBMS_PIPE

DBMS_PIPE.SEND_MESSAGE: send to named pipe (private or public); DBMS_PIPE.RECEIVE_MESSAGE: receive from pipe.

Not transaction-bound — message sent immediately regardless of transaction state.

Now coming to conclusion.

DBMS_ALERT is preferred for EOD/BOD completion notifications; DBMS_PIPE for quick inter-session communication.
