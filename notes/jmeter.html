What is load testing?

Load testing measures system behavior under expected production load — verifying response times, throughput, and error rates stay within SLA at normal and peak concurrent users.

Goal

Validate that the system meets performance SLA (e.g., p95 < 500ms, throughput > 200 TPS) under expected concurrent users.

Identify degradation points: at what load does response time start increasing unacceptably?

Banking

Test the account balance API under 500 concurrent users (morning banking rush simulation).

Test EOD batch initiation API under 50 concurrent admin operations.

Now coming to conclusion.

Load testing should run against a production-like environment with realistic data volume and connection pool sizing.

Load testing vs stress testing.

Load testing validates system behavior at expected load; stress testing pushes beyond normal limits to find the breaking point and observe failure behavior.

Load testing

Run at expected peak load (e.g., 500 users); verify SLA met; identify performance baseline.

Stress testing

Gradually increase load beyond normal (1000, 2000, 5000 users) until system degrades or fails.

Observe: does the system fail gracefully (503 errors) or catastrophically (OOM, crash, data corruption)?

Banking importance

Stress test before festive season campaigns — month-end banking transactions can be 5x normal volume.

Now coming to conclusion.

Stress testing reveals the system's limits and failure modes — plan recovery procedures based on findings.

What is throughput?

Throughput is the number of requests a system processes per unit time — measured as TPS (Transactions Per Second) or RPS (Requests Per Second).

JMeter metric

Aggregate Report's Throughput column: requests/second processed during the test run.

Higher throughput = more capacity; but always read alongside error rate — high throughput with 50% errors is not good.

Banking target

Core banking API: > 200 TPS for account balance; > 50 TPS for fund transfer under 500 concurrent users.

Now coming to conclusion.

Throughput is a capacity metric — combine with p95 latency and error rate for complete performance picture.

What is latency?

Latency is the time delay between sending a request and receiving the first byte of response — distinct from response time which includes full payload transfer.

Components

Network latency: time to establish connection and transmit. Server latency: processing time on server.

In JMeter: Response Time = Latency + Data transfer time; Latency is the time to first byte.

Banking

Network latency matters for SWIFT/payment gateway calls — cross-border latency can be 100-300ms baseline.

Now coming to conclusion.

Optimize server latency (DB queries, processing) first; network latency is often outside the team's control.

What is response time?

Response time is the total time from sending a request to receiving the complete response — includes server processing, DB query, and data transfer.

Metrics

Average response time: mean across all requests. P95: 95% of requests completed within this time.

P95 and P99 are more meaningful than average — they reveal tail latency that 5% or 1% of users experience.

SLA

Typical banking API SLA: P95 < 500ms, P99 < 1000ms for real-time APIs; batch APIs have looser SLAs.

Now coming to conclusion.

Always report P95 and P99, not just average — average hides the worst user experiences that drive complaints.

What is TPS?

TPS (Transactions Per Second) is the number of complete financial or business transactions the system processes per second — the primary capacity metric for banking systems.

JMeter

JMeter reports throughput (requests/sec); for banking TPS, one 'transaction' may involve multiple API calls (debit + credit + notification).

Use Transaction Controller in JMeter to group related requests into one logical transaction for TPS measurement.

Banking targets

Core banking system: typically 100-500 TPS for fund transfers. UPI/IMPS: 1000+ TPS for high-volume payment rails.

Now coming to conclusion.

Design banking systems with TPS headroom above peak — at least 2x headroom for unexpected load spikes.

What is ramp-up period?

The ramp-up period in JMeter is the time to gradually start all virtual threads — preventing a sudden spike that would overwhelm the server from the first second.

Configuration

Thread Group: 500 threads, ramp-up 60 seconds → JMeter starts ~8 threads/second over 60 seconds.

Simulates realistic user load growth (morning log-in ramp) rather than instant 500-user surge.

Best practice

Set ramp-up to at least the number of threads in seconds (500 users → 500s ramp-up) for gradual load.

Zero ramp-up: sudden spike test — useful for stress testing but not realistic load modeling.

Now coming to conclusion.

A proper ramp-up period reveals whether the system handles gradual load growth — more realistic than instant load.

How do you find bottleneck from performance test?

Bottlenecks are identified by correlating JMeter metrics (high response time, errors) with server metrics (CPU, DB wait, GC, thread pool saturation).

Correlation

High response time + high CPU: application processing bottleneck — look for slow algorithms or GC.

High response time + low CPU + high DB wait: database bottleneck — missing index, lock contention, slow query.

High error rate + 503 status: thread pool or connection pool exhaustion — increase pool size or fix slow queries.

Tools

JMeter Aggregate Report + WebLogic Thread Monitor + Oracle AWR report analyzed together.

APM tools (Dynatrace, AppDynamics): automatically pinpoint bottleneck layer (app, DB, external API).

Now coming to conclusion.

Performance bottlenecks are almost always either DB (80%) or connection pool exhaustion — check these first.

How do you test database performance?

Database performance testing uses JMeter JDBC sampler for direct DB load testing, combined with Oracle AWR reports and V$SQL analysis during load tests.

JMeter JDBC

JDBC Request sampler: configure JDBC connection pool, execute SELECT/DML statements, measure query response times.

Test concurrent DML: 100 threads running INSERT transactions simultaneously — check for deadlocks and lock waits.

Oracle analysis

During load test: run SELECT * FROM V$SQL WHERE executions > 100 ORDER BY elapsed_time/executions DESC to find slow queries.

AWR report: buffer gets, disk reads, CPU time per SQL statement — compare pre/post index changes.

Now coming to conclusion.

DB performance testing reveals lock contention and missing indexes that only appear under concurrent load.

How do you test concurrent users?

Concurrent users in JMeter are simulated by Thread Groups — each thread represents one virtual user executing the test scenario in parallel.

Configuration

Thread Group: set Number of Threads (users), Ramp-Up period, Loop count (or duration).

Use CSV Data Set Config to feed unique account numbers/credentials per thread — avoid all threads using same data.

Realistic simulation

Add think time (Timer: Gaussian Random Timer) between requests to simulate human reading/pausing.

Use Transaction Controller to model full user journeys (login → balance check → transfer → logout).

Now coming to conclusion.

Parameterize test data for concurrent users — 500 threads all accessing the same account doesn't reflect reality.
