Process vs Thread vs Virtual Thread must

Three levels of concurrency, each progressively lighter — understanding the hierarchy is essential before talking about scaling and Project Loom.

Core Difference
Process Independent program — own memory, OS-managed.
Thread (platform) Inside a process, shares memory, 1:1 with an OS thread.
Virtual Thread JVM-managed lightweight thread (Java 21+) — millions feasible.
1 Memory
Process
  • Separate address space, separate heap.
  • Inter-process communication via pipes, sockets, shared memory.
Threads (platform & virtual)
  • Share heap, code, file descriptors with other threads in the process.
  • Each has its own stack and program counter.
2 Cost & Footprint
Process / Platform Thread
  • Process — MBs / seconds to spawn. Heavy.
  • Platform thread — ~1 MB stack, ~ms to spawn. A typical server tops out at a few thousand.
Virtual Thread
  • Few KB stack, microseconds to spawn.
  • Millions of concurrent virtual threads on a single JVM.
3 Scheduler
Process / Platform Thread
  • Managed by the OS scheduler.
  • Context switching has kernel-level cost.
Virtual Thread
  • Scheduled by the JVM onto a small pool of carrier (platform) threads.
  • Parks instead of blocking the OS thread on I/O — that's the magic of Loom.
4 When to Use
Process / Platform Thread
  • Process — strong isolation (sandboxing, security), different language.
  • Platform thread — CPU-bound parallel computation (sized to cores).
Virtual Thread
  • I/O-bound services (most backend microservices).
  • "One thread per request" without pool tuning headaches.
  • Write blocking code, get reactive-like scale.
Takeaway: with Java 21 + Spring Boot 3.2 you can flip spring.threads.virtual.enabled=true and your service suddenly handles 10× more concurrent requests on the same hardware — provided your blocking calls aren't pinned (avoid synchronized around I/O; use ReentrantLock).
Thread lifecycle states

A Java thread moves through six states from Thread.State:

  • NEW — created but start() not called.
  • RUNNABLE — eligible to run; OS schedules it. Note: "runnable" lumps together actually-running and ready-to-run.
  • BLOCKED — waiting to acquire a monitor lock (someone else holds the synchronized).
  • WAITING — waiting indefinitely for another thread (wait(), join(), LockSupport.park()).
  • TIMED_WAITING — waiting with a timeout (sleep(n), wait(n), parkNanos).
  • TERMINATED — finished.

When debugging thread dumps, BLOCKED and WAITING are the states you care about — they tell you which threads are stuck and on what monitor or condition.

synchronized — how does it actually work? hot

synchronized uses an intrinsic monitor attached to every Java object. synchronized (obj) { ... } acquires obj's monitor on entry and releases it on exit (even on exception). synchronized instance method = synchronized on this; on a static method = synchronized on ClassName.class.

It provides two guarantees: mutual exclusion (only one thread runs the block) and memory visibility via the happens-before relationship — changes made inside the block are visible to the next thread that acquires the same monitor. The JVM optimizes contention with biased locking, lightweight locking, and only escalates to heavyweight OS-level mutexes under real contention.

Modern guidance: prefer ReentrantLock when you need tryLock, timeouts, fairness, or interruptible locking; use synchronized for simple cases.

wait() / notify() / notifyAll() — usage

These are methods on Object for thread coordination. They must be called while holding the object's monitor — i.e., inside a synchronized block on that object — otherwise IllegalMonitorStateException.

wait() releases the monitor and parks the thread; notify() wakes one waiting thread; notifyAll() wakes all of them. The woken thread re-acquires the monitor before returning from wait().

Idiom — always wait in a loop, never an if:

synchronized (lock) {
    while (!condition) lock.wait();
    // act on condition
}

This handles spurious wake-ups. In modern code I almost never write this — I use BlockingQueue, CountDownLatch, Semaphore, or Condition on a Lock, which are far cleaner.

wait() vs sleep() hot

Both pause the current thread, but they live on different classes and behave very differently with locks. Mixing them up is a classic interview red flag.

Core Difference
wait() On Object — releases the monitor lock, waits for notify().
sleep() On Thread (static) — keeps all locks, just pauses for a duration.
1 Where it's defined
wait()
  • Instance method on Object.
  • Called as obj.wait() — must hold obj's monitor.
sleep()
  • Static method on Thread.
  • Called as Thread.sleep(ms) — affects current thread.
2 Lock Behavior
wait()
  • Releases the monitor while waiting — other threads can enter synchronized blocks on the same lock.
  • Re-acquires the monitor before returning.
sleep()
  • Does NOT release any locks.
  • If called inside a synchronized block, every other thread waiting on that lock stays blocked.
3 How it Wakes Up
wait()
  • Another thread calls obj.notify() / obj.notifyAll().
  • Optional timeout (wait(ms)).
  • Interruption (InterruptedException).
  • Spurious wakeups happen — always wait in a while loop.
sleep()
  • The duration expires.
  • Or another thread interrupts it (InterruptedException).
4 Use Case
wait()
  • Inter-thread coordination — producer/consumer, signaling.
  • Modern code prefers BlockingQueue, CountDownLatch, Condition.
sleep()
  • Throttling, retry backoff, simulating delay in tests.
  • Polling loops (though usually a smell).
Remember: both throw InterruptedException. When you catch it, either propagate it or re-set the interrupt flag with Thread.currentThread().interrupt(). Swallowing it silently is one of the most common bugs in legacy Java code.
What is a deadlock? How do you avoid it? hot

A deadlock is when two or more threads each hold a resource the other needs and wait forever. Classic example: thread A holds lock 1 and wants lock 2; thread B holds lock 2 and wants lock 1.

Coffman's four conditions are all needed: mutual exclusion, hold and wait, no preemption, and circular wait. Break any one of them.

Prevention strategies:

  • Lock ordering — always acquire locks in the same global order (e.g., by account ID ascending). This is the most practical fix.
  • tryLock with timeout — use ReentrantLock.tryLock(t, unit) and back off if the lock isn't acquired in time.
  • Reduce lock scope — hold locks for the minimum critical section.
  • Avoid nested locks when possible.

Diagnosis: take a thread dump (jstack); it explicitly says "Found one Java-level deadlock".

volatile keyword — what does it guarantee?

volatile on a field guarantees two things: (1) visibility — writes by one thread are immediately visible to reads by other threads (no thread-local cache), and (2) ordering — a write to a volatile field happens-before any subsequent read of it.

What it does not give you: atomicity for compound operations. volatile int counter; counter++ is still racy because counter++ is read–modify–write — three steps that can interleave. For that, use AtomicInteger.incrementAndGet().

Typical use: a single boolean volatile boolean running for stop flags, or single-reference publication of an immutable config object. For anything more complex, reach for java.util.concurrent primitives.

ExecutorService — why not raw threads?

Raw threads (new Thread(r).start()) are expensive to create and uncontrolled — under load you can spawn thousands and exhaust memory. ExecutorService separates task submission from thread management: you submit tasks (Runnable/Callable), the pool runs them on a bounded set of worker threads.

Common factories in Executors:

  • newFixedThreadPool(n) — n workers; tasks queue when busy.
  • newCachedThreadPool() — unbounded workers; reuses idle. Dangerous in production — can spawn thousands.
  • newScheduledThreadPool(n) — for delayed/periodic tasks.
  • newVirtualThreadPerTaskExecutor() — Java 21, one virtual thread per task.

In production I prefer constructing ThreadPoolExecutor directly to control queue size, rejection policy, and core/max thread counts. Always shut down with shutdown() + awaitTermination().

ThreadPoolExecutor — sizing and parameters

The full constructor: new ThreadPoolExecutor(core, max, keepAlive, unit, queue, threadFactory, rejectionHandler).

How it actually behaves: tasks first fill up to core threads, then queue up, then create extra threads up to max when queue is full, then trigger the rejection handler. People expect "create more threads first, then queue" — it's the opposite, which is why newFixedThreadPool uses an unbounded queue (core == max).

Sizing rules of thumb:

  • CPU-bound: pool size ≈ number of cores.
  • I/O-bound: cores × (1 + wait/compute ratio); often 50–200 threads.
  • Use a bounded queue and a sensible rejection policy (CallerRunsPolicy applies back-pressure on the submitter).
  • Name threads via ThreadFactory — invaluable in thread dumps.
Callable vs Runnable, Future, CompletableFuture

Runnable — void run(), can't throw checked exceptions, no return value. Callable<V> — V call() throws Exception, returns a value and can throw.

Submit a Callable to ExecutorService and get back a Future<V> — represents the pending result. future.get() blocks until done; future.get(timeout) blocks with timeout. Future is limited: no chaining, no composition, no callbacks.

CompletableFuture<V> is the modern replacement. It can be composed (thenApply, thenCompose, thenCombine), supports callbacks (thenAccept), exception handling (exceptionally, handle), and waiting (allOf, anyOf). I use it for fan-out parallel calls to multiple downstreams.

Atomic classes — how do they work?

Classes in java.util.concurrent.atomic — AtomicInteger, AtomicLong, AtomicReference, AtomicBoolean — provide lock-free thread-safe operations using Compare-And-Swap (CAS) instructions provided by the CPU.

Example: AtomicInteger.incrementAndGet() reads the value, computes value+1, then CAS — if no other thread has changed the value in the meantime, the write succeeds; otherwise it retries. No locks, no thread parking, very fast under low–moderate contention.

Under very high contention, retries dominate and performance drops. For hot counters, prefer LongAdder and LongAccumulator — they shard updates across multiple cells and sum on read. I used LongAdder for request-rate metrics at Indus Net and saw measurable throughput improvement under load.

Race condition vs data race — fixing one

A data race is two threads accessing the same memory location concurrently, at least one writing, with no synchronization. It's a specific JMM violation that causes undefined behavior — torn writes, stale reads.

A race condition is a broader bug — program correctness depends on timing. Example: a check-then-act on a HashMap (if (!map.contains(k)) map.put(k, v);) — two threads might both see "not contains" and both put.

Fixes: synchronized blocks, java.util.concurrent atomic methods (computeIfAbsent), or atomic primitives. At Indus Net I had a race on a session cache — fixed by switching from HashMap with synchronized blocks to ConcurrentHashMap.computeIfAbsent. Always reach for atomic compound methods on concurrent collections rather than rolling your own.

CountDownLatch vs CyclicBarrier vs Semaphore

CountDownLatch(n) — a one-shot counter. One or more threads await() until other threads have called countDown() n times. Use to wait for several initialization tasks to complete. Not reusable.

CyclicBarrier(n) — n threads call await() and all block until the n-th arrives, then all proceed together. Reusable — it resets automatically. Use for repeated phased computations (like simulation rounds).

Semaphore(n) — n permits. Threads acquire() a permit (blocking if none available) and release() when done. Use for rate-limiting or bounding concurrent access to a resource — e.g., limit concurrent HTTP calls to a downstream service.

Mnemonic: latch = wait for events, barrier = sync threads, semaphore = throttle access.

ThreadLocal — when and what to watch for

ThreadLocal<T> gives each thread its own private copy of a value. Common uses: per-request context (user ID, trace ID, locale), SimpleDateFormat (which is not thread-safe), DB connections in legacy patterns.

Two big pitfalls. (1) Memory leaks in thread pools. Pool threads live forever; if you set a ThreadLocal and don't remove it, the value sticks around — and if it references a large object or a classloader, you've leaked memory. Always call threadLocal.remove() in a finally block (Spring's RequestContextHolder does this; custom code often doesn't).

(2) Inheritance — child threads don't inherit. Use InheritableThreadLocal if needed, but be careful with thread pools where threads aren't really "children". Modern alternative: ScopedValue (Java 21, preview).

Virtual threads — should I use them? must

Yes — for I/O-bound workloads, which is most server-side Java. Virtual threads (Java 21) are JVM-managed, ~few KB each, and the JVM unmounts them from a carrier OS thread when they block on I/O. You can run a million of them.

Where they win:

  • Microservices doing remote calls (HTTP, DB, Kafka).
  • Replacing thread-pool sizing headaches — one virtual thread per task is fine.
  • Writing blocking-style code without reactive complexity.

Where they don't help: CPU-bound work — still bounded by cores. Pinned threads — code inside synchronized doing I/O pins the carrier; use ReentrantLock instead. Also be careful with ThreadLocal in code that may run on millions of threads.

I've started using them on internal services with great results — sometimes 5–10× throughput.
