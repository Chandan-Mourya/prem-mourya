SQL query is taking 5 minutes. What will you do?

A slow SQL query is investigated using EXPLAIN PLAN, AWR/V$SQL, and index analysis — then fixed with indexes, query rewrite, or statistics refresh.

Investigation

EXPLAIN PLAN FOR <query>; SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY) — look for FULL TABLE SCAN on large tables.

Check V$SQL: SELECT elapsed_time, buffer_gets, disk_reads, executions FROM V$SQL WHERE sql_id = '<id>'.

Fixes

Missing index: CREATE INDEX idx_txn_account ON transactions(account_id, txn_date) — if query filters on these columns.

Stale statistics: EXEC DBMS_STATS.GATHER_TABLE_STATS('schema', 'transactions') — optimizer needs accurate stats.

Query rewrite: replace correlated subquery with JOIN; replace function on indexed column with alternate expression.

Now coming to conclusion.

Never tune without measuring — compare execution plan and elapsed time before and after each change.

Customer says transaction is debited but not credited. How will you investigate?

Investigate a debit-without-credit issue by tracing the transaction reference through application logs, DB audit tables, and GL postings to find where the credit was lost.

Step 1: verify debit

Query account_transactions: SELECT * FROM account_transactions WHERE txn_ref = '<ref>' — confirm debit posting exists.

Check debit amount, timestamp, and channel — get the exact transaction record.

Step 2: find credit

Check beneficiary account transactions table. Check GL postings for this reference. Check OSB/MQ logs for message routing.

If credit message was sent to queue but not processed: check DLQ and consumer logs for processing failure.

Resolution

If credit was never posted: manual credit posting with proper authorization and audit trail.

If credit was posted to wrong account: reverse and re-post with maker-checker approval.

Now coming to conclusion.

Trace by transaction reference through every system hop — logs must carry the same reference for effective tracing.

Batch job failed during EOD. What will you do?

EOD batch failure is handled by checking logs for the failed step, resolving root cause, and re-running from the failure point — not from the beginning.

Immediate

Check DBMS_SCHEDULER job run details or batch log table: which step failed, error message, timestamp.

Assess impact: which accounts were processed before failure? Safe to continue from failure point?

Resolution

Data issue: fix the bad record that caused failure; mark it as exception; continue batch.

Code/resource issue: fix or add more space/memory; re-run the failed step only.

Notify business: EOD delayed, estimated completion time, any impact on BOD opening.

Now coming to conclusion.

Batch restartability from failure point is critical — design job tracking table from the start.

Message is stuck in queue. How will you debug?

A stuck queue message is debugged by checking consumer service health, examining the message payload for processing errors, and inspecting the DLQ for repeated failures.

Diagnosis

Check consumer service logs: is it running? Any exception for this message type?

Check DLQ: has the message been moved to DLQ (exceeded retry limit)?

Browse message payload (IBM MQ Explorer or JMS browser): is the message malformed or missing required fields?

Resolution

Consumer down: restart consumer service; messages will be processed on reconnect.

Poison message: fix the message data or consumer code; replay from DLQ after fix.

Consumer too slow: scale up consumer instances or increase thread pool size.

Now coming to conclusion.

A message stuck in a payment queue is a potential failed transaction — escalate to operations team immediately.

WebLogic server is down. What will you check?

WebLogic server down is triaged by checking Node Manager status, server state, logs, and resource constraints — then restarting if no data-critical issue exists.

Check

Admin Console: is admin server accessible? Check managed server state (FAILED, SHUTDOWN, UNKNOWN).

Server log: domain/servers/<name>/logs/<name>.log — look for OOM, startup failure, or JVM crash.

OS: check if JVM process is still running (ps -ef | grep weblogic). Check disk space and memory.

Recovery

If Node Manager running: Admin Console → Servers → Control → Start. If not: ssh to server, start Node Manager, then start managed server.

If OOM: adjust -Xmx before restart. If disk full: free space then restart.

Now coming to conclusion.

Always read the full server log before restarting — blindly restarting without understanding the cause leads to repeated outages.

Application is giving OutOfMemoryError. How will you handle?

OutOfMemoryError is diagnosed via heap dump analysis to find the top retained objects, then fixed by fixing the memory leak or increasing heap.

Diagnosis

Take heap dump: -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/ — auto-generated on OOM.

Analyze with Eclipse MAT: find Leak Suspects, top retained objects, and their GC roots.

Fixes

Memory leak: unbounded cache, static collections, unclosed resources — fix the root cause.

Legitimate heap need: increase -Xmx if application genuinely needs more memory.

Short-term: restart application; add OOM auto-restart via WebLogic server lifecycle management.

Now coming to conclusion.

OOM from a leak will recur after restart — always find and fix the leak, not just restart.

REST API works in dev but fails in UAT. What will you check?

API working in DEV but failing in UAT points to environment differences: configuration, data, certificates, network policies, or connection pool settings.

Checklist

Configuration: compare application.properties/JNDI settings between DEV and UAT — DB URL, timeouts, API endpoints.

SSL/TLS: UAT may use different certificates or enforce mTLS that DEV doesn't — check for SSLHandshakeException.

Data: UAT has different/more data — check if query that works on DEV data fails on UAT volume or specific records.

Network

Firewall rules: UAT may block outbound calls to external APIs that DEV allows — check connection refused errors.

DNS: API endpoint resolved differently in UAT — verify with nslookup from UAT server.

Now coming to conclusion.

Environment parity is the goal — document all differences between environments and address them before UAT.

SOAP integration is failing with schema validation error. What will you do?

SOAP schema validation errors mean the request or response XML doesn't conform to the WSDL's XSD — fix by comparing the actual XML against the expected schema.

Diagnosis

Capture actual SOAP request/response using OSB message log or network proxy (Fiddler, Wireshark).

Validate captured XML against XSD: xmllint --schema service.xsd request.xml — shows exact failing element.

Common causes

Missing mandatory element in request, extra unexpected element, wrong data type (sending string where decimal expected).

WSDL version mismatch: producer updated WSDL but consumer not refreshed — regenerate client stubs from latest WSDL.

Fix

Update request XML structure to match schema. If schema change: coordinate with both producer and consumer teams.

Now coming to conclusion.

Always log the full SOAP envelope on validation errors — the element path in the error message tells you exactly what's wrong.

Deployment failed before production release. What will you do?

A deployment failure before production release requires stopping, diagnosing, fixing in lower environment first, then re-deploying — never forcing through a broken deployment.

Immediate

Stop deployment: don't proceed with partial deployment to remaining servers — partial deployment causes split-brain.

Check WebLogic deployment log and application startup log for the root exception.

Fix and redeploy

Fix in DEV: reproduce and fix the deployment issue (missing JAR, wrong descriptor, port conflict).

Redeploy to SIT/staging: verify successful deployment and smoke test before re-attempting production.

Re-raise change request with updated artifact if required.

Now coming to conclusion.

A failed deployment is stressful — stay calm, diagnose first, never apply random fixes under pressure.

Bank wants new field in existing screen. How will you approach?

Adding a new field to an existing banking screen requires requirement analysis, impact assessment on DB schema and APIs, development, testing, and user training.

Analysis

Understand the field: mandatory/optional, data type, validation, storage, and reporting requirements.

Impact: DB schema change (ALTER TABLE), API change (new field in DTO), screen change, reports update.

Implementation

DB: ALTER TABLE accounts ADD kyc_remarks VARCHAR2(500); — with appropriate migration script.

API: add kycRemarks field to AccountDTO; update Swagger. Screen: add input field with validation.

Migration: back-fill default value for existing records if field is mandatory.

Now coming to conclusion.

A seemingly simple new field can cascade to 10+ places — always do full impact analysis before estimating.

Bank wants custom business validation. Where will you implement it?

Custom business validation should be implemented at the service layer in Java (not in the database trigger or UI) for testability, maintainability, and clear separation of concerns.

Service layer

Java @Service class: validate business rules before calling DB — amount limits, account status, AML flags.

Testable with JUnit + Mockito without DB dependency. Reusable across multiple endpoints.

FLEXCUBE hooks

For FLEXCUBE screens: implement validation in PL/SQL hook procedure that FLEXCUBE calls at pre-processing stage.

Hook approach: bank-specific logic without modifying product code — upgrade-safe.

Not in

Not in DB trigger: hard to test, hard to debug, causes mutating table issues.

Not in UI only: UI validation is for UX, not security — server-side validation is mandatory.

Now coming to conclusion.

Service layer validation is the right place — testable, maintainable, and centralized for all callers.

Customer reports wrong report data. How will you debug?

Wrong report data is debugged by tracing the report query to its data source, comparing with source tables, and identifying the transformation or filter causing the discrepancy.

Steps

Run the report query manually against the DB; compare with customer's expected result.

Check report date parameters: is the report filtering on the correct date range? Business date vs. system date confusion.

Check GL vs. account ledger consistency: report may sum from GL while customer expects account-level balance.

Common causes

Wrong join: outer join expected but inner join used — missing records for accounts with no transactions.

Wrong filter: report excludes reversed transactions but business expects to include them.

Data latency: report uses materialized view not refreshed after EOD — stale data.

Now coming to conclusion.

Always validate report results against raw table data before fixing code — it may be a data quality issue.

Performance test shows high response time. How will you analyze?

High response time in performance tests is analyzed by correlating JMeter metrics with server CPU, DB wait times, thread pool usage, and GC behavior to find the bottleneck.

Correlation

High response time + high DB wait: check V$SQL for slow queries; check V$SESSION for lock waits.

High response time + high JVM CPU: thread dump to find hot threads; check GC pauses (gc.log).

High response time + thread pool full: request queuing — increase pool or fix slow downstream calls.

Tools

JMeter Active Threads Over Time graph: shows if threads are completing or accumulating.

Oracle AWR report run during test: TOP SQL by elapsed time reveals DB bottleneck.

Now coming to conclusion.

Performance analysis requires correlating multiple data sources — no single metric tells the full story.

After release, old functionality breaks. How will you handle?

Regression after a release is handled by quickly identifying if the new release caused it (rollback candidate), fixing in hotfix branch, and deploying after fast-track testing.

Triage

Confirm regression: was this functionality working before the release? Check git log for recent changes to affected code.

Assess rollback viability: if regression is severe (Sev1) and fix is complex, rollback the release may be faster.

Fix

Hotfix branch from current production tag: fix, smoke test in staging, emergency change request, deploy.

Add regression test case for the broken scenario to prevent recurrence.

Prevention

Regression test suite should cover this scenario — if it didn't catch it, add it now.

Smoke test checklist for every production release covering top 20 critical flows.

Now coming to conclusion.

Rollback is a valid option for severe regressions — pride in the release should never delay restoring service.
