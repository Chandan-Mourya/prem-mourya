Tell me about a production issue you solved must

On a payments service I owned, four Kubernetes pods were being OOMKilled every five to six hours under traffic — this is how I went from "just restart it" to a clean root-cause fix without losing the evidence.

CORE IDEA Stabilize customers first, but never restart blindly — treat the next OOM as a data-collection opportunity, not just an outage to silence.
1 Situation

At one of my previous companies I was on-call for a payments microservice running 4 replicas behind a service mesh, sustaining roughly 3k RPS. Over a week we saw repeated OOMKilled events at the 5–6 hour mark on every pod. Customer-visible impact was 5xx spikes during rollover — about 8–12 seconds of failed authorisations each cycle, which upstream callers then amplified via retries.

2 Task

Three goals in order: keep customers transacting, capture enough evidence to find the real root cause, and ship a permanent fix with a guardrail so this class of bug couldn't recur silently.

3 Action

First, stabilize. I added a longer preStopHook and a graceful drain on the readiness probe so traffic shifted away cleanly before each pod died; the 5xx spikes on rollover dropped immediately. I deliberately did not raise the heap to "buy time" — that just makes the OOM less frequent and harder to catch.

Then, capture. Enabled -XX:+HeapDumpOnOutOfMemoryError with the dump path mounted on a persistent volume so the next OOM produced a usable .hprof. Within about 4 hours we had a dump.

Then, analyse. Opened the dump in Eclipse MAT; the Leak Suspects report pointed at a ThreadLocal<RequestContext> the request filter set on entry and never cleared on exit. Tomcat worker threads are pooled, so the context piled up request after request. A second offender — a per-tenant config map — was unbounded; I replaced it with a Caffeine cache (size + TTL).

The actual fix was small:

// Filter — the missing finally block
public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
    throws IOException, ServletException {
  try {
    CURRENT.set(buildContext(req));
    chain.doFilter(req, res);
  } finally {
    CURRENT.remove();   // <-- this is what was missing
  }
}

Roll-out discipline: gated behind a feature flag, soaked 24 hours in staging under replayed prod traffic, then a 1-of-4 prod canary while I watched jvm_memory_used_bytes rate-of-change, then full fleet.

4 Result

Heap usage plateaued and stayed flat across a 72-hour soak; zero OOMKilled events since. p99 stabilised around 38 ms (down from a noisy 80–250 ms during the leaking window). On-call pages on this service went from ~3 per week to zero. I wrote up an "OOM checklist" runbook and added a Prometheus alert on the rolling 4-hour growth rate of heap usage — so the next leak gets noticed before customers do.

Tell me about a difficult scalability problem you handled must

On an e-commerce catalog service, a marketing burst turned a healthy 25 ms p99 into a 3 s p99 and pushed the database to 90% CPU — this is how I rescued it with cache strategy instead of a bigger machine.

CORE IDEA Cache strategy is a product decision, not just a code change — jittered TTLs, request coalescing, and a small near-cache are the difference between a stampede and a steady state.
1 Situation

On a catalog service I worked on, traffic ran around 50k RPS overall; about 95% of reads concentrated on the top 1,000 SKUs. After a marketing burst pushed homepage impressions for a flagship SKU, p99 spiked from ~25 ms to ~3 s and downstream Postgres sat at >90% CPU. Each pod's local Caffeine cache expired roughly together, and on miss every pod hit the DB simultaneously — textbook stampede on a hot key.

2 Task

Bring p99 back to ≤ 50 ms under the burst, without vertically scaling the DB and without 10x-ing read cost on RDS.

3 Action

Four layered changes:

  • Moved per-pod Caffeine to a shared Redis cache so cache fill happened once across the fleet, not once per pod.
  • Added jittered TTLs (5–10 minutes) per key so SKUs didn't all expire at the same wall-clock second.
  • Added request coalescing on cache miss using SET NX EX as a distributed lock — only one pod refreshes a key, the rest serve stale-while-revalidate from Redis.
  • Kept a small per-pod near-cache (Caffeine, ~100 entries) for the absolute hottest SKUs so most requests never crossed the network at all.

Wired Micrometer cache metrics + Grafana dashboards: hit rate, miss rate, refresh latency, lock contention. The coalescing lock primitive looked like this:

-- KEYS[1] = "lock:sku:{id}"   ARGV[1] = pod-id   ARGV[2] = 3 (sec)
if redis.call("SET", KEYS[1], ARGV[1], "NX", "EX", ARGV[2]) then
  return 1   -- this pod is the refresher
else
  return 0   -- someone else is refreshing; serve stale-while-revalidate
end
4 Result

Hit rate climbed from 0.78 to 0.97. p99 dropped from ~3 s back to ~35 ms under burst, comfortably under the SLO. DB CPU dropped by ~80% and we cancelled a planned RDS upsize, saving real spend. The service became cleanly horizontally scalable — adding pods now added throughput instead of multiplying DB load.

Describe a time when a deployment failed in production must

On a Friday-evening rolling deploy of an orders service, a single schema migration started locking a 30-million-row table and writes piled up — here's how we stopped the bleed in about 12 minutes and never made that class of mistake again.

CORE IDEA Incompatible schema changes are deployments too — design them as multi-step (expand → migrate → contract), never as a single "add NOT NULL on a hot table" release.
1 Situation

On an orders service I worked on, we did a routine Friday-evening rolling deploy. The migration added a NOT NULL column without a default to a 30-million-row table. Postgres started taking an ACCESS EXCLUSIVE lock while it rewrote the table. Reads were fine, but writes piled up; the writer connection pool saturated within minutes and customers started seeing 503s on order placement.

2 Task

Stop the customer impact, finish or revert the migration safely without data loss, and make sure we never shipped a long-locking migration unreviewed again.

3 Action

Step one — stop the bleed:

  • kubectl rollout pause on the orders deployment so no more pods picked up the new image.
  • Rolled back running pods to the previous image with kubectl rollout undo.
  • Identified the migration session in pg_stat_activity and ran pg_terminate_backend on it. Writes resumed within seconds.

Step two — redo the migration the right way (expand → migrate → contract):

-- 1) EXPAND: add nullable, no rewrite, no table lock
ALTER TABLE orders ADD COLUMN status_v2 TEXT NULL;

-- 2) MIGRATE: backfill in small batches, off-peak, with sleeps
DO $$
DECLARE last_id BIGINT := 0;
BEGIN
  LOOP
    UPDATE orders
       SET status_v2 = status
     WHERE id IN (
       SELECT id FROM orders
        WHERE id > last_id AND status_v2 IS NULL
        ORDER BY id LIMIT 5000
     )
    RETURNING id INTO last_id;
    EXIT WHEN NOT FOUND;
    PERFORM pg_sleep(0.2);
  END LOOP;
END $$;

-- 3) CONTRACT: NOT NULL is cheap once backfilled; drop old col in a later release
ALTER TABLE orders ALTER COLUMN status_v2 SET NOT NULL;

Step three — guardrails so the next person doesn't repeat it:

  • Added a pre-deploy CI hook that runs EXPLAIN on candidate migrations and parses the lock level — anything ACCESS EXCLUSIVE on a table over 1M rows fails the pipeline.
  • Added a "schema change checklist" PR template: expand-migrate-contract, batch size, off-peak window, rollback plan.
  • Made it a team norm: no schema changes on Friday after 3 p.m.
4 Result

Customer impact closed in about 12 minutes; no data loss; the month's SLO breach stayed under 0.5%. The team adopted expand-migrate-contract as the default pattern for schema changes — used cleanly on the next four migrations. The CI lock-level check caught two near-miss PRs in the following months that would have repeated the same mistake.

Wrong way
One migration: ADD COLUMN … NOT NULL DEFAULT … on a hot table, on a Friday. Postgres rewrites the table under ACCESS EXCLUSIVE. Writes stall. Customers see 503s.

Add the column nullable. No rewrite, no table lock. App writes both new and old columns.

How do you mentor junior developers? must

Mentoring is one of the highest-leverage things a senior does — but only if it's structured opportunity plus frequent feedback, not just answering questions when asked.

CORE IDEA Mentorship's success metric isn't how often they ask you for help — it's whether they're operating one level above their title within 6–12 months.
1 What I do day-to-day
  • 1:1s every two weeks, 30 minutes, agenda owned by them — not a status update. We talk about what's blocking, what they want next, and one piece of feedback in each direction.
  • Pair programming on something neither of us has done before — purposely picking unfamiliar territory so they see how a senior handles uncertainty, not just how I demo something I already know.
  • Code reviews focused on the why, not the what. I explain rationale, link to internal docs or postmortems, and phrase comments as "I'd consider… because…" rather than "change this to…".
  • Deliberate handoff of stretch work — assigning the design doc on a service they'd normally just consume, reviewing early, then stepping back.
  • Async written feedback after big moments (design review, incident, demo). Verbal feedback gets forgotten; written feedback they can re-read in a year.
2 What I avoid
  • Turning them into a code-typing extension of me. If I'm the architect on every story they touch, they never grow.
  • Jumping in too fast. Sitting with a bug for two more hours is often the lesson; I rescue only when they're stuck on the wrong thing, not when they're slow.
  • Vague feedback. "Good job" and "be more proactive" are equally useless. Concrete is better: "The way you scoped the PR into three commits made it easy to review — keep doing that."
  • Conflating mentoring with managing. I don't run their performance review; I'm a senior peer they can be honest with.
3 A short STAR story

At one of my previous companies I mentored a 2-year engineer who was technically strong but quiet in design discussions. Over six months we paired on a microservice extraction, but I deliberately asked them to write the design doc and lead the architecture review; my role was early-stage review and defending the direction when the room pushed back. Inside two quarters they ran the next service migration on their own, and were promoted to mid-level the cycle after. The unlock wasn't more 1:1s — it was visible stretch work with a safety net.

How do you review code as a senior engineer? must

A code review from a senior should leave the author feeling smarter, not wrong — and it should still catch the architectural and operational issues a junior reviewer wouldn't see.

CORE IDEA Optimise for the system, not the line. Be kind in tone, ruthless on architecture, generous with rationale.
1 What I look at first
  • The PR description. Does it answer what / why / how-tested? If I can't follow it on one read, neither can a future on-call.
  • PR size. Anything over ~400 lines I'll ask to be split, unless it's a pure refactor. Big PRs hide bugs.
  • Match to design intent. Does the diff actually implement what the design doc said? Drift between design and code is where real bugs live.
2 What I always check
  • Failure paths. Happy path is usually fine; I read the catch, the timeouts, the retries, the partial-failure semantics.
  • Observability. Are the new code paths logged at the right level? Is there a metric? A trace span? If it breaks at 2 a.m., can we tell why?
  • Security & PII. No secrets in logs, no PII in metrics, auth checks on every new endpoint.
  • Backward compatibility. API contracts, DB schema, message formats — anything consumers see.
  • Test coverage on the branch they changed. Not coverage percentage — coverage of the specific new behaviour.
  • Blast radius. Is this behind a feature flag? Can it roll out incrementally? Can it be turned off without a redeploy?
3 Tone rules
  • Ask questions, don't demand. "What happens if this retries forever?" beats "this is wrong, add a max retries".
  • Explain rationale. Every blocking comment has a "because…".
  • Mark blocking vs non-blocking explicitly — "blocking:", "nit:", "consider:" — so the author isn't guessing what's mandatory.
  • Review my own PR first. If I wouldn't approve my own diff on a cold read, I shouldn't ask anyone else to.
  • Praise specifically. "The way you broke this into three commits made it reviewable" — concrete praise teaches the pattern.
4 A short STAR story

On a payments service I reviewed, a teammate added a retry around a downstream call. The retry had no max attempt count and no backoff — it would have caused a thundering-herd cascade the first time the downstream returned 503. I flagged it as a blocking comment, but I attached a one-line code example showing Resilience4j with maxAttempts=3 and exponential backoff, plus a link to a postmortem the org already had on a similar cascade. The author fixed it in 20 minutes, the team added "max attempts + backoff on every retry" to the review checklist, and we haven't seen a retry-cascade incident in that codebase since.

Junior review style
  • Focus on style / formatting / naming.
  • "This is wrong" without rationale.
  • Approves big PRs they didn't fully read.
  • Doesn't notice missing observability.
  • Misses backward-compat issues.
  • Blocks on personal preference.
Senior review style
  • Focus on failure paths, observability, blast radius.
  • Every block has a "because…" and an example.
  • Asks for splitting big PRs; doesn't rubber-stamp.
  • Notices missing metric / log / trace span.
  • Catches contract / schema / message-format drift.
  • Marks nits as nits; never blocks on taste.

Common interview gotchas:

  • Don't list a checklist with no opinion — interviewers want to hear your judgement.
  • Avoid "I never approve until it's perfect" — that's a velocity-killer flag.
  • Don't frame review as catching mistakes — frame it as raising the team's bar.
  • Avoid "I review every PR" — be honest about prioritising risky changes.
  • Don't dismiss style entirely — be clear about what's nit vs blocking.
  • Avoid attacking the author ("sloppy code") — review the code, not the person.

Interview one-liner: A senior code review optimises for the system, not the line. I check the PR description, the design intent, the failure paths, observability, blast radius, and backward compatibility — in that order. The tone is kind, the rationale is explicit, and the bar I hold is simple: the author should leave the review feeling smarter, not wrong.
