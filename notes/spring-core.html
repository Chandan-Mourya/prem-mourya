What is the Spring Framework? must

Spring is a comprehensive Java framework whose core idea is Inversion of Control (IoC) — instead of objects creating their dependencies (new UserService()), a container injects them. The framework manages object lifecycle, wiring, and cross-cutting concerns (transactions, security, logging) declaratively via annotations.

Around that core, Spring grew into a platform: Spring MVC for web APIs, Spring Data for persistence (JPA, MongoDB, Elasticsearch), Spring Security, Spring Cloud for microservices, Spring Batch for ETL. Spring Boot sits on top with opinionated auto-configuration so you don't write XML or write 200 lines of bean wiring.

Every backend role I've held used Spring — it's the de-facto enterprise Java stack.

IoC & Dependency Injection — the foundation of Spring hot must

IoC (Inversion of Control) means the Spring container, not your code, creates and manages objects and their dependencies. Dependency Injection (DI) is the specific technique Spring uses to do that — it injects required objects automatically instead of forcing each class to instantiate its own collaborators with new.

Inversion of Control — what's "inverted"?
Normal flow Your code creates its own objects: new EmployeeRepository(), new PaymentClient(). You control wiring.
Inverted flow The framework creates objects, resolves their dependencies, and hands them to your class. You just declare what you need.

Before Spring vs With Spring:

WITHOUT IoC — tight coupling
class EmployeeService {
    private EmployeeRepository repo;

    public EmployeeService() {
        // EmployeeService is responsible for creating its dependencies
        this.repo = new EmployeeRepository();
    }
}
  • Hard-coded dependency — can't swap implementations.
  • Impossible to unit-test without hitting a real DB.
  • Lifecycle is your problem (creation, destruction, sharing).
WITH IoC — Spring injects the dependency
@Service
class EmployeeService {
    private final EmployeeRepository repo;

    // Spring sees this constructor and injects the bean
    public EmployeeService(EmployeeRepository repo) {
        this.repo = repo;
    }
}
  • Loose coupling — code depends on the interface, not a concrete class.
  • Trivially testable — pass a mock in unit tests.
  • Spring manages the lifecycle (creation, scope, destruction).

The three flavours of Dependency Injection:

TypeHow it looksWhen to use
Constructor InjectionDependency passed via constructor argument.Recommended for all mandatory dependencies. Fields can be final; bean can't exist in a half-built state.
Setter InjectionDependency assigned via a setX(...) method.Optional dependencies, reconfiguration after creation. Bean is mutable.
Field Injection@Autowired directly on a private field.Avoid in production code. Hard to test, hides circular dependencies, fields can't be final.

Constructor Injection (the recommended style):

@Service
class EmployeeService {
    private final EmployeeRepository repository;
    private final NotificationClient notifications;

    // Spring 4.3+ — no @Autowired needed when there's a single constructor
    public EmployeeService(EmployeeRepository repository,
                           NotificationClient notifications) {
        this.repository = repository;
        this.notifications = notifications;
    }
}

With Lombok, this collapses to a single @RequiredArgsConstructor on the class, with private final fields.

Setter and Field Injection (for completeness):

// Setter injection — optional dependency
@Autowired
public void setAuditLogger(AuditLogger logger) {
    this.auditLogger = logger;
}

// Field injection — avoid in new code
@Autowired
private EmployeeRepository repository;

Why IoC / DI are used:

  • Loose coupling — classes depend on interfaces, not concrete implementations. Easy to swap by profile or in tests.
  • Easier testing — inject a mock EmployeeRepository in a unit test; no Spring context needed.
  • Better maintainability — wiring lives in one place (config / annotations), not scattered through new calls.
  • Lifecycle managed — Spring handles creation, scope (singleton / prototype / request), and destruction.
  • Configurability — pick implementations via @Profile, @ConditionalOnProperty, or qualifiers without changing code.

What the Spring container does behind the scenes:

1. Component scan — find classes annotated with @Component, @Service, @Repository, @Controller, @Configuration.
↓
2. Build BeanDefinitions — record each class's dependencies, scope, init/destroy hooks.
↓
3. Resolve the dependency graph — figure out instantiation order so each bean's dependencies exist first.
↓
4. Instantiate beans — call constructors, populate fields/setters, run @PostConstruct.
↓
5. Inject collaborators — wire the dependencies your code declared.
↓
6. ApplicationContext ready — beans are available for use, app starts serving requests.

Concrete example — the full picture:

// 1. Spring scans this and registers a singleton bean
@Repository
public class EmployeeRepository {
    public Employee findById(Long id) { ... }
}

// 2. Spring sees the constructor parameter, looks up the matching bean,
//    and injects it automatically.
@Service
public class EmployeeService {
    private final EmployeeRepository repository;

    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }

    public Employee get(Long id) {
        return repository.findById(id);
    }
}

// 3. Same again — the controller gets the EmployeeService injected.
@RestController
public class EmployeeController {
    private final EmployeeService service;

    public EmployeeController(EmployeeService service) {
        this.service = service;
    }

    @GetMapping("/employees/{id}")
    public Employee get(@PathVariable Long id) {
        return service.get(id);
    }
}

Common interview gotchas:

  • IoC vs DI — IoC is the principle; DI is the technique Spring uses to implement it. Other forms of IoC exist (callbacks, events) but DI is the one you'll talk about.
  • Why constructor injection? Mandatory deps are visible in the constructor signature; final fields are thread-safe and prevent reassignment; the bean is fully built before any method runs; no need to start the Spring context for unit tests.
  • Circular dependency? Constructor injection makes Spring fail-fast on cycles — that's a feature, not a bug. Field injection hides them until runtime.
  • Multiple implementations? Use @Primary or @Qualifier("paypal") to choose between candidate beans.
  • Where does Spring find beans? Component scanning starts at the @SpringBootApplication package and walks downward; anything outside isn't picked up unless you tell Spring with @ComponentScan(basePackages = "...").

Interview one-liner: IoC (Inversion of Control) means the Spring container — not your code — is responsible for creating, wiring, and managing the lifecycle of objects. Dependency Injection is the specific mechanism Spring uses: dependencies are provided to a class (via constructor, setter, or field) instead of the class creating them. The benefits are loose coupling, testability, configurability, and maintainability. I always use constructor injection with final fields — it makes dependencies explicit, beans immutable, unit tests trivial, and circular dependencies fail at startup instead of in production.

BeanFactory vs ApplicationContext

Both are Spring IoC containers, but ApplicationContext is the superset you actually use day-to-day.

Core Difference
BeanFactory The root IoC interface — bare-bones DI, lazy bean creation.
ApplicationContext Extends BeanFactory with enterprise features (events, i18n, AOP, profiles).
1 Bean Instantiation
BeanFactory
  • Lazy — beans created when first requested.
  • Lower startup memory.
ApplicationContext
  • Eager — singletons created at startup by default.
  • Fails fast on misconfiguration (missing beans, circular deps).
  • Lazy can be opted in with @Lazy.
2 Enterprise Features
BeanFactory
  • Just DI and bean lifecycle.
  • No events, no i18n, no env, no AOP wiring.

  • Events — ApplicationEventPublisher, @EventListener.
  • i18n — MessageSource.
  • Environment / profiles / properties.
  • AOP integration for @Transactional, @Async, etc.
  • Resource loading — classpath / file / URL.
  • BeanPostProcessor auto-registration.

  • DefaultListableBeanFactory.
  • Used internally by ApplicationContext — rarely instantiated directly.

  • AnnotationConfigApplicationContext — non-web.
  • AnnotationConfigServletWebServerApplicationContext — what Spring Boot creates for web apps.
  • ClassPathXmlApplicationContext — legacy XML config.
Takeaway: when people say "the Spring container" they mean ApplicationContext. Spring Boot bootstraps one for you — you rarely care which exact subclass. Reach for BeanFactory directly only in very specialized library code where you want lazy-only DI.
Spring Bean Lifecycle — from create to destroy must

The Spring Bean Lifecycle describes the full set of stages a bean goes through inside the IoC container — from instantiation, through dependency injection, initialization, active use, and finally destruction at shutdown. Understanding it is essential for using @PostConstruct, @PreDestroy, AOP proxies, and custom BeanPostProcessors correctly.

CORE IDEA Spring doesn't just call new. It runs each bean through a defined sequence of callbacks — populate properties, run aware hooks, apply BeanPostProcessors, call @PostConstruct, attach AOP proxies, and on shutdown call @PreDestroy. Each phase is an extension point you can plug into.

The simple 5-step view (interview-ready):

1. Bean instantiated (constructor / factory method)
↓
2. Dependencies injected (constructor / setter / field)
↓
3. Initialization callbacks run — @PostConstruct / afterPropertiesSet() / custom init
↓
4. Bean is ready to use → lives in the ApplicationContext
↓
5. On shutdown — destruction callbacks: @PreDestroy / destroy() / custom destroy

The full lifecycle (what actually happens under the hood for a singleton):

#PhaseWhat happens
1InstantiationSpring calls the constructor or factory method to create the bean instance.
2Populate propertiesSpring injects dependencies — fields, setters, or constructor args.
3Aware callbacksIf the bean implements BeanNameAware, BeanFactoryAware, ApplicationContextAware, etc., those callbacks fire so the bean can grab its name / context.
4BeanPostProcessor — before initpostProcessBeforeInitialization() runs for every registered processor. Hook for pre-init logic.
5Initialization@PostConstruct → InitializingBean.afterPropertiesSet() → custom initMethod, in that order if multiple exist.
6BeanPostProcessor — after initpostProcessAfterInitialization() runs — this is where AOP proxies (@Transactional, @Async) get wrapped around your bean.
7Bean readyBean lives in the container, available for injection elsewhere, serves requests.
8Destruction (on shutdown)@PreDestroy → DisposableBean.destroy() → custom destroyMethod, in that order.

Code example showing every hook in action:

@Component
public class CacheService
        implements InitializingBean, DisposableBean,
                   BeanNameAware, ApplicationContextAware {

    private final RedisClient client;

    public CacheService(RedisClient client) {        // 1 + 2: constructor + DI
        this.client = client;
    }

    @Override
    public void setBeanName(String name) {           // 3: aware callback
        System.out.println("Bean name = " + name);
    }

    @Override
    public void setApplicationContext(ApplicationContext ctx) {
        // grab the context if you need it
    }

    @PostConstruct                                   // 5: init (recommended)
    public void warmUp() {
        client.ping();                               // load caches, register listeners
    }

    @Override
    public void afterPropertiesSet() {               // 5: same phase, alternative API
        // prefer @PostConstruct over this
    }

    @PreDestroy                                      // 8: destroy (recommended)
    public void shutdown() {
        client.close();                              // close pools, flush buffers
    }

    @Override
    public void destroy() {                          // 8: same phase, alternative API
        // prefer @PreDestroy over this
    }
}

Init & destroy — three ways, modern recommendation:

StyleInit callbackDestroy callbackRecommendation
JSR-250 annotations@PostConstruct@PreDestroy✅ Preferred — clean, standards-based.
Spring interfacesInitializingBean.afterPropertiesSet()DisposableBean.destroy()⚠️ Couples your code to Spring. Avoid in modern apps.
XML / @Bean attributes@Bean(initMethod="warmUp")@Bean(destroyMethod="shutdown")Useful when you can't annotate the class (3rd-party library).

What @PostConstruct & @PreDestroy are used for:

@PostConstruct — one-time setup
  • Warm up caches.
  • Register message-bus listeners.
  • Load reference data from DB.
  • Open connection pools.
  • Validate configuration that needs injected beans.
@PreDestroy — cleanup on shutdown
  • Close connection pools (DB, Redis, Kafka).
  • Flush in-memory buffers.
  • Deregister from a service registry.
  • Cancel scheduled tasks / executors.
  • Persist state if needed.

Important notes:

  • Use constructor injection so the bean is fully built before any callback runs. With field injection, @PostConstruct runs after fields are injected — but the constructor itself sees null fields, which is a common bug.
  • AOP proxies are attached at step 6 (postProcessAfterInitialization). That's why @Transactional and @Async don't work on calls inside @PostConstruct — the proxy isn't applied yet.
  • @PreDestroy only runs for managed singletons — for prototype beans, Spring lets go after creating them; you have to clean up yourself.
  • Shutdown order matters — Spring calls @PreDestroy in reverse dependency order; your beans see their dependencies still alive when they clean up.
  • Graceful shutdown — for web apps, configure server.shutdown=graceful so in-flight requests complete before @PreDestroy fires.

Common interview gotchas:

  • Order of init callbacks if you have all three: @PostConstruct → afterPropertiesSet() → initMethod.
  • Same order for destroy: @PreDestroy → destroy() → destroyMethod.
  • Prototype beans — Spring instantiates and injects, but doesn't call destroy. You manage their lifecycle.
  • BeanPostProcessor applies to every bean. It's how Spring implements @Async, @Transactional, validation, etc.
  • JSR-250 vs InitializingBean — the modern recommendation is annotations; the interfaces are a holdover from older Spring.

Interview one-liner: The Spring Bean Lifecycle is the sequence Spring runs every bean through inside the IoC container: (1) instantiation → (2) dependency injection → (3) aware callbacks → (4) BeanPostProcessor before-init → (5) initialization (@PostConstruct / afterPropertiesSet() / init method) → (6) BeanPostProcessor after-init (AOP proxies attached here) → (7) bean ready → (8) destruction (@PreDestroy / destroy() / destroy method) on shutdown. We use @PostConstruct for one-time setup like warming caches, and @PreDestroy for cleanup like closing pools. The modern recommendation is the JSR-250 annotations over InitializingBean / DisposableBean — same lifecycle phase, cleaner code.

Spring Bean Scopes — singleton, prototype, request, session must

A Bean Scope defines how many instances of a bean Spring creates and how long they live inside the IoC container. Singleton is the default (and the right answer 95% of the time) — but knowing the others matters for stateful objects, per-request state, and per-user data.

CORE IDEA Decide how often Spring should give you a new object: once per app (singleton), every time (prototype), once per HTTP request / session / app (web scopes). Pick the smallest scope that satisfies your statefulness needs.

The five built-in scopes:

ScopeHow many instancesWhen destroyedUse case
singleton (default)One per Spring container — shared everywhere.At ApplicationContext shutdown.Stateless services, repositories, controllers, config beans.
prototypeA new instance every time the bean is requested.Spring lets go after creation — no destroy callback.Stateful, mutable, short-lived objects.
request (web)One per HTTP request.When the request ends.Per-request context (auth user, MDC, request-scoped cache).
session (web)One per HTTP session.When the session expires.Per-user state in session-based web apps.
application (web)One per ServletContext.At ServletContext destruction.Effectively a singleton scoped to the servlet context.
websocket (web)One per WebSocket session.When the WebSocket session closes.Per-connection state in WebSocket apps.

How to declare a scope:

// Default — singleton, no annotation needed
@Service
public class EmployeeService { ... }

// Prototype — fresh instance every time
@Component
@Scope("prototype")        // or @Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class ReportGenerator { ... }

// Web scopes — only valid in web ApplicationContext
@Component
@RequestScope              // shortcut for @Scope(WebApplicationContext.SCOPE_REQUEST)
public class RequestContext { ... }

@Component @SessionScope     public class UserCart   { ... }
@Component @ApplicationScope public class GlobalInfo { ... }

Singleton — the default, and what you'll use 95% of the time:

@Service
public class EmployeeService { ... }   // singleton — one instance per ApplicationContext

Spring creates one EmployeeService when the container starts and shares it everywhere it's injected. Memory-efficient, but must be stateless or carefully synchronised — multiple threads hit the same object.

Prototype — fresh instance every time:

@Component
@Scope("prototype")
public class ReportGenerator {
    private final StringBuilder buffer = new StringBuilder();   // mutable state OK here
    public void append(String s) { buffer.append(s); }
    public String build() { return buffer.toString(); }
}

Every getBean(ReportGenerator.class) or injection point gets a brand-new instance. Lifecycle stops at creation — @PreDestroy won't run; you clean up yourself.

Singleton vs Prototype — the comparison every interviewer asks about:

Singleton (default)
  • One shared instance per container.
  • Lower memory; faster (no per-request allocation).
  • Must be thread-safe — multiple threads share it.
  • Lifecycle fully managed — @PreDestroy runs at shutdown.
  • Eagerly created at startup (unless @Lazy).
Prototype
  • New instance every request — independent state.
  • Higher GC pressure (lots of short-lived objects).
  • Thread-safety not an issue — each thread gets its own.
  • No destroy callback — Spring forgets it after creation.
  • Created on demand.

The classic gotcha — prototype injected into a singleton:

// BAD — singleton holds one prototype reference forever
@Service
public class OrderService {
    @Autowired
    private ReportGenerator generator;    // injected ONCE — same instance reused!
}

// GOOD — get a fresh prototype every time
@Service
public class OrderService {
    @Autowired
    private ObjectFactory<ReportGenerator> generatorFactory;

    public void create() {
        ReportGenerator g = generatorFactory.getObject();   // fresh each call
    }
}

Use ObjectFactory<T> / Provider<T> / @Lookup to pull a new prototype bean inside a singleton. Without it, the singleton holds onto the very first prototype instance — defeating the point.

When to use which — practical guide:

SituationBest scope
Stateless service, repository, controller, mappersingleton (the default)
Mutable / stateful helper that must not be sharedprototype
Per-request data: current user, traceId, request localerequest
Per-user data in a session-based UI appsession
App-wide state inside a servlet containerapplication
Per-WebSocket-connection statewebsocket

Important notes:

  • Default is singleton — you almost never need to declare it explicitly.
  • Web scopes need a web ApplicationContext — they don't work in a plain Spring app.
  • Prototype lifecycle is limited — Spring creates and injects it, but doesn't track destruction. @PreDestroy doesn't fire.
  • Singleton beans must be thread-safe — no instance fields holding per-request state.
  • Use the smallest scope that works — singleton scales best, request scope is heavier but isolates state.
  • Web scopes need proxyMode when injected into singletons: @SessionScope(proxyMode = ScopedProxyMode.TARGET_CLASS).

Common interview gotchas:

  • Is singleton thread-safe by default? No — Spring just creates one instance. You make sure it's stateless.
  • Why doesn't @PreDestroy fire on prototype? Spring stops managing the bean after creation — by design.
  • Prototype-in-singleton trap — without ObjectFactory/Provider/@Lookup, the prototype is injected once and behaves like a singleton.
  • Singleton vs Singleton pattern — Spring singleton = one per container, not one per JVM. The GoF Singleton enforces JVM-wide uniqueness; Spring doesn't.
  • How to make singleton lazy — annotate with @Lazy so it's created only on first use.

Interview one-liner: A Spring bean scope defines how many instances Spring creates and how long they live. The default is singleton — one shared instance per container, ideal for stateless services and repositories. Prototype creates a new instance every time the bean is requested — used for stateful, mutable, short-lived objects (a fresh ReportGenerator per report). Web-only scopes — request, session, application, websocket — bind the bean's lifetime to an HTTP request, user session, servlet context, or WebSocket connection. Pick the smallest scope that satisfies your state needs; reach for ObjectFactory<T> when injecting a prototype into a singleton.

Constructor vs Field vs Setter Injection — which to use and why must

Dependency Injection (DI) means the Spring container provides a class with its dependencies instead of forcing the class to create them with new. Spring offers three ways to wire those dependencies in — constructor, setter, and field injection — and the choice has real consequences for testability, immutability, and code clarity.

CORE IDEA Dependencies should be explicit, mandatory, and immutable. Constructor injection achieves all three for free — that's why it's the modern Spring recommendation.

The three styles at a glance:

TypeHow it looksWhen to use
Constructor InjectionDependency passed as a constructor argument.Mandatory dependencies — recommended default.
Setter InjectionDependency assigned via setX(...).Optional dependencies or reconfigurable beans.
Field Injection@Autowired directly on a private field.Avoid in production code — convenient but problematic.

Field injection — the tempting shortcut:

@Service
public class EmployeeService {

    @Autowired
    private EmployeeRepository repository;   // Spring injects via reflection
}

Looks clean, but it's hiding several issues — see below.

Setter injection — for optional dependencies:

@Service
public class EmployeeService {
    private EmployeeRepository repository;

    @Autowired           // optional setter wiring
    public void setRepository(EmployeeRepository repository) {
        this.repository = repository;
    }
}

Constructor injection — the recommended style:

@Service
public class EmployeeService {

    private final EmployeeRepository repository;   // final → set once, never changes

    // Spring 4.3+ — no @Autowired needed when there's a single constructor
    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }
}

With Lombok this collapses to a one-liner: @RequiredArgsConstructor on the class + private final fields.

Why constructor injection is preferred — every reason matters:

ReasonWhy it matters
Better testabilityJust pass mocks to the constructor in unit tests — no Spring context, no reflection magic, no Mockito field injection trickery.
ImmutabilityFields can be final → thread-safe, can't be accidentally reassigned later.
Mandatory dependencies enforcedThe bean cannot exist in a half-built state — you literally cannot construct it without its dependencies.
Avoids NullPointerExceptionDependencies are always initialised before any method runs.
Explicit dependenciesThe constructor signature documents every collaborator the class needs — visible at the top of the file.
Surfaces "god class" smellsA 10-parameter constructor screams "this class does too much". Field injection hides that.
Fails fast on missing beansSpring reports a clear startup error pointing at the constructor instead of a runtime NPE much later.
Catches circular dependencies at startupField/setter injection silently allows cycles; constructor injection refuses to start — that's a feature.
Recommended by the Spring teamIt's the documented best practice since Spring 4.3+ — no @Autowired needed on a single constructor.

Why field injection is discouraged:

Field Injection — the problems
  • Hard to unit test — fields are private, so you either start the Spring context or use reflection to set them.
  • Reflection at runtime — Spring writes to private fields via reflection; slower and less safe.
  • Fields can't be final — bean is mutable, prone to accidental reassignment.
  • Hidden dependencies — the class advertises a no-arg constructor while really needing 6 things. Anyone reading the file has to scan the body for @Autowired.
  • Hides cycles — circular dependencies fail silently at runtime instead of refusing to start.
  • "God class" disguise — easy to keep adding more @Autowired fields without noticing the class is too big.
Constructor Injection — the wins
  • Unit-test ready — new EmployeeService(mockRepo), done.
  • No reflection — pure Java constructor.
  • final fields — immutable, thread-safe.
  • Explicit at a glance — constructor signature lists every dependency.
  • Cycles caught at startup — Spring fails fast with a clear error.
  • Big constructors → refactor signal — pushes you to split the class.

AspectConstructorSetterField
Mandatory dependency✅ Enforced by constructor❌ Bean can exist without it❌ Field can be null
final field possible✅❌❌
Testability without Spring✅ Pass mocks directly⚠️ Call setter manually❌ Needs reflection
Uses reflection at runtime❌❌✅

Same example, three styles — to make the choice visceral:

// 1) Field injection — looks short, hides issues
@Service
public class EmployeeService {
    @Autowired private EmployeeRepository repository;
}

// 2) Setter injection — for optional dependencies
@Service
public class EmployeeService {
    private EmployeeRepository repository;
    @Autowired public void setRepository(EmployeeRepository r) { this.repository = r; }
}

// 3) Constructor injection — what to actually write
@Service
public class EmployeeService {
    private final EmployeeRepository repository;
    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }
}

Interview one-liner: Spring supports three styles of Dependency Injection — constructor, setter, and field. Constructor injection is the recommended approach because it makes dependencies explicit (visible in the constructor signature), mandatory (the bean cannot exist without them), and immutable (fields can be final). It also makes unit testing trivial (just pass mocks), avoids reflection, and catches circular dependencies at startup. Field injection (@Autowired on a private field) is convenient but discouraged — it hides dependencies, blocks final, breaks testability, and silently allows cycles. Setter injection is reserved for genuinely optional dependencies.

@Component vs @Service vs @Repository vs @Controller — Spring stereotypes explained must

All four are Spring stereotype annotations — they mark a class as a Spring-managed bean so component scanning picks it up. Functionally they're almost identical, but each one signals which architectural layer the class belongs to — and @Repository adds one bit of real behaviour.

Core Difference
@Component Generic — any Spring-managed bean. Catch-all.
@Service Business / domain layer — business logic, validation, orchestration.
@Repository Persistence layer — adds exception translation.
@Controller / @RestController Web layer — handles HTTP requests via MVC handler mapping.

Side-by-side reference:

AnnotationLayerPurposeExtra behaviour
@ComponentGenericAny Spring bean — utility, helper, mapper.None (just registration).
@ServiceService / businessBusiness logic, validation, orchestration.None (semantic only).
@RepositoryPersistence / DAODatabase access.✅ Exception translation to DataAccessException.
@ControllerWeb (MVC)HTTP endpoints — returns view names by default.Participates in MVC handler mapping.
@RestControllerWeb (REST)HTTP endpoints — returns JSON bodies.@Controller + @ResponseBody.

The standard Spring Boot layered architecture:

  HTTP Request
        ↓
  @RestController        ← Web layer        (REST endpoints)
        ↓
  @Service               ← Service layer    (business logic, validation)
        ↓
  @Repository            ← Persistence      (DB access, exception translation)
        ↓
  Database (MySQL / Mongo / Redis ...)

Concrete code — one class per stereotype:

// 1) @Component — generic helper (no specific layer)
@Component
public class IdGenerator {
    public String nextId() { return UUID.randomUUID().toString(); }
}

// 2) @Repository — persistence layer + automatic exception translation
@Repository
public interface EmployeeRepository extends JpaRepository<Employee, Long> {
    Optional<Employee> findByEmail(String email);
}

// 3) @Service — business logic
@Service
public class EmployeeService {
    private final EmployeeRepository repository;

    public EmployeeService(EmployeeRepository repository) {
        this.repository = repository;
    }

    public Employee getById(Long id) {
        return repository.findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Employee " + id));
    }
}

// 4) @RestController — REST endpoints (returns JSON)
@RestController
@RequestMapping("/api/employees")
public class EmployeeController {
    private final EmployeeService service;

    public EmployeeController(EmployeeService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public Employee getEmployee(@PathVariable Long id) {
        return service.getById(id);
    }
}

@Component vs the others — what's actually different:

@Component (generic)
  • Catch-all stereotype.
  • Use for utilities, mappers, validators, helpers — anything that doesn't fit a specific layer.
  • No special behaviour.
@Service / @Repository / @Controller
  • All are meta-annotated with @Component — same scanning behaviour.
  • Communicate architectural intent to readers and tools.
  • Useful as AOP pointcuts (e.g., "log every @Service method").
  • @Repository adds exception translation.

@Repository — the one with real extra behaviour:

  • The only stereotype that adds a runtime feature beyond bean registration.
  • Spring's PersistenceExceptionTranslationPostProcessor wraps the bean so vendor-specific exceptions (JDBC SQLException, JPA PersistenceException, Mongo errors) are converted into Spring's unified DataAccessException hierarchy.
  • This lets the service layer catch one consistent exception family regardless of which DB technology sits underneath.
  • With Spring Data repositories you don't write your own DAO — the interface plus JpaRepository / MongoRepository is enough; @Repository is often implicit.

@Controller vs @RestController — pick the right one:

@Controller
  • Returns a view name resolved by ViewResolver (Thymeleaf, JSP).
  • Used in server-rendered web apps.
  • Add @ResponseBody on a method to return JSON instead.
@RestController
  • Shortcut for @Controller + @ResponseBody on every method.
  • Every method returns the response body directly — usually JSON via Jackson.
  • The default choice for REST APIs.

How Spring discovers them — under the hood:

@SpringBootApplication includes @ComponentScan
↓
Spring scans the package tree of the main class
↓
Picks up any class annotated with @Component or any meta-annotation of it (@Service, @Repository, @Controller, @RestController)
↓
Registers each as a bean in the ApplicationContext
↓
@Repository beans get wrapped by the exception-translation post-processor

Common interview gotchas:

  • Functionally equivalent — at runtime, all four register a bean. The difference is semantic + the one perk in @Repository.
  • Always pick the most specific — @Service over @Component for a service class, etc. Costs nothing, improves readability.
  • Spring Data repositories — you don't usually annotate them with @Repository; the interface is registered automatically by Spring Data.
  • @Controller + @ResponseBody = @RestController. The shortcut exists because REST APIs always need it.
  • Static analysis & AOP — tools like SonarQube and Spring AOP can target specific stereotypes (e.g., apply transactions only to @Service).

Interview one-liner: @Component, @Service, @Repository, and @Controller are all Spring stereotype annotations — every one of them registers the class as a Spring-managed bean via component scanning. @Component is the generic stereotype; @Service, @Repository, and @Controller are specialisations that signal the architectural layer (business, persistence, web). The only one with extra runtime behaviour is @Repository, which converts vendor-specific DB exceptions into Spring's unified DataAccessException. Always pick the most specific stereotype — it costs nothing and pays off in readability, tooling, and AOP targeting.

@Configuration vs @Component — how is @Configuration special?

@Configuration declares a class containing @Bean methods — explicit bean definitions. It's special because Spring wraps the class in a CGLIB proxy:

@Configuration
public class AppConfig {
    @Bean public DataSource ds() { return new HikariDataSource(); }
    @Bean public JdbcTemplate jdbc() { return new JdbcTemplate(ds()); }
}

Inside jdbc(), the call ds() is intercepted by the proxy — it returns the same singleton DataSource, not a new one. That's "Full" mode.

With @Configuration(proxyBeanMethods=false) (or just using @Component with @Bean), it's "Lite" mode — each ds() call is a plain method call returning a new instance, which is faster but you must inject dependencies as parameters instead. Lite mode is what Spring Boot increasingly uses internally.

Circular dependencies — what causes them, how to fix?

A circular dependency is when bean A depends on B, and B depends on A. With constructor injection, Spring can't build either (chicken-and-egg) and throws BeanCurrentlyInCreationException at startup. With field/setter injection, it can sometimes resolve via early references — but Spring Boot 2.6+ disables this by default; you'd need to set spring.main.allow-circular-references=true (don't).

Fixes (in order of preference):

  • Redesign — usually the cycle indicates a missing third class; extract shared logic to a new bean.
  • Use events (ApplicationEventPublisher) to decouple direction.
  • Inject ObjectProvider<B> for lazy lookup.
  • @Lazy on one side — fixes the symptom, but lazy proxies have their own gotchas.

I treat a circular dependency as a design smell rather than a wiring problem.

What is AOP and how does Spring implement it? hot

AOP (Aspect-Oriented Programming) separates cross-cutting concerns — logging, security, transactions, caching, metrics — from business logic. Instead of sprinkling tx.begin/commit everywhere, you declare an aspect that runs around methods matching a pointcut.

Spring AOP uses proxies:

  • JDK dynamic proxy when the bean implements an interface.
  • CGLIB (subclass-based) when it doesn't.

Spring intercepts calls through the proxy. Important consequence: self-invocation doesn't trigger the aspect — if methodA in the same class calls methodB directly, the @Transactional on methodB is bypassed. You'd inject the bean into itself or use AspectJ weaving.

Spring uses AOP under the hood for @Transactional, @Cacheable, @Async, @PreAuthorize, and metrics.

How @Transactional Works Internally — Proxy-based AOP, commit & rollback must

@Transactional is Spring's way of declaratively managing database transactions. You annotate a method, and Spring takes care of begin → commit → rollback around it — no connection.commit() in your code. The magic? Proxy-based AOP.

CORE IDEA Spring wraps your bean in a proxy. Every call to a @Transactional method goes through the proxy first — the proxy starts a transaction, calls your method, then commits on success or rolls back on exception.

What @Transactional guarantees:

  • Commit if the method returns normally.
  • Rollback if a RuntimeException / Error is thrown (checked exceptions don't roll back unless you say so).
  • One connection bound to the thread for the whole method — every JDBC / JPA call inside reuses it.
  • ACID — atomicity, isolation, consistency, durability — handled by the DB; Spring just controls the boundaries.

The internal flow — what happens on every call:

1. Client calls service.transferMoney(...)
↓
2. Call hits the Spring proxy (not the real bean)
↓
3. TransactionInterceptor kicks in — reads @Transactional metadata (propagation, isolation, rollbackFor)
↓
4. BEGIN TRANSACTION — gets a DB connection, binds it to the current thread, sets autoCommit=false
↓
5. Proxy delegates to the real method — your business logic runs (debit, credit, …)
↓
6a. Method returns normally → COMMIT  |  6b. Exception thrown → ROLLBACK
↓
7. Connection released, thread unbound, result returned to caller

What is proxy-based AOP?

AOP = Aspect-Oriented Programming — a way to add cross-cutting behaviour (transactions, logging, security, metrics) around your business code without polluting the business code itself. Spring's implementation is proxy-based: when the container creates a bean that has AOP advice (like @Transactional), it wraps the bean in a proxy and registers the proxy in the context — so anyone who autowires that bean actually gets the proxy.

Without proxy
service.transferMoney();
// → directly calls the real method
// → no transaction, no rollback
With Spring proxy
proxy.transferMoney();
//   ├─ begin tx
//   ├─ real.transferMoney()
//   └─ commit / rollback

JDK Dynamic Proxy vs CGLIB — how Spring picks:

Proxy typeWhen Spring uses itHow it works
JDK Dynamic ProxyBean implements at least one interface.Generates a runtime class that implements the same interface; delegates via reflection.
CGLIB ProxyNo interface — bean is a plain class.Generates a subclass at runtime; overrides methods to add the around-advice.

Spring Boot defaults to CGLIB since 2.0 (works for both interface and class beans). You can force JDK with spring.aop.proxy-target-class=false.

Concrete example — money transfer with rollback:

@Service
public class BankService {

    private final AccountRepository accounts;

    public BankService(AccountRepository accounts) { this.accounts = accounts; }

    @Transactional                                  // proxy wraps this method
    public void transfer(Long fromId, Long toId, BigDecimal amount) {
        accounts.debit(fromId, amount);             // SQL UPDATE
        if (amount.compareTo(BigDecimal.ZERO) < 0)
            throw new IllegalArgumentException();   // → ROLLBACK both updates
        accounts.credit(toId, amount);              // SQL UPDATE
    }                                               // success → COMMIT
}

If the credit fails halfway, the debit is rolled back too — both updates are atomic.

Key @Transactional parameters:

ParameterMeaningCommon values

The self-invocation gotcha — interviewer's favourite:

@Service
public class OrderService {

    @Transactional
    public void placeOrder() {
        sendEmail();        // ❌ direct self-call — bypasses the proxy!
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void sendEmail() { ... }
}

Because this.sendEmail() doesn't go through the proxy, the REQUIRES_NEW is silently ignored. Fixes:

  • Inject the bean into itself (@Autowired private OrderService self;) and call self.sendEmail().
  • Split into two beans — usually the cleanest answer.
  • Switch to AspectJ compile/load-time weaving — works without proxies, but adds build complexity.

Other common gotchas:

  • Doesn't work on private or final methods — the proxy can't override them.
  • Checked exceptions don't roll back by default — use rollbackFor = Exception.class if you throw checked exceptions you want to roll back on.
  • Catching the exception inside the method — if you swallow it, Spring sees a normal return and commits. Re-throw or call TransactionAspectSupport.currentTransactionStatus().setRollbackOnly().
  • Put it on the service layer, not on repositories — that's the natural transaction boundary.
  • Doesn't work in @PostConstruct — AOP proxies are attached after initialization (step 6 of the bean lifecycle), so the tx interceptor isn't active yet.
  • Long transactions = held connections — keep methods short; never put HTTP calls or Thread.sleep inside.

Propagation — the one that catches people out:

PropagationBehaviour

REQUIRES_NEWSuspend any existing tx, always start a new one.
NESTEDRun inside a savepoint of the existing tx (partial rollback possible).
SUPPORTSUse existing tx if there is one, else run non-transactionally.
MANDATORYMust be called inside an existing tx — else throw.
NEVERMust NOT be inside a tx — else throw.

Where it shows up in real apps:

Money transfer
Debit + credit must be atomic — exception on either rolls back both.
Order creation
Insert order + decrement inventory + create payment row — all-or-nothing.
Batch update
Update 1000 rows; one failure rolls back the whole batch.
Audit logging
REQUIRES_NEW so audit row commits even if outer tx rolls back.

Interview one-liner: @Transactional works through proxy-based AOP. When Spring creates a bean with @Transactional methods, it wraps it in a JDK dynamic proxy (if interfaces exist) or a CGLIB subclass proxy. Every call goes through the proxy — the TransactionInterceptor reads the annotation, starts a transaction, delegates to the real method, then commits on success or rolls back on a runtime exception. Because it's proxy-based, self-invocation bypasses the aspect, private/final methods can't be advised, and AOP isn't active inside @PostConstruct. The same mechanism powers @Cacheable, @Async, @PreAuthorize, and Spring's metrics — pure cross-cutting magic without touching business code.

Transaction Propagation in Spring — REQUIRED, REQUIRES_NEW, NESTED & friends must

Propagation answers one specific question: "What should happen when a @Transactional method is called from inside another @Transactional method?" Should it join the existing transaction? Start a new one? Run with no transaction? Fail? That's the choice propagation controls.

CORE IDEA Propagation decides how a transactional method behaves relative to an already-running transaction. The default — REQUIRED — joins it. REQUIRES_NEW suspends it and starts a fresh one. Other modes let you express "must already exist", "must not exist", or "don't care".

All 7 propagation levels — what each one does:

PropagationIf a tx already existsIf no tx existsCommon use
REQUIRED (default)Join it.Start a new one.99% of business methods.
REQUIRES_NEWSuspend existing, start a brand-new tx.Start a new one.Audit, logs, notifications that must commit independently.
NESTEDRun inside a savepoint of the existing tx.Start a new one.Partial rollback inside a bigger tx (JDBC only).
SUPPORTSJoin it.Run without a tx.Read methods that work either way.
NOT_SUPPORTEDSuspend the existing tx, run non-transactionally.Run without a tx.Long-running reads / external calls.
MANDATORYJoin it.Throws IllegalTransactionStateException.Methods that must be called inside an existing tx.
NEVERThrows IllegalTransactionStateException.Run without a tx.Methods that must never be inside a tx.

REQUIRED — the default, the safe choice:

@Transactional                              // REQUIRED is default
public void placeOrder(Order o) {
    orderRepo.save(o);
    inventoryService.decrement(o.getItems());  // also @Transactional(REQUIRED)
    paymentService.charge(o.getAmount());      // also @Transactional(REQUIRED)
}
// → all three run in ONE transaction
// → if any of them throws, the WHOLE thing rolls back

This is the right choice 95% of the time — atomic "all or nothing" behaviour.

REQUIRES_NEW — the independent transaction:

@Service
public class OrderService {
    @Autowired AuditService audit;

    @Transactional                              // outer tx (REQUIRED)
    public void placeOrder(Order o) {
        orderRepo.save(o);
        audit.log("ORDER_CREATED", o.getId());  // commits independently
        paymentService.charge(o);               // if THIS throws, only order rolls back
    }                                           // — audit row is already committed!
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void log(String event, Long id) { auditRepo.save(...); }
}

Use REQUIRES_NEW when an inner operation must persist even if the outer transaction rolls back — audit trails, error logs, "we tried to do X" markers, sending notifications you've already enqueued.

The internal flow of REQUIRES_NEW:

1. Outer @Transactional starts — tx1 begins, connection1 bound to thread
↓
2. Inner method with REQUIRES_NEW is invoked through the proxy
↓
3. Spring suspends tx1 — unbinds connection1 from the thread
↓
4. Spring starts tx2 with connection2 — bound to the thread
↓
5. Inner method runs → commit / rollback tx2 (independent of tx1)
↓
6. Spring resumes tx1 — connection1 rebound, outer continues
↓
7. Outer commits / rolls back tx1 only — tx2 is already settled

Note: two connections from the pool are held simultaneously — keep an eye on your pool size if you use REQUIRES_NEW heavily.

REQUIRED vs REQUIRES_NEW — when to pick which:

REQUIRED (default)
  • Inner joins outer — one transaction.
  • Rollback of inner = rollback of everything.
  • One connection from the pool.
  • Atomic "all or nothing".
  • Use for: order + inventory + payment.
REQUIRES_NEW
  • Inner runs in its own tx — outer is suspended.
  • Inner can commit even if outer rolls back.
  • Two connections held simultaneously.
  • Independence.
  • Use for: audit logs, notifications, retry markers.

NESTED — savepoint-based partial rollback:

@Transactional                              // outer tx
public void importBatch(List<Row> rows) {
    for (Row r : rows) {
        try { processOne(r); }              // savepoint per row
        catch (Exception e) { log.warn("skipped {}", r); }
    }
}

@Transactional(propagation = Propagation.NESTED)
public void processOne(Row r) { ... }

If processOne fails, only that savepoint rolls back — the outer tx continues. Useful for "process what we can, skip bad rows". Caveat: NESTED works with JDBC savepoints; JPA/Hibernate support is limited. JpaTransactionManager doesn't fully support NESTED by default.

SUPPORTS, NOT_SUPPORTED, MANDATORY, NEVER — the rest:

ModeWhat it's for
SUPPORTSMethod works either way. If called inside a tx → joins. If called standalone → runs without one. Common for read-only utility methods.
NOT_SUPPORTEDExplicitly run outside a transaction. If one exists, Spring suspends it. Use for long reports, external HTTP calls — anything you don't want holding a DB connection.
MANDATORY"You must call me from inside a transaction." Throws if there isn't one. Good for forcing callers into the right context.
NEVER"You must NOT call me from inside a transaction." Throws if one exists. Rare — mainly for safety on operations that shouldn't be transactional (e.g., file system ops).

Real-world example — money transfer with audit:

@Service
public class BankService {
    @Autowired AuditService audit;

    @Transactional                                       // REQUIRED — atomic
    public void transfer(Long from, Long to, BigDecimal amt) {
        accounts.debit(from, amt);
        audit.log("DEBIT", from, amt);                   // REQUIRES_NEW
        accounts.credit(to, amt);                        // if THIS fails…
        audit.log("CREDIT", to, amt);                    // REQUIRES_NEW
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void log(String type, Long acc, BigDecimal amt) { ... }
}

If credit fails: the debit rolls back (it was in the outer tx) but the DEBIT audit row stays (it was in its own tx). You have a forensic trail of what was attempted, even when the business operation failed.

Where each propagation level shows up:

REQUIRED
Order creation, money transfer, any "all-or-nothing" business operation.
REQUIRES_NEW
Audit logs, error logs, sending notifications, exception tracking, retry counters.
NESTED
Batch imports where some rows can fail without killing the whole batch.
NOT_SUPPORTED
Long reports, external API calls, heavy reads you don't want holding a connection.
MANDATORY
Internal helpers that must run inside a caller-controlled tx.
SUPPORTS
Utility reads that work fine with or without a tx.

Common interview gotchas:

  • REQUIRES_NEW only works through the proxy. If the outer method calls the inner one via this.log(...), the propagation is ignored — same self-invocation trap as @Transactional in general. Inject the bean into itself or split into two beans.
  • REQUIRES_NEW holds two connections. If your pool is size 10 and 6 threads use REQUIRES_NEW concurrently, you'll deadlock waiting for connections.
  • Exception in REQUIRES_NEW doesn't roll back the outer — unless you let it propagate. Catch carefully.
  • NESTED needs savepoint support. Works with DataSourceTransactionManager + JDBC; JPA support is limited.
  • If outer rolls back, joined REQUIRED inner rolls back too — even if the inner method "succeeded". They're the same transaction.
  • readOnly=true is independent of propagation — readOnly is a hint to the DB/Hibernate, propagation controls boundaries.

Interview one-liner: Propagation in Spring's @Transactional defines how a transactional method behaves when it's called from inside another transaction. REQUIRED (default) joins the existing transaction or creates a new one — gives "all-or-nothing" atomicity. REQUIRES_NEW suspends the outer transaction and starts a brand-new independent one — ideal for audit logging or notifications that must persist even if the outer rolls back. NESTED uses a savepoint for partial rollback inside a bigger transaction. SUPPORTS, NOT_SUPPORTED, MANDATORY, and NEVER express "use one if available", "run outside", "must be inside", and "must not be inside". The key trade-off — REQUIRED gives atomicity with one connection; REQUIRES_NEW gives independence at the cost of holding two connections at once.

Transaction isolation levels in Spring must

When we use @Transactional in Spring, we are not only starting and committing a transaction — we also choose how that transaction behaves when other transactions run at the same time.

That behavior is controlled by the isolation level.

Isolation is part of ACID. It answers: Can one transaction see uncommitted or changing data from another transaction?

Now coming to the standard isolation levels.

Most databases support these levels (from weakest to strongest):

READ_UNCOMMITTED

READ_COMMITTED

REPEATABLE_READ

SERIALIZABLE

In Spring, we set it on the annotation:

@Transactional(isolation = Isolation.READ_COMMITTED)
public void postTransaction() { ... }

If we do not specify isolation, Spring uses the database default (for Oracle and PostgreSQL this is usually READ_COMMITTED).

Now coming to what each level means in simple terms.

READ_UNCOMMITTED — can read data another transaction has not committed yet (dirty read). Rarely used in banking.

READ_COMMITTED — only committed data is visible. Another transaction’s in-flight changes are not seen. This is the most common production default.

REPEATABLE_READ — once you read a row, other transactions cannot change it until your transaction ends (prevents non-repeatable read within the same transaction).

SERIALIZABLE — strongest isolation; transactions behave almost as if they ran one after another. Highest safety, highest locking/contention cost.

Now coming to the anomalies we are trying to prevent.

Dirty read — reading uncommitted data that may be rolled back.

Non-repeatable read — reading the same row twice in one transaction and getting different values because another transaction updated and committed it.

Phantom read — running the same query twice and getting a different number of rows because another transaction inserted/deleted matching rows.

In interviews, linking isolation level → anomaly prevented shows strong understanding.

Now coming to what I use in real banking / enterprise projects.

For most OLTP APIs (account inquiry, payment posting with short transactions), I keep the default READ_COMMITTED.

I only increase isolation when there is a proven concurrency bug, for example:

balance read and update in separate steps without proper locking

report generation that must see a consistent snapshot

Even then, I often fix the problem with:

SELECT … FOR UPDATE (pessimistic lock)

optimistic locking with @Version

smaller transactions

rather than jumping straight to SERIALIZABLE.

Now coming to Spring-specific points interviewers ask.

Isolation is applied by the same transaction interceptor / proxy as propagation — at transaction begin time, Spring sets the isolation on the JDBC connection.

Isolation only matters inside a transaction. A read-only service method without @Transactional does not get isolation guarantees.

Self-invocation bypasses the proxy — if an outer non-transactional method calls an inner @Transactional method on this, isolation (and propagation) may not apply.

Not every database implements every level the same way — always verify against your DB (Oracle vs MySQL vs PostgreSQL differ slightly).

Now coming to example — why isolation matters in a transfer.

Transaction A reads account balance = 1000.

Transaction B debits 200 and commits → balance 800.

Transaction A reads balance again and still assumes 1000 → wrong business decision.

With proper isolation + locking, Transaction A either sees consistent committed state or waits/blocks according to lock rules.

In conclusion, transaction isolation in Spring is configured via @Transactional(isolation = …), maps to database isolation levels, prevents concurrency anomalies, and in production I default to READ_COMMITTED unless a specific use case needs stronger guarantees or explicit row locking.
