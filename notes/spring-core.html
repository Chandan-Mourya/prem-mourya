What is the Spring Framework? must

Spring is a comprehensive Java framework whose core idea is Inversion of Control (IoC) — instead of objects creating their dependencies (new UserService()), a container injects them. The framework manages object lifecycle, wiring, and cross-cutting concerns (transactions, security, logging) declaratively via annotations.

Around that core, Spring grew into a platform: Spring MVC for web APIs, Spring Data for persistence (JPA, MongoDB, Elasticsearch), Spring Security, Spring Cloud for microservices, Spring Batch for ETL. Spring Boot sits on top with opinionated auto-configuration so you don't write XML or write 200 lines of bean wiring.

Every backend role I've held used Spring — it's the de-facto enterprise Java stack.

Explain Inversion of Control and Dependency Injection hot

IoC means the framework controls the flow — it decides when to create objects and how to wire them. Your code becomes mostly declarative.

Dependency Injection is the specific mechanism: dependencies are provided to a class rather than the class creating them.

@Service
public class OrderService {
    private final PaymentClient payment;

    public OrderService(PaymentClient payment) {
        this.payment = payment;  // injected by Spring
    }
}

Benefits: testability (inject a mock PaymentClient in tests), loose coupling (depend on an interface, swap implementations via config), configurability (pick beans by profile). I use constructor injection everywhere — fields can be final, dependencies are explicit, and the bean can't be in an inconsistent state.

BeanFactory vs ApplicationContext

BeanFactory is the root IoC container interface — basic bean creation and dependency injection. Beans are lazily instantiated.

ApplicationContext extends BeanFactory with enterprise features:

  • Eager instantiation of singleton beans by default (fail-fast at startup).
  • Event publication via ApplicationEvent.
  • Internationalization (MessageSource).
  • AOP integration, environment abstraction (profiles, properties), resource loading.

You almost never use BeanFactory directly today. Spring Boot bootstraps a ConfigurableApplicationContext (specifically AnnotationConfigServletWebServerApplicationContext for web apps). When people say "the Spring container" in practice, they mean ApplicationContext.

Bean lifecycle — from create to destroy

For a typical singleton bean:

  1. Spring instantiates the bean (constructor or factory method).
  2. Populate properties — fields/setters injected.
  3. BeanNameAware, BeanFactoryAware callbacks if implemented.
  4. BeanPostProcessor.postProcessBeforeInitialization() for every registered processor.
  5. @PostConstruct or InitializingBean.afterPropertiesSet() or the initMethod.
  6. BeanPostProcessor.postProcessAfterInitialization() — this is where AOP proxies are wrapped around your bean.
  7. Bean is ready and added to the container.
  8. On shutdown: @PreDestroy or DisposableBean.destroy() or destroyMethod.

I use @PostConstruct for one-time init (warm caches, register listeners) and @PreDestroy for cleanup (close pools, flush buffers).

Bean scopes — singleton, prototype, request, session

singleton (default) — one instance per Spring container, shared everywhere. Almost all services and repositories are singletons. Must be stateless or carefully synchronized.

prototype — a new instance every time the bean is requested. Spring doesn't manage its lifecycle after creation — no destroy callback. Use rarely; if you find yourself injecting prototype-into-singleton, you need ObjectFactory<T> or Provider<T> to get a fresh instance each time.

Web-aware scopes (only in web app context):

  • request — one per HTTP request.
  • session — one per HTTP session.
  • application — one per ServletContext.
  • websocket — one per WebSocket session.

In 5 years I've used 95% singleton and a small fraction of prototype/request for very specific cases.

@Autowired — field, setter, or constructor?

Constructor injection (preferred):

@Service
public class OrderService {
    private final PaymentClient payment;
    public OrderService(PaymentClient payment) { this.payment = payment; }
}

Benefits: fields can be final (immutable, thread-safe), dependencies are explicit, easy to instantiate in tests without Spring, fails fast on missing beans. Spring 4.3+ doesn't even need @Autowired if there's only one constructor.

Setter injection — for optional dependencies. Use sparingly.

Field injection (@Autowired on a private field) — convenient but discouraged. Hard to test without reflection, can't be final, hides circular dependencies, and signals you have too many dependencies. I never write field injection in new code, and convert legacy field injection to constructor injection during refactors.

@Component vs @Service vs @Repository vs @Controller

All four register the class as a Spring bean. They are semantically distinct stereotypes that document layer:

  • @Component — generic catch-all.
  • @Service — business / domain layer. No technical behavior added, but signals intent.
  • @Repository — persistence layer. Adds technical behavior: Spring wraps it with a translator that converts vendor-specific exceptions (SQL, JPA) into DataAccessException hierarchy.
  • @Controller / @RestController — web layer; participates in MVC handler mapping. @RestController = @Controller + @ResponseBody on every method.

Picking the right one helps readers, static analysis tools, and AOP pointcuts (e.g., apply something only to @Service).

@Configuration vs @Component — how is @Configuration special?

@Configuration declares a class containing @Bean methods — explicit bean definitions. It's special because Spring wraps the class in a CGLIB proxy:

@Configuration
public class AppConfig {
    @Bean public DataSource ds() { return new HikariDataSource(); }
    @Bean public JdbcTemplate jdbc() { return new JdbcTemplate(ds()); }
}

Inside jdbc(), the call ds() is intercepted by the proxy — it returns the same singleton DataSource, not a new one. That's "Full" mode.

With @Configuration(proxyBeanMethods=false) (or just using @Component with @Bean), it's "Lite" mode — each ds() call is a plain method call returning a new instance, which is faster but you must inject dependencies as parameters instead. Lite mode is what Spring Boot increasingly uses internally.

Circular dependencies — what causes them, how to fix?

A circular dependency is when bean A depends on B, and B depends on A. With constructor injection, Spring can't build either (chicken-and-egg) and throws BeanCurrentlyInCreationException at startup. With field/setter injection, it can sometimes resolve via early references — but Spring Boot 2.6+ disables this by default; you'd need to set spring.main.allow-circular-references=true (don't).

Fixes (in order of preference):

  • Redesign — usually the cycle indicates a missing third class; extract shared logic to a new bean.
  • Use events (ApplicationEventPublisher) to decouple direction.
  • Inject ObjectProvider<B> for lazy lookup.
  • @Lazy on one side — fixes the symptom, but lazy proxies have their own gotchas.

I treat a circular dependency as a design smell rather than a wiring problem.

What is AOP and how does Spring implement it? hot

AOP (Aspect-Oriented Programming) separates cross-cutting concerns — logging, security, transactions, caching, metrics — from business logic. Instead of sprinkling tx.begin/commit everywhere, you declare an aspect that runs around methods matching a pointcut.

Spring AOP uses proxies:

  • JDK dynamic proxy when the bean implements an interface.
  • CGLIB (subclass-based) when it doesn't.

Spring intercepts calls through the proxy. Important consequence: self-invocation doesn't trigger the aspect — if methodA in the same class calls methodB directly, the @Transactional on methodB is bypassed. You'd inject the bean into itself or use AspectJ weaving.

Spring uses AOP under the hood for @Transactional, @Cacheable, @Async, @PreAuthorize, and metrics.

@Transactional — how does it actually work?

@Transactional wraps a method in a database transaction via AOP. On method entry, the transaction interceptor begins a tx (or joins an existing one); on success it commits; on exception it rolls back.

Key parameters:

  • propagation — REQUIRED (default; join or create), REQUIRES_NEW (always new), NESTED, SUPPORTS, NEVER, etc.
  • isolation — READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE — controls visibility of concurrent changes.
  • rollbackFor — by default rolls back only on unchecked exceptions; checked exceptions commit unless you set rollbackFor = Exception.class.
  • readOnly — hints to the driver/Hibernate for optimizations.

Common bugs: self-invocation skipping the proxy (no transaction), missing rollbackFor on checked exceptions, putting @Transactional on private methods (proxy can't intercept). I almost always put it on the public service layer method, not on repositories.
