IaaS vs PaaS vs SaaS

Three layers of "cloud abstraction" — each one hands more of the stack to the provider and leaves less for you to manage.

Core Difference
IaaS Infrastructure — you get VMs and networks; you manage the OS, runtime, app.
PaaS Platform — you deploy code; the provider runs it.
SaaS Software — you just use the app over the internet.
1 What You Manage
IaaS
  • OS, runtime, middleware, app, data.
  • Provider gives you VM, network, storage.
  • Maximum control, maximum ops work.
PaaS / SaaS
  • PaaS — you just push code. App + data are yours, infra + runtime + scaling are theirs.
  • SaaS — you just log in. Everything else is theirs.
2 Examples
IaaS
  • AWS EC2, Azure VMs, GCP Compute Engine.
  • S3 / EBS for storage. VPC for networking.
PaaS / SaaS
  • PaaS — AWS Elastic Beanstalk, App Service, Heroku, App Engine, ECS Fargate.
  • SaaS — Gmail, Salesforce, Slack, Datadog, GitHub.
3 Tradeoffs
IaaS
  • Maximum flexibility — any tech stack, any OS.
  • You patch, secure, monitor, and scale everything.
PaaS / SaaS
  • Less ops, faster to ship.
  • Vendor lock-in, limited customization.
4 Bonus: FaaS / Serverless

A fourth layer often called out separately: FaaS (Function as a Service) — write a function, deploy it, pay per invocation. Examples: AWS Lambda, Azure Functions, GCP Cloud Functions. Stateless, auto-scaled to zero, but with cold starts and a 15-min max runtime.

In practice: most modern teams mix all four — containers on K8s (between IaaS and PaaS) + managed DBs/queues (PaaS) + Lambdas for event-driven glue (FaaS) + SaaS for observability and dev tools. Pick the highest-level abstraction that still gives you what you need.
AWS core services you'd use for a typical backend must

For a typical Java/Spring Boot microservice:

  • Compute: EKS (Kubernetes) or ECS Fargate; Lambda for event-driven work.
  • Database: RDS (Postgres/MySQL) or Aurora; DynamoDB for KV; DocumentDB for Mongo-compatible; ElastiCache (Redis) for cache.
  • Search: OpenSearch (managed Elasticsearch).
  • Messaging: MSK (managed Kafka), SQS for queues, SNS for fan-out.
  • Storage: S3 for objects/files, EFS for shared file storage.
  • Networking: VPC, ALB/NLB, Route 53 (DNS), CloudFront (CDN).
  • Secrets & config: Secrets Manager, Parameter Store, KMS.
  • Observability: CloudWatch (logs/metrics), X-Ray (tracing).
  • IAM: roles for least-privilege, IRSA for K8s service accounts.
  • CI/CD: CodePipeline / CodeBuild, or external (GitHub Actions, GitLab).

I've shipped services using almost all of these — naming them in interviews signals real experience.

EC2 vs ECS vs EKS vs Lambda — when?

EC2 — raw VMs. Maximum control. I rarely run apps directly on EC2 anymore; mostly worker nodes under EKS.

ECS (Fargate) — managed container orchestration. Great for small/medium teams: no nodes to manage. Less ecosystem than Kubernetes.

EKS — managed Kubernetes. Standard for teams with multiple services, Helm, custom operators, multi-cloud portability. What I use most in production.

Lambda — event-driven, no servers, scales to zero. Best for: short-lived tasks (image resizing), event handlers (S3 upload → process), low-traffic APIs, glue code. Watch: cold starts, max 15 min, fragmented observability, harder local dev.

Rule of thumb: EKS for long-running services, Lambda for bursty/event-driven, Fargate as a Kubernetes-lite option for small teams.

S3 — what makes it special?

S3 is object storage: store any blob (file, image, video, backup) under a key in a bucket. Not a filesystem — flat keys with "/" used as a delimiter for prefix queries.

Properties: 11 nines of durability (99.999999999%), virtually unlimited, multi-region replication, lifecycle policies (move to Glacier after 90 days). Storage classes range from Standard (hot) to Glacier Deep Archive (cents per TB-month).

Common patterns:

  • Pre-signed URLs — clients upload/download directly to S3 without proxying through your service.
  • Event-driven — S3 → SQS/Lambda on object create (image processing, indexing).
  • Static site — host SPAs behind CloudFront.
  • Versioning + MFA delete for protection against accidental overwrites.
  • Server-side encryption with KMS keys.

In one project I used S3 for original resume files and pre-signed URLs for upload — never proxy large files through your API.

IAM — the model in 60 seconds

AWS IAM (Identity and Access Management) controls who can do what on which resource. Four building blocks:

  • Users — human identities (login + access keys).
  • Roles — assumed by services or other accounts; temporary credentials. Used by EC2, Lambda, EKS pods (via IRSA — IAM Roles for Service Accounts).
  • Groups — collections of users for shared permissions.
  • Policies — JSON documents defining allowed/denied actions.

Best practices: least privilege — start with deny, grant minimal actions. No long-lived access keys for services — use roles. MFA on human accounts. Resource-based policies on S3 buckets, KMS keys for who can use them. Use AWS Organizations + SCPs for guardrails across accounts. Periodically run iam-access-analyzer or third-party tools to find over-permissive roles.

VPC basics — subnets, security groups, NACLs

A VPC is your private network in AWS. Composed of:

  • Subnets — segments tied to an AZ. Public (route to Internet Gateway), private (no direct internet; outbound via NAT Gateway).
  • Route tables — control traffic flow between subnets and gateways.
  • Internet Gateway — public internet ingress/egress.
  • NAT Gateway — outbound internet from private subnets.
  • Security Groups — stateful firewall at instance/ENI level. Default: deny all inbound, allow all outbound.
  • NACLs — stateless firewall at subnet level; rarely customized in most apps.

Pattern I use: multi-AZ public subnets for load balancers, private subnets for app pods, isolated subnets for DBs. Never put DBs in public subnets. Use VPC endpoints for S3/DynamoDB to avoid NAT traffic costs.

Auto-scaling — how does it actually work?

AWS Auto Scaling Groups (ASG) maintain a target count of instances. Triggers:

  • Target tracking — keep average CPU at 60%. Simple and effective.
  • Step scaling — add N instances if metric crosses threshold.
  • Scheduled — scale up before known peaks (campaigns, daily peaks).
  • Predictive — ML-based forecast.

For Kubernetes: Horizontal Pod Autoscaler (HPA) scales pods based on CPU/mem/custom metrics; Cluster Autoscaler or Karpenter adds/removes EC2 nodes.

Gotchas: scale-out is fast (seconds–minutes); pod startup may bottleneck (slow JVM warmup, image pulls). Use readiness probes so traffic only hits ready pods. Scale-in needs graceful shutdown — terminate gracefully so in-flight requests complete. At Indus Net I tuned JVM startup with CDS to make Spring Boot pods ready in <10s, which made HPA much more responsive.

Blue-green vs canary vs rolling deployments

Three strategies for shipping new versions without downtime.

Rolling — replace instances one batch at a time. K8s default for Deployments. Simple, gradual, but old and new run simultaneously.

Blue-green — keep two full environments (blue = current, green = new). Cut over traffic at the LB once green is verified. Instant rollback (flip back). Doubles infra cost during deploy.

Canary — send a small % of traffic to the new version, watch metrics, gradually ramp. Lowest risk for big changes. Needs traffic splitting (Istio, Linkerd, AWS App Mesh, or weighted ALB target groups).

For most services I use rolling deploys with proper readiness/liveness probes. For high-risk changes (new ML model, payment integration) I use canary with Argo Rollouts or Flagger, watching error rate and latency.

High availability vs disaster recovery — the difference

Both about resilience, different scales of failure.

High Availability (HA) handles routine failures (one instance crashes, an AZ becomes unhealthy). Achieved within a region: multi-AZ deployments, load balancers, replicated databases, auto-healing. Goal: minutes of degradation max.

Disaster Recovery (DR) handles catastrophic failures — region-wide outage, data corruption, ransomware. Achieved across regions: cross-region replication, periodic backups, runbook drills. Measured by:

  • RTO (Recovery Time Objective) — how fast we restore.
  • RPO (Recovery Point Objective) — how much data we can afford to lose.

Tiered DR: Backup & restore (hours RTO), Pilot light (warm core, scale up), Warm standby (scaled-down full env), Multi-region active-active (zero RTO). Cost rises with each tier. Test DR regularly — un-rehearsed plans fail.

Cost optimization — practical levers

Where cloud bills blow up and how I've cut them:

  • Right-size compute — most EC2/EKS workloads run at 10–20% CPU. Migrate to smaller instances or use ARM (Graviton, 20–40% cheaper).
  • Spot / preemptible instances for batch/build jobs (up to 90% off).
  • Reserved instances / Savings Plans for steady-state production (30–60% off).
  • S3 lifecycle policies — Standard → IA → Glacier as data ages.
  • NAT Gateway egress is often the silent killer; use VPC endpoints for S3/DynamoDB.
  • Right-size RDS — auto-stop dev DBs at night.
  • CloudWatch logs — set retention; logs at default forever are expensive.
  • Tag everything and run cost-explorer + budgets per team.

At Indus Net I cut a non-prod environment's bill ~45% by ARM, scheduled stop/start, and S3 lifecycle policies. FinOps mindset is a real skill.
