IaaS vs PaaS vs SaaS

Three layers of "cloud abstraction" — each one hands more of the stack to the provider and leaves less for you to manage.

Core Difference
IaaS Infrastructure — you get VMs and networks; you manage the OS, runtime, app.
PaaS Platform — you deploy code; the provider runs it.
SaaS Software — you just use the app over the internet.
1 What You Manage
IaaS
  • OS, runtime, middleware, app, data.
  • Provider gives you VM, network, storage.
  • Maximum control, maximum ops work.
PaaS / SaaS
  • PaaS — you just push code. App + data are yours, infra + runtime + scaling are theirs.
  • SaaS — you just log in. Everything else is theirs.
2 Examples
IaaS
  • AWS EC2, Azure VMs, GCP Compute Engine.
  • S3 / EBS for storage. VPC for networking.
PaaS / SaaS
  • PaaS — AWS Elastic Beanstalk, App Service, Heroku, App Engine, ECS Fargate.
  • SaaS — Gmail, Salesforce, Slack, Datadog, GitHub.
3 Tradeoffs
IaaS
  • Maximum flexibility — any tech stack, any OS.
  • You patch, secure, monitor, and scale everything.
PaaS / SaaS
  • Less ops, faster to ship.
  • Vendor lock-in, limited customization.
4 Bonus: FaaS / Serverless

A fourth layer often called out separately: FaaS (Function as a Service) — write a function, deploy it, pay per invocation. Examples: AWS Lambda, Azure Functions, GCP Cloud Functions. Stateless, auto-scaled to zero, but with cold starts and a 15-min max runtime.

In practice: most modern teams mix all four — containers on K8s (between IaaS and PaaS) + managed DBs/queues (PaaS) + Lambdas for event-driven glue (FaaS) + SaaS for observability and dev tools. Pick the highest-level abstraction that still gives you what you need.
AWS core services you'd use for a typical backend must

For a typical Java/Spring Boot microservice:

  • Compute: EKS (Kubernetes) or ECS Fargate; Lambda for event-driven work.
  • Database: RDS (Postgres/MySQL) or Aurora; DynamoDB for KV; DocumentDB for Mongo-compatible; ElastiCache (Redis) for cache.
  • Search: OpenSearch (managed Elasticsearch).
  • Messaging: MSK (managed Kafka), SQS for queues, SNS for fan-out.
  • Storage: S3 for objects/files, EFS for shared file storage.
  • Networking: VPC, ALB/NLB, Route 53 (DNS), CloudFront (CDN).
  • Secrets & config: Secrets Manager, Parameter Store, KMS.
  • Observability: CloudWatch (logs/metrics), X-Ray (tracing).
  • IAM: roles for least-privilege, IRSA for K8s service accounts.
  • CI/CD: CodePipeline / CodeBuild, or external (GitHub Actions, GitLab).

I've shipped services using almost all of these — naming them in interviews signals real experience.

EC2 vs ECS vs EKS vs Lambda — when?

EC2 — raw VMs. Maximum control. I rarely run apps directly on EC2 anymore; mostly worker nodes under EKS.

ECS (Fargate) — managed container orchestration. Great for small/medium teams: no nodes to manage. Less ecosystem than Kubernetes.

EKS — managed Kubernetes. Standard for teams with multiple services, Helm, custom operators, multi-cloud portability. What I use most in production.

Lambda — event-driven, no servers, scales to zero. Best for: short-lived tasks (image resizing), event handlers (S3 upload → process), low-traffic APIs, glue code. Watch: cold starts, max 15 min, fragmented observability, harder local dev.

Rule of thumb: EKS for long-running services, Lambda for bursty/event-driven, Fargate as a Kubernetes-lite option for small teams.

How do you deploy a Spring Boot app to AWS? (step-by-step on EC2) must

Classic interview walk-through: "Take me through deploying a Spring Boot service to AWS." The simplest end-to-end answer uses EC2 + JAR + Nginx; the production-grade answer brings in RDS, S3, IAM roles, CloudWatch, and a CI/CD pipeline. Here is the full picture, starting from the basics.

CORE IDEA Build → Provision → Configure → Ship → Run → Expose → Observe. Every AWS deployment is some version of those seven phases, whether it's a single EC2 VM or a full EKS pipeline.

The 10-step deployment flow (EC2 + JAR — the interview-friendly path):

1. Build the JAR locally — mvn clean package → target/app.jar
↓
2. Launch an EC2 instance (Amazon Linux / Ubuntu) in the right region/VPC
↓
3. Configure a Security Group — open 22 (SSH), 8080 (app), 80 (HTTP)
↓
4. SSH into the instance — ssh -i key.pem ec2-user@<public-ip>
↓
5. Install Java 17 — sudo yum install java-17 -y
↓
6. Copy the JAR — scp -i key.pem target/app.jar ec2-user@<public-ip>:~
↓
7. Run the app in background — nohup java -jar app.jar > app.log 2>&1 &
↓
8. Test — open http://<public-ip>:8080
↓
9. (Optional) Add Nginx in front — route port 80 → 8080
↓
10. Wire in RDS, S3, IAM Role, CloudWatch for a real deployment

Step 1 — Build the application. Use Maven (or Gradle) to package an executable JAR:

mvn clean package
# → target/app.jar

Step 2 — Launch the EC2 instance. AWS Console → EC2 → Launch Instance. Pick:

  • AMI: Amazon Linux 2023 or Ubuntu 22.04.
  • Instance type: t3.micro for testing, t3.small/medium or higher for prod.
  • Key pair: create / select an SSH key pair (download the .pem).
  • VPC + subnet: a public subnet for now (production = private subnet + LB).

Step 3 — Configure the Security Group. A Security Group is a stateful firewall on the instance:

PortProtocolSourceUse
22TCPMy IP onlySSH access (never 0.0.0.0/0 in prod)
8080TCPLB / VPC CIDRSpring Boot app port
80 / 443TCP0.0.0.0/0Public HTTP / HTTPS through Nginx or LB

Step 4 — Connect via SSH:

chmod 400 key.pem
ssh -i key.pem ec2-user@<public-ip>     # Amazon Linux
ssh -i key.pem ubuntu@<public-ip>       # Ubuntu

Step 5 — Install Java on the instance:

# Amazon Linux
sudo yum install java-17-amazon-corretto -y

# Ubuntu
sudo apt update && sudo apt install openjdk-17-jdk -y

java -version

Step 6 — Copy the JAR with SCP:

# From your laptop
scp -i key.pem target/app.jar ec2-user@<public-ip>:/home/ec2-user/

Step 7 — Run the application. Foreground for testing, background for "real" use:

# Quick test
java -jar app.jar

# Detached, survives logout, log to file
nohup java -jar app.jar > app.log 2>&1 &

For anything beyond a demo, register it as a systemd service so it auto-restarts on failure and on reboot:

# /etc/systemd/system/app.service
[Unit]
Description=Spring Boot App
After=network.target

[Service]
User=ec2-user
ExecStart=/usr/bin/java -jar /home/ec2-user/app.jar
SuccessExitStatus=143
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable --now app
sudo systemctl status app

Step 8 — Test it works:

curl http://<public-ip>:8080/actuator/health
# Or open in browser: http://<public-ip>:8080

Step 9 — (Optional) Nginx in front for port 80 / HTTPS:

User → Port 80 / 443 → Nginx → Spring Boot :8080
# /etc/nginx/conf.d/app.conf
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

Add HTTPS with Let's Encrypt (certbot) or terminate TLS at an Application Load Balancer (ALB) with an ACM certificate — that's the production pattern.

Beyond manual EC2 — what real teams do:

Manual EC2 (what we just did)
  • Good for learning, demos, small side projects.
  • No auto-scaling, no rolling deploys, no self-healing.
  • SSH + scp is fine once; brittle after.
Production deployment
  • Containerise the app with Docker, push to ECR.
  • Run on ECS Fargate or EKS — auto-scaling, rolling updates, health checks.
  • CI/CD with GitHub Actions / CodePipeline → build → push image → deploy.
  • Infra as code — Terraform or CloudFormation for VPC/ALB/RDS.
  • IAM Roles everywhere — no access keys in code.

Modern CI/CD flow on AWS:

Developer pushes to GitHub
↓
GitHub Actions / CodePipeline — build, test, scan
↓
Build Docker image → push to ECR with commit-SHA tag
↓
Update ECS service / EKS Deployment with new image
↓
Rolling deploy with health-check gating — old tasks drained, new tasks ramp up
↓
CloudWatch alarms watch error rate / latency → auto-rollback if it spikes

Best practices I always follow:

  • Don't put apps in public subnets — put EC2/ECS/EKS in private subnets behind an ALB.
  • IAM Role, not access keys — every workload gets its own least-privilege role.
  • Secrets in Secrets Manager / Parameter Store, never in application.yml or the AMI.
  • Multi-AZ from day one — RDS Multi-AZ, ALB across 2–3 AZs, ASG spanning AZs.
  • Health checks & readiness probes — so rolling deploys don't send traffic to a half-started JVM.
  • Centralised logs & metrics — CloudWatch Logs + Micrometer; alarms on p99 latency, error rate, JVM heap.
  • Automate everything — Terraform + CI/CD. SSH-to-prod is an emergency tool, not a workflow.

Interview one-liner: To deploy a Spring Boot app to AWS, I build the JAR (mvn clean package), provision an EC2 instance with the right Security Group (22/8080/80), SSH in, install Java, scp the JAR, and run it as a systemd service for auto-restart. I put Nginx (or an ALB) in front for HTTPS, use RDS for the database, S3 for files, IAM Roles for secure access, and CloudWatch for logs/metrics. For real production, I move to Docker → ECR → ECS Fargate or EKS behind an ALB, fronted by Route 53, with CI/CD via GitHub Actions / CodePipeline and infra in Terraform — no SSH, no manual JAR copying.

AWS S3 — object storage explained must

Amazon S3 (Simple Storage Service) is AWS's object storage service — a virtually unlimited place to store files like images, videos, backups, logs, and static assets. It's not a filesystem; it's a flat key-value store of objects organised inside buckets, accessed over HTTP.

CORE IDEA Store any blob — file, image, video, backup, log line — under a unique key in a globally addressable bucket. AWS handles durability (11 nines = 99.999999999%), scale, replication, and HTTP access. You just PUT and GET.

Key concepts:

ConceptMeaning
BucketTop-level container for objects. Globally unique name. Lives in one region.
ObjectThe actual file (up to 5 TB) plus metadata.
KeyUnique identifier within a bucket — e.g., users/42/avatar.png. Looks like a path, but the structure is flat.
RegionGeographic location of the bucket. Pick close to users / compute for latency and cost.
Storage ClassTier: Standard (hot), Infrequent Access, Glacier, Glacier Deep Archive — trades latency for cost.
VersionEach overwrite/delete keeps the previous version when versioning is on.

Simple example:

Bucket: employee-docs   (eu-west-1)
 ├── resumes/alice.pdf      ← key
 ├── resumes/bob.pdf
 ├── photos/alice.png
 └── backups/2026-05-15.zip

Features that matter in production:

  • Durability & availability — 11 nines of durability, designed for 99.99% availability per region.
  • Virtually unlimited capacity — petabytes per bucket, no provisioning.
  • Versioning — keep previous versions automatically; pairs with MFA Delete for ransomware protection.
  • Lifecycle policies — auto-transition objects to cheaper tiers (Standard → IA → Glacier) by age.
  • Encryption — server-side (SSE-S3 / SSE-KMS) and TLS in transit, default-on for new buckets.
  • Replication — cross-region (CRR) or same-region (SRR) for DR and latency.
  • Pre-signed URLs — temporary signed links so clients upload/download directly to S3, bypassing your service.
  • Event notifications — trigger SQS / SNS / Lambda when an object is created or deleted.

Upload from a Spring Boot service (AWS SDK v2):

s3Client.putObject(
    PutObjectRequest.builder()
        .bucket("employee-docs")
        .key("resumes/alice.pdf")
        .contentType("application/pdf")
        .build(),
    RequestBody.fromFile(file)
);

Common use cases:

File upload / download
User-generated content, resumes, attachments — usually via pre-signed URLs so the API never proxies large files.
Backups & archives
Nightly DB dumps, snapshots; lifecycle to Glacier after 30/90 days for cheap retention.
Static website hosting
SPAs (React/Vue/Angular) hosted from S3 behind CloudFront — globally fast, no servers.
Log storage
App / access / VPC flow logs landed in S3, queried with Athena.
Data lake
Parquet/CSV in S3 → queried with Athena, Glue, EMR, Redshift Spectrum.
Event source
S3 PUT → Lambda for image resizing, virus scanning, indexing into ES.

Patterns I always use:

  • Pre-signed URLs for any upload > a few MB — your API stays small.
  • Lifecycle policies from day one — automatic cost optimisation.
  • Block all public access by default; share via pre-signed URLs or CloudFront, not bucket-level public ACLs.
  • VPC endpoint for S3 when calling from inside a VPC — avoids NAT egress costs.

One-liner: S3 is AWS's object storage — buckets of objects identified by keys, with 11 nines of durability, virtually unlimited scale, lifecycle policies, versioning, and pre-signed URLs. It's the default home for files, backups, logs, and static sites in any modern AWS architecture.

AWS IAM — Identity & Access Management must

IAM (Identity and Access Management) is AWS's authentication and authorisation service. It controls who can do what on which AWS resource. Every AWS API call is checked against an IAM policy — get this wrong and you either lock yourself out or hand attackers the keys.

CORE IDEA Define identities (humans, services, apps), attach policies (JSON allow/deny rules), and let AWS enforce them on every API call. Always prefer roles with temporary credentials over long-lived access keys.

The four building blocks:

ComponentPurposeExample
UserLong-lived identity for a human — has a password and/or access keys.chandan@company
GroupCollection of users that share permissions — easier than attaching policies one-by-one.Developers, Admins
RoleIdentity assumed by an AWS service, EC2, Lambda, ECS task, K8s pod (IRSA), or external account. Hands out temporary credentials.EC2 instance role to read S3
PolicyJSON document defining what actions are allowed/denied on which resources.AmazonS3ReadOnlyAccess

Anatomy of a policy:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::employee-docs",
        "arn:aws:s3:::employee-docs/*"
      ]
    }
  ]
}

Four fields decide everything: Effect (Allow/Deny), Action (which API calls), Resource (which ARNs), and optional Condition (e.g., only from a VPC, only with MFA).

User vs Role — when to use which:

IAM User
  • Long-lived credentials (password + access keys).
  • Use for humans logging into the AWS Console / CLI.
  • Always enable MFA.
  • Should NOT be used by applications.
IAM Role
  • Temporary credentials (15 min – 12 hours, auto-rotated).
  • Use for EC2, Lambda, ECS, EKS pods, other AWS accounts.
  • No secrets in your code — credentials delivered via instance metadata.
  • The right answer for almost every workload.

How an IAM role works for a Spring Boot app on EC2:

EC2 instance launched with an Instance Profile attached
↓
App calls s3.putObject(...) using AWS SDK
↓
SDK fetches temporary credentials from the EC2 metadata endpoint
↓
Request signed with those credentials → sent to S3
↓
IAM evaluates the role's policy → S3 allows / denies the action

No credentials in code, in env vars, or in application.yml. Credentials rotate automatically.

Where IAM Roles are typically used:

EC2 instance role
App on a VM accesses S3, RDS, SecretsManager via instance profile.
Lambda execution role
Function gets temporary creds to read DynamoDB, write to SQS, etc.
ECS task role
Each container/task gets its own role — least-privilege per service.
EKS / Kubernetes IRSA
"IAM Roles for Service Accounts" — pods assume a role via OIDC.
Cross-account access
Account A's role trusts Account B — clean alternative to sharing keys.
External / SSO
Federated login (Google, Okta, AWS IAM Identity Center) → assume a role on sign-in.

Real-world example — Spring Boot app uploading to S3:

Spring Boot app on EC2 / ECS / EKS
↓
Attached IAM Role with policy allowing s3:PutObject on employee-docs/*
↓
Access S3 bucket
↓
Upload file (no access keys in code)

Best practices I follow on every project:

  • Least privilege — start with nothing, add the exact actions and resources the workload needs. Avoid "Action": "*" and "Resource": "*".
  • Roles, not access keys, for services. No long-lived secrets in env vars, code, or YAML.
  • MFA on every human account, especially the root user (and lock the root user away).
  • Resource-based policies for cross-account access — S3 bucket policies, KMS key policies.
  • AWS Organizations + SCPs for guardrails across multiple accounts (e.g., deny iam:CreateUser in prod accounts).
  • Periodically audit with IAM Access Analyzer, aws iam generate-credential-report, or third-party tools.
  • Tag resources and use ABAC (Attribute-Based Access Control) for scalable per-team permissions.

Interview one-liner: AWS IAM controls authentication and authorisation in AWS through four primitives — Users (humans), Groups (sets of users), Roles (temporary identities assumed by services or accounts), and Policies (JSON allow/deny rules on actions and resources). The two golden rules are least privilege and use Roles for services — never hard-code access keys. In production, EC2 instance roles, Lambda execution roles, ECS task roles, and EKS IRSA give applications secure, auto-rotated access to S3, RDS, SQS, and other services without storing any credentials in code.

VPC basics — subnets, security groups, NACLs

A VPC is your private network in AWS. Composed of:

  • Subnets — segments tied to an AZ. Public (route to Internet Gateway), private (no direct internet; outbound via NAT Gateway).
  • Route tables — control traffic flow between subnets and gateways.
  • Internet Gateway — public internet ingress/egress.
  • NAT Gateway — outbound internet from private subnets.
  • Security Groups — stateful firewall at instance/ENI level. Default: deny all inbound, allow all outbound.
  • NACLs — stateless firewall at subnet level; rarely customized in most apps.

Pattern I use: multi-AZ public subnets for load balancers, private subnets for app pods, isolated subnets for DBs. Never put DBs in public subnets. Use VPC endpoints for S3/DynamoDB to avoid NAT traffic costs.

Auto-scaling — how does it actually work?

AWS Auto Scaling Groups (ASG) maintain a target count of instances. Triggers:

  • Target tracking — keep average CPU at 60%. Simple and effective.
  • Step scaling — add N instances if metric crosses threshold.
  • Scheduled — scale up before known peaks (campaigns, daily peaks).
  • Predictive — ML-based forecast.

For Kubernetes: Horizontal Pod Autoscaler (HPA) scales pods based on CPU/mem/custom metrics; Cluster Autoscaler or Karpenter adds/removes EC2 nodes.

Gotchas: scale-out is fast (seconds–minutes); pod startup may bottleneck (slow JVM warmup, image pulls). Use readiness probes so traffic only hits ready pods. Scale-in needs graceful shutdown — terminate gracefully so in-flight requests complete. At Indus Net I tuned JVM startup with CDS to make Spring Boot pods ready in <10s, which made HPA much more responsive.

Blue-green vs canary vs rolling deployments hot

Three ways to ship a new version without taking the service down — they differ in risk, cost, and how fast you can roll back.

Rolling Replace pods/instances in batches — default in Kubernetes; old and new run together briefly.
Blue-green Two full stacks; flip traffic at the load balancer — instant rollback, ~2× infra during cutover.
Canary Send a small % of traffic to the new version, watch metrics, ramp gradually — lowest blast radius.
StrategyRollback speedCostBest for
RollingMinutes (undo rollout)LowMost stateless APIs, routine releases
Blue-greenSeconds (LB flip)High (2× env)Big-bang migrations, DB cutovers with rehearsal
CanarySeconds (stop ramp)MediumPayments, ML models, schema-sensitive changes
Canary flow
5% → watch error rate & p99 → 25% → 50% → 100%. Abort if SLO breaches.

Prerequisites for any strategy: readiness probes so traffic only hits warm pods, graceful shutdown (preStop hook + drain), health checks on dependencies, and feature flags for risky logic.

Common interview gotchas:

  • Rolling deploy with a breaking schema change still breaks — deploy strategy ≠ migration strategy.
  • Blue-green does not help if both stacks share one DB you migrated incompatibly.
  • Canary without metrics is just slow rolling — you need error rate, latency, and business KPIs.

Interview one-liner: Rolling is the default for stateless services with good probes. Blue-green buys instant rollback at 2× cost. Canary buys the smallest blast radius when you can split traffic and watch SLOs. Pick the strategy from risk and observability, not fashion.

Securing secrets in cloud deployments must

Secrets never belong in git, images, or plain env vars in prod — use a managed store, short-lived credentials, and least-privilege IAM.

  • Rotation — enable automatic rotation for DB passwords; apps must reconnect on refresh.

Zero-downtime deployment strategy must

Zero downtime is a stack of practices — deploy pattern, backward-compatible APIs, safe migrations, and graceful drain — not a single tool.

CORE IDEA Old and new code must coexist during rollout; the database must tolerate both versions until the deploy finishes.
1 Application layer
  • Backward-compatible APIs — add fields, don't remove/rename in one release (expand-contract).
  • Feature flags — ship code dark; enable after all pods are new.
  • Readiness probes — JVM warmed, DB pool healthy, migrations done.
  • Graceful shutdown — preStop sleep + server.shutdown=graceful so in-flight requests finish.
2 Data layer
  • Never ADD COLUMN NOT NULL without default on a hot table in the same release as app code.
  • Use expand → backfill → contract for schema changes.
  • Dual-write or dual-read windows when renaming columns.
Safe sequence
Deploy tolerant new code → migrate schema (expand) → backfill → enable flag → contract old column in later release.

Common interview gotchas:

  • "We use Kubernetes" is not an answer — probes and PDBs must be configured.
  • Stateful sessions on one pod break rolling deploys — use sticky sessions or externalise state.
  • Cache invalidation during deploy can cause thundering herd — version cache keys with deploy.

Interview one-liner: Zero downtime means old and new versions run together safely: compatible APIs, expand-contract migrations, readiness + graceful shutdown, and a deploy pattern matched to risk. The outage usually comes from the database change, not the load balancer.

High availability vs disaster recovery — the difference

Both about resilience, different scales of failure.

High Availability (HA) handles routine failures (one instance crashes, an AZ becomes unhealthy). Achieved within a region: multi-AZ deployments, load balancers, replicated databases, auto-healing. Goal: minutes of degradation max.

Disaster Recovery (DR) handles catastrophic failures — region-wide outage, data corruption, ransomware. Achieved across regions: cross-region replication, periodic backups, runbook drills. Measured by:

  • RTO (Recovery Time Objective) — how fast we restore.
  • RPO (Recovery Point Objective) — how much data we can afford to lose.

Tiered DR: Backup & restore (hours RTO), Pilot light (warm core, scale up), Warm standby (scaled-down full env), Multi-region active-active (zero RTO). Cost rises with each tier. Test DR regularly — un-rehearsed plans fail.

Cost optimization — practical levers

Where cloud bills blow up and how I've cut them:

  • Right-size compute — most EC2/EKS workloads run at 10–20% CPU. Migrate to smaller instances or use ARM (Graviton, 20–40% cheaper).
  • Spot / preemptible instances for batch/build jobs (up to 90% off).
  • Reserved instances / Savings Plans for steady-state production (30–60% off).
  • S3 lifecycle policies — Standard → IA → Glacier as data ages.
  • NAT Gateway egress is often the silent killer; use VPC endpoints for S3/DynamoDB.
  • Right-size RDS — auto-stop dev DBs at night.
  • CloudWatch logs — set retention; logs at default forever are expensive.
  • Tag everything and run cost-explorer + budgets per team.

At Indus Net I cut a non-prod environment's bill ~45% by ARM, scheduled stop/start, and S3 lifecycle policies. FinOps mindset is a real skill.
