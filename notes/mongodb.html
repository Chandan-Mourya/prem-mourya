What is MongoDB and when to choose it? must

MongoDB is a document database that stores JSON-like records (BSON internally) in collections. Schemaless at the engine level, though you can enforce schema validation in modern versions. It's distributed by design — horizontal scaling via sharding, HA via replica sets.

Pick it when:

  • Flexible schema — fields vary per record, or schema evolves rapidly (early-stage product, multi-tenant SaaS).
  • Nested data fits naturally — embedding lists/objects beats joining 5 tables.
  • You need horizontal write scaling — sharding is built in.
  • You're OK with eventual consistency on reads from secondaries.

I've used it for resume data — each resume is a different shape (different sections, custom fields), and we'd hate a 12-table relational model. For strongly relational data with complex joins, I'd still pick Postgres.

Embedded documents vs References hot

The single most important MongoDB design decision — it shapes how you query, scale, and maintain your data.

Core Difference
Embed Nest child data inside the parent document — one read brings everything.
Reference Store children in a separate collection, link by _id — like SQL foreign keys.
1 Read & Write Pattern
Embed
  • Single round-trip — read parent, get everything.
  • Write is atomic on the whole document — no transactions needed.
Reference
  • Two queries or one $lookup — extra latency.
  • Updates touch only the changed entity.
  • Cross-document writes need multi-document transactions.
2 Relationship Cardinality
Embed
  • 1:1 or 1:few (bounded list).
  • Tight ownership — child can't exist without parent.
Reference
  • 1:many or many:many with unbounded growth.
  • Child has its own identity, often queried independently.
3 Constraints
Embed
  • Hard 16 MB document limit; practical limit much lower (~hundreds of KB).
  • Growing arrays force document migration — fragmentation, slow updates.
  • Duplicated data if the same child belongs to multiple parents.
Reference
  • No size ceiling per relation.
  • No duplicate data.
  • App must handle "missing parent" / orphan references.
4 Use Case
Embed
  • Blog post + its comments (if small).
  • User profile + addresses.
  • Resume + sections (experience, education, skills).
Reference
  • User + millions of orders.
  • Product + reviews (queried independently).
  • Resume + recruiter feedback (separate lifecycle).
Real example: resume sections (experience, education, skills) are embedded — always read with the resume, naturally bounded. Recruiter feedback and search-event history are referenced in separate collections — unbounded, independently queried, separate lifecycle.
Aggregation pipeline — explain with an example hot

The aggregation pipeline is Mongo's data-transformation language — a sequence of stages where each stage's output is the next stage's input. Each stage starts with $:

db.orders.aggregate([
  { $match: { status: "PAID", createdAt: { $gte: ISODate("2026-01-01") } } },
  { $group: { _id: "$customerId", total: { $sum: "$amount" }, count: { $sum: 1 } } },
  { $sort:  { total: -1 } },
  { $limit: 10 },
  { $lookup: { from: "customers", localField: "_id", foreignField: "_id", as: "customer" } }
])

Common stages: $match (filter — push to top to use indexes), $project (reshape), $group (aggregate), $sort, $limit, $lookup (left join), $unwind (array to multiple docs), $facet (multiple sub-pipelines).

It's MongoDB's equivalent of complex SQL. I use explain() to see if $match hits indexes.

Indexes in MongoDB — kinds and pitfalls

Mongo's indexes are B-trees, same idea as SQL. Types I use:

  • Single-field — { email: 1 }.
  • Compound — { tenantId: 1, createdAt: -1 }. ESR rule: Equality fields first, then Sort, then Range — for the planner to use the index efficiently.
  • Text — { description: "text" } for basic full-text (Elasticsearch is better for real search).
  • TTL — { createdAt: 1 }, expireAfterSeconds: 86400 auto-deletes old docs. Great for sessions, audit trails.
  • Partial — index only docs matching a filter; saves space.
  • Unique — enforces uniqueness.
  • Geo (2dsphere) — spatial queries.

Pitfalls: indexes slow writes, take RAM (working set should fit), and unindexed sorts cap out at 32 MB before erroring. Always check explain("executionStats") for new queries.

Replication — replica sets and read preferences

A replica set is a group of mongod nodes — one primary for writes plus secondaries that asynchronously replicate via the oplog. If the primary fails, surviving members hold an election and a new primary takes over (failover typically <10 s).

Reads can hit the primary or secondaries via read preferences:

  • primary (default) — strong consistency.
  • primaryPreferred — primary if available, else secondary.
  • secondary — offload reads, but data may lag.
  • nearest — lowest latency, regardless of role.

Write concern controls acknowledgement: w: "majority" waits for a majority to confirm (durable across failover); w: 1 just the primary. For money and orders I use majority; for analytics events I use w: 1 for throughput.

Sharding — how does it work?

Sharding partitions data across multiple replica sets (shards) for horizontal write scale. Three components:

  • Shards — each is a replica set holding a subset of data.
  • Config servers — store metadata (which chunks live on which shard).
  • mongos routers — entry point for clients; route queries to relevant shards.

The shard key determines partitioning. Hash sharding gives even write distribution but kills range queries. Range sharding is better for range queries but risks hot spots if the key is monotonic (e.g., timestamps — everything writes to the latest shard).

Picking a shard key is irreversible (kind of — there's now reshard but it's expensive). I look for high cardinality, even write distribution, and query locality — so a query can hit one shard. Compound keys like (tenantId, createdAt) often work well.

Transactions in MongoDB — multi-document ACID?

MongoDB has had multi-document transactions since v4.0 (replica sets) and v4.2 (sharded clusters). Use them similarly to SQL transactions:

try (ClientSession s = client.startSession()) {
    s.startTransaction();
    orders.insertOne(s, order);
    inventory.updateOne(s, ...);
    s.commitTransaction();
}

However, the right approach is usually to avoid them by designing schemas around atomic single-document writes — that's the original Mongo philosophy. Transactions have real performance cost, especially on sharded clusters where they coordinate across shards.

I use them when an operation genuinely spans collections and consistency matters (transfer between accounts in two collections, for instance). For most CRUD I rely on embedded documents being atomic.

Change streams — what are they good for?

Change streams let you subscribe to data changes in a collection or database in real time. Under the hood they tail the oplog with a stable resume token — restart-safe.

collection.watch().forEach(change -> {
    // change.operationType: insert, update, replace, delete
    publishToKafka(change.fullDocument);
});

I've used them to feed Elasticsearch: every document insert/update emits a change → Kafka → ES indexer. Idempotent indexing (by document ID) means retries are safe.

Use cases: CDC (change data capture), cache invalidation, real-time analytics, push notifications. They're much cleaner than polling. Note: they require a replica set (not standalone Mongo).

How do you secure a MongoDB cluster in production?

Production checklist:

  • Authentication on — SCRAM-SHA-256 at minimum; LDAP/x509 for enterprise. The default-no-auth setup is how Mongo got a bad reputation for ransom incidents.
  • Role-based authorization — least privilege. App user has readWrite on its own DB, not root.
  • TLS for all connections, including between members of the replica set.
  • Network — bind only to private interfaces, use security groups / firewall, never expose to the public internet. VPC peering or PrivateLink for managed services.
  • Encryption at rest — WiredTiger encryption or storage-layer (EBS, KMS).
  • Auditing — Atlas audit logs or self-hosted equivalent.
  • Backups — automated snapshots, regularly tested restore.

For managed services (MongoDB Atlas), most of this is on by default — much harder to mis-configure.
