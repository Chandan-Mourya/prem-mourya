Your approach to a production incident must

My structured approach to any production issue:

  1. Stabilize first, RCA later. Mitigate (rollback, scale up, fail over) before deep-diving. Customers come first.
  2. Acknowledge in the on-call channel — others know it's being handled. Loop in stakeholders.
  3. Form a hypothesis from metrics — what changed? Recent deploys, traffic spike, downstream issue?
  4. Look at the data — dashboards (RED metrics), logs, traces, error tracker. Don't guess.
  5. Reproduce or narrow — one user, one region, one host? Confine the blast radius.
  6. Fix or mitigate — rollback is your friend if the cause isn't obvious.
  7. Verify with the same metrics that showed the problem.
  8. Blameless post-mortem — root cause, contributing factors, action items, owners.

The goal of a post-mortem isn't "who broke it" — it's "how do we prevent this class of failure?"

Three pillars of observability

Modern observability rests on three complementary signal types:

  • Metrics — numerical time series. Aggregated, cheap, great for dashboards and alerts. Tools: Prometheus, Datadog, CloudWatch, Micrometer. Best for "is something wrong overall?"
  • Logs — discrete events with detail. High cardinality, expensive at scale. Tools: ELK, Loki, CloudWatch Logs. Best for "what exactly happened to this request?"
  • Traces — request-level timing across services. Shows where time was spent. Tools: Jaeger, Zipkin, AWS X-Ray, Tempo. Best for "where in the request did the latency live?"

I add a 4th: events — deploys, config changes, feature flag flips — overlaid on dashboards so I can see correlations.

The trio interlinks: metrics alert me, traces narrow to a service, logs reveal the exact failure. Without all three I'm guessing.

Debugging a Memory Leak in Spring Boot Production — full playbook must

A production memory leak is a senior-engineer test. The first instinct — restart the pod — is the wrong one: a restart destroys the evidence, the leak comes back tomorrow, and you've learned nothing. The right approach is to collect evidence first, diagnose with data, then fix.

CORE IDEA Don't restart blindly. Confirm it is a leak (memory doesn't recover after full GC), grab a heap dump, analyse it in Eclipse MAT / VisualVM, and chase the dominator tree to the object that's holding everything else alive. Then fix the root cause — usually an unbounded cache, an uncleared ThreadLocal, or a static collection.

The 7-step playbook:

1. Check symptoms — confirm heap grows over time, GC frequency rises, latency climbs, eventually OOM

Step 2 — Capture a heap dump (the evidence):

# Find the JVM PID
jps -l                                        # or: ps -ef | grep java

# Option A — jmap (live objects only)
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>

# Option B — jcmd (preferred, no agent attach)
jcmd <pid> GC.heap_dump /tmp/heap.hprof

# Option C — Spring Boot Actuator
curl http://localhost:8080/actuator/heapdump --output heap.hprof

# Option D — auto-capture on OOM (set as JVM args)
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/app/oom-%t.hprof

Heap dumps are large (≈ heap size — often GBs) and briefly pause the JVM. Take one before the OOM if possible. In Kubernetes, also make sure the dump path is on a persistent volume — otherwise the pod restart wipes it.

Analyse it with the right tool:

ToolWhy use it

VisualVMFree, bundled with the JDK historically. Lighter UI; good for live profiling + heap dump browsing.

What to look for in the dump:

  • Histogram — top classes by instance count and retained size. Anything in the hundreds of thousands that shouldn't be? Anything labelled byte[] / char[] with GBs?
  • Dominator tree — the object that "owns" the most retained memory. Follow the chain up — usually leads to a static field or long-lived bean.
  • GC roots — what's keeping the suspect alive? "Path to GC root excluding weak references" in MAT tells you exactly who's holding the reference.
  • Collections growing continuously — a HashMap with 5M entries in a "cache" with no TTL is the classic.
  • Class loaders — multiple instances of the same class loaded → classloader leak (common in old hot-reload setups).

Step 3 — Check GC logs (is it really a leak?):

# Enable GC logging (production-safe, low overhead)
-Xlog:gc*,gc+age=trace,safepoint:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=10,filesize=20M

# Quick live check
jstat -gc <pid> 1000 10   # 10 samples, 1 second apart

The key signal:

Memory churn (NOT a leak)
  • Old Gen shrinks after every full GC.
  • High allocation rate, but heap reclaims fine.
  • Fix: reduce allocations, tune GC, increase heap.
True leak
  • Old Gen stays high after full GC.
  • GC pause times keep growing.
  • Eventual OutOfMemoryError.
  • Fix: find & remove the reference chain.

Step 5 — Check the caching layer (top culprit in microservices):

  • Local cache without TTL — every unique key adds memory, never released.
  • Too many unique keys — caching per-request data (per-user query, per-session token) explodes cache size.
  • Large cached objects — full entity graphs with lazy collections, serialized as deep trees.
  • Cache per pod — local cache duplicates across instances; moving to Redis frees pod memory.

If using Spring Cache + Caffeine, monitor cache.size, cache.gets hit/miss ratio, and cache.evictions via Micrometer. A cache that never evicts is a leak.

Step 6 — Compare two heap dumps (the diff is gold):

# Snapshot 1 — early in the leak
jcmd <pid> GC.heap_dump /tmp/heap-t1.hprof

# Run typical traffic for 30+ minutes...

# Snapshot 2 — when memory is high
jcmd <pid> GC.heap_dump /tmp/heap-t2.hprof

# In Eclipse MAT:
#   File → Open both → Compare Histograms
#   Sort by "shallow heap delta" → leaked class is at the top

The class count that grew the most between dumps points directly at the source. One real example: byte[] grew by 1.8 GB → traced to a Logback async appender with an unbounded buffer.

Step 7 — Reproduce safely & fix:

  • Reproduce in staging with JMeter / Gatling / k6 hitting the suspect endpoint at production-like volume.
  • Verify the fix locally by re-running the same load test; heap should plateau, not climb.
  • Ship behind a feature flag if the fix is invasive.
  • Watch the same dashboards for 24-48 hours post-deploy.

Concrete real-world example — the ThreadLocal trap:

// BAD — fills up over time on Tomcat's worker thread pool
public class TenantContextFilter extends OncePerRequestFilter {
    private static final ThreadLocal<Tenant> CURRENT = new ThreadLocal<>();

    @Override
    protected void doFilterInternal(req, res, chain) {
        CURRENT.set(loadTenantFor(req));
        chain.doFilter(req, res);              // ← if this throws, CURRENT stays set
    }
}

// GOOD — always cleared in finally
@Override
protected void doFilterInternal(req, res, chain) {
    CURRENT.set(loadTenantFor(req));
    try { chain.doFilter(req, res); }
    finally { CURRENT.remove(); }              // ← release the thread's slot
}

Tomcat reuses ~200 worker threads. Without remove(), every request leaves a Tenant object referenced by that thread — multiplied by 200 threads, multiplied by hours of traffic, you get GB of retained "Tenant" objects with no obvious owner. The heap dump shows them rooted at java.lang.Thread → threadLocals → values.

Common interview gotchas:

  • "Would you restart the pod first?" — No. Heap dump first, then rotate the pod. Restart loses the evidence.
  • "How do you distinguish a leak from churn?" — Old Gen behaviour after full GC: shrinks = churn, stays = leak.
  • "What's in a heap dump that's not in a thread dump?" — Every live object's data; thread dump is just thread stacks.
  • "Why are ThreadLocals dangerous in pools?" — Pool threads outlive requests; uncleared entries leak per thread.
  • "How do you take a heap dump in Kubernetes?" — kubectl exec + jcmd, or HeapDumpOnOutOfMemoryError writing to a persistent volume.
  • "What if the pod OOM-kills before you can dump?" — Enable -XX:+HeapDumpOnOutOfMemoryError + -XX:HeapDumpPath ahead of time, on a mounted volume.
  • "Local vs distributed cache for leaks?" — local caches grow the JVM heap; Redis growth shows up in Redis, not the app.

Interview one-liner: When a Spring Boot app leaks memory in production, I never restart blindly — that destroys the evidence. I confirm the leak using Actuator / Grafana / GC logs (Old Gen stays high after full GC), then capture a heap dump via jmap, jcmd, or /actuator/heapdump. I analyse it in Eclipse MAT — the Leak Suspects report + dominator tree usually identifies the offender in minutes. Common culprits in Spring Boot are unbounded local caches, uncleared ThreadLocals on pooled threads, static collections, large session objects, orphan ExecutorServices, and leaked DB / HTTP resources. Comparing two dumps over time pinpoints the growing class; I reproduce in staging with a load test, ship the fix (TTL on the cache, tl.remove() in finally, etc.), and verify the heap plateaus on the same dashboards that flagged the problem in the first place.

How do you read a thread dump?

A thread dump shows every thread's stack at the moment of capture (jstack <pid> or /actuator/threaddump). What to look for:

  • Deadlocks — jstack explicitly says "Found one Java-level deadlock" at the bottom.
  • Hot spots — take 3 dumps a few seconds apart. Threads stuck in the same place are the candidates.
  • Lock contention — many threads BLOCKED waiting for one monitor. The blocked-on lock ID points to the holder.
  • Pool exhaustion — all DB/HTTP pool threads busy. Means downstream is slow or you're starved.
  • Synchronous external calls — threads parked in Socket.read on a downstream service. Add timeouts.

Real example at OneXtel: 200 worker threads stuck waiting for one synchronized block around logging code. Took 3 thread dumps, saw the pattern, replaced with async logger, throughput went up 5×.

How do you debug high CPU usage in production? must

"CPU is at 100%" is one of the most common Java production alerts. The wrong instinct is to scale up — that masks the symptom and the real cost. The right instinct is to figure out which thread is burning the CPU and why, using a small set of standard JDK and Linux tools.

CORE IDEA Identify the hot threads with top -H + jstack, or with async-profiler for a flame graph. Map the hot stack frames to a code path. Common causes: tight loops, JSON / regex blowups, GC churn, lock spin, hash collisions, infinite recursion.
1 The 5-minute triage
  1. Confirm scope — one pod or all pods? One endpoint or all? Did it start after a deploy?
  2. Check basic JVM metrics — heap usage, GC time, GC frequency. If GC is dominating CPU, this is actually a memory problem (see Full-GC question).
  3. Take 3 thread dumps 10 seconds apart — patterns emerge.
  4. If pattern unclear → run async-profiler for 30 seconds → flame graph.
2 The classic toolchain — find the hot thread
# 1. Find the JVM PID
jps -lv

# 2. List per-thread CPU on Linux
top -H -p <pid>
# Note the TID of the busiest thread (e.g. 12345)

# 3. Convert TID to hex
printf "%x\n" 12345        # → 3039

# 4. Get a thread dump and grep for nid=0x3039
jstack <pid> > td.txt
grep -A 30 "nid=0x3039" td.txt

The stack trace tells you which method is burning CPU. Repeat for the top 3 threads; if they all match, you have a clear hotspot.

3 Better — async-profiler flame graphs
# Sample for 30 seconds and produce a flame graph
./profiler.sh -d 30 -f /tmp/cpu.html <pid>

# Or via JFR (built into JDK 11+)
jcmd <pid> JFR.start name=cpu duration=30s filename=/tmp/cpu.jfr
# View in JDK Mission Control or convert to flame graph

Flame graphs show the aggregate CPU time across all threads — much faster than reading individual stacks. Wide bars = where the CPU is going.

4 Common root causes
CauseSignature in dump / flame graphFix
Tight loop / no-sleep retrySame method dominates the flame graphAdd backoff, reactive flow, or fix exit condition
JSON serialization explosionJackson/Gson methods at the topAvoid serializing huge object graphs; use streaming or DTO projection
Catastrophic regex backtrackingPattern.matcher on the hot stackAnchor the regex, fail fast, use possessive quantifiers, or switch library
HashMap/HashSet collisionsHashMap.getNode in hot pathFix hashCode(); use TreeMap or treeified buckets (JDK 8+)
GC churnJVM GC threads (G1 / ParallelGC) at topFind allocation hotspot; reduce object churn; tune heap
Lock spin / synchronizedMany threads in BLOCKED on the same monitorUse ConcurrentHashMap, java.util.concurrent primitives
Logging in a hot pathLogback/Log4j formatting on stackMove to async appender, raise log level, avoid string concat
Infinite recursion / wide fanoutStack depth growing, repeated framesAdd base case / iterative version
Reflection on hot pathMethod.invoke dominatesCache lookups, use MethodHandles or generated code
Cryptography on every requestBCrypt / SHA hotMove to async, cache results, lower work factor where appropriate
5 Container-specific gotchas
  • JVM may misread CPU limits in Kubernetes — set -XX:ActiveProcessorCount=<cpuLimit> or rely on JDK 11+ which honors cgroup limits.
  • "100% CPU" in K8s often means the container is being throttled, not actually busy — check container_cpu_cfs_throttled_periods_total.
  • Pod CPU limit way below request causes constant throttling — symptoms look like a CPU bug.
  • Noisy neighbours on the node — if only one pod is hot but the node CPU is shared, schedule with anti-affinity.
6 Common interview gotchas
  • Don't restart the pod first — the evidence dies with it. Capture dumps first.
  • Don't blame "high traffic" without measuring per-request CPU — a 2× traffic with 10× CPU is an algorithmic regression.
  • Three thread dumps beats one — patterns matter, snapshots lie.
  • Async-profiler / JFR with sampling is preferred over instrumentation in production — < 2% overhead.
  • If GC threads are the top consumers, this is a memory problem in disguise — see Full GC question.
  • The hot thread you're looking for may be a daemon thread (Kafka consumer, scheduled task) not a request thread.
  • Pin a baseline before changes — compare flame graph before/after the fix.

Interview one-liner: When CPU spikes in production, I find the hot thread: top -H -p <pid> for the busiest TID, convert to hex, then jstack and grep nid=0x... to see its stack. For broader visibility I run async-profiler or JFR for 30 seconds and read the flame graph — the wide bars show where CPU is going. Common culprits are tight loops, regex backtracking, JSON serialization of huge graphs, GC churn (often a memory problem in disguise), lock contention, and bad hashCode. Container gotchas: check CPU throttling and that the JVM honors cgroup limits (-XX:ActiveProcessorCount or JDK 11+).

How do you debug frequent Full GC issues? must

Frequent Full GC is the JVM's way of telling you the application is allocating faster than the GC can collect — or that the heap is permanently filling up (a leak). Either way, latency spikes and CPU climbs as GC threads run constantly. The fix is rarely "give it more heap" — it's almost always "find the allocation hotspot or the leak".

CORE IDEA Read GC logs to confirm the pattern (allocation pressure vs leak), find the allocation hotspot with async-profiler's allocation mode or JFR, and fix the code. If it's a leak (Old Gen stays high after Full GC), capture a heap dump and analyse with Eclipse MAT.
1 Confirm it really is Full GC pressure
# Always have GC logs on in production (G1)
-Xlog:gc*,safepoint:file=/var/log/app/gc.log:time,uptime,level,tags:filecount=10,filesize=10M

# Or via Actuator metrics:
jvm.gc.pause                         # pause times by GC name
jvm.gc.memory.allocated              # bytes allocated per second
jvm.memory.used{area=heap, id="G1 Old Gen"}

Three things to read from the log:

  • Frequency — Full GC every 30 s is bad; once an hour is fine.
  • Duration — Full GC pauses > 1 s are user-visible.
  • Heap after collection — if Old Gen stays at 90% after every Full GC, you have a leak; if it drops back to 30%, you have allocation pressure.
2 The two patterns and how to tell them apart
Allocation pressure (churn)
  • Heap usage is sawtooth — fills, GC, drops back down.
  • Most collections are Young GC; Full GC is rare but pause spikes happen during traffic peaks.
  • Cause: hot loop allocating millions of short-lived objects per second.
  • Fix: reduce allocation in the hotspot, or grow heap so Young Gen fits.
Memory leak
  • Heap usage trends up over hours/days, even after Full GC.
  • Old Gen stays near max after every Full GC.
  • Eventually OutOfMemoryError.
  • Fix: heap dump → Eclipse MAT → find dominator → patch (cache TTL, ThreadLocal cleanup, etc.).
3 Find the allocation hotspot
# async-profiler in allocation mode
./profiler.sh -e alloc -d 30 -f /tmp/alloc.html <pid>

# JFR
jcmd <pid> JFR.start name=alloc duration=60s filename=/tmp/alloc.jfr settings=profile

Flame graph in allocation mode shows which methods allocate the most bytes. Common offenders:

  • String.format in hot logging.
  • JSON / XML parsing of large payloads on every request.
  • New collections inside loops (use sized constructors, reuse).
  • Boxing primitives (Integer.valueOf) in hot paths.
  • Streams with intermediate collectors when a primitive loop would do.
  • Reflection allocating small accessor objects.
4 Tune the GC (after fixing the code)
KnobEffect
-Xms = -XmxAvoid heap resize during traffic — pre-commit max heap on startup
-XX:+UseG1GCDefault since Java 9; balanced throughput + latency
-XX:MaxGCPauseMillis=200G1 target pause — too low forces more frequent GC
-XX:+UseZGC / -XX:+UseShenandoahGCSub-10ms pauses for huge heaps; modern JDKs
-XX:G1HeapRegionSizeTune for very large heaps (32G+)
-XX:+HeapDumpOnOutOfMemoryErrorCapture a dump on OOM for post-mortem

5 Container-specific
  • JDK 11+ honors cgroup memory limits — older JDKs may set MaxHeapSize based on host memory and OOM-kill the container.
  • Set -XX:MaxRAMPercentage=75.0 in containers; never -Xmx equal to the pod limit (need overhead for native + thread stacks).
  • Container OOM-kill (exit 137) is different from JVM OOM — check kernel dmesg and pod events to disambiguate.
6 Common interview gotchas
  • "More heap" almost never fixes the underlying problem — it just delays the next OOM by a few hours.
  • Frequent Full GC with low heap utilization = humongous allocations in G1 (objects > 50% region size); break them up or increase region size.
  • Latency-sensitive apps should consider ZGC or Shenandoah — sub-10ms pauses on tens of GB heaps.
  • Comparing two heap dumps over time is the gold standard for finding leaks (Eclipse MAT "Compare heap dumps").
  • SoftReference / WeakReference can be misused — they extend object life unpredictably.
  • Threads have their own stack (1MB default) — leaking threads leaks native memory, not heap.
  • Direct ByteBuffers and Netty pools live off-heap — Heap dumps won't see them; check NMT (Native Memory Tracking).
  • Production GC logs cost almost nothing — keep them on always.

Interview one-liner: Frequent Full GC is either allocation pressure (sawtooth heap, churn) or a leak (Old Gen stays high after Full GC). Always-on GC logs (-Xlog:gc*) tell you which. For allocation pressure, use async-profiler in alloc mode or JFR to find the hotspot — common offenders are JSON parsing, String formatting, boxed primitives, and per-request collection allocations. For leaks, capture a heap dump (jcmd … GC.heap_dump) and analyse in Eclipse MAT. Tune G1 only after fixing the code; for sub-10ms pauses on big heaps consider ZGC/Shenandoah. In containers, set -XX:MaxRAMPercentage=75 and rely on JDK 11+ cgroup awareness.

How do you identify bottlenecks in a distributed system? must

A distributed system's slowest hop dictates user latency, regardless of how fast the rest is. Finding that hop requires distributed tracing + RED metrics per service + resource saturation per node. Without these three signals, you're guessing.

CORE IDEA Use distributed traces to find which span owns the latency, RED metrics (Rate / Errors / Duration) per service to localize the bad service, and the USE method (Utilization / Saturation / Errors) per resource (CPU, memory, disk, network, pool) to find the bottleneck inside that service.

Distributed tracing"Which hop in this request owns the latency?"Jaeger, Zipkin, Tempo, Datadog APM
USE method"Which resource in that service is saturated?"node_exporter, JVM metrics, DB metrics, pool gauges

4 The USE method per resource

For every resource ask three questions:

  • Utilization — what % of capacity is in use? (CPU 90%, pool 95%)
  • Saturation — how much work is queued? (run queue, pool waiters, thread pool queue depth)
  • Errors — error count on that resource (DB rejected connections, timeouts, OOM)

The bottleneck is the resource where utilization is high and saturation > 0 — that's where work is queueing.

5 Synthetic tests — proactive bottleneck discovery
  • Run a baseline load test (k6, Gatling, JMeter) and watch where the latency curve goes non-linear — that's the saturation point.
  • Chaos testing (toxiproxy, Chaos Mesh) — inject latency / packet loss to a downstream and observe blast radius.
  • Continuously run shadow traffic in staging mirroring production volume.
6 Common interview gotchas
  • Without distributed tracing, finding a bottleneck across services is detective work — invest early.
  • Average latency lies — always use p95/p99.
  • Tail latency (p99) is dominated by GC, lock contention, retries, cold-start — not the average code path.
  • "The DB is slow" is usually "one query is slow" — slice by query/endpoint, not aggregate.
  • Capacity issues hide as code issues at peak; reproducing requires production-like load.
  • One bottleneck removed exposes the next — performance work is iterative.
  • Connection / thread pools are silent bottlenecks until they saturate, then everything dies at once.
  • Don't optimize without measurement — fix the visible bottleneck, re-measure, repeat.

Interview one-liner: I find bottlenecks with three lenses: RED metrics per service (Rate / Errors / Duration) tell me which service is degraded; a distributed trace of one slow request tells me which hop owns the latency; USE (Utilization / Saturation / Errors) per resource tells me which CPU / pool / disk inside that service is the actual bottleneck. The most common bottlenecks are DB queries, DB connection pool exhaustion, downstream API slowness, GC pressure, thread pool exhaustion, Kafka consumer lag, and network saturation. Always work from p99/p95, not averages — and confirm the hypothesis with a controlled change before claiming victory.

How do you scale a high-traffic Spring Boot application? must

"Scale a Spring Boot app" splits into three orthogonal axes — vertical (more resources per pod), horizontal (more pods), and architectural (caching, async, read replicas, sharding). Real systems use all three, in that order, and each unlocks the next.

CORE IDEA Make the service stateless + well-tuned per pod, then scale horizontally with K8s HPA, then offload load with caching, async/Kafka, read replicas, and CDN. The DB is almost always the eventual bottleneck — design for it.

3 Layer 3 — Architectural scale
Caching
  • Local cache (Caffeine) for hot config / reference data.
  • Redis distributed cache for session, hot reads, computed results.
  • Cache aside with TTL; jitter TTL to avoid stampedes.
Async / Kafka
  • Move heavy work off the request path — emit event, return 202 Accepted.
  • Background workers process at their own pace.
  • Massive throughput unlock for write-heavy paths.
DB scale
  • Read replicas + smart routing (writes to primary, reads to replica).
  • Partitioning hot tables.
  • Sharding when single-node hits its limit.
  • Move append-only data to a log store (Kafka, ClickHouse).
CDN + edge
  • Cache static + cacheable API responses at the edge (CloudFront, Cloudflare).
  • Reduces origin RPS by 60–90% for read-heavy endpoints.
4 The DB is the eventual bottleneck

Stateless app pods scale linearly; the database doesn't. Plan for it:

  • Index every common query path; remove N+1.
  • Read replicas + routing.
  • Materialized views / search engine for heavy reads (Elasticsearch).
  • Connection pool max ≤ DB max_connections ÷ pod count + headroom.
  • Consider a connection pooler at the DB (PgBouncer) when pods × pool size exceeds DB capacity.
  • Partition / shard when one DB can't hold the working set.
5 Common interview gotchas
  • "Just add more pods" doesn't work if your DB is the bottleneck — you'll just exhaust connections faster.
  • Statefulness kills horizontal scale — session in app memory means sticky load balancing forever.
  • Cache stampede on startup of new pods can spike the origin — use singleflight / probabilistic early refresh.
  • Slow JVM startup (60+ sec) makes HPA reactive too late — use AOT/CDS to drop to 5–10 sec.
  • Misconfigured connection pool: huge pool per pod × many pods = DB connection storm.
  • Tomcat thread count needs to be sized per-endpoint behavior (CPU vs I/O) — same number for everything is wrong.
  • HPA on CPU alone misses I/O-bound workloads — also scale on RPS or queue depth.
  • Scale-down without graceful shutdown causes 5xx — fix shutdown before raising max replicas.
  • Don't forget egress capacity (NAT Gateway throughput) — silent bottleneck for outbound calls.

Interview one-liner: I scale a Spring Boot app in three layers: per-pod tuning (JVM heap %, G1/ZGC, Tomcat threads, HikariCP pool, async logging, AOT for fast startup), horizontal scale (stateless service + K8s HPA on CPU + RPS, plus Cluster Autoscaler / Karpenter for nodes), and architectural offloads (Redis cache, Kafka for async, DB read replicas / partitioning / sharding, CDN at the edge). The DB is almost always the eventual bottleneck — design for it with indexing, read routing, and pooler tuning. Make the service truly stateless (session in Redis or JWT), get graceful shutdown right, and pair HPA with deep readiness probes so deploys are 5xx-free.

How do you optimize a slow API? must

"This API is slow" is the most common performance ticket. The wrong instinct is to start adding caches; the right approach is to measure where the time goes, fix the dominant cost, then re-measure. Most slow APIs lose 80% of their time in 1–2 places — a missing index, an N+1, a synchronous downstream call, or a missing cache.

CORE IDEA Profile the slow path with distributed tracing, find the dominant cost (DB / downstream / serialization / GC), apply the appropriate fix (index, batch, cache, async, parallel fan-out), and re-measure. Optimizing without measurement is guessing.
1 Step 1 — Reproduce and trace
  • Capture a real slow request from production traces (APM).
  • Reproduce in a load test or staging with realistic data volume.
  • Use the trace to see how time splits between: in-app code, DB, downstream HTTP, cache, message broker.

The single most useful tool is the trace waterfall — it tells you where 80% of latency lives in 30 seconds.

4 Quick wins to look for first
  • One missing DB index (single biggest hit in most apps).
  • An N+1 on a list endpoint.
  • A sync HTTP call to a downstream that could be cached or parallelized.
  • Logging full payloads on the hot path.
  • JSON serialization of huge entities (project to DTO).
  • A misconfigured connection pool (too small or not warmed up).
  • A bug returning all rows when the client only needs the first 10 (missing pagination).
5 Common interview gotchas
  • "Add a cache" without measuring is the wrong first move — it can mask a leak or a query bug.
  • Optimizing the wrong thing (5 ms saved on a 10 ms code path while a 500 ms DB query sits unfixed).
  • Average latency lies — optimize p95/p99.
  • Caches without invalidation become correctness bugs — design TTL or write-through.
  • Parallel fan-out without bounding (no Semaphore / executor) → thread pool exhaustion.
  • Forgetting that adding async means the user can't see the result immediately — UX has to support it.
  • Don't keep optimizing once it's "good enough" — diminishing returns.
  • Always re-measure after a change — assumptions are wrong half the time.

Interview one-liner: I optimize a slow API by following the data, not intuition: capture a real slow request from distributed tracing, identify the dominant span (DB / downstream / serialization / GC), then apply the matching fix — add an index, fix N+1 with fetch joins, parallelize sequential downstream calls with CompletableFuture, add a cache for hot reads, move heavy work to async + Kafka, project to a smaller DTO. Re-measure after every change; never optimize without a baseline. Most slow APIs lose 80% of their time in one or two places, and the fix is usually small.

Investigating an API p99 latency spike — incident response playbook must

The pager fires: p99 on the checkout API just jumped from 200 ms to 5 seconds. The wrong first instinct is to SSH into a pod, run top, and start "investigating" — that wastes the first 10 minutes while customers time out. The right first instinct is to confirm scope and protect users: how big is the blast radius, was anything just shipped, and what is the fastest mitigation. Root cause comes after the bleed stops.

CORE IDEA Stabilize first, RCA later. Confirm blast radius → check dashboards / traces / recent deploys → if a release is correlated, rollback immediately; if not, isolate the bottleneck (DB, GC, threads, downstream, cache) → mitigate via rollback / scale-out / circuit breaker / cache / failover → then root-cause properly. Customers come before perfect understanding.

Step 1 — Confirm scope & blast radius (60 seconds of triage):

  • Is it one API or all APIs? — slice the latency dashboard by endpoint / route. A single slow endpoint usually = one query / one downstream; all endpoints slow = JVM-wide problem (GC, CPU, pool starvation) or shared dependency.
  • Is it one pod or all pods? — if 1/10 pods is bad, just kill it; the others absorb the traffic. If all pods are bad, it's the service or a shared backend.
  • Did it start after a deployment / config change / feature-flag flip? — overlay the deploy timeline on the latency graph. A sharp step right after a release ≈ guilty until proven innocent.
  • Is error rate also up, or only latency? — latency-only = saturation / slow path; latency + 5xx = something is breaking, not just slow.
  • One region / one customer / one tenant? — group by region, tenant, customer-ID. A "hot tenant" can crater shared infra without anything else changing.
  • Traffic volume vs baseline (same hour last week)? — a 5× traffic spike with the same code is a capacity problem, not a code problem.

Common pitfalls & interview gotchas:

  • Don't fix what you can't measure. Alert on RED metrics (Rate, Errors, Duration) per endpoint before you need them — flying blind during an incident is the real failure.
  • p99 vs p50 — they tell different stories. High p99 with a normal p50 usually means saturation (pool/queue/GC), not broken code. High p50 too means the hot path is genuinely slower.
  • Always compare to baseline — same hour last week, same day-of-week. "Latency is up" is meaningless without a reference.
  • Cascade failures — one slow downstream is enough to take out the whole service if you have no timeout / no circuit breaker. Always set both, always lower than the caller's timeout.
  • GC pause looks like a hang — threads "frozen" in unrelated code can just be paused for GC. Distinguish via GC logs / jvm.gc.pause; don't chase ghost lock contention.
  • The recent deploy is the #1 cause statistically — check the deploy timeline before you check anything else. Rollback is the cheapest mitigation in your toolbox.
  • Cold cache after deploy looks like the new code is slow — actually the cache just got wiped and the DB is now serving every request. Pre-warm or stagger deploys.
  • "Stabilize first, RCA later." Customers come before perfect understanding. A heroic deep-dive that takes 45 minutes while errors pour out is the wrong call — mitigate in 5, debug in 50.

The mantra is simple: stabilize first, RCA later — customers before curiosity.

What is the difference between a heap dump and a thread dump?

Two different snapshots of a running JVM.

Thread dump — current state of every thread: its name, state, stack trace, locks held, locks waited on. Cheap (milliseconds), no impact on the running app. Tools: jstack, kill -3, Actuator /threaddump. Use for concurrency issues: deadlocks, contention, hangs.

Heap dump — snapshot of every live object in heap memory. Large (= heap size, often GBs), takes seconds, briefly STW. Tools: jmap -dump, JFR, HeapDumpOnOutOfMemoryError. Use for memory issues: leaks, OOM, oversized caches.

Analyze with: Eclipse MAT, VisualVM, JProfiler, async-profiler (for live profiling). Always grab a heap dump before restarting an OOM'd container — restart loses the evidence.

What metrics do you alert on?

I follow the Four Golden Signals (Google SRE):

  • Latency — alert on p95/p99 above SLO for a sustained window. Average is misleading.
  • Traffic — alert on unusual changes (sudden drops can mean upstream issues; spikes can mean abuse).
  • Errors — error rate or count of 5xx, retries, circuit breaker opens.
  • Saturation — how full is the service? CPU/memory utilization, queue depth, thread pool busy %, DB pool utilization, Kafka consumer lag.

Plus business-specific: failed payments, churning users, abandoned cart rate.

Alert design rules: alert on symptoms, not causes (slow checkout matters; high CPU on box A doesn't). Make every alert actionable with a runbook link. Tune ruthlessly — every false page erodes trust.

What's a post-mortem and what makes a good one?

A post-mortem documents an incident — what happened, why, what changes to prevent recurrence. The principle is blameless: focus on systems, not individuals.

Sections I include:

  • Summary — one paragraph for execs.
  • Impact — users affected, duration, business impact in numbers.
  • Timeline — minute-by-minute, with detection and mitigation timestamps.
  • Root cause analysis — five whys, often with multiple contributing factors.
  • What went well — fast detection, good runbook, etc.
  • What went poorly — gaps in monitoring, slow rollback, unclear ownership.
  • Action items — specific tasks with owners and due dates. Track them like tickets.

The biggest mistake is action items that never get done. I treat them as P1 tickets and follow up. At Indus Net every post-mortem ends with 3–5 specific PRs created within a week.

How do you find a slow query in production?

Steps:

  1. Enable slow-query logging on the DB — Postgres auto_explain, MySQL slow_query_log. Pick a sensible threshold (e.g., 500 ms).
  2. Use APM tracing — Datadog, New Relic, AWS X-Ray all attribute DB time to specific SQL statements per endpoint. This is the fastest way to find the culprit.
  3. Check pg_stat_statements (Postgres) or MySQL Performance Schema — ranks queries by cumulative time, calls, and avg time. The top 5 are usually the ones to fix.
  4. EXPLAIN ANALYZE the suspect — look for sequential scans, missing indexes, bad join order.
  5. Look for N+1 in app logs (count queries per request).

Fixes: add index, rewrite query, batch, cache, denormalize. Usually one missing index resolves 80% of slow queries — that's been my experience repeatedly.

Graceful shutdown — why does it matter?

When a pod gets a SIGTERM (deploy, scale-in, eviction), Kubernetes gives it a grace period (default 30 s) to clean up before SIGKILL.

Without graceful shutdown:

  • In-flight HTTP requests get cut mid-response → 502s to users.
  • Open DB transactions abort (rollback or hang on the DB side).
  • Kafka consumer crashes mid-message → duplicate processing on rebalance.
  • Background jobs lose partial work.

Implementation in Spring Boot:

  • server.shutdown=graceful — Tomcat finishes in-flight requests before exiting.
  • spring.lifecycle.timeout-per-shutdown-phase=25s — must be < pod terminationGracePeriodSeconds.
  • Readiness probe should fail immediately on shutdown so the load balancer stops sending new traffic.
  • @PreDestroy hooks to close Kafka consumers, drain executors, flush metrics.
  • Add a preStop hook on the pod with a small sleep to let endpoints propagate before SIGTERM lands.

Done right, rolling deploys are invisible to users — no 5xx blip in the dashboards.

How do you perform root cause analysis?

Root cause analysis (RCA) identifies the underlying cause of an incident through systematic elimination: timeline reconstruction, log analysis, and 5-Why technique.

Steps

Build timeline: when did it start, what changed (deployment, data, config), who reported first symptom.

5-Why: Why did service fail? → DB connection pool exhausted. Why? → Slow query consuming connections. Why? → Missing index after data migration. Why? → Index not included in migration script. Fix: add index, update migration process.

Documentation

RCA report: incident description, timeline, root cause, immediate fix, preventive measures, owner, due date.

Now coming to conclusion.

Root cause is rarely the first thing you find — dig deeper with 5-Why until you reach a process or design gap.

What is RCA document?

An RCA (Root Cause Analysis) document records the incident timeline, root cause, immediate resolution, and preventive actions to avoid recurrence.

Sections

Executive summary: what happened, impact, resolution time. Timeline: chronological sequence of events.

Root cause: the fundamental reason (not just the symptom). Contributing factors: conditions that allowed it.

Corrective actions: immediate fix applied. Preventive measures: long-term fixes with owner and due date.

Banking standard

Mandatory for Sev1 incidents; submitted within 24-48 hours to management and IT risk team.

Reviewed in CAB (Change Advisory Board) to update change process if applicable.

Now coming to conclusion.

RCA prevents recurrence — without preventive actions, you will handle the same incident again.

How do you check database issue?

Database issues are diagnosed using Oracle alert log, V$SESSION, V$SQL, AWR/ASH reports, and specific queries for lock waits, long-running queries, and blocking sessions.

Key queries

SELECT sid, serial#, status, sql_id, wait_class, event, seconds_in_wait FROM V$SESSION WHERE status='ACTIVE' — active sessions and waits.

SELECT * FROM V$LOCK WHERE block=1 — find blocking sessions holding locks.

Oracle alert log: $ORACLE_BASE/diag/rdbms/.../trace/alert_*.log — ORA- errors, redo log issues.

AWR/ASH

AWR report: top SQL by elapsed time, buffer gets; identify regressions after code changes.

ASH (Active Session History): retroactively analyze what sessions were doing at the time of incident.

Now coming to conclusion.

V$SESSION + V$LOCK combination is the fastest way to identify active blocking sessions in production.

How do you identify API timeout?

API timeouts are identified by correlating application logs (timeout exceptions), API gateway metrics (response time > threshold), and downstream service health checks.

Identification

Application log: java.net.SocketTimeoutException or Read timed out at the time of incident.

API gateway (Nginx/Kong) access log: upstream response time column shows actual backend response time.

Zipkin/Jaeger trace: identify which span (service hop) consumed the most time.

Root causes

Slow DB query in the called service; DB lock wait; downstream external API (payment gateway) slow.

Connection pool exhaustion: API waits for connection, total time exceeds read timeout.

Now coming to conclusion.

Always set explicit timeouts on both sides: caller timeout prevents blocked threads; server timeout prevents long-running queries.

How do you handle high CPU issue?

High CPU on app server is diagnosed by correlating OS thread CPU usage with Java thread dumps to identify the hot stack — then fixing the underlying cause.

Diagnosis

top -H -p <pid>: find OS thread with highest CPU. Convert tid to hex. Match to jstack <pid> thread by nid.

Examine RUNNABLE thread's stack trace — look for tight loops, regex patterns, or GC-intensive code.

Common fixes

Excessive GC (full GC every few seconds): increase -Xmx, switch to G1GC, investigate memory leak.

How do you handle stuck thread issue?

Stuck thread issues are diagnosed by thread dump analysis to identify the blocking call, then fixing the underlying slow operation (DB query, external API, lock).

Diagnosis

WebLogic alert: 'ExecuteThread stuck for X seconds'. Take thread dump via Admin Console or kill -3.

Examine BLOCKED/WAITING thread: is it waiting on DB connection, a lock, or an external API call?

Fixes

DB connection pool exhaustion: increase MaxCapacity, add connection timeout, fix slow queries consuming connections.

External API: set read timeout so thread is released instead of waiting indefinitely.

Lock contention: identify blocking query via V$LOCK, kill blocking session, investigate locking pattern.

Now coming to conclusion.

Stuck threads cascade — 10 stuck threads can fill the thread pool, making the entire server unresponsive.

How do you handle DB deadlock?

DB deadlocks (ORA-00060) are handled by catching the exception, rolling back, retrying with exponential backoff, and preventing recurrence through consistent lock ordering.

Immediate handling

Oracle auto-detects and resolves deadlock by rolling back one victim's statement.

Application: catch ORA-00060, ROLLBACK the transaction, wait 1-2 seconds, retry up to 3 times.

Prevention

Always acquire locks in consistent order: lock account with lower ID first in fund transfer.

Use SELECT ... FOR UPDATE NOWAIT or SKIP LOCKED to avoid indefinite waiting.

Keep transactions short — long transactions hold locks longer, increasing deadlock probability.

Now coming to conclusion.

Prevention is better than handling — design lock ordering into the architecture, not as an afterthought.

How do you handle failed batch job?

A failed batch job is handled by identifying the failure step from logs, resolving the root cause (data issue, code bug, resource constraint), and re-running from the failure point.

Steps

Check batch job log table (DBMS_SCHEDULER job run details or custom log): which step failed, what error.

Fix: data issue (update bad record), code bug (hotfix + redeploy), resource (extend tablespace, free memory).

Re-run: restart from the failed step — never re-run already-completed steps to avoid duplicate processing.

Banking design

Batch must be restartable: track processed records in job_progress table; resume from last_processed_id.

Use SAVEPOINT per account batch: failed account rolled back, others committed — partial completion possible.

A batch job that cannot be safely restarted from failure point is a production support nightmare — design restartability in.

How do you handle message queue backlog?

Queue backlog is handled by identifying the consumer bottleneck (slow processing, consumer down, error loop), fixing it, and scaling consumers to drain the backlog.

Diagnosis

Check consumer service: is it running? Any exceptions in consumer log? How many messages/second is it processing?

Check DLQ: high DLQ count suggests messages failing repeatedly — fix the processing error first.

Resolution

Restart consumer if stuck thread or connection issue. Scale up consumer instances if processing is the bottleneck.

For large backlog: temporarily increase consumer thread pool; restore normal after drain.

Banking

Payment queue backlog: business must be informed — pending payments have SLA; breach triggers regulatory reporting.

Now coming to conclusion.

Monitor queue depth with alerting — backlog growth is the early warning sign before SLA breach.

How do you communicate with business during outage?

During an outage, communicate clearly and frequently: initial notification with impact scope, regular updates every 30 minutes, and final resolution notification with ETA for normalcy.

Communication

Initial (within 15 min of Sev1): 'Core banking balance inquiry is unavailable since 10:15 AM. Team is investigating. Next update in 30 minutes.'

Update every 30 min: 'Root cause identified as DB connection pool exhaustion. Fix being applied. ETA: 30 minutes.'

Resolution: 'Service restored at 11:45 AM. Root cause: missing index. No data loss. Detailed RCA to follow.'

Channels

Email to business heads and operations leads; WhatsApp/Teams for real-time updates; bridge call for Sev1.

Over-communicate during outages — silence breeds panic; clear updates with ETA build trust.

How do you prepare incident report?

An incident report documents: what happened, when, impact, timeline of actions, root cause, resolution, and preventive measures — filed within 24 hours for Sev1.

Structure

Incident summary: what failed, when detected, business impact (# customers affected, transaction volume).

Timeline: minute-by-minute log of detection, escalation, diagnosis steps, resolution.

Root cause and contributing factors. Resolution applied. Preventive actions with owners and due dates.

Distribution

Shared with IT management, business stakeholders, IT risk team, and CAB for change management review.

Now coming to conclusion.

A well-written incident report turns a bad outage into an organizational learning opportunity.

How do you prevent repeated issues?

Repeated issues are prevented through RCA-driven preventive actions, automated monitoring/alerting, improved testing, and process changes documented and tracked to completion.

Preventive measures

Automated alert: if the root cause can be monitored (queue depth, slow query, disk space), set up alert to catch it before impact.

Improved testing: add the failure scenario to SIT/performance test suite to catch regression.

Code fix: address the underlying design flaw (add timeout, add index, implement idempotency).

Process

Track all preventive actions in Jira with due dates and owners; review in weekly ops meeting.

Blameless post-mortem: focus on process gaps, not individuals — encourages honest reporting.

Now coming to conclusion.

Repeated incidents indicate incomplete RCA — drill deeper until you find a process or design gap that can be permanently fixed.

What is monitoring and alerting?

Monitoring continuously collects metrics (CPU, memory, response time, error rate); alerting notifies the team when metrics breach defined thresholds.

Monitoring stack

Infrastructure: Nagios, Zabbix, Datadog for CPU, memory, disk, network. Application: Spring Actuator + Prometheus + Grafana.

Database: Oracle Enterprise Manager (OEM) monitors tablespace, session count, long-running queries.

Key banking alerts

App: error rate > 1%, p95 > 1s, JVM heap > 80%, DLQ message count > 0.

DB: tablespace > 85% full, active sessions > 80% of max, ORA-600/ORA-700 in alert log.

Batch: job not started by 22:05, job not completed by 01:00 — missed SLA alert.

Now coming to conclusion.

Monitoring without alerting is useless — define actionable alert thresholds for every critical banking metric.

What is SLA?

An SLA (Service Level Agreement) is a formal commitment on service availability, response time, and incident resolution — with penalties for non-compliance.

Types

Availability SLA: 99.9% uptime = max 8.7 hours downtime/year. 99.99% = max 52 minutes/year.

Performance SLA: API p95 < 500ms. Incident resolution SLA: Sev1 restored within 4 hours.

Banking SLAs

NEFT/RTGS: transactions must settle within prescribed RBI time windows (RTGS: same day, NEFT: hourly batches).

Internet banking API: 99.95% availability; 200ms p95 for balance inquiry.

Now coming to conclusion.

SLA breach in banking has regulatory and financial consequences — treat SLA thresholds as hard constraints in design.

What is escalation matrix?

An escalation matrix defines who to contact at each severity level and at each time threshold — ensuring the right people are engaged quickly during incidents.

Structure

Sev1, 0-15 min: L1 support team lead. 15-30 min: application manager + DBA. 30-60 min: IT head + business head.

Sev2, 0-1 hour: L2 support. 1-4 hours: application manager. 4+ hours: IT head.

Banking

Core banking down: escalate to CTO and COO within 30 minutes — regulatory reporting may be required.

Payment system down: RBI must be notified if RTGS/NEFT is impacted beyond defined duration.

Now coming to conclusion.

A clear escalation matrix prevents the #1 support failure: not getting the right people involved fast enough.
