What is Docker? must

Docker is a containerization platform that packages an application along with its dependencies, libraries, runtime, and configuration into a single lightweight unit called a container. The container then runs identically on any machine that has Docker — dev laptop, CI server, staging, production — solving the infamous "works on my machine" problem.

Core Idea
What A platform to package apps + dependencies into containers — isolated, lightweight runtime units.
Why "Build once, run anywhere" — same container behaves identically in dev, test, and prod.
How Containers share the host OS kernel (Linux namespaces + cgroups), so they're faster & lighter than VMs.
1 Why we need Docker — "works on my machine" 💥
Before Docker
  • Different OS versions on dev / staging / prod
  • Different library / runtime versions (Java 8 vs 17)
  • Missing system tools, broken PATH
  • Manual setup docs that go stale
  • Onboarding a new dev = full day of brew install
With Docker
  • App + everything it needs in one image
  • Identical behavior everywhere
  • Onboard a new dev → docker run, 30 seconds
  • Deploy & rollback are atomic (just swap images)
  • Same artifact promoted dev → staging → prod
2 What is a Container?

A container is an isolated, lightweight runtime that contains everything an app needs to run:

  • Application code & binary
  • Language runtime (JVM, Node, Python interpreter…)
  • Libraries & dependencies
  • System tools (curl, bash, ca-certificates)
  • Configuration (env vars, config files)

Containers share the host OS kernel (via Linux namespaces & cgroups) — that's why they're so cheap. They're not mini-VMs.

4 Docker vs Virtual Machine — quick view
Docker Container
  • Weight: ~tens of MB
  • Startup: milliseconds
  • OS: shares host kernel
  • Memory: low (per-process)
  • Density: 100s on one host
Virtual Machine
  • Weight: GBs (full OS image)
  • Startup: tens of seconds to minutes
  • OS: full guest OS each
  • Memory: hundreds of MB minimum
  • Density: ~10s per host

Interview-friendly answer: Docker is a containerization platform used to package an application along with its dependencies, libraries, and runtime into a lightweight unit called a container. This ensures the application runs consistently across dev, test, and production — solving the classic "works on my machine" problem. Containers share the host OS kernel (via Linux namespaces & cgroups), so they're much lighter and faster than virtual machines — milliseconds to start, tens of MB in size. Docker (Container) vs Virtual Machine must

Both isolate workloads, but at very different layers of the stack — that single difference explains everything about their size, speed, and density.

Core Difference
VM Runs a full guest OS on a hypervisor — strong isolation, heavy.
Container Shares the host kernel — isolated via namespaces + cgroups; lightweight.
1 Architecture
VM
  • Hardware → Hypervisor (KVM, VMware, Hyper-V) → Guest OS → App.
  • Each VM bundles its own kernel.
Container
  • Hardware → Host OS → Container runtime → App.
  • Uses Linux namespaces (PID, network, mount, user) and cgroups (CPU, memory limits).
2 Size & Start Time
VM
  • Images: GBs (full OS).
  • Boot: seconds to minutes.
  • Density: tens per host.
Container
  • Images: MBs to a few hundred MB.
  • Start: milliseconds.
  • Density: hundreds per host.
3 Isolation & Security
VM
  • Strong hardware-level isolation.
  • Different OS family per VM (Windows + Linux on one host).
Container
  • Shared kernel — isolation weaker than VMs.
  • All containers on a Linux host must use the Linux kernel.
  • For untrusted code use additional sandboxing (gVisor, Kata, Firecracker).
4 Use Case
VM
  • Multi-tenant infrastructure where isolation matters.
  • Running different OSes on the same host.
  • Legacy workloads tied to specific kernel versions.
Container
  • Microservices, dev/prod parity, CI runners.
  • Kubernetes, ECS, Cloud Run — modern orchestrators.
  • Fast scaling and rolling deploys.
In practice: the two compose well — cloud providers run containers on top of VMs (EKS nodes are EC2 instances). Docker is the most popular container runtime/image format/build tool; Kubernetes works with any OCI-compliant runtime (containerd, CRI-O).
Dockerfile best practices for a Java app

Things I always do:

  • Multi-stage build — build with the JDK image, run with a smaller JRE base. Final image is much smaller.
  • Use specific base image tags — never :latest. Eclipse Temurin or distroless for security.
  • Layer caching — copy pom.xml and run mvn dependency:go-offline before copying source. Code changes don't bust the deps cache.
  • Non-root user — USER 1001 for security.
  • Healthcheck hitting /actuator/health.
  • .dockerignore to exclude target/, .git, IDE files.
  • Pin JVM flags — heap %, GC settings.
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY pom.xml ./
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package -DskipTests

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /app/target/*.jar app.jar
USER 1001
EXPOSE 8080
ENTRYPOINT ["java","-jar","/app/app.jar"]
Docker image layers and caching

A Docker image is built as a stack of layers — each instruction in a Dockerfile (COPY, RUN, ADD) creates an immutable layer. Layers are content-addressed and cached.

If a layer changes, all layers after it are rebuilt. So order matters: put the least frequently changing things first.

Layered correctly, a small source change rebuilds in seconds because Maven dependencies, base image, and OS packages are all cached. Done wrong, every change downloads everything again.

Other tips:

  • Combine RUN commands with && and clean up apt caches in the same layer — uncleaned cache stays in the layer forever.
  • Multi-stage builds let you discard build-time layers entirely.
  • BuildKit (Docker 23+) has parallel layer building and cache mounts (--mount=type=cache) for Maven/Gradle/npm dirs.
What is Kubernetes (K8s)? must

Kubernetes (often shortened to K8s — "k" + 8 letters + "s") is an open-source container orchestration platform used to automate the deployment, scaling, management, and monitoring of containerized applications. In practice it's the production-grade way to run Docker (or any OCI-compliant container) at scale.

Core Idea
What Open-source container orchestrator originally built by Google (from "Borg"), now run by the CNCF.
Why Running 1 container is easy. Running thousands across many machines — with health checks, scaling, rolling updates — needs orchestration.
How You declare desired state in YAML; the control plane continuously reconciles reality with that state.
1 Why we need Kubernetes — without vs with
Without K8s
  • Manual docker run on every server
  • A container crashes → it stays dead until someone notices
  • Traffic spike → scaling means waking up the on-call
  • Deploying = SSH + restart, hope for the best
  • Networking, secrets, configs scattered everywhere
With K8s
  • Declare desired state in YAML — K8s makes it real
  • Self-healing — crashed pods are restarted automatically
  • Auto-scaling — HPA spins up replicas on CPU / RPS
  • Rolling updates — zero-downtime deploys + 1-command rollback
  • Built-in service discovery, load balancing, secret management
2 What K8s actually does — its 6 superpowers
FeatureWhat it does
Container Orchestration Schedules pods onto nodes with enough CPU/memory; respects affinities, taints, tolerations.
Self-Healing If a container crashes or a node dies, K8s recreates the pod elsewhere — automatically.
Auto-Scaling HPA scales pod count on CPU / custom metrics; Cluster Autoscaler adds/removes nodes; VPA right-sizes per pod.
Load Balancing Built-in Service objects distribute traffic across all pods of a deployment.
Rolling Updates & Rollbacks Replace pods one batch at a time, with health checks; kubectl rollout undo reverts in seconds.
Service Discovery Built-in DNS — any pod can reach orders-service.default.svc.cluster.local without knowing IPs.
Config & Secret Mgmt ConfigMap & Secret objects inject env vars or files into pods — no rebuilds.
Storage Abstraction PersistentVolume + PVC abstract EBS, NFS, Ceph, etc. for stateful workloads.

5 Example — a minimal Deployment + Service

Declare 3 replicas of a Spring Boot app, with a service to load-balance traffic:

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-app
spec:
  replicas: 3                          # K8s keeps 3 pods running
  selector:
    matchLabels: { app: orders }
  template:
    metadata:
      labels: { app: orders }
    spec:
      containers:
      - name: orders
        image: myrepo/orders:1.0       # the Docker image
        ports:
        - containerPort: 8080
        readinessProbe:                # only route traffic when healthy
          httpGet: { path: /health, port: 8080 }
---
# service.yaml
apiVersion: v1
kind: Service
metadata:
  name: orders-svc
spec:
  selector: { app: orders }
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP                      # internal LB; use LoadBalancer for external

Then apply with one command:

kubectl apply -f deployment.yaml -f service.yaml
kubectl get pods                                # see all 3 pods running
kubectl scale deployment/orders-app --replicas=10
kubectl rollout status deployment/orders-app    # watch a rolling update
6 Docker vs Kubernetes — different roles
Docker
  • What: container runtime + image builder
  • Scope: single machine
  • Job: create & run containers
  • Builds the image, runs one instance
Kubernetes
  • What: container orchestrator
  • Scope: entire cluster (many machines)
  • Job: schedule, scale, heal containers at scale
  • Manages thousands of instances across many nodes

In short: Docker creates and runs containers; Kubernetes manages those containers in production.

Interview-ready answer: Kubernetes (K8s) is an open-source container orchestration platform that automates the deployment, scaling, management, and monitoring of containerized applications — most commonly Docker containers. You declare the desired state in YAML (e.g. "run 3 replicas of this app, expose port 8080, restart on failure") and the K8s control plane continuously reconciles reality with that state. It provides auto-scaling, self-healing, rolling updates, service discovery, load balancing, and config / secret management out of the box. Docker creates and runs individual containers on a single machine; Kubernetes manages thousands of containers across a cluster of many machines. It's the cloud-native standard — multi-cloud portable, with managed offerings like AWS EKS, Google GKE, and Azure AKS.
Pod vs Deployment vs Service vs Ingress

The core K8s objects you touch daily:

  • Pod — smallest deployable unit, one or more co-located containers sharing network and storage. You rarely create pods directly.
  • ReplicaSet — keeps N pods running. Created by Deployment.
  • Deployment — desired state for a stateless app: image, replicas, rolling update strategy. Manages ReplicaSets to safely transition versions.
  • StatefulSet — for stateful apps (DBs, Kafka). Stable network identity, ordered scaling, persistent storage per pod.
  • Service — stable virtual IP + DNS that load-balances to a set of pods. Types: ClusterIP (internal), NodePort, LoadBalancer (cloud LB), Headless.
  • Ingress — HTTP/HTTPS routing rules from outside the cluster to Services. Implemented by an ingress controller (Nginx, AWS ALB, Traefik).
  • Job/CronJob — one-shot or scheduled batch work.

Typical service: Deployment + Service + Ingress + ConfigMap + Secret + HPA.

Liveness, readiness, startup probes — differences

(Also covered in Spring Boot.) Three K8s probes:

  • Liveness — is the container alive? Failure → K8s restarts the pod. Should check only fatal in-process state. Wrong checks cause restart loops.
  • Readiness — is it ready to serve traffic? Failure → K8s removes from Service endpoints. Should check downstream dependencies. Used to gate traffic during startup or temporary unhealthiness.
  • Startup — slow-start apps. Once it passes, liveness/readiness take over. Lets you set generous startup time without making liveness too lax later.

For Java services I use /actuator/health/liveness and /health/readiness. Tune initialDelaySeconds, periodSeconds, failureThreshold based on real startup time. Misconfiguring probes is one of the top causes of production incidents — I always check them in PRs.

Resource requests vs limits

Every container can declare requests (minimum guaranteed CPU/memory) and limits (maximum allowed).

  • CPU request — used by the scheduler to find a node with capacity. Used for fair sharing under contention.
  • CPU limit — throttled if exceeded. Aggressive throttling is often the root cause of "slow service" mystery.
  • Memory request — guaranteed; used by scheduler.
  • Memory limit — exceeding it → OOMKilled by the kernel. Hard kill.

For Java: heap should be well under the memory limit (leave room for metaspace, threads, native memory). I set -XX:MaxRAMPercentage=70 with a slightly higher container memory limit so JVM has headroom.

Quality of Service classes: Guaranteed (request==limit), Burstable, BestEffort. Production services should be Guaranteed or Burstable; BestEffort gets evicted first.

ConfigMap vs Secret — what's the difference?

Both store key-value data and can be mounted as env vars or files in pods.

ConfigMap is for non-sensitive config (feature flags, URLs, log levels). Stored as plain text in etcd.

Secret is for sensitive data (DB passwords, API keys). Stored base64-encoded in etcd — which is not encryption. The security comes from RBAC (who can read secrets) and from enabling encryption-at-rest for etcd.

In production I use external secrets stores:

  • AWS Secrets Manager / Parameter Store + External Secrets Operator (ESO) to sync into K8s Secrets.
  • HashiCorp Vault + Vault Agent injector.
  • Sealed Secrets if you want secrets in git encrypted with a cluster public key.

Never commit raw secrets to git; never log secret env vars. Rotate regularly.

Horizontal Pod Autoscaler (HPA)

HPA automatically scales pod replicas based on metrics. Typical metrics:

  • CPU utilization — most common. Target ~60–70%.
  • Memory utilization — for memory-bound apps.
  • Custom metrics via Prometheus Adapter — e.g., requests-per-second, Kafka consumer lag, queue depth. This is what really matters in production.
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  scaleTargetRef: { kind: Deployment, name: my-app }
  minReplicas: 3
  maxReplicas: 30
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }

Sizing: minReplicas should survive a single-AZ outage. Tune behavior stabilization windows to avoid flapping. Pair with cluster autoscaler so adding pods triggers node growth. At Indus Net I scaled the resume-parsing service on Kafka lag rather than CPU — more responsive to actual demand.

How does service discovery work in K8s?

K8s ships service discovery out of the box.

When you create a Service, K8s assigns it a stable cluster IP and a DNS name: my-service.my-namespace.svc.cluster.local (or just my-service within the same namespace). CoreDNS resolves these to the cluster IP.

Behind the cluster IP, kube-proxy programs iptables (or IPVS) rules that load-balance to the actual pod IPs. Pod IPs change on every restart, but the Service IP and DNS are stable.

For headless services (clusterIP: None), DNS returns all pod IPs directly — useful for clients that want to do their own LB (e.g., gRPC client-side balancing, StatefulSet members talking to each other).

Modern setups add a service mesh (Istio, Linkerd) on top for mTLS, traffic splitting, retries, and observability — sidecar proxies (Envoy) handle service-to-service calls.

Rolling updates and rollbacks in K8s

K8s Deployments handle rolling updates declaratively. You update the pod template (e.g., new image tag); K8s creates a new ReplicaSet and gradually shifts pods from old to new.

Knobs:

  • maxSurge — how many extra pods can run during update (default 25%).
  • maxUnavailable — how many old pods can be down (default 25%).
  • Readiness probe — new pods must pass before old ones are killed.

Rollback is simple: kubectl rollout undo deployment/my-app. K8s keeps ReplicaSet history (configurable revisionHistoryLimit).

For higher-risk changes I use Argo Rollouts or Flagger on top — they add canary, blue/green, and automated metric-based rollback. At Indus Net we use Argo Rollouts to canary 5% → 25% → 100% over 10 minutes, watching error rate and p99 latency, and auto-rolling back if either spikes.

How do you debug a failing pod?

My triage sequence:

  1. kubectl get pods -n ns — what's the status? Pending, ImagePullBackOff, CrashLoopBackOff, Error?
  2. kubectl describe pod <name> — events at the bottom usually tell you exactly what's wrong (scheduling failure, probe failure, OOMKilled, image issue).
  3. kubectl logs <name> --previous — logs from the previous container instance (essential for CrashLoopBackOff).
  4. kubectl logs <name> -c <container> — multi-container pods need the container name.
  5. kubectl exec -it <pod> -- sh — exec into the pod for live inspection (curl localhost, check files).
  6. kubectl get events --sort-by=.lastTimestamp -n ns — broader cluster events.
  7. kubectl top pod — current resource usage.
  8. For "service unreachable": check Service endpoints (kubectl get endpoints) — empty means no pods are Ready.

Common culprits: OOM (raise limit or fix leak), probe misconfigured, missing config, image tag typo, network policy blocking traffic.

Helm — what is it and why?

Plain YAML manifests don't scale: same Deployment + Service + Ingress + ConfigMap repeated across services and environments, with small differences. Helm is the package manager for Kubernetes — templates YAML with Go templating, packaging the result as a chart.

A chart has:

  • Templates — parameterized YAML.
  • values.yaml — defaults, overridden per environment with values-prod.yaml, values-staging.yaml.
  • Chart.yaml — metadata, versioning.

Run helm install / upgrade / rollback — Helm tracks releases and supports rollback.

I use Helm for: (a) installing off-the-shelf software (Prometheus, ingress-nginx, Argo CD) — the community charts are mature; (b) packaging our own services. For tighter control / kustomize-style, some teams prefer Kustomize. Both are fine; pick one and be consistent.
