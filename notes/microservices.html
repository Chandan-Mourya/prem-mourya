Monolith vs microservices — when to choose? must

A monolith ships as one deployable unit — one DB, one repo, one process. Microservices split functionality into independently deployable services, usually with their own DB.

Monoliths win when: team is small (<15 engineers), product is still finding fit, transactional boundaries are unclear. They're fast to ship. Most failed microservices migrations started in this phase too early.

Microservices win when: team scales beyond a single squad, parts of the system have very different scaling/release profiles, organizational boundaries demand independent deploys, or specific subsystems need different tech (Python ML vs Java web).

My take after 5 years: start with a modular monolith, extract services only when monolith pain is real — slow deploys, team-blocking PRs, distinct scaling needs. Premature split = distributed monolith, the worst of both worlds.

What is a "distributed monolith" and how to avoid it?

A distributed monolith is microservices in name only — services tightly coupled by synchronous calls, shared databases, shared deployment timing, or shared models. Symptoms:

  • Deploying service A requires also deploying service B.
  • A typical user request touches 8 services synchronously.
  • You can't change a field without coordinating across teams.
  • One service's outage takes down "unrelated" features.

You get all the complexity of distributed systems with none of the independence benefits.

Avoidance: per-service database, API contracts via OpenAPI/proto with backward compatibility, async events where possible (Kafka), tolerant readers, careful Domain-Driven Design with explicit bounded contexts. At Indus Net I pushed back on splitting CRUD-heavy modules — they stayed in one service and we only carved out async/LLM workloads.

How do microservices communicate?

Two broad categories:

Synchronous — caller waits for a response.

  • REST over HTTP — most common; easy debugging, language-agnostic.
  • gRPC — typed (protobuf), faster, streaming. Good for internal service-to-service.
  • GraphQL — single endpoint, client-driven schema; good for BFFs.

Asynchronous — caller doesn't wait.

  • Message queues (RabbitMQ, SQS) — point-to-point work distribution.
  • Event streams (Kafka) — pub/sub, replayable.

Best practice: sync where the caller really needs the result, async for everything else — state changes that other services react to. Async decouples deployment timing and isolates failures. On Punctuations.ai, resume upload returns immediately, then Kafka triggers parsing, indexing, and notifications independently.

Service discovery — how do services find each other? hot

Services in a microservice architecture have dynamic IPs (containers come and go). Service discovery lets clients find healthy instances by name.

Two patterns:

  • Client-side discovery — clients query a registry (Eureka, Consul) and pick an instance. Spring Cloud LoadBalancer does this. Smart but requires client logic.
  • Server-side discovery — a load balancer / proxy in front of each service handles routing. Kubernetes Services + kube-proxy work this way; AWS ALB + target groups too. Dumb client, smart infrastructure.

In Kubernetes — which is where most of my services run — discovery is essentially built in: my-service.my-namespace.svc.cluster.local resolves via CoreDNS, and the Service object load-balances over Pod IPs. No Eureka needed. For external traffic, an Ingress + LB handle it.

API Gateway — what does it do?

An API Gateway is a single entry point in front of your services. Responsibilities:

  • Routing — map paths/hosts to backend services.
  • Authentication — verify tokens before requests reach services.
  • Rate limiting & throttling.
  • Request/response transformation — versioning, header rewriting.
  • Aggregation — combine multiple service calls into one client response (BFF pattern).
  • SSL termination, logging, metrics, CORS.

Tools I've used: Spring Cloud Gateway (Java/Project Reactor), Kong, AWS API Gateway, Nginx, Envoy (often via Istio in K8s).

Pitfall: don't put business logic in the gateway. It should be thin. Heavy aggregation belongs in a BFF service. At Indus Net we use Spring Cloud Gateway for auth + routing; service-to-service calls inside the cluster skip the gateway.

What is the Saga pattern? hot

Distributed transactions across microservices are hard — 2PC is slow and brittle. The Saga pattern is the standard alternative: model the transaction as a sequence of local transactions in each service, with compensating actions if a step fails.

Example — booking flow: reserveSeat → chargeCard → confirmBooking. If chargeCard fails, run cancelReservation compensation.

Two coordination styles:

  • Choreography — services react to events from each other; no central coordinator. Loose coupling, but flow is implicit and hard to trace.
  • Orchestration — a coordinator service explicitly drives the saga. Easier to observe and modify. Tools: Camunda, Temporal, AWS Step Functions.

I lean orchestration for non-trivial flows — observability and recoverability are worth the central service. Always ensure all steps and compensations are idempotent.

Eventual consistency — explain it

Eventual consistency means: if updates stop, all replicas will eventually converge to the same value — but not at the exact same instant. The opposite of strong consistency, which guarantees every read sees the latest write.

It's the consistency model most distributed systems choose because CAP forces a tradeoff during partitions, and pure strong consistency limits scale and availability.

Practical implications:

  • A user might update their profile and see the old value on the next page load (read-your-writes problem) — fix by routing to primary for that user briefly.
  • UI design needs to communicate "processing" states.
  • Background jobs eventually reconcile — for instance, a CDC pipeline updating Elasticsearch from MongoDB takes a few hundred milliseconds.

It's a design choice, not a bug. Most user-facing features tolerate it gracefully if you build for it.

CAP theorem — and PACELC

CAP theorem: in a distributed system you can have at most two of Consistency, Availability, Partition tolerance. Partitions are inevitable in real networks, so the real choice is between CP (refuse requests during partition for consistency) and AP (serve possibly-stale data for availability).

  • CP — HBase, MongoDB (with majority writes), Zookeeper, etcd.
  • AP — Cassandra, DynamoDB, Couchbase by default.

PACELC extends this: even when there's no Partition, you choose between Latency and Consistency. A "PA/EL" system favors availability during partition and low latency otherwise; "PC/EC" favors consistency in both cases.

This is useful framing in design interviews — interviewers love when you frame a system's tradeoffs as PACELC rather than just CAP.

How do you handle distributed transactions?

Three practical patterns:

  • Saga (see earlier) — sequence of local transactions with compensations. Best for multi-service workflows.
  • Outbox pattern — write the business state and an outbox row in the same local DB transaction; a separate process publishes outbox rows to Kafka. Guarantees "if the DB says it happened, the event will be published."
  • Transactional messaging — Kafka transactions (within the same producer) for exactly-once semantics across topics; useful when you produce to multiple topics atomically.

What I don't use: 2PC across microservices — it's slow, fragile, and most modern DBs/queues don't support XA well together. The combination of outbox + idempotent consumers + saga covers nearly every real-world distributed-transaction need.

Inter-service communication failures — how to handle?

The fundamental rule: networks fail, downstreams slow down — your service must remain healthy when its dependencies aren't.

My toolkit:

  • Timeouts on every outbound call — never block forever. Set them generous-but-realistic.
  • Retries with exponential backoff + jitter for transient errors only. Make calls idempotent.
  • Circuit breaker — fail fast when a downstream is unhealthy.
  • Bulkheads — separate thread pools / connection pools per downstream so one slow dependency doesn't starve the rest.
  • Fallbacks — return cached / degraded responses where possible.
  • Async over sync — if the caller doesn't need the result immediately, send an event instead.

All of this is Resilience4j in Spring Boot. Combined with timeouts at the HTTP client level, this stack has saved my services through multiple downstream outages.

Database per service — really?

Yes — it's the most important rule that makes microservices actually independent. Each service owns its data and is the only one that writes to its database. Other services consume via APIs or events.

Why it matters: shared databases create the worst kind of coupling — schema changes block all consumers, performance issues in one service affect everyone, transactional boundaries blur. A "microservice" reading from another service's tables is a distributed monolith in disguise.

Costs you accept:

  • Cross-service queries become API calls or async data replication.
  • Reporting/analytics need a separate data warehouse (CDC → Snowflake/BigQuery).
  • Distributed transactions need Saga or Outbox.

The tradeoff is worth it. At Indus Net we have a single Mongo cluster, but each service uses its own database (logical separation) — close enough to db-per-service for a small team.

Centralized configuration — Spring Cloud Config / Consul

Hard-coding config in YAML doesn't scale across many services × multiple environments. Centralized config stores all config in one place — services pull on startup (and optionally refresh at runtime).

Options:

  • Spring Cloud Config Server — git-backed, integrates with Spring Boot.
  • Consul KV or etcd — distributed KV stores.
  • AWS Parameter Store / Secrets Manager / HashiCorp Vault for secrets.
  • Kubernetes ConfigMaps + Secrets — what I use most now; mounted into pods.

Runtime refresh via @RefreshScope + /actuator/refresh in Spring Cloud — useful for toggles and log levels. Never commit secrets to git. Audit log changes. Pair with a feature-flag service (LaunchDarkly, Unleash) for behavioral toggles.

Twelve-Factor App — what are the key principles?

A 2011 manifesto that's aged surprisingly well for cloud-native apps. The 12 factors:

  1. Codebase — one repo per app, many deploys.
  2. Dependencies — declared explicitly, isolated.
  3. Config — in environment, not code.
  4. Backing services — DBs/queues as attached resources, swappable via config.
  5. Build/release/run — strictly separate stages.
  6. Processes — stateless, share-nothing (state in DB).
  7. Port binding — app exports HTTP via a port.
  8. Concurrency — scale out by process model.
  9. Disposability — fast startup, graceful shutdown.
  10. Dev/prod parity — minimize gaps.
  11. Logs — write to stdout; let the platform aggregate.
  12. Admin processes — run one-off tasks (migrations) in the same environment.

Every Spring Boot service I ship follows these — they're the foundation for Kubernetes-friendly apps.
