Monolith vs Microservices must

Two architectural styles at opposite ends of the spectrum. The right choice depends on team size, scale, and the cost of distributed-system complexity — not on fashion.

Core Difference
Monolith One deployable unit — one repo, one DB, one process.
Microservices Many small services — independently deployable, each owning its data.
1 Deployment
Monolith
  • One artifact, one deploy.
  • Simple pipelines and ops.
  • Any change requires deploying the whole app.
Microservices
  • Each service deploys independently.
  • Teams ship without blocking each other.
  • More pipelines, more infra to manage.
2 Scaling
Monolith
  • Scale the whole app together.
  • Can't scale just the hot module.
Microservices
  • Scale each service independently based on load.
  • Different tech stacks per service (Python ML, Go API, Java core).
3 Data & Transactions
Monolith
  • Single shared DB.
  • Strong ACID transactions across modules.
  • Easy joins and reporting.
Microservices
  • Database per service.
  • No cross-service transactions — use Saga + Outbox.
  • Eventual consistency by design.
4 Complexity
Monolith
  • Simple infra (one app, one DB).
  • In-process calls — no network failures, no serialization.
  • Debugging via stack traces.
Microservices
  • Distributed systems — network, retries, timeouts, circuit breakers.
  • Need service discovery, API gateway, distributed tracing, centralized logging.
  • Much higher ops cost.
5 When to Choose
Monolith
  • Small team (< 15 engineers).
  • Product still finding fit, boundaries unclear.
  • Want to ship fast and iterate.
Microservices
  • Team scales beyond a single squad.
  • Parts of the system have very different scaling/release profiles.
  • Organizational boundaries demand independent deploys.
  • Need polyglot tech for specific subsystems.
My take after 5 years: start with a modular monolith, extract services only when monolith pain is real — slow deploys, team-blocking PRs, distinct scaling needs. Premature splitting = distributed monolith, the worst of both worlds.
What is a "distributed monolith" and how to avoid it?

A distributed monolith is microservices in name only — services tightly coupled by synchronous calls, shared databases, shared deployment timing, or shared models. Symptoms:

  • Deploying service A requires also deploying service B.
  • A typical user request touches 8 services synchronously.
  • You can't change a field without coordinating across teams.
  • One service's outage takes down "unrelated" features.

You get all the complexity of distributed systems with none of the independence benefits.

Avoidance: per-service database, API contracts via OpenAPI/proto with backward compatibility, async events where possible (Kafka), tolerant readers, careful Domain-Driven Design with explicit bounded contexts. At Indus Net I pushed back on splitting CRUD-heavy modules — they stayed in one service and we only carved out async/LLM workloads.

How do microservices communicate?

Two broad categories:

Synchronous — caller waits for a response.

  • REST over HTTP — most common; easy debugging, language-agnostic.
  • gRPC — typed (protobuf), faster, streaming. Good for internal service-to-service.
  • GraphQL — single endpoint, client-driven schema; good for BFFs.

Asynchronous — caller doesn't wait.

  • Message queues (RabbitMQ, SQS) — point-to-point work distribution.
  • Event streams (Kafka) — pub/sub, replayable.

Best practice: sync where the caller really needs the result, async for everything else — state changes that other services react to. Async decouples deployment timing and isolates failures. In one platform I worked on, resume upload returns immediately, then Kafka triggers parsing, indexing, and notifications independently.

Service discovery — how do services find each other? hot

Services in a microservice architecture have dynamic IPs (containers come and go). Service discovery lets clients find healthy instances by name.

Two patterns:

  • Client-side discovery — clients query a registry (Eureka, Consul) and pick an instance. Spring Cloud LoadBalancer does this. Smart but requires client logic.
  • Server-side discovery — a load balancer / proxy in front of each service handles routing. Kubernetes Services + kube-proxy work this way; AWS ALB + target groups too. Dumb client, smart infrastructure.

In Kubernetes — which is where most of my services run — discovery is essentially built in: my-service.my-namespace.svc.cluster.local resolves via CoreDNS, and the Service object load-balances over Pod IPs. No Eureka needed. For external traffic, an Ingress + LB handle it.

What is an API Gateway? must

An API Gateway is a single entry point between clients and your backend services in a microservices architecture. Instead of clients calling each microservice directly, all requests first go through the gateway, which then routes them to the right service — and handles cross-cutting concerns like auth, rate limiting, and observability along the way.

Core Idea
What A reverse proxy that sits in front of all your microservices — the only door from the outside world into your system.
Why Centralize cross-cutting concerns (auth, rate limiting, logging, routing) so individual services stay focused on business logic.
How Path/host-based routing: /users/* → User Service, /orders/* → Order Service, etc.
1 Why we need it — without vs with
Without an API Gateway
  • Clients know every service's URL and port
  • Each service implements auth, rate limiting, logging — duplicated everywhere
  • Frontend has to call 5 services for one screen (chatty & slow)
  • Every service is publicly exposed → bigger attack surface
  • Version / route changes break clients
With an API Gateway
  • Clients call one URL — the gateway
  • Auth, rate limiting, CORS, logging — handled once
  • Gateway can aggregate multiple service calls (BFF pattern)
  • Internal services hide behind the gateway → smaller attack surface
  • Routes / versions change without touching clients
2 Architecture — single door in
┌────────────┐ │ Client │ (browser, mobile) └─────┬──────┘ │ 1 request, 1 URL ▼ ┌────────────┐ │ API GATEWAY│ ◀── auth, rate limit, log, CORS, route └─────┬──────┘ ┌─────────────┼─────────────┐ ▼ ▼ ▼ ┌────────┐ ┌─────────┐ ┌──────────┐ │ User │ │ Order │ │ Payment │ │ Service│ │ Service │ │ Service │ └────────┘ └─────────┘ └──────────┘ ▲ ▲ ▲ │ │ │ DB1 DB2 DB3
3 What the gateway actually does
ResponsibilityWhat it does
Routing Maps incoming paths / hosts / methods to the right backend service.
Authentication Validates JWT / OAuth token before the request reaches any service.
Authorization Checks roles / scopes per route.
Rate Limiting / ThrottlingPer-user or per-API-key limits — protects services from abuse and spikes.
Load Balancing Distributes traffic across multiple instances of the same service.
Request/Response TransformationHeader rewriting, payload shaping, protocol bridging (REST ↔ gRPC).
Caching Cache GET responses for hot endpoints to offload backends.
SSL / TLS Termination Decrypts HTTPS once at the edge → plaintext to internal services.
Logging & Monitoring Single chokepoint to capture metrics, request IDs, distributed-trace headers.
Aggregation (BFF) Fan out one client request to N services, merge the responses.
Circuit Breaking / RetriesStop calling a failing service; retry idempotent calls.
CORS Handle browser preflight requests centrally.
4 Routing example — an e-commerce app

All requests come in via https://api.shop.com/*. The gateway routes them by path prefix:

Incoming pathGoes toGateway also does
GET /users/42 User Service Validate JWT, fetch user role from claim
POST /orders Order Service Auth + rate-limit (10/min per user)
GET /orders/99/statusOrder Service Cache for 5s, add tracing header
POST /payments Payment Service Extra strict auth, audit log
GET /products/* Product Service Public — no auth required, heavy caching

Spring Cloud Gateway example (YAML):

spring:
  cloud:
    gateway:
      routes:
        - id: users-route
          uri: lb://user-service          # service discovery
          predicates:
            - Path=/users/**
          filters:
            - StripPrefix=0
            - AddRequestHeader=X-Source, gateway
        - id: orders-route
          uri: lb://order-service
          predicates:
            - Path=/orders/**
          filters:
            - RewritePath=/orders/(?<rest>.*), /api/v1/$\{rest}
5 Popular API Gateway tools

Spring Cloud Gateway

  • Java, reactive (Project Reactor)
  • Filter-chain model, YAML or programmatic routes
  • Tight integration with Spring ecosystem
Best for: Java/Spring Boot stacks.

Kong

  • Built on NGINX + Lua / OpenResty
  • Massive plugin ecosystem (auth, rate-limit, logging…)
  • Has both self-hosted & managed (Kong Konnect)
Best for: polyglot stacks, big plugin needs.

AWS API Gateway

  • Fully managed, pay-per-request
  • Integrates with Lambda, IAM, Cognito out of the box
  • REST & HTTP API flavors, also WebSocket
Best for: serverless / AWS-native apps.

NGINX / Envoy

  • NGINX — proven, lightweight L7 proxy
  • Envoy — modern, used in Istio service mesh
  • Traefik — auto-discovers K8s services
Best for: K8s / cloud-native + service mesh setups.
6 Common pitfalls (production lessons)
  • Don't put business logic in the gateway. Keep it thin — routing, auth, observability only. Heavy aggregation belongs in a BFF (Backend-For-Frontend) service.
  • It's a single point of failure. Run multiple instances, fronted by a real load balancer (ALB, GCP LB) — never just one gateway pod.
  • Latency tax. Every request now hops through the gateway. Keep filter chains short; profile p99 regularly.
  • Internal service-to-service calls usually skip the gateway. Inside the cluster, services call each other directly (or via a service mesh) — going via the gateway adds a needless hop.
  • Beware "smart gateway" creep — orchestration, transformations, data joins gradually pile up until it's a monolith disguised as a gateway.
  • Distinguish North–South vs East–West. Gateway = North–South (client ↔ system). East–West (service ↔ service) belongs to a service mesh (Istio, Linkerd) — different problem, different tool.
Interview one-liner: An API Gateway acts as a reverse proxy and single entry point for all client requests in a microservices architecture. It routes incoming requests to the right backend service (/users/* → User Service, /orders/* → Order Service…) and handles cross-cutting concerns centrally — authentication, rate limiting, load balancing, caching, logging, transformation, and SSL termination. This simplifies the client (one URL instead of many) and centralizes security and traffic management. Popular tools: Spring Cloud Gateway, Kong, NGINX, AWS API Gateway, Traefik, Envoy. Keep it thin — no business logic in the gateway.
API Gateway vs Load Balancer — what's the difference? must

Both API Gateway and Load Balancer sit between clients and backend servers, so people confuse them — but they solve different problems and they're routinely used together in modern microservices architectures.

Core Difference
Load Balancer Distributes traffic across multiple servers — solves scalability & availability.
API Gateway Manages APIs — auth, routing, rate limiting, transformation — solves API lifecycle & security.
Rule of thumb LB is about boxes. Gateway is about APIs. Use both.
1 What each one actually does
Load Balancer
  • Distributes incoming traffic across multiple server instances
  • Health-checks backends; drains the unhealthy ones
  • Works at L4 (TCP/UDP) or L7 (HTTP)
  • Algorithms: round-robin, least-connections, IP hash
  • Goal: prevent overload, maximize availability
  • Examples: NGINX, HAProxy, AWS NLB/ALB, F5
API Gateway
  • Single entry point for all client API calls
  • Path-based routing to many microservices
  • Authentication, authorization, rate limiting
  • Caching, logging, transformation, API aggregation
  • Goal: centralize cross-cutting concerns across APIs
  • Examples: Kong, Spring Cloud Gateway, AWS API Gateway, Apigee
2 Side-by-side comparison
AspectLoad BalancerAPI Gateway
Primary job Distribute traffic across servers Route & manage API calls
Layer L4 / L7 L7 (always app-layer)
Knows about APIs? No — just hosts & ports Yes — paths, verbs, payloads
Auth Pass-through Validates JWT / OAuth
Rate limiting Basic, per-IP Rich — per user, key, endpoint
Routing Distribute across same service Route by path/host to many services
Transformation None Headers, payload, REST ↔ gRPC
Aggregation (BFF) No Yes
Caching Basic HTTP cache Endpoint-level cache
Health checks Yes (built-in) Yes (downstream services)
Used in Any distributed system Microservices, public APIs
Cost / complexity Low Higher
3 The architectural picture — different shapes

Load Balancer — spreads requests across identical copies of one service:

┌─────────────┐ │ Users │ └──────┬──────┘ ▼ ┌─────────────┐ │ Load │ ← round-robin │ Balancer │ └──────┬──────┘ ┌──────────┼──────────┐ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ │Server 1│ │Server 2│ │Server 3│ (same app — many copies) └────────┘ └────────┘ └────────┘

API Gateway — routes requests to different services:

┌─────────────┐ │ Clients │ └──────┬──────┘ ▼ ┌─────────────┐ │ API Gateway │ ← path-based routing, auth, rate-limit └──────┬──────┘ ┌──────────┼──────────┐ ▼ ▼ ▼ ┌────────┐ ┌─────────┐ ┌──────────┐ │ User │ │ Order │ │ Payment │ (different services) │ Service│ │ Service │ │ Service │ └────────┘ └─────────┘ └──────────┘
4 Can an API Gateway also do load balancing?

Yes — modern API gateways (Kong, Spring Cloud Gateway, AWS API Gateway, Envoy) usually have built-in load balancing across multiple instances of each backend service. But:

  • Dedicated load balancers are optimized for raw traffic distribution — millions of requests/sec at L4 with near-zero overhead.
  • API gateways are optimized for API management — auth, transformation, observability per API call.
  • In practice, most production systems use both — a dedicated LB (ALB / NLB) in front of the gateway tier itself for HA, and gateways doing finer-grained routing + balancing across services.
5 Real-world production architecture — both used together

A typical setup at scale uses both:

┌────────────┐ │ Client │ └──────┬─────┘ ▼ ┌────────────┐ │ Cloud LB │ ← TLS termination, L7, HA │ (ALB/NLB) │ in front of gateway pods └──────┬─────┘ ┌───────────────┼──────────────┐ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ │Gateway1│ │Gateway2│ │Gateway3│ └────────┘ └────────┘ └────────┘ │ │ │ └─────────────┴──────────────┘ ▼ ┌────────────────────┐ │ Internal LB / Mesh │ ← service-to-service LB │ (Envoy / Istio) │ (East–West) └─────────┬──────────┘ ┌───────────────┼──────────────┐ ▼ ▼ ▼ ┌────────┐ ┌─────────┐ ┌──────────┐ │ User │ │ Order │ │ Payment │ │ Service│ │ Service │ │ Service │ └────────┘ └─────────┘ └──────────┘

Why both:

  • Cloud LB in front handles HA + TLS for the gateway tier itself (you don't want the gateway to be a single point of failure).
  • API Gateway handles auth, routing, rate-limiting, transformation per API.
  • Internal LB / service mesh handles East–West (service-to-service) traffic with retries, circuit breakers, mTLS.
6 Mental model — North-South vs East-West
  • North–South traffic (client ↔ system, outside ↔ inside): API Gateway is the right tool. It's the front door.
  • East–West traffic (service ↔ service inside the cluster): Internal load balancer or service mesh (Istio, Linkerd) handles it. Gateways are not for internal calls.
  • For raw scaling of any service tier (gateway, app server, etc.): Load Balancer in front of identical replicas.
Interview-ready answer: A Load Balancer distributes traffic across multiple servers to improve scalability and availability — it doesn't care what the requests are, just that the work is spread evenly. An API Gateway is a centralized entry point for APIs that provides authentication, routing, rate limiting, caching, transformation, and monitoring — it's API-aware. The two solve different problems: LB = traffic distribution; Gateway = API management. In microservices architectures, both are typically used together — a cloud LB fronts the gateway tier for HA, and the gateway routes requests to the right service. A gateway can do basic load balancing, but a dedicated LB is optimized for raw distribution; you don't have to pick one — use both.
What is the Saga pattern? hot

Distributed transactions across microservices are hard — 2PC is slow and brittle. The Saga pattern is the standard alternative: model the transaction as a sequence of local transactions in each service, with compensating actions if a step fails.

Example — booking flow: reserveSeat → chargeCard → confirmBooking. If chargeCard fails, run cancelReservation compensation.

Two coordination styles:

  • Choreography — services react to events from each other; no central coordinator. Loose coupling, but flow is implicit and hard to trace.
  • Orchestration — a coordinator service explicitly drives the saga. Easier to observe and modify. Tools: Camunda, Temporal, AWS Step Functions.

I lean orchestration for non-trivial flows — observability and recoverability are worth the central service. Always ensure all steps and compensations are idempotent.

Eventual consistency — explain it

Eventual consistency means: if updates stop, all replicas will eventually converge to the same value — but not at the exact same instant. The opposite of strong consistency, which guarantees every read sees the latest write.

It's the consistency model most distributed systems choose because CAP forces a tradeoff during partitions, and pure strong consistency limits scale and availability.

Practical implications:

  • A user might update their profile and see the old value on the next page load (read-your-writes problem) — fix by routing to primary for that user briefly.
  • UI design needs to communicate "processing" states.
  • Background jobs eventually reconcile — for instance, a CDC pipeline updating Elasticsearch from MongoDB takes a few hundred milliseconds.

It's a design choice, not a bug. Most user-facing features tolerate it gracefully if you build for it.

CAP theorem — and PACELC

CAP theorem: in a distributed system you can have at most two of Consistency, Availability, Partition tolerance. Partitions are inevitable in real networks, so the real choice is between CP (refuse requests during partition for consistency) and AP (serve possibly-stale data for availability).

  • CP — HBase, MongoDB (with majority writes), Zookeeper, etcd.
  • AP — Cassandra, DynamoDB, Couchbase by default.

PACELC extends this: even when there's no Partition, you choose between Latency and Consistency. A "PA/EL" system favors availability during partition and low latency otherwise; "PC/EC" favors consistency in both cases.

This is useful framing in design interviews — interviewers love when you frame a system's tradeoffs as PACELC rather than just CAP.

How do you handle distributed transactions?

Three practical patterns:

  • Saga (see earlier) — sequence of local transactions with compensations. Best for multi-service workflows.
  • Outbox pattern — write the business state and an outbox row in the same local DB transaction; a separate process publishes outbox rows to Kafka. Guarantees "if the DB says it happened, the event will be published."
  • Transactional messaging — Kafka transactions (within the same producer) for exactly-once semantics across topics; useful when you produce to multiple topics atomically.

What I don't use: 2PC across microservices — it's slow, fragile, and most modern DBs/queues don't support XA well together. The combination of outbox + idempotent consumers + saga covers nearly every real-world distributed-transaction need.

Inter-service communication failures — how to handle?

The fundamental rule: networks fail, downstreams slow down — your service must remain healthy when its dependencies aren't.

My toolkit:

  • Timeouts on every outbound call — never block forever. Set them generous-but-realistic.
  • Retries with exponential backoff + jitter for transient errors only. Make calls idempotent.
  • Circuit breaker — fail fast when a downstream is unhealthy.
  • Bulkheads — separate thread pools / connection pools per downstream so one slow dependency doesn't starve the rest.
  • Fallbacks — return cached / degraded responses where possible.
  • Async over sync — if the caller doesn't need the result immediately, send an event instead.

All of this is Resilience4j in Spring Boot. Combined with timeouts at the HTTP client level, this stack has saved my services through multiple downstream outages.

Database per service — really?

Yes — it's the most important rule that makes microservices actually independent. Each service owns its data and is the only one that writes to its database. Other services consume via APIs or events.

Why it matters: shared databases create the worst kind of coupling — schema changes block all consumers, performance issues in one service affect everyone, transactional boundaries blur. A "microservice" reading from another service's tables is a distributed monolith in disguise.

Costs you accept:

  • Cross-service queries become API calls or async data replication.
  • Reporting/analytics need a separate data warehouse (CDC → Snowflake/BigQuery).
  • Distributed transactions need Saga or Outbox.

The tradeoff is worth it. At Indus Net we have a single Mongo cluster, but each service uses its own database (logical separation) — close enough to db-per-service for a small team.

Centralized configuration — Spring Cloud Config / Consul

Hard-coding config in YAML doesn't scale across many services × multiple environments. Centralized config stores all config in one place — services pull on startup (and optionally refresh at runtime).

Options:

  • Spring Cloud Config Server — git-backed, integrates with Spring Boot.
  • Consul KV or etcd — distributed KV stores.
  • AWS Parameter Store / Secrets Manager / HashiCorp Vault for secrets.
  • Kubernetes ConfigMaps + Secrets — what I use most now; mounted into pods.

Runtime refresh via @RefreshScope + /actuator/refresh in Spring Cloud — useful for toggles and log levels. Never commit secrets to git. Audit log changes. Pair with a feature-flag service (LaunchDarkly, Unleash) for behavioral toggles.

Twelve-Factor App — what are the key principles?

A 2011 manifesto that's aged surprisingly well for cloud-native apps. The 12 factors:

  1. Codebase — one repo per app, many deploys.
  2. Dependencies — declared explicitly, isolated.
  3. Config — in environment, not code.
  4. Backing services — DBs/queues as attached resources, swappable via config.
  5. Build/release/run — strictly separate stages.
  6. Processes — stateless, share-nothing (state in DB).
  7. Port binding — app exports HTTP via a port.
  8. Concurrency — scale out by process model.
  9. Disposability — fast startup, graceful shutdown.
  10. Dev/prod parity — minimize gaps.
  11. Logs — write to stdout; let the platform aggregate.
  12. Admin processes — run one-off tasks (migrations) in the same environment.

Every Spring Boot service I ship follows these — they're the foundation for Kubernetes-friendly apps.
