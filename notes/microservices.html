Monolith vs Microservices must

Two architectural styles at opposite ends of the spectrum. The right choice depends on team size, scale, and the cost of distributed-system complexity — not on fashion.

Core Difference
Monolith One deployable unit — one repo, one DB, one process.
Microservices Many small services — independently deployable, each owning its data.
1 Deployment
Monolith
  • One artifact, one deploy.
  • Simple pipelines and ops.
  • Any change requires deploying the whole app.
Microservices
  • Each service deploys independently.
  • Teams ship without blocking each other.
  • More pipelines, more infra to manage.
2 Scaling
Monolith
  • Scale the whole app together.
  • Can't scale just the hot module.
Microservices
  • Scale each service independently based on load.
  • Different tech stacks per service (Python ML, Go API, Java core).
3 Data & Transactions
Monolith
  • Single shared DB.
  • Strong ACID transactions across modules.
  • Easy joins and reporting.
Microservices
  • Database per service.
  • No cross-service transactions — use Saga + Outbox.
  • Eventual consistency by design.
4 Complexity
Monolith
  • Simple infra (one app, one DB).
  • In-process calls — no network failures, no serialization.
  • Debugging via stack traces.
Microservices
  • Distributed systems — network, retries, timeouts, circuit breakers.
  • Need service discovery, API gateway, distributed tracing, centralized logging.
  • Much higher ops cost.
5 When to Choose
Monolith
  • Small team (< 15 engineers).
  • Product still finding fit, boundaries unclear.
  • Want to ship fast and iterate.
Microservices
  • Team scales beyond a single squad.
  • Parts of the system have very different scaling/release profiles.
  • Organizational boundaries demand independent deploys.
  • Need polyglot tech for specific subsystems.
My take after 5 years: start with a modular monolith, extract services only when monolith pain is real — slow deploys, team-blocking PRs, distinct scaling needs. Premature splitting = distributed monolith, the worst of both worlds.
What is a "distributed monolith" and how to avoid it?

A distributed monolith is microservices in name only — services tightly coupled by synchronous calls, shared databases, shared deployment timing, or shared models. Symptoms:

  • Deploying service A requires also deploying service B.
  • A typical user request touches 8 services synchronously.
  • You can't change a field without coordinating across teams.
  • One service's outage takes down "unrelated" features.

You get all the complexity of distributed systems with none of the independence benefits.

Avoidance: per-service database, API contracts via OpenAPI/proto with backward compatibility, async events where possible (Kafka), tolerant readers, careful Domain-Driven Design with explicit bounded contexts. At Indus Net I pushed back on splitting CRUD-heavy modules — they stayed in one service and we only carved out async/LLM workloads.

Breaking a Monolith into Microservices — a step-by-step migration playbook must

The interview question is rarely "what are microservices?" — it's "how would you break this existing monolith into microservices?". The expected answer is not a big-bang rewrite. It's an incremental, domain-driven migration: identify bounded contexts from the business, extract one service at a time using the Strangler Fig pattern, route new traffic to the new service through an API gateway, and keep the monolith running until the last bounded context is carved out. The split is by business capability — not by technical layer — and the database is separated gradually, not on day one.

Core Idea
Decompose by domain Identify bounded contexts in the monolith, extract one low-risk service at a time behind an API gateway (Strangler Fig), give each service its own database, and let asynchronous events glue them together — never a big-bang rewrite.
1 Understand the existing monolith

Before drawing any new boxes, map what's already there. You can't split what you don't understand — and most "failed microservices" stories start with skipping this step.

  • Modules & packages — what code lives where, which packages are tangled, which are already cleanly separated.
  • Database tables & foreign keys — which tables are joined together in queries, which span multiple business areas, which are owned by one module vs shared.
  • Business flows — end-to-end user journeys (signup, checkout, refund) and which modules each flow touches.
  • Dependencies & coupling — call graphs between services / classes, shared models, shared utilities, hidden cross-module DB writes.
  • Pain points — slow build / deploy times, modules that block other teams' PRs, areas with the highest defect / incident rate.
  • Scaling hotspots — which subsystem actually needs to scale independently (search, notifications, image processing). That's almost always a strong candidate for extraction.
2 Identify bounded contexts — split by business capability, not by technical layer

A bounded context (Domain-Driven Design) is a piece of the business with its own language, its own model, and its own data — User, Order, Payment, Inventory, Notification, Catalog, Pricing. Each bounded context becomes a candidate microservice. The single biggest mistake is splitting by technical layer (Controller / Service / Repository / Validation) — that creates a distributed monolith where every business request still touches every service.

Bad split — by technical layer
  • controller-service, repository-service, validation-service, dto-service
  • Every business request still hops through all services synchronously
  • A single feature change touches every repo → coordinated deploys
  • No service owns a bounded context — they all share the same data model
  • You inherit all the pain of distribution and none of the autonomy
Good split — by business capability
  • user-service, order-service, payment-service, inventory-service, notification-service
  • Each service owns its own data, own API, own deploy pipeline
  • Most features change exactly one service
  • Teams align with services — clear ownership and on-call
  • Maps directly to the business — easy to reason about at every level

Practical heuristic: if two pieces of code change for different business reasons and are owned by different teams, they probably belong in different services. If they always change together, they probably belong in the same service.

3 Start with a low-risk service — pick the right first cut

The first extraction is the most important — it sets the template, builds team confidence, and forces you to put real platform plumbing (CI/CD, observability, gateway) in place. Pick a module that is:

  • Loosely coupled from the rest of the monolith — few inbound calls, few shared tables.
  • High business value — extraction is justified by a real benefit (independent scaling, faster iteration, distinct compliance boundary).
  • Low DB dependency — owns its own tables (or close to it); you don't have to untangle a giant join graph on day one.
  • Independently testable — clear inputs / outputs, can be exercised end-to-end without spinning up the whole platform.

Classic safe first cuts: Notification service (email / SMS / push — already async), Reporting / Analytics (read-only, eventually consistent is fine), Audit Log, Image / Document Processing, Search Indexer. Avoid starting with the core transactional module (Order, Payment) — extract those last, once the platform is mature.

4 Strangler Fig Pattern — extract incrementally behind a gateway

Named after the strangler fig vine that gradually grows around a tree until the host is gone — the pattern, popularized by Martin Fowler, is to route new traffic to a new microservice while the monolith keeps serving the rest. Over time the monolith shrinks until nothing is left to call.

1. Stand up an API Gateway (or reverse proxy) in front of the monolith — all traffic now flows through it
↓
2. Build the new microservice with the same contract for one bounded context (e.g. /notifications/*)
↓
3. Update the gateway: route /notifications/* → new service, everything else → monolith
↓
4. Run both in parallel — shadow traffic, compare responses, monitor errors and latency
↓
5. When confident, delete the old code path from the monolith — bounded context is fully extracted
↓
6. Repeat for the next bounded context — the monolith strangles one capability at a time
┌─────────────────────┐ client ───────────▶│ API Gateway │ │ (path-based route) │ └────────┬────────────┘ │ ┌────────────────┼─────────────────┐ │ │ │ /notifications/* /orders/*, /users/* /reports/* │ │ │ ▼ ▼ ▼ ┌──────────────────┐ ┌────────────┐ ┌──────────────────┐ │ Notification svc │ │ Monolith │ │ Reporting svc │ │ (extracted) │ │ (shrinking)│ │ (extracted) │ └──────────────────┘ └────────────┘ └──────────────────┘

Why this works: no big-bang cutover, easy rollback (flip the gateway rule back), users never notice, and you only carry the migration risk for one bounded context at a time.

5 Separate the database — gradually, not on day one

Database-per-service is the target, not the starting state. Splitting the schema is the hardest, riskiest part of the migration — do it in stages.

Stage A — Shared DB. The new microservice talks to the same database the monolith uses, but only to its own tables. Fast to extract, but coupling remains.
↓
Stage B — Schema split. Move the service's tables into a separate schema (or separate logical DB) on the same physical engine. Foreign keys to other contexts are dropped — replaced by IDs only.
↓
Stage C — Physical split. The service gets its own DB instance. order-service → orders_db, payment-service → payments_db, inventory-service → inventory_db. Cross-context reads happen via API calls or events, never SQL joins.
↓
Stage D — Dual-write & backfill. While migrating data, write to both old and new stores, backfill historical data, then cut reads over, then cut writes. CDC tools (Debezium) or the Outbox pattern make this safe.

Once a service owns its data, schema changes stop blocking other teams, performance issues stop bleeding across services, and you've finally bought the autonomy microservices are supposed to give you.

6 Inter-service communication — sync where you must, async where you can

Once data is split, services need to talk. Pick the right channel for the right job:

StyleTechWhen to use
Synchronous request/responseREST / HTTP, gRPC, GraphQLThe caller genuinely needs the result now — login, "is this user allowed?", reading a product detail.
Asynchronous eventsKafka, RabbitMQ, AWS SNS/SQSState changes that other services react to — OrderCreated, PaymentCompleted, UserSignedUp. Decouples deploy timing and isolates failures.
Streaming / pub-subKafka topics, change-data-captureMany consumers reacting to the same event stream — analytics, search indexing, audit, notifications.

Worked example — placing an order:

Client → Order Service creates order in PENDING state and publishes OrderCreated
↓
Inventory Service consumes OrderCreated → reserves stock → publishes InventoryReserved
↓
Payment Service consumes InventoryReserved → charges card → publishes PaymentCompleted
↓
Notification Service consumes PaymentCompleted → emails the customer
↓
Order Service consumes PaymentCompleted → flips order to CONFIRMED

No service synchronously waits on another for the whole flow — each one does its local work and emits what it knows. That's how services stay independently deployable.

7 Handle distributed transactions — Saga, Outbox, idempotency

Once you've split the database, a single business flow no longer fits in one ACID transaction. You need patterns that give you eventual consistency without 2PC. (See the dedicated Saga Pattern and Transactional Outbox entries for full depth.)

  • Saga pattern — model the cross-service flow as a sequence of local transactions, each with a compensating action that semantically undoes it on failure. Pick orchestration (a central state machine) for non-trivial flows, choreography (event-driven) for tiny ones.
  • Transactional Outbox — never dual-write to DB and Kafka. Save the business row and the event in the same DB transaction (an outbox table); a relay publishes the event afterwards. Solves the dual-write problem.
  • Event-driven architecture — services emit domain events as the source of truth for cross-service reactions; consumers project them into their own read models.
  • Idempotency — every consumer must handle the same message twice with the same effect. Use natural business keys, idempotency-key tables, or version checks. At-least-once delivery + idempotent consumers ≈ effective exactly-once.
  • Outbound retries with backoff and dead-letter queues for poison messages — don't let a single bad event jam the whole pipeline.
8 Add observability before you split too much

Debugging "why did this order fail?" across one process is easy. Across ten services it's impossible without instrumentation. Put this in place before the third or fourth extraction, not after a production incident:

  • Centralized logging — every service ships structured JSON logs to one place (ELK / Loki / CloudWatch / Datadog).
  • Correlation IDs — the gateway stamps a trace-id / request-id header; every service propagates it on every log line and every outbound call. Without this, cross-service debugging is archaeology.
  • Distributed tracing — OpenTelemetry / Jaeger / Zipkin / Datadog APM — see the full span tree of a request as it hops services.
  • Metrics — RED (rate / errors / duration) per endpoint, USE (utilization / saturation / errors) per resource. Prometheus + Grafana is the default stack.
  • Health checks & readiness probes — /actuator/health, Kubernetes liveness / readiness probes; the orchestrator restarts unhealthy pods automatically.
  • Alerting on SLOs, not on raw thresholds — wake people up when the user experience degrades, not when CPU briefly spikes.

ChallengeWhy it hurtsHow to handle
Data consistency No more single ACID transaction across the flow — partial failures leave the system in inconsistent states. Saga pattern with compensations, Outbox for atomic write-and-publish, idempotent consumers, and eventual consistency contracts on the API.
Too many service calls (chatty graph) One user request fans out to 8 sync hops → high tail latency, cascading failures, brittle dependency chain. Debugging across services A failure can originate three hops upstream — tail -f on one container tells you nothing. Correlation IDs, distributed tracing (OpenTelemetry / Jaeger), centralized log aggregation, structured logs, runbooks per service.
Deployment complexity 10 services × N environments = a lot of moving parts; manual deploys collapse under their own weight. CI/CD per service, container images, Kubernetes + Helm / Argo CD, blue-green or canary deploys, contract tests in the pipeline.
Duplicate logic / shared code Auth, validation, DTOs end up copy-pasted across services and drift over time. Tiny, stable shared libraries for cross-cutting concerns only (logging, tracing, security primitives); rich domain logic stays inside its owning service.
Service ownership & on-call Without a clear owner, services rot — nobody upgrades the framework, nobody triages incidents, nobody owns the SLOs. One owning team per service, on-call rotation, service catalog (Backstage), explicit SLOs and runbooks. Conway's Law: align teams to services.
Schema / contract evolution A breaking change in one service quietly breaks every consumer. Backward-compatible APIs (additive changes only), OpenAPI / protobuf with versioning, consumer-driven contract tests (Pact), tolerant readers.

10 What to migrate first — safe early extractions

Notification service

Email / SMS / push. Already async by nature, no transactional coupling, owns its own templates and provider keys.

Reporting / Analytics

Read-only, eventually consistent is fine, can be fed by events from the monolith without changing any write paths.

Audit log

Append-only, narrow API, no business logic — perfect first cut to validate the platform plumbing.

Image / document processing

CPU-heavy, scales differently from the rest of the app, naturally async behind a queue.

Search indexer

Consumes domain events, owns its own Elasticsearch / OpenSearch index, easy to rebuild from scratch.

Auth / identity

Often already a separate concern (Keycloak, Auth0, Cognito) — extracting it first gives the gateway a clean place to enforce auth.

ML / scoring service

Different stack (Python), different scaling, low coupling to the monolith — typical wedge for the first non-Java service.

Feature flags / config

Tiny, read-heavy, well-understood contract; gives every other team a self-service control plane.

Avoid extracting the core transactional module (Order, Payment, Inventory) first — those have the most coupling, the most data, and the highest blast radius. Earn the right to touch them by first proving the platform on the safe edges.

11 Common interview gotchas
  • Don't do a big-bang rewrite. Rewriting the monolith from scratch in parallel is the canonical way to fail. Strangler Fig + incremental extraction is the expected answer.
  • Don't split by technical layer. "Controller service / Repository service / Validation service" is the textbook anti-pattern — split by business capability (bounded context).
  • Database-per-service is a target, not a starting point. Stage it: shared DB → schema split → physical split. Trying to split data on day one is how migrations get cancelled.
  • Shared libraries should be tiny and stable. Logging, tracing, auth primitives — yes. Domain models — no. Big shared libs recreate the monolith at the dependency layer.
  • Cross-service joins are an anti-pattern. If you need data from another service, call its API or subscribe to its events and project a local read model — never reach into another service's tables.
  • Not every system needs microservices. A small team on a small product is faster shipping a modular monolith. Microservices pay off when independent scaling, independent deploys, or independent teams become a real constraint.
  • Conway's Law — team structure must match service structure. If two teams share a service, or one team owns ten services, you'll feel it. Services are sociotechnical, not just technical.
  • CI/CD and observability maturity is a prerequisite. If you can't deploy the monolith reliably and trace a request through it, you definitely can't run ten microservices. Build the platform before you split.
  • Synchronous chains are silent killers. A 5-hop sync call graph multiplies tail latency and failure probability. Default to async events; use sync only where the caller truly needs the answer now.
  • Versioning and backward compatibility matter from day one — once two services depend on a contract, breaking it without a migration plan breaks production.
Interview one-liner: The way to break a monolith is incrementally, by domain — not by big-bang rewrite. Start by mapping the existing modules, tables, flows, and pain points; identify bounded contexts (User, Order, Payment, Inventory, Notification) and split by business capability, never by technical layer. Pick a low-risk, loosely-coupled module first (notifications, reporting, audit) and extract it behind an API gateway using the Strangler Fig pattern — the gateway routes the carved-out paths to the new service while everything else still hits the monolith, and the monolith shrinks one bounded context at a time. Move to database-per-service in stages — shared DB → schema split → physical split — and replace cross-context joins with API calls or events. Glue services together with REST/gRPC for sync calls and Kafka / RabbitMQ events for async state propagation, so deploys and failures are isolated. Handle distributed transactions with the Saga pattern and the Transactional Outbox for atomic write-and-publish, with idempotent consumers for at-least-once delivery. Put centralized logging, correlation IDs, distributed tracing, metrics, and health checks in place before the third extraction — observability is a prerequisite, not a follow-up. And remember the meta-rules: not every system needs microservices, team structure must match service structure (Conway's Law), and CI/CD maturity is a non-negotiable prerequisite.
How do microservices communicate?

Two broad categories:

Synchronous — caller waits for a response.

  • REST over HTTP — most common; easy debugging, language-agnostic.
  • gRPC — typed (protobuf), faster, streaming. Good for internal service-to-service.
  • GraphQL — single endpoint, client-driven schema; good for BFFs.

Asynchronous — caller doesn't wait.

  • Message queues (RabbitMQ, SQS) — point-to-point work distribution.
  • Event streams (Kafka) — pub/sub, replayable.

Best practice: sync where the caller really needs the result, async for everything else — state changes that other services react to. Async decouples deployment timing and isolates failures. In one platform I worked on, resume upload returns immediately, then Kafka triggers parsing, indexing, and notifications independently.

Service discovery — how do services find each other? hot

Services in a microservice architecture have dynamic IPs (containers come and go). Service discovery lets clients find healthy instances by name.

Two patterns:

  • Client-side discovery — clients query a registry (Eureka, Consul) and pick an instance. Spring Cloud LoadBalancer does this. Smart but requires client logic.
  • Server-side discovery — a load balancer / proxy in front of each service handles routing. Kubernetes Services + kube-proxy work this way; AWS ALB + target groups too. Dumb client, smart infrastructure.

In Kubernetes — which is where most of my services run — discovery is essentially built in: my-service.my-namespace.svc.cluster.local resolves via CoreDNS, and the Service object load-balances over Pod IPs. No Eureka needed. For external traffic, an Ingress + LB handle it.

What is an API Gateway? must

An API Gateway is a single entry point between clients and your backend services in a microservices architecture. Instead of clients calling each microservice directly, all requests first go through the gateway, which then routes them to the right service — and handles cross-cutting concerns like auth, rate limiting, and observability along the way.

Core Idea
What A reverse proxy that sits in front of all your microservices — the only door from the outside world into your system.
Why Centralize cross-cutting concerns (auth, rate limiting, logging, routing) so individual services stay focused on business logic.
How Path/host-based routing: /users/* → User Service, /orders/* → Order Service, etc.
1 Why we need it — without vs with
Without an API Gateway
  • Clients know every service's URL and port
  • Each service implements auth, rate limiting, logging — duplicated everywhere
  • Frontend has to call 5 services for one screen (chatty & slow)
  • Every service is publicly exposed → bigger attack surface
  • Version / route changes break clients
With an API Gateway
  • Clients call one URL — the gateway
  • Auth, rate limiting, CORS, logging — handled once
  • Gateway can aggregate multiple service calls (BFF pattern)
  • Internal services hide behind the gateway → smaller attack surface
  • Routes / versions change without touching clients

6 Common pitfalls (production lessons)
  • Don't put business logic in the gateway. Keep it thin — routing, auth, observability only. Heavy aggregation belongs in a BFF (Backend-For-Frontend) service.
  • It's a single point of failure. Run multiple instances, fronted by a real load balancer (ALB, GCP LB) — never just one gateway pod.
  • Latency tax. Every request now hops through the gateway. Keep filter chains short; profile p99 regularly.
  • Internal service-to-service calls usually skip the gateway. Inside the cluster, services call each other directly (or via a service mesh) — going via the gateway adds a needless hop.
  • Beware "smart gateway" creep — orchestration, transformations, data joins gradually pile up until it's a monolith disguised as a gateway.
  • Distinguish North–South vs East–West. Gateway = North–South (client ↔ system). East–West (service ↔ service) belongs to a service mesh (Istio, Linkerd) — different problem, different tool.
Interview one-liner: An API Gateway acts as a reverse proxy and single entry point for all client requests in a microservices architecture. It routes incoming requests to the right backend service (/users/* → User Service, /orders/* → Order Service…) and handles cross-cutting concerns centrally — authentication, rate limiting, load balancing, caching, logging, transformation, and SSL termination. This simplifies the client (one URL instead of many) and centralizes security and traffic management. Popular tools: Spring Cloud Gateway, Kong, NGINX, AWS API Gateway, Traefik, Envoy. Keep it thin — no business logic in the gateway.
API Gateway vs Load Balancer — what's the difference? must

Both API Gateway and Load Balancer sit between clients and backend servers, so people confuse them — but they solve different problems and they're routinely used together in modern microservices architectures.

Core Difference
Load Balancer Distributes traffic across multiple servers — solves scalability & availability.
API Gateway Manages APIs — auth, routing, rate limiting, transformation — solves API lifecycle & security.
Rule of thumb LB is about boxes. Gateway is about APIs. Use both.
1 What each one actually does
Load Balancer
  • Distributes incoming traffic across multiple server instances
  • Health-checks backends; drains the unhealthy ones
  • Works at L4 (TCP/UDP) or L7 (HTTP)
  • Algorithms: round-robin, least-connections, IP hash
  • Goal: prevent overload, maximize availability
  • Examples: NGINX, HAProxy, AWS NLB/ALB, F5
API Gateway
  • Single entry point for all client API calls
  • Path-based routing to many microservices
  • Authentication, authorization, rate limiting
  • Caching, logging, transformation, API aggregation
  • Goal: centralize cross-cutting concerns across APIs
  • Examples: Kong, Spring Cloud Gateway, AWS API Gateway, Apigee

4 Can an API Gateway also do load balancing?

Yes — modern API gateways (Kong, Spring Cloud Gateway, AWS API Gateway, Envoy) usually have built-in load balancing across multiple instances of each backend service. But:

  • Dedicated load balancers are optimized for raw traffic distribution — millions of requests/sec at L4 with near-zero overhead.
  • API gateways are optimized for API management — auth, transformation, observability per API call.
  • In practice, most production systems use both — a dedicated LB (ALB / NLB) in front of the gateway tier itself for HA, and gateways doing finer-grained routing + balancing across services.

6 Mental model — North-South vs East-West
  • North–South traffic (client ↔ system, outside ↔ inside): API Gateway is the right tool. It's the front door.
  • East–West traffic (service ↔ service inside the cluster): Internal load balancer or service mesh (Istio, Linkerd) handles it. Gateways are not for internal calls.
  • For raw scaling of any service tier (gateway, app server, etc.): Load Balancer in front of identical replicas.
Interview-ready answer: A Load Balancer distributes traffic across multiple servers to improve scalability and availability — it doesn't care what the requests are, just that the work is spread evenly. An API Gateway is a centralized entry point for APIs that provides authentication, routing, rate limiting, caching, transformation, and monitoring — it's API-aware. The two solve different problems: LB = traffic distribution; Gateway = API management. In microservices architectures, both are typically used together — a cloud LB fronts the gateway tier for HA, and the gateway routes requests to the right service. A gateway can do basic load balancing, but a dedicated LB is optimized for raw distribution; you don't have to pick one — use both.
Distributed Caching with Redis in Microservices — design, implementation, and production concerns must

In a microservices architecture each service runs as multiple replicas behind a load balancer. An in-process cache (HashMap, Caffeine, EhCache local) lives inside one JVM — replica A's cache is invisible to replica B. The result is duplicated work, inconsistent reads, and stale data after a write. The fix is a centralized distributed cache — typically Redis — that every replica of every service reads from and writes to over the network.

Core Idea
Pattern Cache-aside (read-aside) — every replica reads and writes the same Redis. The service first checks Redis; on a miss it falls through to the DB / upstream service, populates Redis with a TTL, then returns the response.
Why Redis In-memory, sub-millisecond latency, shared across all service instances, horizontally scalable via Cluster / Sentinel, rich data types (string, hash, set, sorted-set, stream).
Net effect Lower response time, less DB load, consistent reads across replicas, ability to scale services horizontally without multiplying cache misses.
1 Without vs With a distributed cache
Local in-process cache per replica
  • Each replica warms its own cache — N copies of the same data
  • A write on replica A leaves replica B serving stale data → inconsistent reads
  • Auto-scaling adds new pods with cold caches → DB spike
  • Cache is lost on every restart / rolling deploy
  • No way to invalidate a key across the fleet
Distributed Redis cache
  • Shared across every replica and every service that needs it
  • Write once → all replicas see the new value immediately
  • New pods join with a warm cache — no cold-start spike
  • Survives app restarts; lives in its own tier
  • Central place to evict, broadcast invalidations, and observe hit ratio

ProductService.java — use Spring Cache annotations on the read/write paths:

@Service
@CacheConfig(cacheNames = "products")
public class ProductService {

  private final ProductRepository repo;

  @Cacheable(key = "#productId")                 // read-through: cache miss → run method, cache result
  public Product getProduct(Long productId) {
    return repo.findById(productId)
               .orElseThrow(() -> new NotFoundException(productId));
  }

  @CachePut(key = "#product.id")                 // always run method, refresh cache with new value
  public Product update(Product product) {
    return repo.save(product);
  }

  @CacheEvict(key = "#product.id")               // remove the key on delete
  public void delete(Product product) {
    repo.delete(product);
  }
}

9 Resilience — what if Redis goes down?

Treat Redis as an optional accelerator, not a hard dependency. If it's unreachable the app must degrade to the source of truth, not crash. Three layered patterns:

Graceful fallback
  • Wrap cache calls in try / catch — on any Redis error, log and fall through to the DB
  • Register a CacheErrorHandler so @Cacheable failures don't propagate
  • Enable spring.cache.redis.enable-statistics to track miss / error rates
Circuit breaker + bulkhead
  • Wrap the cache layer with Resilience4j (@CircuitBreaker, @TimeLimiter)
  • If Redis latency or error rate spikes, the breaker opens → calls skip Redis entirely
  • Half-open probes restore traffic gradually once Redis recovers
10 Common pitfalls
  • Cache stampede (thundering herd). A popular key expires → every replica misses simultaneously and hammers the DB. Fix: add TTL jitter (random offset on each key), use a single-flight lock (Redisson getLock) so only one request repopulates, or use a stale-while-revalidate pattern.
  • Stale data. Without invalidation, the cache drifts from the DB. Fix: set sensible TTLs, evict on writes, or use event-driven invalidation via Kafka / Redis Pub-Sub.
  • Hot-key problem. One "celebrity" key (top product, viral post) absorbs all traffic → Redis CPU spikes. Fix: add an L1 in-process cache (Caffeine) in front of L2 Redis (two-tier caching), or shard the key.
  • Big-key problem. Multi-MB values block Redis' single thread on every read/write. Fix: split into smaller keys, use hashes (HSET), or store the big blob in S3 / blob storage and cache only its metadata.
  • Serialization mismatch. Default JDK serializer is slow and version-fragile — one DTO field rename and every cached entry becomes unreadable. Use GenericJackson2JsonRedisSerializer or Kryo.
  • Thundering herd on cold start. A newly deployed pod with an empty cache hits the DB hard on first traffic. Fix: warm critical caches at startup (preload top-N keys in @PostConstruct / ApplicationReadyEvent).
  • Cache penetration. Repeated requests for keys that don't exist bypass cache and hit the DB every time. Fix: cache the negative result (shorter TTL) or front Redis with a Bloom filter.
  • Not setting TTL. Untimed keys accumulate forever; Redis fills up and starts evicting unpredictably under maxmemory-policy. Always set a TTL.

Interview one-liner: In microservices each service runs as many replicas, so an in-process cache no longer works — you need a shared distributed cache, and Redis is the standard choice. The pattern is cache-aside: check Redis → on a miss, load from DB / upstream and write back with a TTL. In Spring Boot you wire it with spring-boot-starter-data-redis + spring-boot-starter-cache, configure a RedisCacheManager with per-cache TTLs, and use @Cacheable / @CachePut / @CacheEvict on the service layer. Redis is preferred in microservices because it provides a shared distributed cache, improves response time, reduces database load, and works well with horizontally scaled service instances.
Distributed Transactions & the Saga Pattern in microservices must

In microservices, one business flow typically touches many services — an e-commerce checkout hits Order → Payment → Inventory → Delivery, each owning its own database. Wrapping all four in a single ACID transaction isn't realistic: there's no shared DB, no shared connection, and brokers like Kafka don't participate in XA. So we deliberately trade strong consistency for eventual consistency and coordinate the flow with a pattern — the Saga being the standard answer.

Core Idea
Saga A saga is a sequence of local transactions in different services. Each step commits in its own DB and publishes an event (or replies to a command). If any step fails, the saga runs compensating transactions in reverse order to semantically undo the work already done — no global lock, no 2PC.
1 Why not 2PC / XA across microservices?

2PC (the classic distributed-commit protocol) does give you ACID across systems — at a cost that's unacceptable in a microservices world.

  • Tight coupling. Every participant must speak XA and trust the same transaction manager — the opposite of independent services.
  • Blocking locks. The coordinator holds locks on every participant from prepare until commit. A slow participant freezes everyone.
  • Low scalability. Lock duration grows with the slowest hop; throughput collapses under network latency.
  • Poor heterogeneous support. Modern stacks barely support XA — Kafka, most NoSQL stores, and many cloud DBs don't participate in 2PC at all.
  • Bad failure semantics. If the coordinator dies between prepare and commit, participants are stuck in a doubt state holding locks until manual intervention.
  • Single point of failure. The transaction manager becomes a global SPOF for the whole platform.

Use a Saga instead: many small local transactions + compensations + asynchronous events. No global locks, each service stays independent, and the broker stays out of the transaction.

2 Happy path — Order checkout saga
Order Service — create Order in PENDING local tx
↓
Inventory Service — reserve stock for the order local tx
↓
Payment Service — charge the customer local tx
↓
Delivery Service — schedule shipment local tx
↓
Order Service — mark order CONFIRMED saga complete

Each step is a normal local ACID transaction in its own service. The saga is only "complete" once the final step commits — until then the order is in an intermediate state and clients must be prepared to see PENDING / RESERVING / PAYING.

3 Failure path — compensating transactions
Order created ok
↓
Inventory reserved ok
↓
Payment fails (insufficient funds / gateway timeout)
↓
Compensation 1 — Inventory Service releases the reservation
↓
Compensation 2 — Order Service marks order CANCELLED

Compensation ≠ rollback. The earlier steps already committed in their local DBs — you can't undo a commit. Instead each service exposes a new business transaction that semantically reverses the effect: releaseReservation, refundPayment, cancelOrder. Compensations run in reverse order of the steps that already succeeded, and must themselves be idempotent (they will be retried).

4 Two saga styles — Choreography vs Orchestration
Choreography (event-driven)
  • No central brain — each service listens to events from peers and decides what to do next.
  • Order publishes OrderCreated → Inventory reacts and publishes InventoryReserved → Payment reacts and publishes PaymentCompleted → …
  • Pros: loose coupling, no orchestrator to deploy, easy to bootstrap for small flows.
  • Cons: business flow is implicit in event subscriptions — hard to visualize, hard to debug, easy to turn into a tangled "event spaghetti" past 3–4 services.
  • Compensation is also distributed — each service listens for failure events (e.g. PaymentFailed) and runs its own compensation.
Orchestration (command-driven)
  • A central Saga Orchestrator (often its own service) drives the flow — sends commands, waits for replies, decides the next step.
  • Orchestrator calls ReserveInventory → on success calls ProcessPayment → on success calls ScheduleDelivery → marks order CONFIRMED.
  • Pros: the saga is explicit and centralized — easy to visualize as a state machine, easy to monitor, easy to add a new step.
  • Cons: the orchestrator becomes critical infrastructure (must be HA + persistent); slightly more upfront design.
  • Built with state-machine engines like Camunda, Temporal, AWS Step Functions, or a hand-rolled SAGA_INSTANCE table.
PickWhen
Choreography2–3 services, simple linear flow, team comfortable with event-driven design, no strict need for a visual saga view.
Orchestration4+ services, branching / conditional steps, regulated / audit-heavy flows (payments, banking), or whenever you need a single place to monitor saga status and retry stuck instances.

Rule of thumb: start with choreography for tiny flows, but switch to orchestration earlier than you think — most teams regret staying on pure choreography past 3–4 services because debugging "why did this order get stuck?" becomes archaeology across N Kafka topics.

5 Choreography flow — events driving each other
Order Service — commit Order(PENDING) + publish OrderCreated
↓
Inventory Service consumes OrderCreated → reserves stock → publishes InventoryReserved
↓
Payment Service consumes InventoryReserved → charges card → publishes PaymentCompleted or PaymentFailed

No central coordinator — the saga "exists" only as the sum of these event subscriptions. On failure (e.g. PaymentFailed), Inventory and Order also listen and run their own compensations.

6 Orchestration flow — central coordinator
Order Service — commit Order(PENDING) → call Saga Orchestrator: startCheckoutSaga(orderId)
↓
Orchestrator → Inventory: ReserveInventory command → reply InventoryReserved
↓
Orchestrator → Payment: ProcessPayment command → reply PaymentCompleted
↓
Orchestrator → Delivery: ScheduleDelivery command → reply DeliveryScheduled
↓

// --- Saga state persisted in the orchestrator's DB ---
@Entity
@Table(name = "saga_instance")

    private String  orderId;

    private Instant updatedAt;
    // getters / setters omitted
}

// --- Orchestrator: drive the next step based on the latest reply ---
@Service
@RequiredArgsConstructor
public class CheckoutSagaOrchestrator {
    private final SagaInstanceRepository sagas;
    private final KafkaTemplate<String, Object> kafka;

    @KafkaListener(topics = "inventory.replies", groupId = "checkout-saga")
    @Transactional                                       // local tx in orchestrator DB
    public void onInventoryReply(InventoryReply reply) {
        SagaInstance s = sagas.findById(reply.sagaId()).orElseThrow();

        if (reply.success()) {
            s.setCurrentStep("PROCESS_PAYMENT");
            sagas.save(s);
            kafka.send("payment.commands",
                new ProcessPaymentCmd(s.getSagaId(), s.getOrderId()));
        } else {
            // Inventory said "no stock" — compensate Order, no payment yet
            s.setStatus("COMPENSATING");
            sagas.save(s);
            kafka.send("order.commands",
                new CancelOrderCmd(s.getSagaId(), s.getOrderId(), "OUT_OF_STOCK"));
        }
    }

    @KafkaListener(topics = "payment.replies", groupId = "checkout-saga")
    @Transactional
    public void onPaymentReply(PaymentReply reply) {
        SagaInstance s = sagas.findById(reply.sagaId()).orElseThrow();

        if (reply.success()) {
            s.setCurrentStep("SCHEDULE_DELIVERY");
            sagas.save(s);
            kafka.send("delivery.commands",
                new ScheduleDeliveryCmd(s.getSagaId(), s.getOrderId()));
        } else {
            // Payment failed — walk compensations backwards
            s.setStatus("COMPENSATING");
            sagas.save(s);
            kafka.send("inventory.commands",
                new ReleaseInventoryCmd(s.getSagaId(), s.getOrderId()));   // compensation
            kafka.send("order.commands",
                new CancelOrderCmd(s.getSagaId(), s.getOrderId(), "PAYMENT_FAILED"));
        }
    }
}

// --- Inventory service: forward step + compensation, both idempotent ---
@Service
@RequiredArgsConstructor
public class InventoryService {
    private final StockRepository       stock;
    private final ReservationRepository reservations;
    private final KafkaTemplate<String, Object> kafka;

    @KafkaListener(topics = "inventory.commands", groupId = "inventory")
    @Transactional
    public void handle(Object cmd) {
        if (cmd instanceof ReserveInventoryCmd c) reserve(c);
        else if (cmd instanceof ReleaseInventoryCmd c) release(c);     // compensation
    }

    private void reserve(ReserveInventoryCmd c) {
        // idempotency — saga may retry; same sagaId must not double-reserve
        if (reservations.existsBySagaId(c.sagaId())) return;
        stock.decrement(c.orderId());
        reservations.save(new Reservation(c.sagaId(), c.orderId()));
        kafka.send("inventory.replies", InventoryReply.ok(c.sagaId()));
    }

    private void release(ReleaseInventoryCmd c) {                       // compensation
        reservations.findBySagaId(c.sagaId()).ifPresent(r -> {
            stock.increment(c.orderId());
            reservations.delete(r);
        });
        // safe to call twice — no-op if reservation already gone
    }
}

Two things to notice: (1) the orchestrator persists SagaInstance in its own DB at every transition — a crash mid-flight can be resumed from the last persisted step; (2) every command handler (both forward and compensation) is written to be safely retried — existsBySagaId on the forward path, ifPresent on the compensation path. In a real codebase you'd publish these commands and replies via the Transactional Outbox pattern so the event publishing is atomic with the local DB write.

10 Common interview gotchas
  • Sagas give eventual consistency, not ACID. Clients can briefly observe inconsistent intermediate states (order PENDING but payment already charged). UI and APIs must be designed for it.
  • Compensation is not rollback. The earlier local tx already committed — you can't undo it. Compensation is a new business transaction (refund, release, cancel) that semantically reverses the effect.
  • Some operations have no compensation. "Send email", "fire missile", "print receipt" — you can't unsend. Order saga steps so non-compensable actions happen last, or expose a forward-recovery action (apology email, refund) instead.
  • Don't reach for 2PC because it sounds simpler. It buys "easier" semantics at the cost of locks, coupling, and a global SPOF — it's worse at scale, not better.
  • Choreography looks simple, then explodes. Past 3–4 services it becomes "event spaghetti" — switch to orchestration earlier than you think, especially when flows branch or have conditional steps.
  • Outbox is almost always paired with Saga. Without the Transactional Outbox, "commit local tx + publish event" is two non-atomic steps — your saga can silently lose a step.
  • Saga state must be persisted. An orchestrator that holds state only in memory loses every in-flight saga on a pod restart. Use a SAGA_INSTANCE table or a workflow engine (Temporal / Camunda) that persists for you.
  • Idempotency on every step is non-negotiable. At-least-once delivery + retries + crash recovery guarantee you'll process the same command twice. Key on sagaId + stepName.
  • Always set step timeouts. A silent downstream that never replies will leave the saga RUNNING forever — define an SLA per step and trigger compensation when it elapses.
Interview one-liner: A microservices business flow spans many services and DBs, so a single ACID transaction across all of them isn't realistic — 2PC / XA is rejected because it's blocking, tightly coupled, doesn't work with brokers like Kafka, and creates a global SPOF. The standard answer is the Saga pattern: model the flow as a sequence of local transactions, each committing in its own service and publishing an event; if any step fails, run compensating transactions in reverse order (which are new business transactions like refund / release / cancel, not real rollbacks). Two flavors — Choreography (services react to each other's events; loose coupling but quickly becomes event spaghetti) and Orchestration (a central coordinator persists SAGA_INSTANCE state and drives every step; clearer, easier to monitor, scales to complex flows — Temporal / Camunda / AWS Step Functions). Production essentials are non-negotiable: idempotency on every step and compensation, dedup via event_id, the Transactional Outbox pattern to atomically commit DB + event, a correlation / sagaId across services, retries with backoff + DLQ, step timeouts, and monitoring + alerts on stuck or compensating sagas. The trade-off you accept is eventual consistency in exchange for independent, scalable services that don't share locks.
Eventual consistency — explain it

Eventual consistency means: if updates stop, all replicas will eventually converge to the same value — but not at the exact same instant. The opposite of strong consistency, which guarantees every read sees the latest write.

It's the consistency model most distributed systems choose because CAP forces a tradeoff during partitions, and pure strong consistency limits scale and availability.

Practical implications:

  • A user might update their profile and see the old value on the next page load (read-your-writes problem) — fix by routing to primary for that user briefly.
  • UI design needs to communicate "processing" states.
  • Background jobs eventually reconcile — for instance, a CDC pipeline updating Elasticsearch from MongoDB takes a few hundred milliseconds.

It's a design choice, not a bug. Most user-facing features tolerate it gracefully if you build for it.

CAP theorem — and PACELC

CAP theorem: in a distributed system you can have at most two of Consistency, Availability, Partition tolerance. Partitions are inevitable in real networks, so the real choice is between CP (refuse requests during partition for consistency) and AP (serve possibly-stale data for availability).

  • CP — HBase, MongoDB (with majority writes), Zookeeper, etcd.
  • AP — Cassandra, DynamoDB, Couchbase by default.

PACELC extends this: even when there's no Partition, you choose between Latency and Consistency. A "PA/EL" system favors availability during partition and low latency otherwise; "PC/EC" favors consistency in both cases.

This is useful framing in design interviews — interviewers love when you frame a system's tradeoffs as PACELC rather than just CAP.

How do you handle distributed transactions in microservices? must

A "distributed transaction" in microservices means coordinating state changes across multiple services / databases / brokers so the system never ends up half-committed. Classical 2PC (XA) is the textbook answer but rarely the right one — modern systems use Saga + Outbox + idempotent consumers, which trade strict ACID for practical, scalable correctness.

CORE IDEA Replace one global transaction with a sequence of local ACID transactions (Saga), use the Transactional Outbox to atomically commit DB state and outgoing events, and require all consumers to be idempotent. No 2PC, no XA — just well-designed eventual consistency.
1 Why 2PC (XA) is avoided
  • Synchronous blocking — every participant locks its data while the coordinator decides commit/abort.
  • Coordinator SPOF — coordinator crash leaves participants stuck holding locks.
  • Heterogeneous systems — Kafka has no XA; Mongo's XA is limited; cross-cloud DBs rarely cooperate.
  • Latency penalty — multiple round trips per transaction.
  • Operationally fragile — recovery scripts, in-doubt transactions, manual cleanup.

5 When to choose what
Use Saga when
  • Workflow spans 2+ services with side effects.
  • Each step has a meaningful business compensation (refund, release inventory).
  • Eventual consistency in seconds is acceptable.
Use Outbox when
  • One service needs to update DB and publish events atomically.
  • You're hitting "DB committed but Kafka publish failed" bugs.
Use 2PC/XA only when
  • All participants are XA-capable databases under your control.
  • Latency budget allows synchronous coordination.
  • You truly cannot tolerate eventual consistency (rare).
6 Common interview gotchas
  • Sagas don't roll back — they compensate. Compensations must be designed up front (and may have their own side effects, e.g., refunds visible to the customer).
  • Each saga step is independently committed — the system passes through legal intermediate states (PENDING, RESERVED) that downstream code must tolerate.
  • Outbox + Kafka gives at-least-once → consumers must dedupe by event_id.
  • Don't confuse Saga with workflow engines (Temporal, Camunda) — those are tools that can implement orchestrated sagas.
  • Choreography across 5+ services becomes "what just happened?" debugging — switch to orchestration earlier than you think.
  • Long-running sagas need timeouts on each step + a watchdog to cancel stuck instances.
  • Idempotency keys must be stable — using a UUID generated at consume time defeats dedup.

Interview one-liner: In microservices we don't use 2PC — instead we combine Saga (a sequence of local transactions with compensations), the Transactional Outbox (atomic DB write + event publish), and idempotent consumers (dedup by event_id). Each step is a local ACID transaction; failures unwind via compensating transactions, not rollback. For complex flows we prefer orchestration (a central state machine like Temporal/Camunda or a custom orchestrator) over choreography. The system is eventually consistent in seconds, scales horizontally, and never holds cross-service locks.

4 End-user identity propagation

When a user-initiated request flows through 5 services, each downstream service needs to know who the end user is to apply authorization. Two approaches:

  • Forward the original user JWT — pass through unchanged in Authorization or a custom X-User-Token header. Each service validates it.
  • Token exchange — gateway swaps the user token for a service-internal token that contains the user claims (RFC 8693). Lets the gateway strip external scopes.

Avoid blindly trusting headers from the network — anyone inside the cluster could spoof them.

5 Secrets — never in source, never in plaintext at rest

  • Inject at runtime via env vars or mounted files (K8s + CSI Secrets Store driver).

6 Common interview gotchas
  • "VPC isolation is enough" — no, lateral movement inside a compromised VPC is the norm. Defense in depth.
  • Long-lived bearer tokens are a footgun — keep TTLs at minutes, not days.
  • mTLS without authorization policies just encrypts; any service with a valid cert can still call any other. Add L7 authz.
  • Forwarding the end-user JWT raw exposes user PII to every hop — consider a stripped internal token.
  • Don't sign your own JWTs in each service — central auth server with rotating keys (JWKS endpoint).

  • Audit who calls what — service-call audit logs are gold during incident response.

Interview one-liner: Secure service-to-service communication is layered: mTLS (often via a service mesh like Istio/Linkerd or SPIFFE/SPIRE) for transport encryption + workload identity; short-lived JWTs (client_credentials flow with internal Auth Server) for caller identity over HTTP/gRPC; L7 authorization at the receiver via @PreAuthorize with scopes; end-user identity propagation via forwarded or token-exchanged JWTs; and secrets in a vault with workload identity (IRSA, GKE WI) replacing long-lived API keys. The rule is "never trust the network" — every internal call is authenticated, authorized, and audited.

How do you prevent cascading failures in microservices? must

A cascading failure is when one slow or failing service drags down its callers, which drag down their callers, until a single downstream issue takes the whole system offline. The defense is a stack of patterns that isolate failure, shed load early, and fail fast instead of fail slowly.

CORE IDEA Combine timeouts + retries with backoff + circuit breakers + bulkheads + rate limiters + load shedding + graceful degradation. The goal: a slow downstream causes controlled, partial degradation in callers, not a total outage.
1 How cascades happen
Payment downstream becomes slow (5s instead of 100ms)
↓
Order Service threads pile up waiting on Payment
↓
Order's Tomcat thread pool exhausts → all endpoints (even unrelated) start failing
↓
Checkout (which calls Order) sees timeouts → its threads pile up
↓
Cascading thread starvation → entire request path is dead

The root cause is almost always missing timeouts + missing isolation — a single slow dependency consumes shared resources (threads, connections, memory) until nothing else can run.

4 Architectural choices that prevent cascades
  • Async over sync — if the caller doesn't need the answer in this request, send a Kafka event instead.
  • Read-side caching — Redis cache absorbs transient downstream outages for read-heavy endpoints.
  • Per-dependency thread pools / connection pools — one slow API can't exhaust the pool another API uses.
  • Backpressure on producers when consumer / DB is unhealthy.
  • Bulkheading at the resource level — separate DB user/connection pools for hot vs cold endpoints.
  • Multi-AZ / multi-region for the dependency itself so partial failure doesn't take all traffic down.
5 Common interview gotchas
  • The single most common production bug: no timeout on an HTTP client. Default infinite timeout is a cascade waiting to happen.
  • Retries without circuit breakers amplify outages — multiply request load on an already-broken service.
  • Retries without jitter cause synchronized recovery storms ("thundering herd").
  • Tomcat / undertow shared thread pool means one slow endpoint can starve all others — use bulkheads or per-route executors.
  • Circuit breakers need sufficient sample size — too small and they trip on noise; too large and they trip too late.
  • Fallbacks must be cheap and side-effect-free — falling back to a "cached price" beats failing, but only if the cache is healthy.
  • Don't put retries at every layer — pick one layer (typically the client) and don't multiply.
  • Health checks must be deep enough to fail when the downstream is broken, but shallow enough not to cascade themselves.

Interview one-liner: Cascading failures happen when a slow downstream consumes shared resources (threads, connections) in callers until everything dies. Prevent them with a stack of patterns: timeouts on every outbound call, circuit breakers to fail fast, bulkheads to isolate per-dependency thread pools, retries with exponential backoff + jitter for transient errors, rate limiters at the edge, load shedding when overloaded, and graceful degradation via fallbacks. In Spring Boot the toolkit is Resilience4j; architecturally, prefer async over sync and cache hot reads. The rule: a slow dependency should cause controlled, partial degradation, never a system-wide outage.

Database per service — really?

Yes — it's the most important rule that makes microservices actually independent. Each service owns its data and is the only one that writes to its database. Other services consume via APIs or events.

Why it matters: shared databases create the worst kind of coupling — schema changes block all consumers, performance issues in one service affect everyone, transactional boundaries blur. A "microservice" reading from another service's tables is a distributed monolith in disguise.

Costs you accept:

  • Cross-service queries become API calls or async data replication.
  • Reporting/analytics need a separate data warehouse (CDC → Snowflake/BigQuery).
  • Distributed transactions need Saga or Outbox.

The tradeoff is worth it. At Indus Net we have a single Mongo cluster, but each service uses its own database (logical separation) — close enough to db-per-service for a small team.

Implementation

Client sends unique idempotency key (UUID) in request header: Idempotency-Key: uuid.

Server: check DB for this key before processing; if found, return cached response; if not, process and store key+response.

DB schema

Table: idempotency_keys(key UUID PK, response JSON, created_at, expires_at). TTL: 24 hours.

Banking

How do you manage configuration?

Microservice configuration is managed externally using Spring Cloud Config Server, Kubernetes ConfigMaps/Secrets, or Vault — enabling environment-specific config without code changes.

Spring Cloud Config

Config Server serves properties from Git repo; microservices fetch on startup with spring.cloud.config.uri.

Refresh: @RefreshScope + /actuator/refresh endpoint — update config without restart.

Kubernetes

ConfigMap: non-sensitive config (DB URL, feature flags). Secret: sensitive (DB password, API keys) — injected as env vars or files.

Banking

Interest rates, fee structures, and payment limits stored in Config Server — business can update without deployment.

Now coming to conclusion.

Never hardcode environment-specific config in code — externalized config enables safe promotion from SIT to PROD.

How do you deploy microservices?

Microservices are deployed as Docker containers orchestrated by Kubernetes using rolling deployments, blue-green, or canary strategies.

Process

Build Docker image → push to private registry (Nexus/ECR) → update Kubernetes Deployment manifest → kubectl apply.

Rolling deployment: Kubernetes gradually replaces old pods with new — zero-downtime deployment.

Banking strategies

Blue-green: run both versions simultaneously; switch traffic instantly; instant rollback by switching back.

Canary: route 5% traffic to new version; monitor error rate; if OK, gradually increase to 100%.

Now coming to conclusion.

Always have a rollback plan — blue-green makes rollback instantaneous, which is critical for banking.

How do you monitor microservices?

Microservices monitoring uses metrics (Prometheus/Grafana), centralized logging (ELK/Splunk), distributed tracing (Jaeger), and health checks (Actuator endpoints).

Metrics

Spring Boot Actuator: /actuator/health, /actuator/metrics, /actuator/prometheus.

Prometheus scrapes metrics; Grafana visualizes: JVM heap, request rate, error rate, response time P95.

Logging and tracing

Centralized logs (ELK): structured JSON logs with trace ID; search across all services in Kibana.

Distributed tracing (Jaeger/Zipkin): visualize request spans across services; identify slow hops.

Alerting

PagerDuty/OpsGenie: alert on error rate > 1%, p95 > 1s, pod crash loops, DLQ message accumulation.

Now coming to conclusion.

Golden signals: latency, traffic, errors, saturation — monitor all four for complete microservice health visibility.

How do you secure microservices?

Microservices are secured using mTLS for service-to-service authentication, OAuth2/JWT for user context, API gateway enforcement, and network policies for isolation.

Service-to-service

mTLS: each service has a certificate; Istio service mesh auto-provisions and rotates certs — transparent to application code.

API gateway validates JWT and forwards user claims as headers to downstream services.

Authorization

Each service enforces RBAC on its own endpoints — doesn't trust caller claims blindly.

Spring Security: @PreAuthorize('hasAuthority('SCOPE_account.read')') on service methods.

Network

Kubernetes NetworkPolicy: restrict pod-to-pod traffic — payment service can only call account service, not admin service.

Now coming to conclusion.

Defense in depth: gateway authentication + mTLS + RBAC + network policy — no single point of security failure.

What challenges have you faced in microservices?

Key microservices challenges include distributed transaction management, service discovery reliability, debugging across services, and data consistency.

Distributed transactions

No ACID across service boundaries — Saga pattern with compensating transactions required; complex to implement correctly.

Debugging

A transaction involves 5 services — finding which service caused a latency spike requires distributed tracing.

Without trace ID correlation, searching logs across services is nearly impossible.

Data consistency

Eventual consistency: payment posted in Transfer Service but not yet reflected in Account Service balance — user sees stale data briefly.

Solution: read-your-writes guarantee via sticky routing or read from write-behind cache.

Now coming to conclusion.

Microservices challenges are mostly operational — invest in observability before decomposing a monolith.
