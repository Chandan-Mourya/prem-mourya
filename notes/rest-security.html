What does "RESTful" actually mean? must

An API is RESTful when it follows the principles of REST (Representational State Transfer) — an architectural style from Roy Fielding's 2000 PhD thesis. In one line: treat everything as a resource, identify it with a URL, and act on it using the standard HTTP methods.

Core Idea
Resource Everything is a "thing" — users, orders, products — identified by a URL.
Verb HTTP method tells you the action: GET / POST / PUT / PATCH / DELETE.
Stateless Every request is self-contained — the server keeps no per-client session.
1 The classic example — a /users resource

In a RESTful API, you don't invent ad-hoc endpoint names like /getUser or /createUser. Instead, you have one URL per resource and the HTTP verb decides what happens.

MethodURLWhat it doesTypical status
GET /users Get all users (list) 200 OK
GET /users/1 Get user with ID 1 200 OK · 404 Not Found
POST /users Create a new user 201 Created
PUT /users/1 Replace user 1 (full update) 200 OK · 204 No Content
PATCH /users/1 Update some fields of user 1 200 OK
DELETE /users/1 Delete user 1 204 No Content
 
# Real curl examples
curl       https://api.example.com/users               # list all
curl       https://api.example.com/users/42            # one user
curl -X POST -d '{"name":"Alice"}' .../users           # create
curl -X PUT  -d '{"name":"Alice","email":"x@y"}' .../users/42
curl -X DELETE .../users/42
2 The 6 REST principles (Roy Fielding's constraints)
  1. Client–Server — clear separation of concerns: UI on one side, data & logic on the other.
  2. Stateless — every request carries all info needed (auth token, params). The server holds no session about the client. Easy to scale horizontally.
  3. Cacheable — responses indicate whether they can be cached (Cache-Control, ETag). GETs are cacheable by default.
  4. Uniform Interface — same set of HTTP verbs everywhere, resources are URLs, payloads are self-describing (JSON + content type).
  5. Layered System — clients don't know if they're talking directly to the server or through a load balancer / CDN / proxy.
  6. Code on Demand (optional) — server can ship code (e.g. JavaScript) for the client to execute.

In practice you'll hear "RESTish" — most real APIs are pragmatic and skip HATEOAS (hypermedia links in responses) since few clients use it.

3 Good vs Bad URL design
RESTful — Resources (nouns)
  • GET /users
  • GET /users/42
  • GET /users/42/orders
  • POST /orders
  • DELETE /orders/99
Not RESTful — Verbs in URL
  • GET /getUsers
  • GET /getUserById?id=42
  • POST /createUser
  • POST /deleteOrder?id=99
  • GET /users/list

Rule: URLs identify what (the noun); HTTP methods describe what to do (the verb).

4 Common HTTP status codes you should use

5 What "RESTful" looks like in practice
  • JSON over HTTP — almost always (binary / XML in rare cases).
  • Stateless auth — JWT in Authorization: Bearer ... header, no server-side session.
  • Resource-oriented URLs — /users/42, not /getUser?id=42.
  • Plural nouns — /users not /user (consistent).
  • Nesting for relationships — /users/42/orders.
  • Filtering / sorting / paging via query params — ?status=active&page=2&limit=20.
  • Versioning — usually /v1/users.
  • Correct status codes — never return 200 OK with {"error": "..."} in the body.
  • HTTPS always — REST itself is transport-agnostic, but you should be encrypting in transit.

Interview one-liner: A RESTful API follows REST principles for designing web services. In REST, everything is treated as a resource, accessed through URLs, and operated on using standard HTTP methods — GET to fetch, POST to create, PUT/PATCH to update, DELETE to remove. It's stateless (each request carries all info needed), uses standard HTTP status codes, and typically exchanges data in JSON. The classic example: GET /users lists users, POST /users creates one, PUT /users/1 updates user 1, DELETE /users/1 deletes them. Real APIs are usually "RESTish" — pragmatic and skip HATEOAS.
REST vs SOAP — what is the difference? must

REST and SOAP are two different styles of building web services, and in banking projects you often see both.

REST is an architectural style. SOAP is a protocol with a strict XML message format.

This difference matters a lot in Oracle / core banking interviews because many legacy bank integrations still use SOAP, while new microservices usually use REST.

Now coming to REST.

REST treats everything as a resource identified by a URL.

We use standard HTTP methods:

GET to read

POST to create

PUT / PATCH to update

DELETE to remove

Data is usually JSON (sometimes XML).

REST is stateless — each request carries everything needed (headers, token, body).

Example:

GET /accounts/12345

POST /payments

REST is lightweight, easy for browsers and mobile apps, and very common in modern Spring Boot microservices.

Now coming to SOAP.

SOAP (Simple Object Access Protocol) is a formal XML-based protocol.

Every SOAP message has a standard structure:

Envelope

Header (optional — security, routing)

Body (the actual request/response)

SOAP services are described using WSDL (contract) and often validated with XSD.

SOAP usually runs over HTTP but can run over other transports (JMS, SMTP in older systems).

SOAP has built-in standards for:

WS-Security

WS-Addressing

transaction coordination (in enterprise stacks)

That is why many core banking and enterprise vendors still expose SOAP APIs.

Now coming to key differences (interview table in words).

Message format: REST → mostly JSON; SOAP → XML only.

Contract: REST → OpenAPI/Swagger is common but optional; SOAP → WSDL is mandatory for code generation and integration.

Operations: REST → resource + HTTP verb; SOAP → operation name inside SOAP body (for example transferFunds).

State: REST → stateless by design; SOAP → can be stateless or stateful depending on design.

Security: REST → HTTPS + JWT/OAuth2; SOAP → HTTPS + WS-Security (signing, encryption in XML).

Performance: REST → smaller payloads, faster for mobile/web; SOAP → heavier XML parsing, more overhead.

Tooling: REST → Postman, curl, browser; SOAP → SoapUI, XML logs, WSDL-based clients.

Now coming to when I would use which.

I choose REST when:

building new microservices

exposing APIs to mobile/web channels

needing fast iteration and simple integration

I choose SOAP when:

integrating with legacy core banking or vendor systems

WSDL contract is already published and fixed

strict XML security standards (WS-Security) are required

In many bank projects, the pattern is: internal new services = REST, integration with CBS/vendor = SOAP, sometimes bridged by an ESB/OSB.

Now coming to how we consume them in Java.

For REST in Spring Boot: @RestController, WebClient / Feign.

For SOAP: generate stubs from WSDL using JAX-WS or Spring WS; call port types like transferPort.transfer(request).

Debugging SOAP often means reading full XML request/response in logs (with masking for sensitive fields).

Now coming to conclusion.

REST is a flexible, lightweight style for modern APIs. SOAP is a strict, XML-based protocol with strong enterprise features and WSDL contracts.

For Oracle banking roles, show you can work with both — REST for new development, SOAP for legacy and vendor integration.

REST vs gRPC — when to pick which must

Both REST and gRPC are ways for services to talk to each other in a distributed system, but they sit on different ends of the spectrum. REST is resource-oriented, JSON over HTTP/1.1, browser-friendly. gRPC is RPC-oriented, Protocol Buffers over HTTP/2, optimized for service-to-service performance.

Core Difference
REST Resource-oriented: URIs identify resources, HTTP verbs act on them, JSON payloads. Simple, human-readable, ubiquitous.
gRPC Action-oriented (RPC): you call methods defined in a .proto contract. Binary protobuf over HTTP/2. Fast and strongly typed.
Rule of thumb REST for external / public-facing APIs. gRPC for internal microservice-to-microservice traffic.
1 How they look — side-by-side
REST — JSON over HTTP
  • Endpoints are nouns: GET /users/42
  • Payload is JSON (human readable)
  • Built on top of HTTP/1.1 (or HTTP/2)
  • Contract is informal — OpenAPI / Swagger optional
  • Test from curl / browser / Postman
gRPC — Protobuf over HTTP/2
  • Endpoints are verbs: UserService.GetUser({id: 42})
  • Payload is binary protobuf — small & fast
  • Built on HTTP/2 (multiplexing, header compression)
  • Contract is the .proto file — generates client + server stubs
  • Strongly typed end-to-end across languages

4 Performance — why gRPC wins on the wire
  • Protobuf vs JSON: binary encoding, field numbers instead of names, no whitespace — usually 3–5× smaller payloads.
  • HTTP/2 multiplexing: many requests share one TCP connection — no head-of-line blocking, no connection-per-call overhead.
  • HPACK header compression: HTTP headers (auth tokens, trace IDs) are compressed and reused across requests.
  • Strong typing → fewer bugs: the compiler catches schema mismatches before runtime.
  • Persistent connections + keep-alive: ideal for high-frequency service-to-service traffic.
  • Typical real-world wins: 2–10× faster latency, 50–80% smaller bandwidth.
5 Streaming — gRPC's killer feature

gRPC supports four call types out of the box, none of which REST gives you natively:

TypePatternExample use
Unary1 request → 1 responseStandard CRUD call
Server streaming1 request → N responsesLog tail, price ticker, LLM tokens
Client streamingN requests → 1 responseFile chunk upload, metric batches
Bi-directionalN ↔ NChat, real-time game state

REST would need SSE or WebSocket for any of the streaming patterns. gRPC bakes it in.

6 When to use which

Use REST when…

  • Public / external API — third parties consume it
  • Browsers / mobile apps call you directly
  • You want CDN caching of GETs
  • Maximum ecosystem & tooling support
  • Casual curl / Postman debugging
Examples: GitHub API, Stripe API, public Twitter/X API.

Use gRPC when…

  • Internal microservice ↔ microservice
  • Low latency & high throughput required
  • You need streaming (server / bidi)
  • Polyglot services share a strict contract
  • Service mesh (Istio, Linkerd) — gRPC is first-class
Examples: Google internal, Netflix, Square, most modern microservice platforms.

Use both (common pattern)

  • REST/JSON at the edge (public, browser-friendly)
  • gRPC internally between services
  • API Gateway translates REST → gRPC
Tools: grpc-gateway, Envoy, Istio. You write the gRPC service once, expose REST automatically.

GraphQL — the third option?

  • Flexible queries, single endpoint, client picks fields
  • Used by Facebook, Shopify, GitHub (v4)
  • Different shape problem: client-driven aggregation
Note: GraphQL is not a direct replacement for either — orthogonal concern.
7 Operational trade-offs
  • Browser support: gRPC needs gRPC-Web + a proxy (Envoy) — you can't directly call gRPC from a browser. REST works everywhere.
  • Debugging: REST = curl & eyeball the JSON. gRPC = binary on the wire, needs grpcurl or BloomRPC.
  • Caching: REST GETs cache beautifully in CDNs / proxies. gRPC has no equivalent — caching must be at the app layer.
  • Versioning: protobuf field tags make backward compatibility easy — never reuse a tag, mark removed fields reserved. REST relies on URL versions or media-type negotiation.
  • Load balancers: classic L4 LBs can break gRPC because all calls share one TCP connection — use an L7 LB that's HTTP/2-aware (Envoy, ALB, NGINX).
  • Code-gen workflow: gRPC requires a build step. Helpful tooling (Buf, protoc, plugins) but it's overhead REST avoids.
Interview one-liner: Both REST and gRPC are communication mechanisms for distributed systems. REST is resource-oriented, uses JSON over HTTP, and is simple, human-readable, and browser-friendly — ideal for public-facing APIs. gRPC is an RPC framework using Protocol Buffers over HTTP/2, offering smaller payloads, lower latency, strong typing, and built-in streaming — ideal for internal service-to-service traffic where performance matters. The common pattern in modern systems is to use both: REST at the edge for external clients, and gRPC internally between microservices, with an API gateway bridging the two.
HTTP methods — GET / POST / PUT / PATCH / DELETE

Each has semantic meaning that matters for caching, retries, and idempotency:

  • GET — read. Safe and idempotent. No body. Cacheable.
  • POST — create or "operation". Not idempotent. Body carries the payload.
  • PUT — full replace of a resource at a known URI. Idempotent.
  • PATCH — partial update. Not guaranteed idempotent.
  • DELETE — remove. Idempotent (deleting an already-deleted resource is a no-op or 404, but state is the same).

The idempotency property matters: clients (and proxies) can safely retry GET/PUT/DELETE on network errors, but POST retries can create duplicates — hence idempotency keys.

Important status codes

Categories: 1xx info, 2xx success, 3xx redirect, 4xx client error, 5xx server error. The ones I use most:

  • 200 OK — success with body. 201 Created — POST that creates a resource; include Location header. 204 No Content — success with no body (DELETE, PUT idempotent updates).
  • 301 permanent redirect, 302 temporary, 304 Not Modified for conditional GETs.
  • 400 Bad Request — validation. 401 Unauthorized — not authenticated. 403 Forbidden — authenticated but no permission. 404 Not Found. 409 Conflict — version/state conflict. 422 Unprocessable Entity — semantic validation. 429 Too Many Requests — rate-limited.
  • 500 — generic server error (avoid; be specific). 502/503/504 — upstream/availability/timeout — important to distinguish for retry decisions.
How do you implement idempotency in distributed systems? must

Idempotent means: making the same request many times has the same effect as making it once. In distributed systems, retries are unavoidable — networks drop, clients reconnect, queues redeliver — so non-idempotent endpoints turn every retry into a duplicate charge, duplicate order, or duplicate payment. Production systems make every state-changing operation idempotent by design.

CORE IDEA Stamp every write request with a stable Idempotency-Key. The server records the key + result on first execution; on retry with the same key, it returns the cached result without re-executing the side effect.
1 Where idempotency matters
  • Payments — duplicate charges are catastrophic.
  • Order placement — duplicate orders are at best confusing, at worst inventory loss.
  • External API calls — Stripe, Twilio, AWS SDK — anything where the network might drop after the side effect.
  • Kafka consumers — at-least-once delivery means the same event will be processed twice.
  • Webhook receivers — providers retry; you must dedupe.
2 The HTTP idempotency-key flow (Stripe pattern)
Client generates UUID for the operation: Idempotency-Key: 5f3b...
↓
Server checks idempotency store keyed by (key, endpoint)
↓
First time → execute business logic → persist (key, status, response) in same DB transaction
↓
Return response with Idempotency-Replayed: false
↓
Same key arrives again (retry) → return stored response with Idempotency-Replayed: true
3 Server-side implementation
// Idempotency table — colocated with the business DB
CREATE TABLE idempotency_records (
    key            VARCHAR(64)  NOT NULL,
    endpoint       VARCHAR(128) NOT NULL,
    request_hash   VARCHAR(64)  NOT NULL,    -- guard against same key, different body
    response_body  JSONB,
    response_code  INT,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (key, endpoint)
);
@PostMapping("/payments")
@Transactional
public ResponseEntity<PaymentResult> charge(
        @RequestHeader("Idempotency-Key") String key,
        @RequestBody @Valid ChargeRequest req) {

    String requestHash = sha256(req);
    String endpoint = "/payments";

    Optional<IdempotencyRecord> existing = idempotencyRepo.findByKeyAndEndpoint(key, endpoint);
    if (existing.isPresent()) {
        IdempotencyRecord rec = existing.get();
        if (!rec.getRequestHash().equals(requestHash)) {
            return ResponseEntity.status(409)
                .body(new PaymentResult("Idempotency-Key reused with different body"));
        }
        return ResponseEntity.status(rec.getResponseCode())
            .header("Idempotency-Replayed", "true")
            .body(deserialize(rec.getResponseBody()));
    }

    PaymentResult result = paymentService.charge(req);

    idempotencyRepo.save(new IdempotencyRecord(key, endpoint, requestHash,
                                               serialize(result), 200));
    return ResponseEntity.ok(result);
}

Persisting the idempotency record + business write in the same DB transaction is the key. If the transaction commits, both succeeded; if it rolls back, the next retry with the same key starts fresh.

4 Two storage choices
Same DB as business data
  • Atomic with the business write — no dual-write risk.
  • Slower but simpler.
  • Default choice for financial / order systems.
Redis with TTL
  • Fast — sub-millisecond lookups.
  • Lossy — Redis isn't always durable across failover.
  • Use only when the operation itself is also recoverable (e.g., the natural-key check would catch duplicates).
5 Natural-key idempotency (no separate key needed)

Sometimes the business itself provides idempotency:

  • UPSERT … ON CONFLICT (order_id) DO NOTHING — same orderId twice = no-op.
  • Optimistic locking with @Version — second update with stale version fails.
  • Webhook providers stamp every event with a unique event_id — dedupe in a small processed_events table.

Prefer natural-key idempotency where it's possible — fewer moving parts than an idempotency-key header.

6 Common interview gotchas
  • Idempotency-Key on the request is generated by the client, not the server. Server-generated keys defeat the purpose.
  • The key must be stable across retries — same UUID for the same business operation.
  • Store the request hash alongside the key — replay with the same key but a different body should return 409, not silently succeed.
  • Idempotency record + business write must be in the same DB transaction, otherwise retries can run side effects twice.
  • TTL the table (24h–7d) — keys live forever otherwise.
  • GET / HEAD are inherently idempotent and need no key. PUT and DELETE are idempotent by HTTP definition. POST is the case that needs an explicit key.
  • Don't reuse the idempotency key for retries with logically different inputs.
  • For Kafka consumers, the equivalent is a processed_events(event_id PRIMARY KEY) dedup table.
  • Document the key in your API spec — clients need to know it exists.

Interview one-liner: In a distributed system every state-changing call must be idempotent — same request applied N times has the same effect as once. The standard pattern (popularised by Stripe) is an Idempotency-Key request header plus an idempotency table keyed by (key, endpoint) with the request hash and stored response. The first call executes the business logic and persists the record in the same DB transaction; subsequent calls with the same key return the stored response without re-executing. For Kafka consumers, the equivalent is dedup by event_id in a processed_events table. Where possible, prefer natural-key idempotency (UPSERT on a business id) — simpler, no extra header.

Application Security with Spring Security — overview must

Spring Security is the standard framework for securing Spring / Spring Boot applications. It handles authentication (who you are), authorization (what you can do), and a bunch of cross-cutting concerns — JWT/OAuth2 integration, password hashing, CSRF protection, session management, and common attack mitigations — through a pluggable chain of servlet filters.

CORE IDEA Every HTTP request goes through a chain of security filters before it ever reaches your controller. Each filter handles one concern — authentication, CSRF, CORS, authorization. Configure them once; every endpoint is protected by default.

What Spring Security gives you out of the box:

AuthorizationDecide what an authenticated user can access — by role, by permission, by SpEL expression.
JWT / OAuth2 / OIDCModern, stateless API security via tokens — built-in resource-server support.

Authentication vs Authorization — the foundation everyone confuses:

Authentication (AuthN)

"Who are you?"

  • Verify credentials — password, token, certificate.
  • Result: a verified Authentication object in the SecurityContext.
  • Example: Login.
Authorization (AuthZ)

"What are you allowed to do?"

  • Decide if the authenticated user can access this resource.
  • Enforced via roles / authorities / SpEL rules.
  • Example: only ADMIN can hit /admin/**.

How a request flows through Spring Security:

Client request hits the server
↓
Security Filter Chain intercepts (a list of servlet filters)
↓
Authentication filter (e.g., JwtAuthFilter) reads the token / credentials
↓
AuthenticationManager validates and produces an Authentication object
↓
Stored in SecurityContextHolder for the rest of the request
↓

↓

The minimum modern config (Spring Security 6 / Boot 3) — stateless JWT API:

@Configuration
@EnableWebSecurity
@EnableMethodSecurity     // for @PreAuthorize / @PostAuthorize
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http,
                                           JwtAuthFilter jwt) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())                             // stateless API
            .sessionManagement(s ->
                 s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**", "/actuator/health").permitAll()
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwt, UsernamePasswordAuthenticationFilter.class)
            .build();
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

JWT-based authentication — the typical flow:

User POST /auth/login with credentials
↓
Server validates credentials → issues a signed JWT (with sub, roles, exp)
↓
Client stores the token, sends Authorization: Bearer <token> on every request
↓

↓

Password storage — never plain text:

String hash = passwordEncoder.encode(rawPassword);    // store this
boolean ok = passwordEncoder.matches(rawPassword, hash);

BCryptPasswordEncoder (or Argon2) — slow, salted, designed to resist brute-force. Spring Boot picks a sensible default; never roll your own hashing.

Role-based access control:

// URL-level
.authorizeHttpRequests(auth -> auth
    .requestMatchers("/admin/**").hasRole("ADMIN")
    .requestMatchers("/users/**").hasAnyRole("USER", "ADMIN")
    .anyRequest().authenticated());

// Method-level
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) { ... }

@PreAuthorize("hasRole('USER') and #userId == authentication.principal.id")
public Profile getProfile(Long userId) { ... }

Why Spring Security in production:

  • Secure by default — every endpoint requires authentication unless explicitly opened with permitAll().
  • Battle-tested filters — CSRF, CORS, secure headers, session fixation are handled for you.
  • Industry-standard auth — built-in support for OAuth2, OIDC, JWT, SAML, LDAP.
  • Fine-grained access control — per-URL, per-method, per-row with SpEL.
  • Plays well with the ecosystem — Keycloak, Auth0, AWS Cognito, Spring Cloud Gateway.

Interview one-liner: Spring Security is the framework for securing Spring Boot applications. It handles authentication ("who you are"), authorization ("what you can do"), and common protections like JWT/OAuth2, password encryption (BCryptPasswordEncoder), CSRF, CORS, and secure headers — implemented as a chain of servlet filters that run before every request reaches the controller. The typical setup is a stateless JWT-based API: client logs in once, receives a signed token, and sends it on every request in the Authorization: Bearer ... header; Spring Security validates the signature, populates the SecurityContext, and enforces role-based access via @PreAuthorize or URL matchers.

Spring Security Filter Chain — how requests flow through filters, and JWT auth in detail must

Spring Security isn't magic — under the hood it is a chain of servlet filters. Every HTTP request that hits a Spring Boot app passes through this chain before reaching your @RestController. Each filter handles one concern (authentication, authorization, CSRF, CORS, JWT parsing, exception translation, security headers) and they run in a strict, well-known order. Understanding this chain is the single most useful mental model for debugging Spring Security in interviews and in production.

CORE IDEA Spring Security is just a chain of servlet Filters registered with the servlet container via FilterChainProxy. Every request walks the chain top-to-bottom — authentication first, authorization later — and only reaches the controller if no filter rejects it.

What the filter chain handles:

  • Authentication — verify the caller's identity (form login, Basic auth, JWT, OAuth2).
  • Authorization — check the authenticated user against URL / method rules.
  • JWT validation — extract Authorization: Bearer ..., verify signature + exp.
  • Session management — load / save SecurityContext across requests, control the session creation policy.

The custom JwtAuthenticationFilter — one job: validate the token and populate the context:

@Component
public class JwtAuthenticationFilter extends OncePerRequestFilter {

    private final JwtUtil jwt;
    private final UserDetailsService users;

    public JwtAuthenticationFilter(JwtUtil jwt, UserDetailsService users) {
        this.jwt = jwt;
        this.users = users;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req,
                                    HttpServletResponse res,
                                    FilterChain chain)
            throws ServletException, IOException {

        String header = req.getHeader("Authorization");
        if (header != null && header.startsWith("Bearer ")) {
            String token = header.substring(7);
            try {
                String username = jwt.extractUsername(token);              // throws if signature / exp invalid
                if (username != null &&
                    SecurityContextHolder.getContext().getAuthentication() == null) {

                    UserDetails ud = users.loadUserByUsername(username);
                    UsernamePasswordAuthenticationToken auth =
                        new UsernamePasswordAuthenticationToken(ud, null, ud.getAuthorities());
                    auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                    SecurityContextHolder.getContext().setAuthentication(auth);
                }
            } catch (JwtException ignored) {
                // invalid token — leave context empty; ExceptionTranslationFilter → 401
            }
        }
        chain.doFilter(req, res);                                          // hand off to next filter
    }
}

Important — request blocked early: if any filter rejects the request (bad token, expired token, missing auth, failed authorization), the response is written immediately by ExceptionTranslationFilter and the controller never runs. That's the whole point of putting auth in filters — invalid traffic dies at the edge, before any business code is touched.

JWT Authentication — the end-to-end flow

JWT (JSON Web Token) is the dominant pattern for stateless REST APIs. The flow has two distinct phases: login (issue a token once) and every subsequent request (validate the token cheaply, no DB hit for session lookup).

1. Client POST /login with username + password
↓
2. AuthenticationManager validates credentials via UserDetailsService + PasswordEncoder
↓
3. Server signs a JWT (header.payload.signature) and returns it in the response body
↓
4. Client stores the token (localStorage / sessionStorage / HttpOnly cookie)
↓
5. Every subsequent request carries Authorization: Bearer <token>
↓
6. JwtAuthenticationFilter parses → verifies signature → checks exp → loads UserDetails → sets SecurityContextHolder
↓
7. Request reaches the controller (or 401 Unauthorized if any check fails)

The two flows side-by-side:

Login (issue token)
  • POST /auth/login with credentials.
  • AuthenticationManager.authenticate(...) loads the user and checks the BCrypt hash.
  • On success, build a JWT with sub, roles, iat, exp.
  • Sign with the server secret (HS256) or private key (RS256).
  • Return { "token": "eyJhbGciOi..." }.
  • Happens once.
Subsequent request (validate token)
  • Client sends Authorization: Bearer <token>.
  • JwtAuthenticationFilter extracts the token.
  • Verifies signature (no DB call) and exp.
  • Loads UserDetails, populates SecurityContextHolder.
  • Controller runs with a full auth context.
  • Happens on every API call.

The three parts of a JWT — header.payload.signature:

PartContentsEncoding
HeaderAlgorithm (HS256, RS256) and token type (JWT).Base64Url JSON
PayloadClaims — sub (user id), roles, iat, exp, custom fields.Base64Url JSON
SignatureHMAC/RSA over base64(header) + "." + base64(payload) using the server's secret / private key.Base64Url bytes

Why JWT for modern APIs:

  • Stateless — the server holds no session; the token is self-contained.
  • Scalable — any instance behind a load balancer can validate the token without sticky sessions.
  • No server-side session store — no Redis / DB hit per request just to identify the user.
  • Microservices-friendly — one token works across services that share the same secret / public key.
  • Signed and tamper-proof — any change to the payload invalidates the signature.

JWT gotchas — what trips people up:

  • Never store secrets in the payload — it's base64, not encrypted; anyone with the token can read every claim.
  • Always validate signature and exp — checking one without the other is a classic security bug.
  • Short TTL + refresh tokens — 5–15 min access tokens, longer refresh tokens stored more securely.
  • Hard to revoke — a valid signed token works until exp. Mitigations: short TTL, a server-side denylist, or token versioning.
  • HS256 vs RS256 — HS256 (shared secret) is simpler but every verifier needs the secret; RS256 (asymmetric) lets others verify with a public key without ever holding the signing key.
  • Storage matters — localStorage is readable from any JS (XSS theft risk); HttpOnly + Secure cookies protect against XSS but reintroduce CSRF concerns.

Common interview gotchas:

  • Filter order matters — use addFilterBefore / addFilterAfter deliberately; the JWT filter must run before UsernamePasswordAuthenticationFilter so the context is populated before authorization runs.
  • Extend OncePerRequestFilter — guarantees the filter runs exactly once per request, even with RequestDispatcher forwards and async dispatches.
  • SecurityContextHolder is ThreadLocal — in @Async or reactive code the context doesn't propagate automatically; use DelegatingSecurityContextExecutor and clear it explicitly to avoid leaks.
  • permitAll() still goes through the chain — the whole filter chain runs for every request; permitAll() only tells the authorization filter to allow it.
  • Disable CSRF for stateless JWT APIs — CSRF attacks rely on cookies being auto-sent; with Authorization: Bearer the browser never auto-attaches the token, so CSRF protection is unnecessary noise.
  • Why JWT filter goes before UsernamePasswordAuthenticationFilter — if the JWT is valid, the request is already authenticated and the username/password filter silently skips. Putting it after lets an unauthenticated context fall through and 401 the request even when the token is valid.

Interview one-liner: Spring Security is a chain of servlet filters registered by FilterChainProxy; every request walks the chain — CORS, CSRF, headers, SecurityContext persistence, an authentication filter (form login / Basic / JWT), ExceptionTranslationFilter, and finally the authorization filter (AuthorizationFilter in Spring Security 6, formerly FilterSecurityInterceptor). For modern stateless APIs the pattern is JWT: on POST /login the AuthenticationManager validates credentials via UserDetailsService + BCryptPasswordEncoder and the server signs a token; every subsequent request carries Authorization: Bearer <token>, a custom JwtAuthenticationFilter (extending OncePerRequestFilter, registered with addFilterBefore(..., UsernamePasswordAuthenticationFilter.class)) verifies the signature + exp, loads the user, and populates SecurityContextHolder — so the controller runs with full auth and rejected requests die at the filter without ever touching business code. Filters are the right abstraction because cross-cutting concerns (auth, CORS, CSRF, headers) belong outside business logic, and the stateless JWT pattern scales horizontally with zero session storage.

JWT — what is it, how does it work? hot

JWT (JSON Web Token) is a compact, URL-safe token format with three base64-encoded parts: header (algorithm), payload (claims like sub, exp, roles), and signature (HMAC or RSA over the first two). Format: header.payload.signature.

It's self-contained — the server doesn't need to look up session state. To validate: verify the signature with the secret/public key, check exp, then trust the claims.

Tradeoffs: stateless and scales horizontally, but can't be revoked before expiry without a denylist. Keep tokens short-lived (5–15 min for access tokens) and pair with longer-lived refresh tokens. Never put secrets in the payload — it's signed, not encrypted. Always validate signature on the server; never trust client claims.

Session Management & Cookies — how stateful auth works must

HTTP is stateless — the server forgets about a request the moment it's done. Session Management is how we re-introduce state across requests so the same user stays logged in, keeps their shopping cart, and sees their preferences — usually by combining a server-side session with a client-side cookie.

CORE IDEA On login, the server creates a session (an object holding the user's state) and gives the browser a unique session ID via a Set-Cookie header. The browser sends that cookie back on every request, and the server uses it to look up "who is this?" without asking again.

A cookie is a small piece of data (max ~4 KB) the server sends to the browser, which the browser stores and automatically attaches to subsequent requests for the same domain. Used for session tracking, "remember me", and user preferences.

Session vs Cookie — common confusion cleared up:

Session (server-side)
  • Stored on the server — in memory, Redis, or DB.
  • Holds the actual user data (ID, roles, cart…).
  • More secure — the client only ever sees an opaque ID.
  • Limited by server memory / requires shared store to scale horizontally.
Cookie (client-side)
  • Stored in the browser.
  • Usually carries just the session ID, not user data.
  • Visible to the browser (and to JS unless HttpOnly).
  • Sent automatically by the browser on every same-origin request.

OAuth2 vs JWT — what's the actual difference? must

Comparing OAuth2 and JWT is a category mistake — they solve different problems and are commonly used together. OAuth2 is a protocol for delegated authorization; JWT is a token format. The right answer in an interview is "they're not alternatives — OAuth2 typically uses JWT as the token format".

CORE IDEA OAuth2 = protocol (how clients obtain tokens from an Authorization Server). JWT = token format (a self-contained, signed JSON token). Most modern OAuth2 deployments issue access tokens encoded as JWTs.

  • Web/mobile/SPA apps logging users in.
  • User redirected to Auth Server → consents → returns with auth code.
  • App exchanges code (+ PKCE verifier) for access token + refresh token.
  • The default modern flow.

  • Machine-to-machine — no user involved.
  • Service authenticates with client_id + client_secret → gets access token.

  • Devices without browsers (TVs, CLI tools) — user logs in on a phone using a code.

4 The two scenarios that confuse people
"OAuth2 with JWT" (modern default)
  • Auth Server issues access tokens as JWTs.
  • Resource Server validates JWT signature locally — no introspection call.
  • Fast, scalable, stateless.
"OAuth2 with opaque tokens"
  • Token is a random string — meaningful only to Auth Server.
  • Resource Server calls /introspect per request to validate.
  • Easy to revoke (Auth Server checks DB) but slow.

"Plain JWT auth" (no OAuth2) is also valid for internal systems — your service issues JWTs at login and validates them on every request. Cheap, fast, and doesn't need a full OAuth2 setup.

6 Common interview gotchas
  • "OAuth2 vs JWT" is the wrong question — they're complementary. The right comparison is OAuth2 with JWT vs OAuth2 with opaque tokens, or session cookies vs JWT.
  • JWTs cannot be revoked on demand without external state — use short TTL (5–15 min) + refresh tokens.
  • JWTs are signed but not encrypted — anyone with the token can read the claims. Don't put PII or secrets in them.
  • Always validate iss, aud, exp, and the signature — accepting "any valid JWT" is a critical bug.
  • OAuth2 is for authorization, not authentication — for "who is the user?" use OpenID Connect (OIDC), the identity layer on top of OAuth2.
  • Don't store JWTs in localStorage if your app is also vulnerable to XSS — XSS reads them. Prefer HttpOnly cookies or secure mobile storage.
  • PKCE is mandatory for public clients (SPA, mobile) — it's no longer optional.
  • Symmetric (HS256) signing requires sharing a secret between Auth Server and every Resource Server — prefer asymmetric (RS256/ES256).

Interview one-liner: OAuth2 and JWT solve different problems — OAuth2 is a protocol for delegated authorization (Authorization Server, Resource Server, Client, flows like Authorization Code + PKCE and Client Credentials), while JWT is a token format (signed, base64-encoded JSON with claims like sub, scope, exp). Modern systems combine them: OAuth2 issues access tokens encoded as JWTs, validated locally by Resource Servers via the Auth Server's JWKS. The right comparison is "OAuth2 with JWT" vs "OAuth2 with opaque tokens", or "JWT-based stateless auth" vs "session cookies". Plain JWT auth (no OAuth2) is fine for purely internal services; full OAuth2/OIDC is required when third parties or users sign in.

How do you implement role-based access control (RBAC) in Spring? must

Role-Based Access Control assigns permissions to roles and roles to users — instead of binding users directly to permissions. It's the dominant authorization model for enterprise apps because it scales: 10,000 users × 5 roles is far easier to maintain than 10,000 × 50 permissions.

CORE IDEA Users → Roles → Permissions. Authorization checks the role membership (URL or method level), or the permission (finer grained). Spring Security exposes both via hasRole(), hasAuthority(), and SpEL inside @PreAuthorize.
1 Roles vs Authorities (Spring Security terminology)
  • Authority — a generic permission string. Example: "orders:write".
  • Role — an authority with a ROLE_ prefix (Spring convention). Example: "ROLE_ADMIN".
  • hasRole("ADMIN") ↔ hasAuthority("ROLE_ADMIN").
  • Use roles for coarse-grained checks (USER, ADMIN, SUPPORT). Use authorities for fine-grained permissions (orders:read, orders:write).

3 Loading roles + permissions into the SecurityContext
@Service
@RequiredArgsConstructor
public class JpaUserDetailsService implements UserDetailsService {
    private final UserRepository users;

    @Override
    public UserDetails loadUserByUsername(String email) {
        User u = users.findByEmail(email)
            .orElseThrow(() -> new UsernameNotFoundException(email));

        Set<GrantedAuthority> auths = new HashSet<>();
        for (Role r : u.getRoles()) {
            auths.add(new SimpleGrantedAuthority("ROLE_" + r.getName()));
            for (Permission p : r.getPermissions()) {
                auths.add(new SimpleGrantedAuthority(p.getName()));   // e.g. orders:write
            }
        }
        return new org.springframework.security.core.userdetails.User(
            u.getEmail(), u.getPasswordHash(), auths);
    }
}

For JWT-based APIs, the same authorities are encoded as "scope": "orders:read orders:write" or a custom "roles" claim, parsed into SimpleGrantedAuthority by a JwtAuthenticationConverter.

Authentication vs Authorization

Two distinct security concerns that always get mentioned together. Mixing them up is a common security bug.

Core Difference
Authentication (AuthN) Who are you? — proves identity.
Authorization (AuthZ) What can you do? — checks permissions.
1 Order & Dependency
AuthN
  • Comes first.
  • Establishes a verified principal (user identity).
AuthZ
  • Comes after authentication.
  • Decides if the authenticated user can perform the requested action.
2 Mechanisms
AuthN
  • Username + password.
  • MFA / OTP / passkeys.
  • OAuth 2 / OIDC / SSO.
  • API keys, JWT tokens, mTLS for services.
AuthZ
  • Roles (RBAC): admin / user / viewer.
  • Permissions (ACL): can_edit_order.
  • OAuth scopes.
  • Attribute-based (ABAC), policy engines (OPA, Casbin).
3 HTTP Status Codes
AuthN failed
  • 401 Unauthorized — no / invalid credentials.
  • "You haven't proved who you are."
AuthZ failed
  • 403 Forbidden — authenticated but not allowed.
  • "You're known, but you can't do this."
4 In Spring Security
AuthN
  • Filters validate credentials / tokens.
  • Populates SecurityContext with an Authentication object.
AuthZ
  • http.authorizeHttpRequests(...).hasRole("ADMIN").
  • @PreAuthorize("hasAuthority('orders:write')") on methods.
Mnemonic: AuthN = "who", AuthZ = "what can". The biggest real-world bug is Broken Object Level Authorization (BOLA) — you authenticate the user but forget to check whether they own the resource. Always check ownership/scope on every endpoint that returns user data.
CORS — what's the actual problem?

Same-Origin Policy is a browser security feature: a script on a.com can't read responses from b.com by default. This is what prevents a malicious site from reading your bank balance via an iframe.

CORS (Cross-Origin Resource Sharing) is the controlled relaxation — servers send headers telling browsers it's safe to share specific origins. Key headers: Access-Control-Allow-Origin, -Allow-Methods, -Allow-Headers, -Allow-Credentials.

For "non-simple" requests (custom headers, content types) the browser does a preflight OPTIONS request first. If the server doesn't respond correctly, the real request never happens.

In Spring Boot: @CrossOrigin per controller, or a global CorsConfiguration. Pitfalls: don't use * with credentials, and remember CORS is enforced by the browser — server-to-server calls ignore it.

How do you manage API versioning in microservices? must

Once an API has external consumers — mobile apps, partner integrations, or other internal services — every breaking change becomes a coordination problem. Versioning gives consumers a stable contract while letting the API evolve. The non-obvious part: the best versioning strategy is to avoid versioning when possible by making changes backward-compatible.

CORE IDEA Prefer backward-compatible (additive) changes so versioning isn't needed. When a breaking change is unavoidable, use URI versioning (most teams), publish a deprecation policy with Sunset headers, and run versions side by side until consumers migrate.
1 The four versioning styles
StyleExampleProsCons
URI versioning /v1/orders, /v2/orders Visible, easy to route at gateway, easy to test in browser, easy to deprecate per-route Couples version to URL; "RESTful purists" object
Header versioning Accept: application/vnd.shop.v2+json Cleaner URLs, content-negotiation idiomatic to HTTP Invisible in logs/traces; harder to test in browser
Query param /orders?api-version=2 Trivial to implement Pollutes query, easy to forget, cache-unfriendly
Custom header X-API-Version: 2 Decouples from URL, doesn't abuse Accept Non-standard; needs gateway support

For most teams, URI versioning wins because it's visible, debuggable, and obvious at the routing layer.

2 Backward vs Breaking changes — the rule
Backward-compatible (no version bump)
  • Add a new optional field to a request or response.
  • Add a new endpoint.
  • Add a new enum value (only if clients tolerate unknowns).
  • Loosen a constraint (max length increased).
  • New optional query parameter with a default.
Breaking (requires new version)
  • Remove or rename a field.
  • Change a field's type (string → object, int → string).
  • Change response schema shape.
  • Make a previously optional field required.
  • Change authentication / authorization rules.
  • Change endpoint URL or HTTP method.
  • Tighten validation that was previously permissive.
3 Spring Boot — URI versioning
// v1 controller
@RestController
@RequestMapping("/v1/orders")
public class OrderControllerV1 {
    @GetMapping("/{id}")
    public OrderV1Response get(@PathVariable Long id) { ... }

// v2 controller — separate class, separate DTO
@RestController
@RequestMapping("/v2/orders")

    @GetMapping("/{id}")

4 Deprecation policy headers (RFC 8594, draft RFC 9745)
HTTP/1.1 200 OK

Link: <https://api.shop.com/docs/migrate-v1-v2>; rel="deprecation"
Warning: 299 - "Use /v2/orders instead. v1 will be removed on 2026-09-01."

Combined with consumer-side telemetry (which clients are still calling v1?) this makes deprecation a managed process, not a surprise.

5 Internal vs external API versioning
Internal (service-to-service)
  • Use schema evolution (Avro/Protobuf with backward-compat rules) — no explicit versioning needed.
  • Or release v1 + v2 endpoints simultaneously and migrate caller-by-caller.
  • Coordinate via a Schema Registry.
External (public)
  • URI versioning + long deprecation window (6–12 months).
  • Publish OpenAPI spec per version.
  • Track per-client usage; reach out before sunset.
  • Never delete v1 without confirming zero traffic.
6 Versioning the events too

For event-driven systems, the same rules apply to Kafka events:

  • Schema Registry + Avro/Protobuf with backward + forward compatibility configured.
  • Add fields with defaults, never remove or rename.
  • For breaking changes, emit a new event type (OrderPlaced.v2) and let consumers migrate at their pace; deprecate v1 on a schedule.
7 Common interview gotchas
  • "Just version everything" — overuse of versioning creates a maintenance graveyard. Most changes can be additive.
  • Three concurrent live versions is the practical max — beyond that, support cost dominates.
  • Versions should be major numbers only (/v1, /v2) — semantic versioning belongs in libraries, not URLs.
  • "Version" the response shape, not internal implementation — moving from one DB to another should be invisible.
  • Don't set additionalProperties: false aggressively in JSON schemas — it makes adding new fields a breaking change.
  • Document the deprecation policy publicly; don't surprise consumers.
  • Use feature flags for behavioral changes, not version numbers — flags are reversible per request.
  • Keep /v1 alive on a maintenance branch — security patches, but no new features.
  • Track usage per version per consumer — sunset only when traffic is zero.

Interview one-liner: Prefer backward-compatible additive changes over versioning — adding fields, adding endpoints, optional new query params. When a breaking change is unavoidable, use URI versioning (/v1/orders, /v2/orders) with separate controllers and DTOs but a shared service layer; publish deprecation headers (Deprecation, Sunset, Warning) and a 6–12 month deprecation window. For events, use a Schema Registry (Avro/Protobuf) with forward+backward compatibility; for breaking changes, version the event type (OrderPlaced.v2). Track per-version, per-consumer usage so sunset is data-driven, not guesswork.

Rate limiting — strategies

Protects APIs from abuse, runaway clients, and DOS. Common algorithms:

  • Token bucket — a bucket of N tokens refilled at rate r; each request consumes one. Allows bursts up to bucket size. Most popular.
  • Leaky bucket — fixed outflow rate, requests queue up. Smooths bursts.
  • Fixed window — N per minute; simple but edge-of-window bursts double up.
  • Sliding window — fairer; counts requests in a moving window.

Where to implement: API Gateway (Kong, AWS API Gateway, NGINX) for global limits, plus per-service for fine-grained. In Spring Boot I use Bucket4j backed by Redis for distributed counting. Respond with 429 Too Many Requests + Retry-After header. Always exempt or boost limits for authenticated/internal traffic.

What are idempotent APIs?

An idempotent API produces the same result regardless of how many times it is called with the same input — essential for safe retries in banking.

HTTP methods

GET, HEAD, OPTIONS: inherently idempotent (no state change). PUT, DELETE: idempotent by definition.

POST: not idempotent by default — creating a resource twice creates two resources unless dedup is implemented.

Implementation

Idempotency key: client sends unique UUID in Idempotency-Key header; server checks if already processed.

Return same response for duplicate requests without re-executing business logic.

Banking

POST /payments is made idempotent with idempotency key — retry on timeout won't double-debit the account.

Now coming to conclusion.

All payment APIs must be made idempotent — network timeouts and retries are inevitable in banking.

What are HTTP status codes?

HTTP status codes communicate the outcome of an API request: 2xx success, 3xx redirect, 4xx client error, 5xx server error.

Common codes

200 OK, 201 Created (new resource), 204 No Content (success, no body), 206 Partial Content (pagination).

400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests.

500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout.

Now coming to conclusion.

Return semantically correct status codes — returning 200 with an error body breaks client error handling logic.

Difference between 400, 401, 403, 404, 409, 500.

These HTTP status codes each have distinct meanings: 400=invalid input, 401=unauthenticated, 403=unauthorized, 404=not found, 409=conflict, 500=server error.

Definitions

400 Bad Request: malformed request (missing required field, invalid format) — client bug.

401 Unauthorized: no valid authentication credentials — must login/get token first.

403 Forbidden: authenticated but lacks permission — valid token but wrong role.

404 Not Found: resource doesn't exist at this URL. 409 Conflict: state conflict (duplicate record, version mismatch).

500 Internal Server Error: unexpected server-side failure — log it and investigate.

Now coming to conclusion.

Don't return 403 for missing resources (information leakage) — return 404 if user shouldn't know if it exists.

How do you handle pagination?

Pagination returns large result sets in chunks using offset/limit or cursor-based pagination to control response size and server load.

Offset pagination

GET /accounts?page=2&size=20 or ?offset=20&limit=20. Simple to implement; page-by-page navigation.

Problem: if records are inserted/deleted between pages, results may skip or duplicate entries.

Cursor pagination

GET /transactions?after=cursor123&limit=20 — cursor is last seen record's ID/timestamp.

Stable: no skipped records on inserts. Used by social media APIs and high-volume banking exports.

Response

Include: data array, totalCount, pageSize, currentPage (offset) or nextCursor (cursor-based), hasMore.

Now coming to conclusion.

Cursor pagination is superior for banking transaction history — stable under concurrent inserts.

Offset pagination vs cursor pagination.

Offset pagination skips N records (simple but unstable on inserts); cursor pagination uses a record pointer (stable, efficient for large datasets).

Offset

LIMIT 20 OFFSET 40 — skip 40, return next 20. Simple SQL. Problem: O(n) cost for high offsets (DB scans skipped rows).

Cursor

WHERE created_at < :cursor ORDER BY created_at DESC LIMIT 20 — uses index, O(log n) regardless of depth.

Ideal for: infinite scroll, large transaction histories, real-time data with frequent inserts.

Now coming to conclusion.

Use cursor pagination for banking transaction APIs — offset pagination breaks when new transactions are posted during browsing.

How do you handle timeout while calling external APIs?

External API timeouts are handled by setting explicit connection/read timeouts, implementing circuit breaker pattern, and returning a fallback response or queuing for async retry.

Configuration

RestTemplate: requestFactory.setConnectTimeout(3000); requestFactory.setReadTimeout(5000); — set both, never leave at default.

WebClient (reactive): .timeout(Duration.ofSeconds(5)) on the Mono/Flux.

Resilience

Circuit breaker (Resilience4j): after N timeouts, open circuit — fail fast without waiting for timeout.

Banking

How do you make APIs backward compatible?

Backward compatibility is maintained by only making additive changes (new optional fields, new endpoints) and never removing or changing existing fields or their types.

Safe changes

Add new optional request fields with defaults. Add new response fields — clients ignore unknown fields (if using lenient deserialization).

Add new endpoints — existing endpoints unchanged.

Breaking changes (require versioning)

Removing or renaming a field. Changing field type (String to Integer). Changing HTTP method or status code semantics.

Practices

@JsonIgnoreProperties(ignoreUnknown=true) on DTOs — ignores new fields from newer server versions.

Semantic versioning: PATCH for bug fixes, MINOR for backward-compatible additions, MAJOR for breaking changes.

Now coming to conclusion.

Backward compatibility protects existing consumers — breaking it silently causes production failures in dependent systems.

What is PKI?

PKI (Public Key Infrastructure) is the framework of CAs, certificates, and policies enabling trusted public key cryptography for authentication and encryption.

Components

Certificate Authority (CA): issues and signs digital certificates. Root CA → Intermediate CA → End-entity cert.

X.509 certificate: contains public key, subject, issuer, validity period, and CA signature.

Banking use

HTTPS: TLS certificates issued by trusted CA for bank's web and API servers.

SWIFT: digital signing of messages using HSM-stored private keys; recipient verifies with sender's public key.

mTLS: each service has a certificate for mutual authentication in API-to-API calls.

Now coming to conclusion.

PKI is the trust foundation for all secure communications in banking — certificate management is a critical security function.

Public key vs private key.

In asymmetric cryptography, the public key encrypts or verifies; the private key decrypts or signs — only the key holder has the private key.

Uses

Encryption: sender encrypts with recipient's public key; only recipient's private key can decrypt.

Digital signature: signer signs with private key; verifier checks with signer's public key — proves authenticity and non-repudiation.

Banking

JWT RS256: API server signs token with private key; consumers verify with public key — no need to share secret.

SWIFT message signing: bank signs with private key stored in HSM; receiving bank verifies with sender's public key.

Now coming to conclusion.

Public key can be freely shared; private key must never leave the owner's control — store in HSM for critical banking keys.

Symmetric vs asymmetric encryption.

Symmetric encryption uses one key for both encrypt and decrypt (fast, AES); asymmetric encryption uses a key pair (slower, RSA/ECC) — used together in TLS.

Symmetric (AES)

AES-256: fast, suitable for bulk data encryption (database encryption, file encryption).

Key distribution problem: how to share the secret key securely? Solved by using asymmetric for key exchange.

Asymmetric (RSA/ECC)

Slower than symmetric; used for key exchange and digital signatures, not bulk encryption.

TLS uses asymmetric for handshake (key exchange), then switches to symmetric (AES) for data transfer.

Banking

Database encryption: AES-256 for column-level encryption of PAN, account numbers. TLS: RSA/ECC for key exchange.

Now coming to conclusion.

TLS combines both: RSA handshake establishes an AES session key — asymmetric for trust, symmetric for speed.

What is digital certificate?

A digital certificate is a CA-signed document binding a public key to an identity (domain, organization, person) — enabling others to trust that public key.

Contents

Subject: who the cert belongs to (CN=api.bank.com). Issuer: the CA that signed it. Public key. Validity: notBefore, notAfter.

Extensions: Subject Alternative Names (SANs), key usage (for signing, encryption), CRL distribution point.

Validation

TLS handshake: server presents certificate; client verifies CA signature, checks expiry and hostname against SAN.

Now coming to conclusion.

Monitor certificate expiry — an expired certificate causes SSL errors that bring down banking APIs immediately.

What is certificate authority?

A Certificate Authority (CA) is a trusted entity that issues and signs digital certificates, creating the chain of trust that browsers and OS systems rely on.

Hierarchy

Root CA (offline, highly secured) → Intermediate CA (online, issues end-entity certs) → Server/Client cert.

Public CAs (DigiCert, Let's Encrypt): trusted by browsers. Private CA: internal banking API certificates.

Banking

Bank deploys an internal CA (ADCS/Vault) for issuing server and client mTLS certificates for internal APIs.

Public-facing APIs (internet banking, mobile): certificates from public CA for browser trust.

Now coming to conclusion.

Compromise of a CA key requires revoking all its issued certificates — protect CA private keys with HSM.

What is SSL/TLS?

SSL/TLS encrypts network communication between client and server — TLS 1.2/1.3 are the current standards; SSL is deprecated and insecure.

TLS handshake (simplified)

1. Client Hello: supported cipher suites, TLS version. 2. Server Hello: chosen cipher, certificate.

3. Client verifies certificate. 4. Key exchange (RSA/ECDHE). 5. Symmetric session key established. 6. Encrypted data transfer.

Banking requirement

Minimum TLS 1.2; PCI DSS mandates TLS 1.2+. Configure: disable RC4, DES, MD5; enable ECDHE for perfect forward secrecy.

Now coming to conclusion.

Configure TLS correctly — weak cipher suites and TLS 1.0/1.1 are exploitable vulnerabilities in banking APIs.

What is mTLS?

mTLS (Mutual TLS) extends TLS by requiring both client and server to present and validate certificates — providing bidirectional authentication.

How it works

Standard TLS: server authenticates to client. mTLS: additionally, client presents its certificate; server validates it.

Both parties verified by a trusted CA — eliminates the need for API keys or tokens for service-to-service calls.

Banking use

Bank API-to-API communication: payment service to account service authenticated via mTLS — no shared secret needed.

SWIFT connectivity: bank's SWIFT gateway uses mTLS certificates for connectivity to SWIFT network.

Istio service mesh: auto-provisions mTLS certificates for all pod-to-pod communication — transparent to application.

Now coming to conclusion.

mTLS is the gold standard for service-to-service authentication in banking — stronger than API keys or JWT tokens.

How do you store passwords securely?

Passwords must be stored as salted hashes using a slow hashing algorithm (bcrypt, Argon2, PBKDF2) — never as plaintext or reversible encryption.

Algorithm

bcrypt (work factor 10-12): Spring Security's BCryptPasswordEncoder. Argon2: newer, memory-hard, preferred for new systems.

Each password gets a unique random salt — prevents rainbow table attacks on the hash database.

Anti-patterns

MD5/SHA-1 (without salt): broken, crackable. SHA-256 alone (without slow algorithm): too fast for brute force.

Reversible encryption of passwords: if key is compromised, all passwords exposed.

Now coming to conclusion.

BCryptPasswordEncoder is the Spring Security default — use it; don't implement password hashing yourself.

What is hashing vs encryption?

Hashing is a one-way transformation (no key, cannot reverse); encryption is a two-way transformation with a key (encrypted data can be decrypted with the key).

Hashing

SHA-256, bcrypt, Argon2 — same input always produces same output; different input produces different output.

Use for: password storage, data integrity check (hash of file), digital signatures.

Encryption

AES (symmetric), RSA (asymmetric) — data encrypted with key; decrypted with same (AES) or paired (RSA) key.

Use for: storing sensitive data that must be retrieved (account number, PAN in DB), secure transmission.

Banking

Password: bcrypt hash. PAN/account number at rest: AES-256 encryption. Data in transit: TLS encryption.

Now coming to conclusion.

Passwords: hash. Sensitive retrievable data: encrypt. Use the right tool — hashing passwords makes them unrecoverable.

How do you prevent SQL injection?

SQL injection is prevented by using parameterized queries (PreparedStatement) with bind variables — never concatenating user input into SQL strings.

Java

PreparedStatement ps = conn.prepareStatement('SELECT * FROM accounts WHERE id = ?'); ps.setLong(1, accountId);

JPA/JPQL: @Query('SELECT a FROM Account a WHERE a.id = :id') with @Param('id') — parameterized.

PL/SQL

Dynamic SQL: EXECUTE IMMEDIATE 'SELECT ... WHERE id = :1' USING p_id; — always use bind variables.

Never: EXECUTE IMMEDIATE 'SELECT ... WHERE name = ''' || p_name || ''''; — injectable.

Additional defenses

Input validation (whitelist allowed characters). ORMs handle parameterization automatically.

Database user with minimal privileges — even if injection succeeds, damage is limited.

Now coming to conclusion.

Parameterized queries are the complete solution — input validation and ORMs are additional defense-in-depth layers.
