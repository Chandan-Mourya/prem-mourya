What does "RESTful" actually mean? must

REST (Representational State Transfer) is an architectural style from Roy Fielding's 2000 thesis. The core constraints:

  • Client–server separation.
  • Stateless — every request carries all info needed; the server holds no session state about the client (one of the most important).
  • Cacheable responses where appropriate.
  • Uniform interface — identify resources via URIs, manipulate via standard methods (GET, POST, PUT, PATCH, DELETE), self-descriptive messages, HATEOAS (links in responses, rarely fully applied).
  • Layered system, optional code-on-demand.

In practice "RESTful" today usually means: JSON over HTTP, resource-oriented URIs (/users/{id}, not /getUser?id=), correct verbs and status codes, stateless auth via tokens. Most real APIs are RESTish — pragmatic, not religious about HATEOAS.

HTTP methods — GET / POST / PUT / PATCH / DELETE

Each has semantic meaning that matters for caching, retries, and idempotency:

  • GET — read. Safe and idempotent. No body. Cacheable.
  • POST — create or "operation". Not idempotent. Body carries the payload.
  • PUT — full replace of a resource at a known URI. Idempotent.
  • PATCH — partial update. Not guaranteed idempotent.
  • DELETE — remove. Idempotent (deleting an already-deleted resource is a no-op or 404, but state is the same).

The idempotency property matters: clients (and proxies) can safely retry GET/PUT/DELETE on network errors, but POST retries can create duplicates — hence idempotency keys.

Important status codes

Categories: 1xx info, 2xx success, 3xx redirect, 4xx client error, 5xx server error. The ones I use most:

  • 200 OK — success with body. 201 Created — POST that creates a resource; include Location header. 204 No Content — success with no body (DELETE, PUT idempotent updates).
  • 301 permanent redirect, 302 temporary, 304 Not Modified for conditional GETs.
  • 400 Bad Request — validation. 401 Unauthorized — not authenticated. 403 Forbidden — authenticated but no permission. 404 Not Found. 409 Conflict — version/state conflict. 422 Unprocessable Entity — semantic validation. 429 Too Many Requests — rate-limited.
  • 500 — generic server error (avoid; be specific). 502/503/504 — upstream/availability/timeout — important to distinguish for retry decisions.
Idempotency — why and how to implement?

Idempotent: making the same request many times has the same effect as making it once. Critical for POST endpoints that handle money, orders, or external integrations — clients retry on network errors and you don't want duplicate charges.

Pattern: client sends an Idempotency-Key header (UUID). Server stores the key + first response in a fast store (Redis/Postgres) with a TTL. On retry: same key → return the stored response instead of re-executing.

POST /payments
Idempotency-Key: 5f3b...
{ "amount": 1000, "card": "..." }

Stripe popularised this and it's now the industry standard. At Indus Net I added it on the resume-upload endpoint to prevent duplicate parsing when mobile clients retried over flaky networks.

JWT — what is it, how does it work? hot

JWT (JSON Web Token) is a compact, URL-safe token format with three base64-encoded parts: header (algorithm), payload (claims like sub, exp, roles), and signature (HMAC or RSA over the first two). Format: header.payload.signature.

It's self-contained — the server doesn't need to look up session state. To validate: verify the signature with the secret/public key, check exp, then trust the claims.

Tradeoffs: stateless and scales horizontally, but can't be revoked before expiry without a denylist. Keep tokens short-lived (5–15 min for access tokens) and pair with longer-lived refresh tokens. Never put secrets in the payload — it's signed, not encrypted. Always validate signature on the server; never trust client claims.

OAuth2 — flows and use cases

OAuth2 is a delegation framework: let a third-party app act on your behalf without sharing your password. Four main flows:

  • Authorization Code — server-side web apps. Redirect user to login, get a code, exchange code+secret for tokens. With PKCE for mobile/SPA — most secure modern flow.
  • Client Credentials — machine-to-machine; no user. Used for service-to-service auth with a client ID + secret.
  • Refresh Token — get a new access token without re-auth.
  • Implicit and Password — legacy, no longer recommended.

OpenID Connect (OIDC) is a thin identity layer on top of OAuth2 that adds the ID token (a JWT identifying the user). Most "Sign in with Google" buttons are OIDC. In Spring Boot I use spring-boot-starter-oauth2-resource-server to validate access tokens from an identity provider like Keycloak, Auth0, or AWS Cognito.

Authentication vs Authorization

Authentication (AuthN) — proving who you are. Username/password, MFA, OAuth, SSO. The result is an authenticated principal.

Authorization (AuthZ) — deciding what an authenticated user is allowed to do. Roles, permissions, scopes, policies. @PreAuthorize("hasRole('ADMIN')"), attribute-based access control, OPA, Casbin.

The mnemonic: AuthN = "who", AuthZ = "what can". They're often discussed together but solved separately. Common mistake: relying on AuthN alone — once a user is logged in, they can access everything. Always layer AuthZ on top, ideally on the server (never trust the client to hide a button).

In Spring Security: AuthN populates SecurityContext with an Authentication object; AuthZ rules (method security, request-matcher rules) consume it.

CORS — what's the actual problem?

Same-Origin Policy is a browser security feature: a script on a.com can't read responses from b.com by default. This is what prevents a malicious site from reading your bank balance via an iframe.

CORS (Cross-Origin Resource Sharing) is the controlled relaxation — servers send headers telling browsers it's safe to share specific origins. Key headers: Access-Control-Allow-Origin, -Allow-Methods, -Allow-Headers, -Allow-Credentials.

For "non-simple" requests (custom headers, content types) the browser does a preflight OPTIONS request first. If the server doesn't respond correctly, the real request never happens.

In Spring Boot: @CrossOrigin per controller, or a global CorsConfiguration. Pitfalls: don't use * with credentials, and remember CORS is enforced by the browser — server-to-server calls ignore it.

API versioning strategies

Once an API has external clients, breaking changes need versioning. Common approaches:

  • URI versioning — /v1/users, /v2/users. Simple, very visible, easy routing. Most popular.
  • Header versioning — Accept: application/vnd.app.v2+json. Cleaner URLs, but invisible in logs and harder to test in browser.
  • Query param — ?v=2. Easy but messy.
  • Media-type / content negotiation — used by GitHub and other strict APIs.

Best practice — regardless of style — is to avoid versioning when you can by making additive changes (new fields, new endpoints) and using feature flags. When a breaking change is unavoidable, give at least one quarter of overlap with a clear deprecation header (Sunset, Deprecation) and migration guide.

Rate limiting — strategies

Protects APIs from abuse, runaway clients, and DOS. Common algorithms:

  • Token bucket — a bucket of N tokens refilled at rate r; each request consumes one. Allows bursts up to bucket size. Most popular.
  • Leaky bucket — fixed outflow rate, requests queue up. Smooths bursts.
  • Fixed window — N per minute; simple but edge-of-window bursts double up.
  • Sliding window — fairer; counts requests in a moving window.

Where to implement: API Gateway (Kong, AWS API Gateway, NGINX) for global limits, plus per-service for fine-grained. In Spring Boot I use Bucket4j backed by Redis for distributed counting. Respond with 429 Too Many Requests + Retry-After header. Always exempt or boost limits for authenticated/internal traffic.

Common API security risks (OWASP Top 10)

OWASP API Security Top 10 highlights:

  • Broken Object Level Authorization (BOLA) — endpoint /orders/{id} doesn't check ownership; user can read others' orders. The most common vulnerability.
  • Broken Authentication — weak tokens, missing MFA, exposed credentials.
  • Excessive Data Exposure — returning entire entity when API only needs a subset (e.g., password hash or internal flags).
  • Lack of Rate Limiting — leads to scraping, brute force.
  • Mass Assignment — auto-binding request JSON to entity lets attackers set isAdmin: true. Use DTOs, never bind to entities.
  • Injection — SQL, NoSQL, LDAP, OS command. Always use parameterized queries.
  • Improper Asset Management — old API versions still live.
  • Insufficient Logging & Monitoring — can't detect or investigate attacks.

I bake security review into every PR for endpoints touching auth, money, or PII.
