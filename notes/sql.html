Types of joins — INNER, LEFT, RIGHT, FULL, CROSS must

Joins combine rows from two tables based on a condition.

  • INNER JOIN — only rows that match in both tables.
  • LEFT JOIN — all rows from left table; matching rows from right (or NULLs).
  • RIGHT JOIN — opposite of LEFT. Rare in practice; rewrite as LEFT for readability.
  • FULL OUTER JOIN — all rows from both sides; unmatched cells are NULL. Not supported in MySQL natively (use UNION).
  • CROSS JOIN — Cartesian product; M × N rows. Used intentionally for generating combinations.
  • SELF JOIN — a table joined to itself, e.g., employees + their managers from the same employees table.

Watch out: LEFT JOIN ... WHERE right.col IS NOT NULL turns it back into an INNER JOIN. Put filters on the right table in the ON clause, not WHERE.

Primary key vs unique key vs foreign key

Primary key uniquely identifies a row. Implicit constraints: NOT NULL, unique, one per table. Usually backed by a clustered index in InnoDB / SQL Server (table physically ordered by PK). Choose stable, narrow values — synthetic IDs (BIGINT, UUID v7) usually beat natural keys.

Unique key / unique constraint also enforces uniqueness but allows NULLs (one per column in most DBs). You can have many unique keys per table — e.g., email and phone both unique on a users table.

Foreign key references the primary (or unique) key of another table and enforces referential integrity. The DB rejects inserts that reference non-existent parents, and you can cascade on delete/update. Some teams skip FKs at scale for write throughput; I prefer keeping them on for OLTP and only relaxing in event-sourced or sharded systems.

ACID properties hot

A — Atomicity. A transaction is all-or-nothing. Either every statement commits or every change is rolled back. Implemented via undo logs (e.g., InnoDB's undo segments).

C — Consistency. The DB moves from one valid state to another. Constraints (FK, unique, CHECK) and triggers stay satisfied at commit time.

I — Isolation. Concurrent transactions don't see each other's intermediate state. The strictness is configurable via isolation levels — see next question.

D — Durability. Once committed, changes survive crashes. Implemented via write-ahead logs (WAL / redo logs) flushed to disk before commit returns.

ACID is the contract that lets you trust a relational database. NoSQL stores trade ACID for scale; modern systems like CockroachDB or Spanner reclaim much of it across distributed nodes.

Transaction isolation levels

Standard isolation levels from weakest to strongest:

  • READ UNCOMMITTED — can see uncommitted changes (dirty reads). Rarely used.
  • READ COMMITTED — only sees committed data. Each statement gets a fresh view. Default in Postgres, Oracle, SQL Server. Allows non-repeatable reads (same query, different results in same tx).
  • REPEATABLE READ — same row reads the same value throughout the tx. Allows phantom reads (new rows appear) in standard, but InnoDB's gap locks prevent them. Default in MySQL/InnoDB.
  • SERIALIZABLE — strongest; transactions execute as if serial. Usually implemented via predicate locks or 2PL.

Picking the level is a perf/correctness tradeoff. I default to READ COMMITTED and reach for higher only when I see real concurrency bugs.

Indexing strategy for large-scale systems must

Indexes are the single biggest lever for query performance — and the most over-applied feature in production databases. A correct indexing strategy speeds up reads by orders of magnitude while keeping writes affordable. The wrong strategy makes writes slow, doubles storage, and confuses the optimizer.

CORE IDEA Index WHERE / JOIN / ORDER BY columns of the queries that actually run in production — not every column "just in case". Compose indexes by selectivity (most selective leftmost), prefer covering indexes for hot read paths, and remove indexes that the optimizer never picks.

2 Composite indexes — leftmost prefix and column order
-- Useful for queries on (tenant_id), (tenant_id, created_at), and ORDER BY created_at within tenant
CREATE INDEX ix_orders_tenant_created ON orders (tenant_id, created_at DESC);

-- Useless for queries that filter ONLY on created_at — wrong leading column
SELECT * FROM orders WHERE created_at > now() - interval '1 day';   -- won't use it

Rules:

  • Leftmost prefix — only queries that filter on the leading column(s) can use the index.
  • Equality before range — once a range column is reached, subsequent index columns can't be used for further filtering.
  • Most selective column leftmost if both are filtered with equality.
  • Match ORDER BY direction with the index direction (ASC/DESC) for sort-free reads.
3 Covering indexes — the biggest read-side win
-- Postgres / SQL Server: include extra columns
CREATE INDEX ix_users_email_covering
ON users (email)
INCLUDE (id, name, status);

-- Query never touches the table heap — read directly from the index
SELECT id, name, status FROM users WHERE email = 'foo@bar.com';

For hot endpoints (login, profile lookup), a covering index can drop latency by 5–10× because the DB skips the row fetch entirely.

4 The cost of indexes
  • Slower writes — every INSERT/UPDATE/DELETE must maintain every affected index.
  • Storage — wide indexes can rival table size; secondary indexes in InnoDB include the PK value.
  • Optimizer confusion — too many similar indexes can cause poor plan choice.
  • Maintenance — bloat, REINDEX, statistics updates.

Rule of thumb: a high-write OLTP table tolerates 5–8 well-chosen indexes; beyond that, write throughput degrades.

5 Operational practices
  • Use EXPLAIN ANALYZE on every slow query before adding an index.
  • Postgres: pg_stat_user_indexes shows scan counts — drop indexes with idx_scan = 0.
  • Create indexes CONCURRENTLY in production (Postgres) to avoid table locks.
  • Watch index bloat — REINDEX or pg_repack on bloated indexes.
  • For very large tables, partition first, then index per partition (smaller, faster).
  • Maintain statistics (ANALYZE / auto-vacuum) so the optimizer picks the right index.
  • For UUID PKs, prefer UUIDv7 (time-ordered) over UUIDv4 — secondary indexes don't fragment.
6 Special cases at large scale
High-write tables
  • Minimize secondary indexes; consider write-optimized engines (TimescaleDB, ClickHouse).
  • Partition by time, drop old partitions instead of DELETE.
Multi-tenant
  • Lead every composite index with tenant_id.
  • Consider per-tenant partitioning for large tenants.
Search
  • Move full-text out of the OLTP DB — use Elasticsearch / OpenSearch.
  • Sync via CDC (Debezium) or outbox.
Soft delete
  • Partial index WHERE deleted_at IS NULL keeps the index small.
7 Common interview gotchas
  • Indexing every column "just in case" is a write-side disaster.
  • Composite index column order is not commutative — design from query patterns.
  • Functions on indexed columns (e.g., LOWER(email)) defeat the index unless you create an expression index.
  • OR in WHERE often defeats indexes — rewrite as UNION or IN.
  • Implicit type casts disable index use — match column type to parameter type.
  • LIKE 'foo%' uses the index; LIKE '%foo' doesn't (consider trigram / GIN).
  • Wide PK (UUIDv4) bloats every secondary index — prefer BIGINT or UUIDv7.
  • NULL handling differs by engine — Postgres allows NULL in indexes; some engines need partial indexes.
  • Adding an index in production blocks writes by default — use CONCURRENTLY (Postgres) or online DDL tools (gh-ost / pt-osc for MySQL).
  • Index statistics drift over time — ANALYZE is mandatory after big data changes.

Interview one-liner: A production indexing strategy is driven by the queries that actually run, not by table structure. Use B-tree as the default; build composite indexes with the most selective and equality-filtered columns leftmost, matching ORDER BY. Use covering indexes (INCLUDE) for hot read paths to skip the row fetch. Use partial indexes for soft-deleted / filtered subsets. Index everything in WHERE / JOIN / ORDER BY of hot queries; remove indexes that pg_stat_user_indexes shows are never used. In production, create indexes CONCURRENTLY, monitor bloat, and prefer narrow PKs (BIGINT or UUIDv7) so secondary indexes stay small. The biggest cost of bad indexing is slow writes — fewer, sharper indexes beat many speculative ones.

Clustered vs non-clustered index

A clustered index determines the physical order of rows on disk. A table has at most one — typically the primary key. In InnoDB and SQL Server the PK is automatically clustered. Range scans on the PK are very fast because the rows are adjacent.

A non-clustered (secondary) index is a separate structure that stores the indexed column(s) plus a pointer back to the row. In InnoDB the pointer is the PK value (so PK lookups are an extra hop unless the index is covering).

Implication: a wide PK (long UUID v4 strings) bloats every secondary index. That's why UUID v7 (time-ordered) or sequential BIGINT IDs are preferred for high-write tables — narrow and locality-friendly.

EXPLAIN / query plans — how do you read them?

EXPLAIN shows how the optimizer plans to execute a query. Things I look for:

  • Access type — const/ref/range are fine; ALL means full table scan (red flag on big tables).
  • Index used (key) — is it the one you expected?
  • Rows examined vs returned — high ratio means the query reads too much.
  • Extra — "Using filesort" (sort on disk if needed), "Using temporary" (temp table), "Using index" (covering index — good).
  • Cost — Postgres shows actual cost; MySQL has EXPLAIN FORMAT=JSON.

I prefer EXPLAIN ANALYZE (Postgres) or EXPLAIN FORMAT=TREE (MySQL 8) which actually run the query and show timing per step. Combined with auto_explain in production, it tells you which queries are slow and why.

Normalization vs denormalization

Normalization organizes data to reduce redundancy. The levels build on each other:

  • 1NF — atomic columns, no repeating groups.
  • 2NF — no partial dependency on a composite key.
  • 3NF — no transitive dependency.

3NF is the practical sweet spot for OLTP — fewer anomalies on update.

Denormalization deliberately duplicates data for read performance — caching computed totals, embedding lookup names, materialized views. Common in OLAP, search indices, and high-read services.

My approach: design normalized (3NF), then denormalize specific reads if profiling shows pain. Don't pre-optimize. Async pipelines (CDC → ES) often beat in-table denormalization because they can be rebuilt safely.

WHERE vs HAVING — and aggregate order of execution

The logical order of a SELECT statement: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

WHERE filters rows before aggregation. HAVING filters after aggregation — it operates on grouped/aggregated values.

SELECT dept, COUNT(*) AS cnt
FROM employees
WHERE active = TRUE          -- pre-filter
GROUP BY dept
HAVING COUNT(*) > 10;        -- post-filter on aggregate

You can't put COUNT(*) > 10 in WHERE — aggregates aren't computed yet. Common interview trick: which clause filters which stage?

Bonus: column aliases from SELECT aren't usable in WHERE or HAVING in most DBs (MySQL is loose); subquery or CTE if you need that.

Window functions — ROW_NUMBER, RANK, LAG

Window functions compute over a "window" of rows related to the current row, without collapsing them like GROUP BY does. They make many complex queries simple:

-- Top 3 paid employees per department
SELECT * FROM (
  SELECT name, dept, salary,
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
) t WHERE rn <= 3;

Key functions: ROW_NUMBER (always unique within window), RANK (ties share rank, leaves gaps), DENSE_RANK (no gaps), LAG/LEAD (previous/next row), SUM/AVG OVER (...) running totals, moving averages.

Modern OLTP queries I write lean on these heavily — they replace the "self-join with subquery" patterns from older SQL.

Subquery vs CTE vs JOIN

All three combine data, but with different readability and performance characteristics.

JOIN — the optimizer's first choice for combining tables. Almost always rewriteable from a subquery.

Correlated subquery — runs per-row of the outer query. Easy to write but can be slow (N+1 in SQL form). Modern optimizers often unnest them automatically.

CTE (WITH clause) — names a result set for reuse and readability. Recent versions of Postgres/MySQL/SQL Server inline CTEs into the plan (so they're usually free); older Postgres used to materialize them, which sometimes hurt. Recursive CTEs let you query hierarchies (org tree, comments tree).

I write CTEs over deeply nested subqueries for readability, and trust the optimizer. EXPLAIN ANALYZE shows whether a CTE is inlined or materialized.

Lazy Loading — why and where we use it (Hibernate / JPA / Spring) must

Lazy Loading is a design technique where an object or its related data is loaded only when it's actually needed, instead of loading everything upfront. It's a core ORM concept and a frequent backend interview topic.

CORE IDEA Defer expensive work until the moment you need its result. Instead of pulling every related row into memory the first time, fetch the parent now and the children only when the code actually touches them. Saves DB calls, memory, and startup time.

Real-life intuition. When Netflix opens, it doesn't pre-load every movie's metadata, trailer, and reviews. It loads the home screen first, and movie details only when you open a specific tile. That's lazy loading — exactly the same pattern ORMs apply to entity relationships.

Why we use it:

BenefitHow lazy loading helps
PerformanceSkip work the user may never trigger — fewer SQL joins, smaller result sets.
Memory usageOnly the entities actually accessed live in memory.
Faster startupApp boots quickly because heavy beans/objects are created on first use, not at start.
Database optimizationAvoid unnecessary joins; let the ORM emit a follow-up query only if the relationship is read.
ScalabilityLess wasted CPU/IO per request — system handles more load on the same hardware.

Where lazy loading shows up:

Hibernate / JPA
Load related entities (@OneToMany, @ManyToOne) only when accessed — FetchType.LAZY.
Spring Beans
@Lazy defers bean instantiation until first injection — speeds up startup.
Frontend / images
Browsers load <img loading="lazy"> only as they scroll into view.
Microservices
Fetch enrichment data on-demand instead of joining everything upfront.
Caching
Compute and cache values only when first requested (lazy cache population).
Singletons / heavy objects
Build expensive resources (connections, ML models) on first use.

The canonical example — Hibernate FetchType.LAZY:

@Entity
class Department {
    @Id Long id;
    String name;

    @OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
    private List<Employee> employees;   // not loaded with Department
}

What happens internally — step by step:

User requests Department
↓
SELECT * FROM department WHERE id = 1  — only the parent loads
↓
Hibernate returns a proxy for employees (not real data)
↓
Code calls department.getEmployees()
↓
Proxy triggers SELECT * FROM employee WHERE department_id = 1
↓
Real employee list returned and cached on the entity

FetchType examples:

@OneToMany(fetch = FetchType.LAZY)    // default — load on access
@ManyToOne(fetch = FetchType.EAGER)   // default — load with parent

Spring @Lazy — same idea, applied to beans:

@Component
@Lazy
public class HeavyReportService {
    // bean is created only when first injected/used, not at app startup
}

The two big gotchas:

1. LazyInitializationException

Happens when you try to access a lazy field after the Hibernate session is closed (typical when accessing in the controller layer or after the transaction ends).

department.getEmployees().size();
// → LazyInitializationException: could not initialize proxy - no Session

Fixes:

  • JOIN FETCH in JPQL — load relationship in the same query.
    SELECT d FROM Department d JOIN FETCH d.employees
  • @EntityGraph on the repository method — declarative per-query eager fetch.
  • DTO projection — return a flat DTO from the query instead of the entity.
  • Open-Session-in-View (Spring Boot default) — keeps session open across the HTTP request; convenient but easy to abuse.
2. N+1 Query Problem

Lazy loading inside a loop is the most common cause:

List<Department> depts = deptRepo.findAll();   // 1 query
for (Department d : depts) {
    d.getEmployees().size();                   // N more queries
}
// Total: 1 + N queries

Fixes:

  • JOIN FETCH — one query with a join.
  • @EntityGraph — per-query fetch plan on Spring Data repos.
  • @BatchSize — Hibernate batches child queries (e.g., 1 + N/10).
  • Two-step fetch in code — parents, then a single WHERE id IN (...) for children.

Advantages and disadvantages at a glance:

Advantages
  • Faster startup, smaller initial payload.
  • Lower memory footprint.
  • Better scalability under load.
  • Lets you keep entity relationships in code without paying for them every time.
Disadvantages
  • Risk of N+1 queries if you iterate over lazy associations.
  • LazyInitializationException when session/transaction is closed.
  • Harder to debug — proxy objects, hidden queries fired on field access.
  • Open-Session-in-View can mask issues and slow APIs silently.

Best practices I follow:

  • Default to LAZY for collections and large relationships. Mark only small, always-needed ones as EAGER.
  • Be explicit per use case — use JOIN FETCH or @EntityGraph when a screen needs the relationship, instead of changing the entity-level default.
  • Return DTOs from query endpoints — projections avoid both LazyInitializationException and N+1 entirely.
  • Enable SQL logging in dev — watch query counts for list endpoints; one bad N+1 can break production under load.
  • Turn off Open-Session-in-View in serious projects and handle fetching explicitly in the service layer.

One real-world example. In an e-commerce app, when listing orders, we don't want to load every product's full details for every order. Order → Items are LAZY. The order list endpoint uses a DTO projection (just orderId, total, status). When the user opens a specific order, a separate query with JOIN FETCH pulls the items and product summaries. Result: list endpoint stays under 50 ms; detail endpoint still loads in one round-trip.

Interview-ready one-liner: Lazy Loading is a design technique where related data is loaded only when needed, mainly to improve performance, reduce memory, and minimize unnecessary DB calls. In Hibernate / JPA, it's enabled via FetchType.LAZY — Hibernate returns a proxy and fires the child query only when the relationship is accessed. For example, fetching a Department doesn't load employees until department.getEmployees() is called. It scales well, but watch out for LazyInitializationException and the N+1 query problem — solved with JOIN FETCH, @EntityGraph, or DTO projections.

N+1 Problem in JPA — what it is and how to fix it must

The N+1 query problem is one of the most common performance killers in JPA / Hibernate applications. It happens when loading a list of N parent entities triggers N additional queries to load their child data — turning one logical "give me orders with items" request into 1 + N round trips to the database.

CORE IDEA One query loads the parents. Then, for every parent, another query loads its children. 1 + N queries for what should be a single join. The cause is almost always lazy loading inside a loop — and it's invisible in unit tests but lethal under production load.

Where the name comes from:

  • 1 query loads the parent list.
  • N queries — one per parent — load each parent's children.
  • Total: 1 + N = "N+1".

The classic example — Department → Employees:

@Entity
class Department {
    @OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
    List<Employee> employees;
}

// In service:
List<Department> depts = deptRepo.findAll();          // 1 query
for (Department d : depts) {
    d.getEmployees().size();                          // 1 query EACH
}

What Hibernate actually fires:

-- Query 1
SELECT * FROM department;

-- Query 2  (dept 1)
SELECT * FROM employee WHERE department_id = 1;
-- Query 3  (dept 2)
SELECT * FROM employee WHERE department_id = 2;
-- ...
-- Query 11 (dept 10)
SELECT * FROM employee WHERE department_id = 10;

-- TOTAL: 1 + 10 = 11 queries  (for 10 departments)
-- With 1000 departments → 1001 queries

Each extra query is a round trip — network latency + parse + plan + execute. At 5 ms per query, 1001 queries = ~5 seconds wasted on what should be a single join.

Why does it happen?

  • Lazy loading (default for collections) — @OneToMany and @ManyToMany are LAZY by default. Touching the collection inside a loop fires one query each time.
  • Eager loading can do it too — @ManyToOne(fetch = EAGER) on a list endpoint fires one extra query per row to load the parent.
  • Hibernate doesn't see the loop — it sees N individual property accesses on N proxies and dutifully fires N queries.

The symptoms:

  • Endpoint takes 100 ms with 10 rows, 5 s with 500 rows, times out with 5 000 rows.
  • Database CPU spikes on list endpoints.
  • Hibernate SQL logs show repeating SELECT … WHERE id = ? after the parent query.
  • Unit tests pass; production grinds to a halt.

Fix 1 — JOIN FETCH (the most common solution):

@Query("SELECT d FROM Department d JOIN FETCH d.employees")
List<Department> findAllWithEmployees();
-- Single query — fixed!
SELECT d.*, e.*
FROM department d
LEFT JOIN employee e ON e.department_id = d.id;

One query, all data. Caveat: for collections, JOIN FETCH can produce duplicate parents (one row per child) — use SELECT DISTINCT d or a Set in the entity. Also you can JOIN FETCH only one collection per query (Hibernate throws MultipleBagFetchException otherwise).

Fix 2 — @EntityGraph (declarative, Spring Data friendly):

public interface DeptRepo extends JpaRepository<Department, Long> {

    @EntityGraph(attributePaths = {"employees"})
    List<Department> findAll();
}

Per-query fetch plan without changing the entity's default. Reusable, clean, and lets different endpoints have different fetch strategies.

Fix 3 — DTO Projection (often the cleanest):

public interface DeptSummary {
    Long getId();
    String getName();
    Long getEmployeeCount();
}

@Query("""
    SELECT d.id AS id, d.name AS name, COUNT(e) AS employeeCount
    FROM Department d LEFT JOIN d.employees e
    GROUP BY d.id, d.name
""")
List<DeptSummary> findSummaries();

Fetches only the columns you need, in one query, with no lazy proxies and no LazyInitializationException risk. Ideal for list/index endpoints.

Fix 4 — Batch Fetching (@BatchSize):

@OneToMany(mappedBy = "department", fetch = FetchType.LAZY)
@BatchSize(size = 50)
List<Employee> employees;

Hibernate collapses the N queries into ceil(N / 50) queries by batching IDs:

SELECT * FROM employee WHERE department_id IN (1, 2, 3, …, 50);
SELECT * FROM employee WHERE department_id IN (51, 52, …, 100);

You can also set it globally: spring.jpa.properties.hibernate.default_batch_fetch_size=50.

All four fixes — side by side:

FixHow it worksBest forWatch out for
JOIN FETCHOne JPQL with explicit JOIN.Detail endpoints; small/medium child sets.Duplicate parents; one collection per query.
@EntityGraphDeclarative fetch plan per repo method.Spring Data repos; reusable fetch profiles.Same join behaviour & limits as JOIN FETCH.

Why EAGER is NOT the answer:

  • Switching to FetchType.EAGER makes every query load the children — even when you don't need them.
  • It often causes N+1 itself on list endpoints (one extra query per row for @ManyToOne(EAGER)).
  • It encourages "load the world" entity graphs that fall apart under load.
  • Best practice: keep relationships LAZY by default; opt-in to fetching per use case via JOIN FETCH, @EntityGraph, or DTOs.

How to detect N+1 in dev — non-negotiable:

# application.yml

  jpa:
    show-sql: true

Real-world example — list orders with customer:

// BEFORE — N+1 (1 + N queries)
@GetMapping("/orders")
public List<Order> list() {
    return orderRepo.findAll();      // 1 query
    // serializer calls order.getCustomer() → N queries (1 per order)
}

// AFTER — single query
@Query("SELECT o FROM Order o JOIN FETCH o.customer")
List<Order> findAllWithCustomer();

Before: 500 orders → 501 queries → ~3 s. After: 500 orders → 1 query → ~50 ms.

Best practices — the production checklist:

  • Default to FetchType.LAZY on every relationship. Never change the entity-level default to satisfy one endpoint.
  • Be explicit per use case — JOIN FETCH / @EntityGraph / DTOs for the specific screen that needs the children.
  • Return DTOs from list endpoints — projections sidestep both N+1 and LazyInitializationException.
  • Enable SQL logging in dev — count queries on every list endpoint before merging.
  • Use @BatchSize as a global safety net (default_batch_fetch_size=50).
  • Watch for MultipleBagFetchException — you can't JOIN FETCH two collections at once; use Set or split into queries.

Common interview gotchas:

  • EAGER fixes N+1? — No, it often causes it and always wastes work.
  • MultipleBagFetchException — appears when you JOIN FETCH two List collections; change them to Set or fetch separately.
  • Cartesian product — joining two collections inflates row counts (N × M rows); use Set or split queries.
  • Pagination + JOIN FETCH — Hibernate logs a warning and does in-memory pagination. Solution: fetch IDs paginated, then a second query with IN + JOIN FETCH.
  • It happens with @ManyToOne(EAGER) too — list endpoint loads parent → N queries to load each child's parent.

Interview one-liner: The N+1 problem in JPA happens when loading N parent entities triggers N additional queries to load their children — usually caused by lazy loading inside a loop. For example, fetching Departments and then iterating to access employees fires 1 + N SQL statements. The most common fix is JOIN FETCH to load related entities in a single query; other fixes are @EntityGraph for declarative fetch plans, DTO projections for list endpoints, and @BatchSize for batching child queries. The right approach is to keep relationships LAZY by default and opt in to fetching per use case — never switch to EAGER, and always count SQL statements during development.

Optimistic vs Pessimistic locking

Two strategies to prevent lost updates when multiple users edit the same row at the same time. The right choice depends on contention.

Core Difference
Pessimistic Lock the row up-front — others wait until you're done.
Optimistic No lock — check on update; if someone else changed it, you fail and retry.
1 How it Works
Pessimistic
  • SELECT ... FOR UPDATE takes a row-level lock immediately.
  • Other transactions block until the lock is released (commit/rollback).
  • JPA: @Lock(LockModeType.PESSIMISTIC_WRITE).
Optimistic
  • Read without locking, include a version column.
  • On update: UPDATE ... WHERE id = ? AND version = ?.
  • 0 rows affected → someone else wrote first → retry or 409.
  • JPA: @Version field.
2 Performance under Contention
Pessimistic
  • Predictable — first writer wins, others wait.
  • Holds locks while user "thinks" — bad for long edit sessions.
  • Risk of deadlocks.
Optimistic
  • No locks held — high concurrency under low contention.
  • Under high contention, retries pile up and can become wasteful.
  • No deadlocks.
3 Conflict Handling
Pessimistic
  • No conflicts at write time — second writer simply waited.
  • User may not realize they were blocked.
Optimistic
  • Conflicts surface as OptimisticLockException / 0 rows updated.
  • Caller chooses: retry transparently, or return 409 Conflict for the user to refresh and re-submit.
4 Use Case
Pessimistic
  • Short critical sections with high contention.
  • Inventory decrement at sale time, financial postings.
  • When losing a write is worse than blocking briefly.
Optimistic
  • Default for most web CRUD — profile updates, settings, orders.
  • Long edit sessions where you don't want to hold a row lock.
// Optimistic — JPA @Version
@Entity class Order { @Version Long version; }
// UPDATE … WHERE id = ? AND version = ?  → 0 rows = conflict

// Pessimistic — short critical section
@Lock(LockModeType.PESSIMISTIC_WRITE)
Inventory findForUpdate(String sku);  // SELECT … FOR UPDATE

Common interview gotchas:

  • Optimistic under extreme contention — retries pile up; use pessimistic for hot rows.
  • Pessimistic during long user think-time — holds locks, deadlocks.
  • Forgetting OptimisticLockException in the API — return 409, not 500.

Interview one-liner: Default to optimistic (@Version) for web CRUD. Use pessimistic (FOR UPDATE) only for short, high-contention money/inventory paths. Always surface conflicts to the user with a clear refresh message.

Sharding vs partitioning vs replication

All three split or copy data, but for different reasons.

Replication — copy the entire data to one or more replicas. Adds read capacity (read replicas) and fault tolerance (failover). Doesn't help write throughput. Asynchronous replication has lag; synchronous is slower but consistent.

Partitioning — split a single table into chunks within the same database by range (date), list (region), or hash. Each partition is a separate physical structure. Smaller indexes per partition, can drop old partitions cheaply. Postgres has declarative partitioning; MySQL supports it natively.

Sharding — split data across multiple databases/servers by a shard key. Adds write throughput. Complex: cross-shard joins are hard, rebalancing is painful, you need a router. Reach for it only when you've exhausted vertical scaling and replication.

How do you design database transactions in high-concurrency systems? must

Under high concurrency, naive transactions lock too long, escalate to deadlocks, or get retried into pile-ups. The art is to keep transactions tiny, pick the right isolation level, choose the right concurrency control (optimistic vs pessimistic), and structure the code so failures retry safely.

CORE IDEA Tiny transactions, deterministic lock order, the right isolation level for the workload (READ COMMITTED is the production default; bump only if you have a real anomaly to prevent), and explicit choice between optimistic (low contention) and pessimistic (hot rows, money). Make the surrounding code idempotent so retries are safe.
1 The 7 rules
  1. Keep transactions short — open late, commit early. Never call external APIs or wait on user input inside a transaction.
  2. Read outside, write inside — pre-load data outside the transaction; only the actual mutation belongs inside.
  3. Pick a deterministic lock order — always acquire row locks in the same order across the codebase to prevent deadlocks (e.g., always lock account_a before account_b by ascending id).
  4. Use SELECT … FOR UPDATE SKIP LOCKED for queue-style work distribution across many workers.
  5. Default isolation = READ COMMITTED; bump to REPEATABLE READ or SERIALIZABLE only for specific anomalies, with retry logic.
  6. Optimistic locking (version column) for "many readers, occasional conflicts" (CRUD on profiles, orders).
  7. Pessimistic locking only for hot rows where conflicts are frequent and correctness is critical (inventory decrement, balance update).
2 Isolation levels — when each one is right
LevelAllowsWhen to use
READ UNCOMMITTEDDirty readsAlmost never
READ COMMITTEDNon-repeatable reads, phantomsDefault for most apps; Postgres / Oracle default
REPEATABLE READPhantoms (Postgres prevents most)Reports / analytics needing a stable snapshot; MySQL InnoDB default
SERIALIZABLENothing — full serial scheduleTruly conflicting workflows (financial postings) — accept retries on serialization failures
3 Optimistic locking pattern (high concurrency, low conflict)
@Entity
public class Order {
    @Id Long id;
    @Version Integer version;          // Hibernate increments + checks
    String status;
    BigDecimal totalCents;
}

// Hibernate generates: UPDATE orders SET status=?, version=version+1
//                      WHERE id=? AND version=?
// 0 rows affected → OptimisticLockException → retry or 409 Conflict

Pair with retry-on-conflict (Spring Retry or manual loop with a small max attempts) for transparent recovery.

4 Pessimistic + SKIP LOCKED for distributed work queues
// Multiple worker pods read disjoint rows safely
SELECT * FROM jobs
WHERE status = 'PENDING'
ORDER BY created_at
LIMIT 10
FOR UPDATE SKIP LOCKED;

SKIP LOCKED is the killer feature for outbox publishers and async job runners — each worker grabs rows nobody else has, no coordinator needed.

5 Avoiding hot-row contention
  • Sharded counters — split a hot counter across N rows; sum on read.
  • Async aggregation — write events to Kafka/queue; a reducer updates the counter in batches.
  • Per-key serialization — funnel hot-row writes through a single thread (or single Kafka partition).
  • Row partitioning — split per-tenant or per-region so contention stays local.
  • Memoization at the app — Redis CAS or single-flight to absorb concurrent writes.
6 Retry-safe transactions

Any transaction that may be retried (optimistic conflict, deadlock victim, serialization failure) must be:

  • Idempotent — running twice produces the same result.
  • Side-effect-isolated — no external API call inside the transaction (move to outbox + post-commit hook).
  • Time-bounded — capped retries with exponential backoff so we don't infinite-loop.
  • Observable — log + count retries; alert on excess.
7 Common interview gotchas
  • Long transactions hold locks → cascading slowdown for everyone.
  • External HTTP call inside a transaction → connection holds for seconds → pool exhaustion.
  • SERIALIZABLE without retry logic → mysterious 500s under load.
  • Reading and updating without ordering → deadlocks across workers.
  • Putting @Transactional on a private/self-invoked method → silently no-op (Spring proxy).
  • Using SELECT FOR UPDATE without an index → scans + locks more rows than expected, deadlock magnet.
  • Ignoring OptimisticLockException → silent overwrites of concurrent edits.
  • Multi-statement transactions across multiple services → distributed transaction smell; use Saga.

Interview one-liner: Under high concurrency, design transactions to be tiny, retry-safe, and idempotent. Default isolation is READ COMMITTED; bump up only for specific anomalies. Use optimistic locking (@Version) for most CRUD with low conflict rate; use pessimistic locking (SELECT … FOR UPDATE) for hot rows where correctness can't tolerate retries. SKIP LOCKED is the killer feature for distributed work queues. Always acquire locks in a deterministic order, never call external APIs inside a transaction, and log/alert on conflict rates and deadlocks. Hot-row contention is solved with sharded counters, async aggregation via Kafka, or per-key serialization, not by holding locks longer.

How do you handle deadlocks in database systems? must

A deadlock is two or more transactions each waiting for a lock the other holds — the DB detects the cycle and aborts one as the "deadlock victim". Deadlocks are inevitable in concurrent systems; the engineering goal is to make them rare, debuggable, and automatically recoverable.

CORE IDEA Prevent deadlocks by acquiring locks in a consistent order across the codebase, keeping transactions short, and indexing the columns used in WHERE clauses (so the DB locks fewer rows). When deadlocks happen, the DB throws a deadlock exception — the application retries with backoff on idempotent transactions.
1 Anatomy of a classic deadlock
Tx A: UPDATE orders SET … WHERE id = 1 — locks row 1
↓
Tx B: UPDATE orders SET … WHERE id = 2 — locks row 2
↓
Tx A: UPDATE orders SET … WHERE id = 2 — waits for B
↓
Tx B: UPDATE orders SET … WHERE id = 1 — waits for A → CYCLE
↓
DB detects, picks a victim, aborts it with deadlock error (Postgres SQLSTATE 40P01 / MySQL ER_LOCK_DEADLOCK)
2 Prevention rules
  • Consistent lock order — always lock rows in the same order (e.g., ascending PK). Eliminates the cycle.
  • Short transactions — fewer locks held for less time → less chance of overlap.
  • Index the WHERE column — without an index the DB may take more locks than necessary (page or table locks).
  • Avoid mixing access patterns — code paths that lock the same rows in different orders are deadlock generators.
  • Use SELECT … FOR UPDATE at the start of the transaction to declare all locks upfront.
  • Lower lock granularity — InnoDB row-level > MyISAM table-level.
  • Avoid SERIALIZABLE when not needed; it acquires more locks.
3 Code pattern — sorted lock acquisition
// Bad — order varies by call site, deadlock magnet
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amt) {
    Account from = repo.findForUpdate(fromId);     // arbitrary order
    Account to   = repo.findForUpdate(toId);
    from.debit(amt);  to.credit(amt);
}

// Good — deterministic ordering by id
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amt) {
    Long firstId  = Math.min(fromId, toId);
    Long secondId = Math.max(fromId, toId);
    Account a = repo.findForUpdate(firstId);
    Account b = repo.findForUpdate(secondId);
    Account from = (firstId.equals(fromId)) ? a : b;
    Account to   = (firstId.equals(fromId)) ? b : a;
    from.debit(amt);  to.credit(amt);
}
4 Recovery — retry the victim
// Spring Retry on deadlock victim
@Retryable(
    retryFor = { CannotAcquireLockException.class,
                 DeadlockLoserDataAccessException.class },
    maxAttempts = 3,
    backoff = @Backoff(delay = 50, multiplier = 2.0, random = true)
)
@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amt) { ... }

Retries work only if the transaction is idempotent — replaying it must be safe. With backoff + jitter, a small number of deadlocks is a non-event for users.

5 Diagnose deadlocks in production
  • Postgres: log_lock_waits = on, deadlock_timeout = 1s — every deadlock is logged with both involved queries.
  • MySQL InnoDB: SHOW ENGINE INNODB STATUS shows the LATEST DETECTED DEADLOCK with both transactions and locks.
  • Enable innodb_print_all_deadlocks = ON to capture every deadlock to the error log.
  • APMs (Datadog, New Relic) usually surface deadlock errors with stack traces.
  • Track the metric deadlocks_per_minute; alert on a sudden rise.
6 Common interview gotchas
  • Deadlocks are detected, not prevented, by the DB — engineering prevents them.
  • Lock waits and deadlocks are different — long lock waits don't cycle (no victim) but cause latency.
  • SELECT FOR UPDATE on a non-indexed column locks far more rows than expected → deadlock magnet.
  • Retry without idempotency = silent double-execution.
  • SERIALIZABLE in Postgres causes "could not serialize access" failures — application must retry.
  • InnoDB picks the smaller transaction (least undo) as the victim — predictable but the bigger one wins, which can starve small writes.
  • Deadlock storms after a deploy → recently changed code path likely introduced a non-deterministic lock order.
  • Don't try to "lock everything upfront" globally — it serializes the system.

Interview one-liner: Deadlocks happen when two transactions hold locks the other wants — the DB detects the cycle and aborts a victim. Prevent them by acquiring locks in a deterministic order (e.g., always by ascending PK), keeping transactions short, indexing WHERE clauses (so fewer rows are locked), and avoiding higher isolation levels than necessary. Recover with retry-on-deadlock using exponential backoff + jitter — works only for idempotent transactions. Diagnose via SHOW ENGINE INNODB STATUS (MySQL) or log_lock_waits (Postgres); alert on deadlock rate. The art is "make them rare, automatic, invisible to users", not "eliminate them entirely".

How does database connection pooling work internally? must

Opening a TCP connection to a database, doing the auth handshake, and tearing it down again costs 5–50 ms — much longer than most queries. A connection pool keeps a fixed set of physical connections warm and hands them out per request. Every production Java app uses one (HikariCP is the default in Spring Boot 2+).

CORE IDEA A bounded pool of pre-opened DB connections. The app borrows one, runs SQL, returns it. The pool handles validation, recycling, leak detection, and back-pressure when the pool is exhausted (callers wait or timeout).
1 Lifecycle of a borrowed connection
App calls dataSource.getConnection()
↓
Pool finds an idle connection or creates one (up to maximumPoolSize)
↓
Validates the connection (test query / ping)
↓
Returns a proxy to the app — looks like a JDBC Connection
↓
App runs SQL, then calls connection.close()
↓
Proxy intercepts close() → returns the physical connection to the pool, never actually closes it
2 The HikariCP knobs that matter
spring:
  datasource:
    hikari:
      maximum-pool-size: 20            # hard cap; sized per app + per DB capacity
      minimum-idle: 20                 # often = max for steady-state services
      connection-timeout: 3000         # ms to wait for a connection before failing
      idle-timeout: 600000             # ms before idle connections are closed (if > min-idle)
      max-lifetime: 1800000            # max age — recycle to avoid stale TCP / DB-side timeouts
      leak-detection-threshold: 30000  # log a warning if borrowed > 30s
      validation-timeout: 5000
      pool-name: HikariCP-orders
3 How big should the pool be?
  • Per pod: a pool of 10–20 is usually enough; more usually means a query problem.
  • Total: pods × pool ≤ DB max_connections minus headroom for admin and replicas.
  • Beyond what the DB can handle in parallel, more connections add contention, not throughput.
  • For Postgres, consider PgBouncer in transaction-pooling mode — many app pools converge into a small DB-side pool.
  • Hikari's classic guidance: connections = ((cores × 2) + spindles) for typical OLTP — a small, hot pool beats a huge cold one.
4 Pool exhaustion — what it looks like
  • App threads stuck on HikariPool.getConnection in dumps.
  • SQLTransientConnectionException: HikariPool-1 - Connection is not available, request timed out in logs.
  • Latency rises sharply at peak; 5xx if connection-timeout is short.
  • Root causes: long-running queries, too-small pool, transactions held over external calls, or downstream DB slowdown.

Fix: shorten transactions, find the slow query, raise pool size cautiously, or add a circuit breaker on the slow endpoint.

5 Connection validation & staleness
  • Pool periodically tests idle connections (SELECT 1 or driver ping) — drops dead ones.
  • max-lifetime recycles connections proactively to dodge DB / firewall idle timeouts (a 1-hour wait_timeout on MySQL is a classic source of Communications link failure).
  • For RDS Proxy / connection routers, set max-lifetime below the proxy's idle timeout.
6 Connection leak detection

leak-detection-threshold logs a stack trace if a connection is held longer than the threshold — invaluable for catching code that forgets to close (rare with try-with-resources, common with custom code that bypasses Spring).

Connection leak detection triggered for HikariProxyConnection@12345,
stack trace:
  at com.shop.repo.OrderRepo.findAll(OrderRepo.java:42)
  ...
7 Common interview gotchas
  • Bigger pools aren't always better — beyond DB parallelism, they add contention.
  • Pool exhaustion presents as "the DB is slow" — actually the app can't borrow a connection.
  • External HTTP calls inside a transaction hold the connection — pool exhaustion in disguise.
  • Default connection-timeout (30s) is too long — fail-fast in 1–3s + retry.
  • Long idle-timeout + DB-side wait_timeout mismatch → "Communications link failure" after midnight.
  • Pools per data source — don't share a pool across logical databases.
  • Pool size + replicas: total active connections across all pods can swamp the DB if HPA scales aggressively.
  • For serverless / Lambda, traditional pooling doesn't fit — use RDS Proxy or Aurora Serverless for connection multiplexing.
  • Always export pool metrics (active, idle, waiting, total) to Prometheus and alert on waiters > 0.

Interview one-liner: A connection pool keeps a bounded set of warm DB connections so the app avoids the 5–50 ms cost of opening one per request. HikariCP is the default; the knobs that matter are maximum-pool-size, connection-timeout (fail-fast), max-lifetime (recycle to dodge DB-side idle timeouts), and leak-detection-threshold. Size the pool small and hot — a 10–20 connection pool is enough for most pods; beyond DB parallelism, more connections only add contention. Always export metrics (active/idle/waiting) and alert on waiters > 0. Pool exhaustion looks like "DB is slow" but is actually the app stuck on getConnection — fix by shortening transactions, killing long-running queries, or adding circuit breakers on slow endpoints.

Difference between DELETE, TRUNCATE, DROP. must

DELETE removes rows (can have WHERE, rollback, triggers fire). TRUNCATE removes all rows fast (minimal logging, cannot rollback easily, resets identity). DROP removes table structure.

Now coming to when to use.

DELETE for partial cleanup; TRUNCATE for emptying staging tables; DROP to remove object.

Now coming to conclusion.

In banking, prefer DELETE with audit for production data.

Difference between WHERE and HAVING.

WHERE filters rows before grouping; HAVING filters groups after GROUP BY aggregation.

Rules

WHERE: cannot reference aggregate functions (SUM, COUNT). HAVING: can reference aggregates.

Execution order: WHERE → GROUP BY → HAVING → SELECT → ORDER BY.

Example

SELECT branch, SUM(balance) FROM accounts WHERE status='ACTIVE' GROUP BY branch HAVING SUM(balance) > 1000000;

WHERE filters active accounts first (performance); HAVING filters branches by total balance.

Difference between UNION and UNION ALL.

UNION combines result sets and removes duplicates; UNION ALL combines without removing duplicates — faster because it skips the sort/dedup step.

Performance

UNION: sorts combined results to identify and remove duplicates — O(n log n) extra cost.

UNION ALL: no dedup, no extra sort — always use UNION ALL unless you specifically need dedup.

Banking use

Combine current and savings transactions: use UNION ALL (same reference can't appear in both). UNION for unique customer IDs across two systems.

Now coming to conclusion.

Default to UNION ALL for better performance — add UNION only when deduplication is explicitly required.

What is composite key?

A composite key is a primary or unique key composed of two or more columns whose combination uniquely identifies a row.

Usage

CREATE TABLE account_transactions (account_id NUMBER, txn_date DATE, seq_no NUMBER, CONSTRAINT pk PRIMARY KEY (account_id, txn_date, seq_no));

Banking

Composite key on (account_id, transaction_date, sequence_number) uniquely identifies each transaction within an account on a date.

Composite indexes follow left-prefix rule — index on (account_id, txn_date) supports queries filtering on account_id alone but not txn_date alone.

Now coming to conclusion.

Composite keys model multi-attribute uniqueness; composite index column order matters for query optimization.

What is function-based index?

A function-based index indexes the result of a function or expression on a column — enabling index use for queries that apply functions in the WHERE clause.

Example

CREATE INDEX idx_upper_email ON customers(UPPER(email)); — supports WHERE UPPER(email) = 'USER@BANK.COM'.

Without this: query on UPPER(email) = '...' would cause full table scan even with index on email.

Banking

Case-insensitive customer name search: CREATE INDEX idx_upper_name ON customers(UPPER(name));

Now coming to conclusion.

Function-based indexes solve the 'function on column prevents index use' problem — create one per function used in WHERE.

What is bitmap index?

A bitmap index stores a bitmap for each distinct value, efficient for low-cardinality columns in data warehouse queries but unsuitable for OLTP due to locking.

Usage

CREATE BITMAP INDEX idx_status ON accounts(status); — for columns with few distinct values (ACTIVE, DORMANT, CLOSED).

Very efficient for WHERE status='ACTIVE' AND type='SAVINGS' — bitmaps ANDed together, fast row retrieval.

Limitations

DML locks entire bitmap segment — concurrent INSERTs/UPDATEs on the same value cause lock contention.

Avoid on OLTP tables with heavy DML; use in read-only or near-read-only data warehouse scenarios.

Now coming to conclusion.

Bitmap indexes are for data warehouse columns — NEVER use on an OLTP banking transaction table.

When should we not use index?

Avoid indexes on low-cardinality columns, small tables, columns with high NULL percentage in NOT NULL queries, and columns frequently used in DML — they add overhead without selectivity benefit.

Avoid when

Low cardinality: status column with 3 values — index provides little selectivity, FTS may be faster.

Small tables (< 1000 rows): Oracle optimizer may choose FTS over index — it's faster for small tables.

Heavy DML: every INSERT/UPDATE/DELETE must maintain the index — too many indexes slow write performance.

Banking

Don't index transaction_type on accounts table if 90% are 'SAVINGS' — query returns too many rows for index to help.

Now coming to conclusion.

Index design is about selectivity and DML balance — the right number of indexes, on the right columns.

How do you find duplicate records?

Find duplicate records using GROUP BY + HAVING COUNT(*) > 1 to identify duplicated key combinations.

Query

SELECT account_id, txn_ref, COUNT(*) FROM transactions GROUP BY account_id, txn_ref HAVING COUNT(*) > 1;

To see full duplicate rows: SELECT * FROM transactions WHERE (account_id, txn_ref) IN (SELECT account_id, txn_ref FROM transactions GROUP BY account_id, txn_ref HAVING COUNT(*) > 1);

Banking

Find duplicate payment references before EOD to prevent double posting.

What is view?

A view is a named SQL query stored in the database — used as a virtual table that simplifies complex queries, enforces security, and abstracts schema details.

Benefits

Simplify: vw_customer_balances hides 5-table JOIN behind a simple SELECT.

Security: grant SELECT on view but not base tables — expose only permitted columns/rows.

Abstraction: application queries the view; underlying schema can change without affecting the view consumers.

Limitations

Non-materialized view: executes underlying query every time — no performance benefit for complex queries.

Simple views (single table, no aggregation) are updatable; complex views are read-only.

Now coming to conclusion.

Views are excellent for reporting abstraction and security — use materialized views when performance is needed.

What is materialized view?

A materialized view stores the result of a query physically on disk — it can be pre-aggregated for fast reporting, refreshed periodically, and indexed.

Refresh

REFRESH COMPLETE: full re-compute. REFRESH FAST (on commit or on demand): incremental using materialized view log.

REFRESH ON COMMIT: auto-refresh after DML on base tables — overhead on DML, instant fresh data.

Banking

Monthly branch balance summary materialized view: refreshed nightly, indexed by branch — instant reporting query.

MV for reconciliation: pre-aggregate account balances per GL code — used in end-of-day GL report.

Now coming to conclusion.

Use materialized views for expensive aggregations used in reports — they trade storage and refresh latency for query speed.

What is sequence?

An Oracle sequence is a schema object that generates unique, sequential numbers — used for generating primary key values without table-level locking.

Usage

CREATE SEQUENCE txn_seq START WITH 1 INCREMENT BY 1 CACHE 20 NOCYCLE;

SELECT txn_seq.NEXTVAL FROM DUAL — get next value. txn_seq.CURRVAL — current value in session.

In INSERT: INSERT INTO transactions(id, ...) VALUES(txn_seq.NEXTVAL, ...);

An Oracle synonym is an alias for a database object (table, view, procedure) — enabling transparent cross-schema references and abstracting object location.

Range partition vs hash partition.

Range partition assigns rows to partitions based on value ranges (dates, amounts); hash partition uses a hash function for even distribution across partitions.

Range

PARTITION BY RANGE(txn_date) with yearly or quarterly partitions — ideal for date-ranged data.

Query with WHERE txn_date BETWEEN date1 AND date2 — Oracle prunes to only relevant partitions.

Hash

PARTITION BY HASH(account_id) PARTITIONS 16 — even distribution across 16 partitions.

Eliminates hotspots when range partition would put all recent activity in one partition.

Banking choice

Transactions table: RANGE partition by txn_date (archive old partitions), HASH sub-partition by account_id for even distribution.

Now coming to conclusion.

Combine RANGE+HASH (composite partitioning) for large banking transaction tables — date range for archiving, hash for balance.

What is rownum?

ROWNUM is a pseudo-column in Oracle assigning sequential numbers to result rows before ORDER BY — use ROW_NUMBER() analytic function for reliable ordered pagination.

Limitation

ROWNUM is assigned before ORDER BY — WHERE ROWNUM <= 10 without subquery gives first 10 unordered rows.

Correct: SELECT * FROM (SELECT * FROM transactions ORDER BY txn_date DESC) WHERE ROWNUM <= 10;

Oracle 12c+

FETCH FIRST 10 ROWS ONLY — SQL standard pagination, cleaner than ROWNUM tricks.

OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY — standard pagination without subquery.

Now coming to conclusion.

What are analytical functions?

Analytical (window) functions compute values over a set of rows related to the current row — without collapsing rows like GROUP BY.

Common functions

ROW_NUMBER() OVER(PARTITION BY account_id ORDER BY txn_date DESC) — row number per account by date.

RANK(), DENSE_RANK() — ranking with gaps vs. no gaps. LAG(col, 1), LEAD(col, 1) — access previous/next row value.

SUM(amount) OVER(PARTITION BY account_id ORDER BY txn_date) — running total per account.

Banking use

Latest transaction per account: SELECT * FROM (SELECT *, ROW_NUMBER() OVER(PARTITION BY account_id ORDER BY txn_date DESC) rn FROM txns) WHERE rn=1;

Now coming to conclusion.

Window functions replace complex self-joins and correlated subqueries — learn them deeply for banking SQL.

What is hierarchical query?

A hierarchical query in Oracle traverses tree-structured data (org charts, GL account hierarchies) using CONNECT BY to define parent-child relationships.

Syntax

SELECT id, name, LEVEL FROM gl_accounts START WITH parent_id IS NULL CONNECT BY PRIOR id = parent_id;

LEVEL pseudo-column: 1=root, 2=children, etc. PRIOR: references the parent row. SYS_CONNECT_BY_PATH: full path string.

Banking

GL account hierarchy: top-level GL → sub-accounts → individual posting accounts. CONNECT BY traverses the full tree.

Organization hierarchy for maker-checker: find all approvers up the chain from a specific branch.

Now coming to conclusion.

Oracle CONNECT BY is the efficient way to traverse GL hierarchies — alternatives (CTE recursion) are more portable but slower.

What is connect by prior?

In Oracle hierarchical queries, CONNECT BY PRIOR defines the relationship between parent and child rows — PRIOR references the parent row's column.

Direction

CONNECT BY PRIOR id = parent_id — traverses from parent to children (top-down).

CONNECT BY id = PRIOR parent_id — traverses from child to parent (bottom-up).

Example

SELECT * FROM accounts START WITH account_id = 100 CONNECT BY PRIOR account_id = parent_account_id — all sub-accounts under account 100.

Now coming to conclusion.

PRIOR is always on the parent side for top-down traversal — reverse it for bottom-up ancestor queries.

What is merge statement?

The Oracle MERGE statement performs INSERT, UPDATE, or DELETE on a target table based on whether matching rows exist in a source — atomically combining upsert logic.

Syntax

MERGE INTO target_table t USING source_table s ON (t.id = s.id) WHEN MATCHED THEN UPDATE SET t.col=s.col WHEN NOT MATCHED THEN INSERT VALUES(...);

Banking use

Reconciliation: MERGE account_balances from staging table — update existing, insert new accounts.

Product rate update: MERGE interest_rates from new_rates — update changed rates, insert new products.

Now coming to conclusion.

MERGE is more efficient than separate INSERT + UPDATE — single statement, single table scan, single transaction.

What is upsert?

An upsert (update or insert) inserts a row if it doesn't exist, or updates it if it does — implemented in Oracle using MERGE or INSERT ... ON DUPLICATE KEY equivalents.

Oracle pattern

MERGE with WHEN MATCHED THEN UPDATE + WHEN NOT MATCHED THEN INSERT — the standard Oracle upsert.

Alternative: BEGIN INSERT INTO t VALUES(...); EXCEPTION WHEN DUP_VAL_ON_INDEX THEN UPDATE t SET ...; END; — less efficient.

Banking

Upsert exchange rates: if rate for USD/INR today exists → update; else → insert new rate record.

Now coming to conclusion.

Use MERGE for upsert — it's atomic, efficient, and avoids the insert-try-catch-update anti-pattern.

What is deadlock in database?

A database deadlock occurs when two transactions each hold a lock the other needs — neither can proceed, and the database detects and breaks the cycle by rolling back one victim.

Oracle handling

Oracle detects deadlock via lock graph cycle detection; automatically rolls back one statement (not transaction) with ORA-00060.

Application must catch ORA-00060, rollback the full transaction explicitly, then retry.

Prevention

Always acquire locks in consistent order (lower account_id first in fund transfer).

Use SELECT ... FOR UPDATE NOWAIT to fail immediately rather than wait indefinitely.

Now coming to conclusion.

Deadlock prevention through consistent lock ordering is better than relying on Oracle's detection.

What is locking in Oracle?

Oracle uses row-level locking — SELECT ... FOR UPDATE acquires row locks; DML (INSERT/UPDATE/DELETE) auto-acquires row locks on affected rows.

Mechanism

Oracle MVCC: readers don't block writers (read from undo); writers don't block readers.

SELECT ... FOR UPDATE: acquires exclusive row lock — other sessions cannot UPDATE/DELETE same row until lock released.

Table-level locks (TM lock) acquired on DML to prevent DDL conflicts — allows concurrent DML.

Banking

SELECT balance FROM accounts WHERE account_id = 100 FOR UPDATE — lock before checking balance and debiting.

Now coming to conclusion.

Oracle's MVCC means reads are never blocked — only concurrent DML on same rows causes lock waits.

Shared lock vs exclusive lock.

Shared locks allow multiple readers simultaneously; exclusive locks block all other readers and writers until released.

Shared (S)

Acquired by SELECT ... FOR UPDATE SHARE (less common); multiple sessions can hold shared locks concurrently.

Used when you want to read and prevent others from deleting but allow concurrent reads.

Exclusive (X)

Acquired by SELECT ... FOR UPDATE or implicit with DML (INSERT/UPDATE/DELETE).

Prevents all other sessions from acquiring any lock on the same row — ensures exclusive modification.

Oracle in practice

Normal SELECT: no lock (MVCC provides read consistency). DML: exclusive row lock. DDL: table-level lock.

Now coming to conclusion.

Oracle DML acquires exclusive row locks automatically — SELECT FOR UPDATE is needed when read+write must be atomic.

Find gaps in sequence numbers.

Find gaps in sequence numbers by comparing each row's value with the next row's value using LAG() or self-join.

Query

SELECT seq_no + 1 AS gap_start FROM (SELECT seq_no, LEAD(seq_no) OVER(ORDER BY seq_no) next_seq FROM seq_table) WHERE next_seq - seq_no > 1;

Or: SELECT s1.seq_no + 1 AS gap_start FROM seq_table s1 WHERE NOT EXISTS (SELECT 1 FROM seq_table WHERE seq_no = s1.seq_no + 1) AND s1.seq_no < (SELECT MAX(seq_no) FROM seq_table);

Find consecutive failed transactions.

Find consecutive failed transactions using window functions to group consecutive failures and count streaks.

Approach

Use LAG() to check if previous transaction also failed; assign group IDs using conditional sum, then GROUP BY group ID.

SELECT account_id, COUNT(*) streak, MIN(txn_date) start_date, MAX(txn_date) end_date FROM (SELECT *, SUM(CASE WHEN status='FAILED' THEN 0 ELSE 1 END) OVER(PARTITION BY account_id ORDER BY txn_date) grp FROM transactions) WHERE status='FAILED' GROUP BY account_id, grp HAVING COUNT(*) >= 3;

How do you delete duplicate records?

Delete duplicate records keeping one copy using ROWID — identify duplicates with ROW_NUMBER() and delete where rn > 1.

Query

DELETE FROM transactions WHERE rowid NOT IN (SELECT MIN(rowid) FROM transactions GROUP BY account_id, txn_ref, amount);

Using ROW_NUMBER: DELETE FROM transactions WHERE rowid IN (SELECT rowid FROM (SELECT rowid, ROW_NUMBER() OVER(PARTITION BY account_id, txn_ref ORDER BY rowid) rn FROM transactions) WHERE rn > 1);

Now coming to conclusion.

Always backup and verify the duplicate-identification query before running DELETE in banking tables.

View vs materialized view.

A view executes its query on each access (virtual, no storage); a materialized view stores the query result physically (real storage, refreshed periodically).

View

No storage; always shows latest data; query executed on every access — overhead for complex views.

Materialized view

Physical storage; fast queries; refresh lag (on commit or scheduled); can be indexed.

Trade-off: storage + refresh overhead vs. query performance.

Now coming to conclusion.

Use view for simple abstraction; materialized view when reporting queries on large aggregations need sub-second response.
