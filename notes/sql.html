SQL — joins, transactions, indexes

The questions every backend interview hits. Master joins, ACID, indexing, and EXPLAIN — they decide whether you pass.

Types of joins — INNER, LEFT, RIGHT, FULL, CROSS must

Joins combine rows from two tables based on a condition.

  • INNER JOIN — only rows that match in both tables.
  • LEFT JOIN — all rows from left table; matching rows from right (or NULLs).
  • RIGHT JOIN — opposite of LEFT. Rare in practice; rewrite as LEFT for readability.
  • FULL OUTER JOIN — all rows from both sides; unmatched cells are NULL. Not supported in MySQL natively (use UNION).
  • CROSS JOIN — Cartesian product; M × N rows. Used intentionally for generating combinations.
  • SELF JOIN — a table joined to itself, e.g., employees + their managers from the same employees table.

Watch out: LEFT JOIN ... WHERE right.col IS NOT NULL turns it back into an INNER JOIN. Put filters on the right table in the ON clause, not WHERE.

Primary key vs unique key vs foreign key

Primary key uniquely identifies a row. Implicit constraints: NOT NULL, unique, one per table. Usually backed by a clustered index in InnoDB / SQL Server (table physically ordered by PK). Choose stable, narrow values — synthetic IDs (BIGINT, UUID v7) usually beat natural keys.

Unique key / unique constraint also enforces uniqueness but allows NULLs (one per column in most DBs). You can have many unique keys per table — e.g., email and phone both unique on a users table.

Foreign key references the primary (or unique) key of another table and enforces referential integrity. The DB rejects inserts that reference non-existent parents, and you can cascade on delete/update. Some teams skip FKs at scale for write throughput; I prefer keeping them on for OLTP and only relaxing in event-sourced or sharded systems.

ACID properties hot

A — Atomicity. A transaction is all-or-nothing. Either every statement commits or every change is rolled back. Implemented via undo logs (e.g., InnoDB's undo segments).

C — Consistency. The DB moves from one valid state to another. Constraints (FK, unique, CHECK) and triggers stay satisfied at commit time.

I — Isolation. Concurrent transactions don't see each other's intermediate state. The strictness is configurable via isolation levels — see next question.

D — Durability. Once committed, changes survive crashes. Implemented via write-ahead logs (WAL / redo logs) flushed to disk before commit returns.

ACID is the contract that lets you trust a relational database. NoSQL stores trade ACID for scale; modern systems like CockroachDB or Spanner reclaim much of it across distributed nodes.

Transaction isolation levels

Standard isolation levels from weakest to strongest:

  • READ UNCOMMITTED — can see uncommitted changes (dirty reads). Rarely used.
  • READ COMMITTED — only sees committed data. Each statement gets a fresh view. Default in Postgres, Oracle, SQL Server. Allows non-repeatable reads (same query, different results in same tx).
  • REPEATABLE READ — same row reads the same value throughout the tx. Allows phantom reads (new rows appear) in standard, but InnoDB's gap locks prevent them. Default in MySQL/InnoDB.
  • SERIALIZABLE — strongest; transactions execute as if serial. Usually implemented via predicate locks or 2PL.

Picking the level is a perf/correctness tradeoff. I default to READ COMMITTED and reach for higher only when I see real concurrency bugs.

Indexes — what kinds and when?

An index is an auxiliary data structure that speeds up lookups in exchange for slower writes and extra storage.

  • B-tree (B+tree) — default; balanced tree giving O(log n) lookups, range scans, and ordered reads. Good for equality and range queries.
  • Hash — O(1) equality only; no range, no ORDER BY. Used by some engines for in-memory tables.
  • Composite (multi-column) — order matters: (a, b) helps queries on a or (a, b), but not b alone (leftmost prefix rule).
  • Covering — includes all columns the query needs; the DB never has to touch the row.
  • Partial / filtered — index only rows matching a predicate (Postgres, SQL Server).
  • Full-text, GIN/GIST — specialized for text and JSON.

Rule: index columns in WHERE, JOIN, and ORDER BY. Don't over-index — every INSERT/UPDATE pays.

Clustered vs non-clustered index

A clustered index determines the physical order of rows on disk. A table has at most one — typically the primary key. In InnoDB and SQL Server the PK is automatically clustered. Range scans on the PK are very fast because the rows are adjacent.

A non-clustered (secondary) index is a separate structure that stores the indexed column(s) plus a pointer back to the row. In InnoDB the pointer is the PK value (so PK lookups are an extra hop unless the index is covering).

Implication: a wide PK (long UUID v4 strings) bloats every secondary index. That's why UUID v7 (time-ordered) or sequential BIGINT IDs are preferred for high-write tables — narrow and locality-friendly.

EXPLAIN / query plans — how do you read them?

EXPLAIN shows how the optimizer plans to execute a query. Things I look for:

  • Access type — const/ref/range are fine; ALL means full table scan (red flag on big tables).
  • Index used (key) — is it the one you expected?
  • Rows examined vs returned — high ratio means the query reads too much.
  • Extra — "Using filesort" (sort on disk if needed), "Using temporary" (temp table), "Using index" (covering index — good).
  • Cost — Postgres shows actual cost; MySQL has EXPLAIN FORMAT=JSON.

I prefer EXPLAIN ANALYZE (Postgres) or EXPLAIN FORMAT=TREE (MySQL 8) which actually run the query and show timing per step. Combined with auto_explain in production, it tells you which queries are slow and why.

Normalization vs denormalization

Normalization organizes data to reduce redundancy. The levels build on each other:

  • 1NF — atomic columns, no repeating groups.
  • 2NF — no partial dependency on a composite key.
  • 3NF — no transitive dependency.

3NF is the practical sweet spot for OLTP — fewer anomalies on update.

Denormalization deliberately duplicates data for read performance — caching computed totals, embedding lookup names, materialized views. Common in OLAP, search indices, and high-read services.

My approach: design normalized (3NF), then denormalize specific reads if profiling shows pain. Don't pre-optimize. Async pipelines (CDC → ES) often beat in-table denormalization because they can be rebuilt safely.

WHERE vs HAVING — and aggregate order of execution

The logical order of a SELECT statement: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.

WHERE filters rows before aggregation. HAVING filters after aggregation — it operates on grouped/aggregated values.

SELECT dept, COUNT(*) AS cnt
FROM employees
WHERE active = TRUE          -- pre-filter
GROUP BY dept
HAVING COUNT(*) > 10;        -- post-filter on aggregate

You can't put COUNT(*) > 10 in WHERE — aggregates aren't computed yet. Common interview trick: which clause filters which stage?

Bonus: column aliases from SELECT aren't usable in WHERE or HAVING in most DBs (MySQL is loose); subquery or CTE if you need that.

Window functions — ROW_NUMBER, RANK, LAG

Window functions compute over a "window" of rows related to the current row, without collapsing them like GROUP BY does. They make many complex queries simple:

-- Top 3 paid employees per department
SELECT * FROM (
  SELECT name, dept, salary,
    ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
) t WHERE rn <= 3;

Key functions: ROW_NUMBER (always unique within window), RANK (ties share rank, leaves gaps), DENSE_RANK (no gaps), LAG/LEAD (previous/next row), SUM/AVG OVER (...) running totals, moving averages.

Modern OLTP queries I write lean on these heavily — they replace the "self-join with subquery" patterns from older SQL.

Subquery vs CTE vs JOIN

All three combine data, but with different readability and performance characteristics.

JOIN — the optimizer's first choice for combining tables. Almost always rewriteable from a subquery.

Correlated subquery — runs per-row of the outer query. Easy to write but can be slow (N+1 in SQL form). Modern optimizers often unnest them automatically.

CTE (WITH clause) — names a result set for reuse and readability. Recent versions of Postgres/MySQL/SQL Server inline CTEs into the plan (so they're usually free); older Postgres used to materialize them, which sometimes hurt. Recursive CTEs let you query hierarchies (org tree, comments tree).

I write CTEs over deeply nested subqueries for readability, and trust the optimizer. EXPLAIN ANALYZE shows whether a CTE is inlined or materialized.

N+1 query problem — and how to fix it

The N+1 query problem: fetching a list of N parents (1 query), then fetching children for each (N more queries) = N+1 round trips. Common with JPA/Hibernate lazy associations:

List<Order> orders = orderRepo.findAll();   // 1 query
for (Order o : orders) o.getItems().size();   // N queries — bad

Fixes:

  • JOIN FETCH in JPQL — one query with a JOIN.
  • @EntityGraph on Spring Data repos — declarative eager fetch per query.
  • Batch fetch — Hibernate @BatchSize groups child queries.
  • Two queries: parents + WHERE IN (parentIds) for children, assembled in code — often the cleanest at scale.

I've fixed dozens of N+1 issues in production — they're invisible in unit tests and lethal under load. Always enable SQL logging in dev and watch the query count for any list endpoint.

How would you optimize a slow query? hot

My playbook:

  1. Reproduce and measure. Get the real query and run EXPLAIN ANALYZE. Don't guess.
  2. Read the plan. Are we scanning whole tables? Doing filesort? Using the index I expect?
  3. Add or fix indexes. The most common win. Mind the leftmost-prefix rule on composites. Use covering indexes for hot read paths.
  4. Rewrite the query. Replace correlated subqueries with joins, push filters early, select only needed columns.
  5. Avoid N+1 (see previous answer).
  6. Cache hot read-only data in Redis or app-level when DB tuning hits limits.
  7. Partition or shard tables that don't fit in working set anymore.
  8. Async pre-compute heavy aggregations (materialized views, refresh jobs).

One Indus Net example: a dashboard query took 12 s. EXPLAIN showed a missing index on (tenant_id, created_at). Adding it brought the query to 80 ms.

Optimistic vs pessimistic locking

Both prevent lost updates when multiple users edit the same row.

Pessimistic — lock the row at read time (SELECT ... FOR UPDATE); others wait. Strong correctness, but holds locks while you think — bad for contention. Risk of deadlocks.

Optimistic — read without locking, include a version column. On update: UPDATE ... WHERE id = ? AND version = ?. If 0 rows affected, someone else wrote first — retry or surface a 409 Conflict. JPA's @Version annotation gives you this declaratively.

I prefer optimistic for most CRUD on the web — low contention, no held locks, clear conflict semantics for users. Pessimistic for short, transactional sections where contention is high (inventory decrement at sale time).

Sharding vs partitioning vs replication

All three split or copy data, but for different reasons.

Replication — copy the entire data to one or more replicas. Adds read capacity (read replicas) and fault tolerance (failover). Doesn't help write throughput. Asynchronous replication has lag; synchronous is slower but consistent.

Partitioning — split a single table into chunks within the same database by range (date), list (region), or hash. Each partition is a separate physical structure. Smaller indexes per partition, can drop old partitions cheaply. Postgres has declarative partitioning; MySQL supports it natively.

Sharding — split data across multiple databases/servers by a shard key. Adds write throughput. Complex: cross-shard joins are hard, rebalancing is painful, you need a router. Reach for it only when you've exhausted vertical scaling and replication.
