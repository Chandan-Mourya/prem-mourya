How do you approach a system design question? must

My structure for any 45-minute design interview:

  1. Clarify requirements (5 min) — functional (what does it do?) and non-functional (scale, latency, consistency, availability). Don't assume — ask numbers.
  2. Capacity estimation (5 min) — back-of-envelope: DAU, QPS, storage growth, bandwidth. Helps justify decisions later.
  3. API design (5 min) — define the main endpoints / events.
  4. High-level architecture (10 min) — draw boxes: clients, LB, app servers, DB, cache, queue, CDN. State the data flow.
  5. Deep dive (15 min) — pick 1–2 critical components and detail data model, scaling, failure modes. The interviewer guides you here.
  6. Bottlenecks & tradeoffs (5 min) — where it can break, what you'd add next.

The interview is about communication and tradeoffs, not a "correct" answer. Stay structured, think out loud, ask before assuming.

Vertical vs horizontal scaling

Vertical scaling — make one box bigger (more CPU, RAM, faster disks). Simple, no app changes. Limited by single-machine ceiling and downtime to resize. Cost grows non-linearly at the high end.

Horizontal scaling — add more boxes. Scales nearly linearly if your app is stateless and shardable. Requires a load balancer in front and architectural discipline — no in-memory session state, no local file caches.

My defaults: app tier horizontal (stateless services behind LB, auto-scaling in K8s/AWS), cache horizontal (Redis cluster), DB primary vertical first then horizontal (read replicas, then sharding when really needed).

The 12-Factor approach makes horizontal scaling natural — keep services stateless and let the orchestrator scale them.

What is Load Balancing? must

Load balancing is the process of distributing incoming network traffic across multiple servers so that no single server gets overloaded. A load balancer sits in front of a pool of backend servers and decides which one handles each incoming request. It's one of the most fundamental building blocks in any scalable system.

Core Idea — what it gives you
Availability If one server dies, traffic automatically shifts to healthy ones — no downtime.
Scalability Add or remove servers horizontally — the LB picks them up. Handles 10K → 10M users with the same architecture.
Performance No single box is overwhelmed → lower latency, better throughput, faster response times.
1 Why we need it — the simple picture
Without a Load Balancer
  • 10,000 users → 1 server → it dies / slows down
  • Single point of failure
  • Vertical scaling only (bigger box) — expensive & capped
  • Deploys cause downtime — server has to restart
With a Load Balancer
  • 10,000 users → LB → spread across N servers
  • One server dies? LB drains it, others keep serving
  • Horizontal scaling — add cheap commodity servers
  • Rolling deploys — restart one server at a time, zero downtime
2 Architecture — single front door, many backends
┌─────────────┐ │ Users │ (clients, browsers, mobile apps) └──────┬──────┘ │ ▼ ┌─────────────┐ │ LOAD │ ← health checks, routing algorithm │ BALANCER │ └──────┬──────┘ ┌────────┼────────┐ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ │Server 1│ │Server 2│ │Server 3│ (identical app instances) └────────┘ └────────┘ └────────┘

The LB performs health checks on each server (e.g. ping /health every 5s). Unhealthy ones are drained — no traffic routed to them. This is what turns load balancing from "spread requests" into a real availability mechanism.

3 Common Load-Balancing Algorithms (overview)
AlgorithmHow it works
Round Robin Requests distributed sequentially — server 1, 2, 3, 1, 2, 3, …
Weighted Round Robin Bigger / faster servers get more traffic via weights (e.g. 3:1:1).
Least Connections Routes to the server with the fewest active connections — great for long-lived connections.
IP Hash Hash of client IP → always picks the same server. Used for session stickiness.
Least Response Time Picks the server currently responding fastest.
Geo-based / GeoDNS Routes users to their nearest region or data center.

For full details on when to use each algorithm and the real-world tools, see the "Load balancing — strategies and where they're used" question below.

4 Benefits — at a glance
  • Prevents server overload — work is spread evenly.
  • Improves response time — no single box becomes a bottleneck.
  • High availability — automatic failover when servers go down.
  • Supports horizontal scaling — just spin up more servers, the LB picks them up.
  • Zero-downtime deploys — rolling restart, one server at a time.
  • SSL termination — decrypt HTTPS once at the LB, pass plain HTTP to backends.
  • Security — single ingress point to harden, hide internal IPs.

Why we load-balance — 3 goals
Performance No single server gets overwhelmed → lower latency, better throughput.
Scalability Add or remove instances horizontally without app changes.
Availability If one server dies, health checks drain it and traffic shifts to healthy ones.

Caching strategies hot

Cache reduces latency and DB load. Patterns:

  • Cache-aside (lazy loading) — app checks cache; on miss, reads DB and populates. Most common. Risk: stale data on writes.
  • Read-through — cache handles DB read on miss transparently.
  • Write-through — every write goes to cache + DB synchronously. Consistent but slow.
  • Write-behind — writes go to cache, async flush to DB. Fast but risky on cache loss.
  • Write-around — writes skip cache; reads populate it. Good when writes aren't read soon.

Layers: browser/CDN for static, API gateway for hot GETs, Redis for app-level, local in-process (Caffeine) for tiny ultra-hot data.

Always set TTLs. Invalidate on write or accept brief staleness. Watch out for cache stampede (single-flight or lock-on-miss) and thundering herd on restarts (pre-warm or use probabilistic refresh).

Consistent Hashing — what, why, and where must

Consistent hashing is the technique distributed systems use to spread data across multiple servers without having to remap almost all the keys whenever a server is added or removed. It's the foundation behind Cassandra, DynamoDB, Redis Cluster, memcached clients, and most CDNs.

Core Idea
Problem hash(key) % N breaks badly when N changes — almost every key gets reassigned.
Solution Place both servers and keys on a circular hash ring. Each key goes to the next server clockwise.
Win When you add/remove a node, only ~K/N keys move (not all K). Smooth rebalance, no thundering-herd cache misses.
1 The Problem — naive modulo hashing breaks on rebalance

With 3 servers and the rule server = hash(key) % 3:

key "user-42" → hash = 17 → 17 % 3 = 2 (server 2) key "user-91" → hash = 25 → 25 % 3 = 1 (server 1)

Now you add a 4th server. The denominator changes from 3 to 4:

key "user-42" → hash = 17 → 17 % 4 = 1 (was 2, now 1 ❌) key "user-91" → hash = 25 → 25 % 4 = 1 (was 1, still 1 ✅ — lucky)

The disaster: roughly (N−1)/N of all keys end up on a different server. For a cache cluster, that's a cold-cache stampede — every request misses, hits the DB, takes the site down.

2 The Solution — the hash ring

Hash both servers and keys onto a circular space (e.g. 0 → 2³² − 1). Each key is owned by the next server clockwise on the ring.

0 / 2³² • [S1]•─ ─ ─ ─ ─ ─•[S2] / \ / key K1 \ • ◀────────── • // K1 goes clockwise → S2 \ / \ / [S4]•─ ─ ─ ─ ─ ─•[S3] •

Rule: for a key with hash h, walk clockwise on the ring until you hit the first server — that's where the key lives.

3 What happens when a server is added or removed?
Add a server
  • New server lands at some point on the ring.
  • It "steals" only the keys in the arc between itself and its clockwise predecessor.
  • Every other key on the ring stays where it was.
  • Average keys moved: K / N (where K = total keys, N = servers).
Remove a server
  • Its keys are inherited by the next clockwise server.
  • No other keys move.
  • Average keys moved: K / N.
  • The cache stays mostly warm — only one arc rebuilds.

Contrast with modulo hashing: there, adding one node moved ~(N−1)/N of all keys. With consistent hashing, you move only 1/N. That's the whole point.

4 Virtual Nodes (vnodes) — fixing uneven distribution

Problem: with just N points on the ring, the spacing can be wildly uneven — one server might end up owning a huge arc and getting hammered while another barely sees traffic.

Fix: each physical server registers many virtual nodes at different hash positions (typically 100–250 per node).

Without vnodes: With vnodes (each server = 4 points): [S1]──────────[S2] [S1]─[S3]─[S2]─[S1] / \ / \ • uneven arcs • • even spread • \ / \ / [S3]──────────[ ] [S2]─[S3]─[S1]─[S2]

Benefits of vnodes:

  • Load is statistically even across servers.
  • Heterogeneous capacity: a 2× bigger server owns 2× the vnodes.
  • When a server dies, its load is spread across all other servers, not just one neighbor.
5 Modulo Hashing vs Consistent Hashing — side by side
Modulo Hashing
  • Rule: hash(key) % N
  • Add/remove node: ~(N−1)/N keys move 💥
  • Effect: cache stampede, DB overload
  • Load balance: usually OK
  • Use when: N is fixed forever
Consistent Hashing
  • Rule: servers + keys on a ring, key → next server clockwise
  • Add/remove node: only ~K/N keys move ✅
  • Effect: graceful rebalance, cache mostly warm
  • Load balance: good — perfect with vnodes
  • Use when: N grows / shrinks dynamically
6 Benefits — at a glance
  • Minimal rehashing — only ~K/N keys move on any topology change.
  • Scalability — add/remove servers without downtime or full rebalance.
  • Even load distribution (with vnodes) — no hotspots.
  • High availability — failure of one node spreads its keys to many others.
  • Predictable routing — the same key always maps to the same server (until topology changes).
  • Cache-friendly — most existing cache entries stay valid after rebalance.
7 Where it's used in the real world

Distributed Databases

  • Apache Cassandra — partitioner places rows on a ring (Murmur3 hash + vnodes by default).
  • Amazon DynamoDB — partition keys mapped via consistent hashing.
  • Riak, ScyllaDB — same model.
Why: add a node → only that node's arc rebuilds, cluster stays online.

Distributed Caches

  • Redis Cluster (16,384 hash slots, similar idea)
  • Memcached via ketama client-side consistent hashing
  • Twitter's Twemproxy / Pelikan
Why: avoid cold-cache stampedes when scaling the cache tier.

CDNs & Edge

  • Akamai — picks the right edge node for each URL
  • Cloudflare, AWS CloudFront edge routing
  • Object storage front-ends
Why: minimal cache disruption when edge nodes come and go.

Load Balancers & Service Meshes

  • Envoy / HAProxy — ring-hash / maglev load balancing
  • gRPC client-side load balancers
  • Session-affinity routing without sticky cookies
Why: stable routing for user/session to backend without server-side state.
Interview one-liner: Consistent hashing maps both servers and keys onto a circular hash ring, and each key is owned by the next server clockwise. When a server is added or removed, only ~K/N keys move (instead of almost all, like with hash(key) % N). Virtual nodes spread each physical server across many ring positions to keep load even. It's the foundation behind Cassandra, DynamoDB, Redis Cluster, memcached, Akamai/CDNs, and ring-hash load balancers — it's what lets a distributed system scale and rebalance gracefully without cold-cache stampedes.
WebSocket vs Server-Sent Events (SSE) — real-time push must

Both WebSocket and Server-Sent Events (SSE) solve the same core problem — pushing real-time updates from a server to a browser without polling — but they differ in direction, protocol, and operational complexity. Picking the right one is a classic system design call.

Core Difference
WebSocket Full-duplex — both client and server can send messages anytime, over a persistent TCP connection.
SSE One-way push (server → client) — client cannot send back over the same channel; uses a long-lived HTTP response.
Rule of thumb If the client just consumes updates → SSE. If the client also sends data → WebSocket.
1 How they work — conceptually
WebSocket
  • Starts as a normal HTTP request with Upgrade: websocket header.
  • Server agrees → connection upgrades to the WebSocket protocol (ws:// / wss://).
  • Now it's a persistent TCP socket — both sides can send frames anytime.
  • Supports binary + text frames.
  • You handle reconnects, heartbeats (ping/pong), and back-pressure yourself.
Server-Sent Events (SSE)
  • Plain HTTP request from client with header Accept: text/event-stream.
  • Server replies with never-ending HTTP response and pushes data lines as events arrive.
  • Stays standard HTTP/HTTPS — works through proxies, load balancers, firewalls.
  • Text only (UTF-8). Use base64 for binary.
  • Browser auto-reconnects on disconnect with Last-Event-ID header.

3 When to use which

Use WebSocket — Chat / Collab

  • Chat apps (Slack, WhatsApp Web)
  • Live collaboration (Google Docs, Figma)
  • Multiplayer games
  • Trading platforms with order placement
Why: client must send data back constantly (typing, edits, moves, orders).

Use SSE — One-way Push

  • Live notifications (in-app toasts)
  • Stock / crypto price tickers
  • News & sports score feeds
  • Progress updates (uploads, jobs)
  • LLM token streaming (ChatGPT-style)
Why: client only consumes — no need to pay the cost & complexity of full-duplex.

Use Polling — Quick fix

  • Low-frequency updates (every 10s+)
  • When proxies/CDNs block long-lived connections
  • Legacy clients
Tip: use long-polling as a fallback when SSE/WebSocket aren't available — same UX, plain HTTP.

Use HTTP/2 Server Push? — No

  • HTTP/2 Server Push is dead — deprecated by Chrome & major browsers.
  • For app-level push: use SSE or WebSocket.
Note: HTTP/2 push was for sub-resources (CSS, JS), never for app data.

6 Operational gotchas
  • Load balancers: WebSocket needs sticky sessions or a stateless message bus (Redis pub/sub, Kafka). Most cloud LBs need explicit WS support enabled (AWS ALB, GCP HTTPS LB).
  • Connection limits: each persistent connection holds an OS file descriptor and JVM thread/goroutine. Plan for ulimit, kernel somaxconn, and connection-per-instance budgets.
  • Heartbeats: WS doesn't auto-detect dead connections — send ping/pong every 20–30s, drop on missed pong.
  • Scaling out: a publish from one instance must reach connections on other instances — use Redis pub/sub, NATS, or Kafka as the fanout layer.
  • Backpressure: slow consumers can OOM your server. Buffer with limits, drop or coalesce when the queue grows.
  • Authentication: JWT in the initial handshake (URL param or first message). Re-auth on token refresh.
  • SSE reconnect: server should honor Last-Event-ID header to replay missed events.
Interview one-liner: Both WebSocket and SSE push real-time updates from server to browser. WebSocket is full-duplex over a persistent TCP socket — use it for chat, collab, games, and trading where the client also sends data. SSE is one-way (server → client) over plain HTTP with automatic reconnect — use it for notifications, live feeds, price tickers, and LLM token streaming. SSE is simpler, scales easier (it's just HTTP), and is great when you only need server push. For anything truly interactive, WebSocket is the right tool — at the cost of more operational complexity (sticky sessions, heartbeats, fanout bus).
Design a URL shortener (bit.ly) hotmust

The main idea of a URL shortener is simple: we take a long URL, generate a short unique key, store the mapping, and when someone opens the short URL, we redirect them to the original URL.

First, the core APIs would be:

POST /shorten
This takes a long URL and returns something like:

https://short.ly/aB12xZ

GET /{shortCode}
This takes the short code, finds the original URL, and returns an HTTP redirect, usually 301 or 302.

Now coming to the database design.

We can have a table like:

url_mapping

with fields like:

id, short_code, long_url, user_id, created_at, expires_at, click_count

The most important thing here is that short_code should be unique and indexed, because redirection is the most frequent operation.

Now coming to short code generation.

There are a few approaches:

One approach is using an auto-increment ID and converting it into Base62.

Base62 means characters like:

a-z, A-Z, 0-9

So ID 1000001 can become something short like 4fG9.

This is simple, fast, and avoids collision.

Another approach is generating random strings, but then we need collision handling. So in real projects, I would prefer Base62 with a unique numeric ID.

Now coming to the high-level flow.

When a user creates a short URL:

First, validate the long URL.

Then insert a record into DB.

Then take the generated ID and convert it to Base62.

Then update the row with the short code.

Finally return the short URL to the user.

For redirect:

First, receive the short code.

Then check Redis cache.

If found, redirect immediately.

If not found, query DB.

If found in DB, put it into Redis and redirect.

If not found, return 404.

Now coming to scalability.

Read traffic will be much higher than write traffic, because one short URL may be opened thousands or millions of times.

So we should optimize redirect flow.

In real projects, I would use:

  • Redis cache for short_code -> long_url
  • Database index on short_code
  • Load balancer in front of multiple application instances
  • Read replicas if DB traffic becomes high

For analytics like click count, I would not update DB synchronously on every redirect, because that can slow down the redirect API.

Instead, I would publish an event to Kafka or a queue, and process analytics asynchronously.

Now coming to collision and uniqueness.

If we use Base62 from a unique database ID or distributed ID generator, collision is basically avoided.

If we use random code generation, we must check DB before saving and retry if collision happens.

Now coming to expiration.

Some short URLs may expire after a certain time.

So during redirect, we check expires_at.

If expired, return a proper error page instead of redirecting.

Now coming to system design components.

We would have:

  • Client
  • API Gateway or Load Balancer
  • URL Shortener Service
  • Redis Cache
  • Database
  • Kafka or Queue
  • Analytics Service

For storage, we can use MySQL/PostgreSQL for strong consistency. At very large scale, we can shard by short_code or id.

In conclusion, the key points are:

Generate a unique short code, store the mapping, make redirect very fast using cache, keep analytics async, and design the system mainly for high read traffic.

For a URL shortener, I would mainly use PostgreSQL or MySQL as the primary database.

The reason is simple: the core data is a mapping:

shortCode -> longUrl

This data must be reliable. Once we generate a short URL, we should not lose it, and the short code should always be unique.

In real projects, I would choose PostgreSQL because it gives strong consistency, good indexing, transactions, and it works very well for this kind of structured data.

The table would be something like:

id, short_code, long_url, user_id, created_at, expires_at

Here, short_code will have a unique index, because redirect requests will always search by short code.

Now coming to performance, I would not hit the database for every redirect.

I would use Redis in front of the database as a cache.

So the read flow is:

First check Redis.

If found, redirect immediately.

If not found, read from PostgreSQL, put it into Redis, then redirect.

At very large scale, we can add read replicas for PostgreSQL and later do sharding based on short_code or id.

So my final choice would be:

PostgreSQL as the main persistent database, and Redis as the caching layer.

Design a File Upload/Storage System must

The main idea of a file upload and storage system is simple:

We allow users to upload files, store the actual file in object storage, and store only the file metadata in our database.

In real projects, we usually don’t store files directly inside PostgreSQL or MySQL, because files can be large and database storage becomes expensive and hard to scale.

First, the main components would be:
  • Client
  • Upload Service
  • Metadata Database
  • Object Storage like S3, Azure Blob, or GCP Cloud Storage
  • Virus Scanner
  • CDN
  • Notification or Processing Service
Now coming to the upload flow.

There are two common approaches.

For small files, the client can upload the file directly to our backend API.

The backend validates the file, uploads it to S3 or Blob Storage, stores metadata in DB, and returns the file URL or file ID.

But for large files, I would prefer pre-signed URL upload.

In this flow:

Client asks backend for an upload URL.

Backend validates user permission and creates a pre-signed URL.

Client uploads the file directly to object storage.

After upload completes, client calls backend to confirm.

Backend stores file metadata in DB.

This is better because large file traffic does not pass through our application servers.

Now coming to database design.

We can have a files table:

id

user_id

file_name

storage_path

content_type

size

status

checksum

created_at

Here, storage_path points to the object storage location.

Status can be:

UPLOADING, UPLOADED, SCANNING, AVAILABLE, FAILED, DELETED

Now coming to security.

We should validate file type, file size, and extension.

But extension alone is not enough. We should also check MIME type or file signature.

For sensitive systems, after upload we should run virus scanning asynchronously.

Until scanning is complete, the file should not be available for download.

Also, files should not be public by default.

We should keep them private and generate temporary download URLs when needed.

Now coming to download flow.

User requests file download.

Backend checks permission.

If allowed, backend generates a pre-signed download URL.

Client downloads directly from object storage or CDN.

This keeps our backend lightweight.

Now coming to large file support.

For very large files, we can use multipart upload.

The client uploads the file in chunks.

If one chunk fails, only that chunk is retried, not the full file.

This improves reliability and user experience.

Now coming to scalability.

Object storage already scales very well.

Our backend mainly handles metadata, permissions, and pre-signed URL generation.

For frequently accessed public files, we can put CDN in front.

For private files, we can still use signed CDN URLs.

Now coming to reliability.

Sometimes upload may start but not complete.

So we should have a cleanup job that deletes incomplete files after some time.

Also, we should keep metadata and storage consistent.

For example, if DB save fails after file upload, we need a cleanup mechanism.

Now coming to real project usage.

In real projects, I would use:

S3 or Azure Blob for actual file storage

PostgreSQL for metadata

Redis for temporary upload session tracking

Kafka or queue for async scanning and processing

CDN for fast downloads

In conclusion, I would design the system with object storage for files, database for metadata, pre-signed URLs for upload and download, async virus scanning, permission checks, and cleanup jobs.

This keeps the system scalable, secure, and cost-effective.

Design API Rate Limiter must

The main idea of an API Rate Limiter is to control how many requests a user, IP, API key, or service can make in a given time.

For example:

100 requests per minute per user

If the user crosses that limit, we return:

HTTP 429 Too Many Requests

First, I would place the rate limiter at the API Gateway level, because we want to block excessive traffic before it reaches backend services.

In real projects, we can also have service-level rate limiting for sensitive APIs like login, OTP, payment, or password reset.

Now coming to the basic flow.

When a request comes in:

We identify the client by userId, apiKey, or IP address.

Then we create a key like:

rate_limit:user_123:/orders

Then we check how many requests this user has made in the current time window.

If the count is within the limit, we allow the request.

If the count crosses the limit, we reject it with 429.

Now coming to the algorithm.

For simple cases, we can use Fixed Window Counter.

Example:

100 requests per minute

But fixed window has a small problem.

A user can send 100 requests at 10:00:59 and another 100 at 10:01:00.

So practically, they send 200 requests in 2 seconds.

That’s why in real systems, I would prefer Token Bucket or Sliding Window.

With Token Bucket, every user has a bucket with tokens.

Each request consumes one token.

Tokens are refilled at a fixed rate.

If tokens are available, allow the request.

If no tokens are available, reject it.

This is good because it supports controlled burst traffic.

Now coming to storage.

For a distributed system, we cannot keep counters only in application memory, because we may have multiple instances.

So I would use Redis.

Redis is fast, supports atomic operations, and works well for counters with expiry.

For example, we can use Redis commands like increment and expiry for fixed window.

For token bucket, we can store current token count and last refill timestamp.

To avoid race conditions, we can use Lua scripts in Redis so the check-and-update happens atomically.

Now coming to distributed setup.

The flow would be:

Client

API Gateway

Rate Limiter

Redis Cluster

Backend Services

The gateway checks Redis before forwarding the request.

If allowed, it goes to backend.

If blocked, gateway returns 429.

Now coming to different limits.

In real projects, limits are not the same for everyone.

For example:

Anonymous user: 20 requests/minute

Logged-in user: 100 requests/minute

Premium user: 1000 requests/minute

Internal service: higher limit

So we need a rate_limit_rules table or configuration service where we define limits by user type, API, or tenant.

Now coming to failures.

If Redis is down, we need to decide between two approaches.

Fail-open means allow traffic even if rate limiter is down.

Fail-closed means block traffic.

In most consumer applications, I would choose fail-open for normal APIs, because we don’t want to block all users.

But for sensitive APIs like OTP or login, we may choose fail-closed or use local fallback limits.

Now coming to headers.

A good API should return rate limit headers like:

X-RateLimit-Limit

X-RateLimit-Remaining

X-RateLimit-Reset

This helps clients understand when they can retry.

Now coming to real project concerns.

We should rate limit based on multiple dimensions.

For example:

Per IP for public APIs.

Per user for logged-in APIs.

Per API key for external partners.

Per endpoint for expensive APIs.

Also, for login APIs, we may combine rate limiting with account lock or CAPTCHA after repeated failures.

In conclusion, I would design the rate limiter at the API Gateway level, use Redis for distributed counters, prefer Token Bucket or Sliding Window for better accuracy, support different limits by user/API type, and return 429 when the limit is crossed.

The main focus is protecting backend services without affecting normal users.

Design a distributed rate limiter must

  • One round trip per request → 0.5–1 ms added latency.
  • Exact quota globally — no overshoot.
  • Redis cluster is the bottleneck at very high QPS.
  • Default choice for almost everyone.
Cell-based / sharded counters
  • One key per shard of the API key (k:shard0..N).
  • Eliminates single-hot-key contention.
  • Each pod consults one shard; sum periodically.
  • Trade exactness for throughput (small over/undershoot).
Local + sync (token-stealing)
  • Each pod pre-fetches N tokens, decrements locally.
  • When local pool empties, fetches another batch from Redis.
  • Sub-ms latency, scales linearly with pods.
  • Allows brief overshoot equal to (batch × pods).
Gateway sidecar (Envoy + RLS)
  • Sidecar offloads the limit check to an external service.
  • Used in Istio, Lyft's ratelimit service.
  • Decouples app code from limit policy.
  • Standard for service-mesh deployments.

Common interview gotchas:

  • Hot-key shard hotspot — one famous API key on one Redis slot = melted shard; use key sharding.
  • Lua latency — keep scripts under 100 µs of Redis CPU; preload with SCRIPT LOAD and EVALSHA.
  • Multi-region — true global counters need consensus; usually accept per-region quotas and sum offline.
  • Fairness — without weighting, one greedy caller will starve others sharing a bucket.
  • Clock drift across pods can cause double-counting at window boundaries; rely on server time in the Lua script.
  • Fail-open vs fail-closed — fail-open keeps the site up, fail-closed protects a fragile downstream; pick deliberately.
  • Observability — emit allowed, denied, fallback, p99 per key prefix; rate-limit metrics drive product decisions.
  • Test under chaos — kill Redis primary, induce 200 ms latency, ensure the system degrades, not collapses.

Interview one-liner: A distributed rate limiter keeps shared counters in a Redis cluster and mutates them with an atomic Lua script per request. For very hot keys you shard the counter or use a local-token-bucket pattern that batch-syncs to Redis. The hard parts are not the algorithm — they're hot-key contention, fail-open behaviour when Redis blinks, accurate quotas across regions, and emitting the right metrics so quotas can be tuned over time.

Redis Pub/Sub vs Kafka — when to use which must

Both Redis Pub/Sub and Kafka are messaging systems, but they sit at opposite ends of the spectrum. Redis Pub/Sub is a fire-and-forget broadcast bus with no persistence; Kafka is a distributed, durable, replayable log. Picking the wrong one is a classic production bug.

CORE IDEA Redis Pub/Sub = "tell everyone listening right now"; Kafka = "write to a durable log so any consumer, now or tomorrow, can read it". Redis Streams sits in between — Redis-grade ops with Kafka-like consumer groups.

Use Redis Pub/Sub for…
  • Cache invalidation broadcasts ("user 42 changed").
  • Chat fan-out to currently-connected WebSocket pods.
  • Real-time presence / typing indicators.
  • Cluster-wide config refresh.
  • Anywhere "missed = fine, we'll re-sync later" holds.
Use Kafka for…
  • Event sourcing / change-data-capture pipelines.
  • Order events, payment events, audit logs.
  • Stream processing (Flink, Spark, ksqlDB).
  • Saga / outbox patterns across services.
  • Any "we must never lose a message" workflow.
Use Redis Streams for…
  • Light-weight job queues with consumer groups.
  • When you already run Redis and don't want to operate Kafka.
  • Short-retention event log with replay (minutes/hours).
  • Replacing in-process queues across pods.
Avoid Redis Pub/Sub when…
  • You need durability or replay.
  • You require fan-out with backpressure (slow consumers).
  • You need partition-level ordering across many consumers.
  • You need exactly-once semantics.

Code shape — same producer/consumer expressed in both:

# Redis Pub/Sub — broadcast cache invalidation
PUBLISH cache.invalidate.user '{"userId":42}'

SUBSCRIBE cache.invalidate.user
  # each subscriber gets EVERY message; if disconnected, missed = lost

# Redis Streams — durable, with consumer groups
XADD orders * type ORDER_PAID id o_123
XGROUP CREATE orders billing 0
XREADGROUP GROUP billing worker-1 COUNT 10 BLOCK 5000 STREAMS orders >
XACK orders billing 1716123-0

# Kafka — log + consumer groups + partition ordering
producer.send(new ProducerRecord<>("orders", orderId, json));   // key = orderId
// Consumer group "billing": each partition consumed by one member
props.put("group.id","billing");
props.put("enable.auto.commit","false");
consumer.subscribe(List.of("orders"));
for (var rec : consumer.poll(Duration.ofSeconds(1)))
    process(rec);                                       // at-least-once
consumer.commitSync();

Common interview gotchas:

  • Redis Pub/Sub has no buffer — a slow subscriber is disconnected and loses messages.
  • Pub/Sub for chat works as the fan-out fabric between WebSocket pods, but the durable message store must be DB/Kafka, not Pub/Sub itself.
  • Kafka ordering is per-partition, not per-topic — choose your partition key carefully.
  • Kafka exactly-once works only inside Kafka (transactional producer + consumer); end-to-end exactly-once requires idempotency in the consumer too.
  • Operating Kafka is non-trivial — ZK/KRaft, broker rebalances, ISR tuning, disk planning; managed (MSK, Confluent) is usually right at startups.
  • Redis Streams is bounded — set MAXLEN ~ N aggressively or you'll OOM.
  • Cluster vs single Redis — Pub/Sub in Redis Cluster has weaker fan-out semantics; understand SPUBLISH in 7+.
  • Latency vs throughput — Pub/Sub wins on latency for small payloads; Kafka wins on sustained throughput and durability.

Interview one-liner: Redis Pub/Sub is an at-most-once, zero-retention broadcast bus — perfect for cache invalidation, real-time fanout, presence. Kafka is a durable, replayable, partition-ordered log — perfect for event sourcing, audit, ETL, sagas. Redis Streams is the middle ground: Kafka-like consumer groups inside a Redis you already operate. Choose by asking "do I need replay, durability, and ordered consumer groups?" — if any of those is yes, go Kafka.

Design Real-Time Messaging System must

The main idea of a Real-Time Messaging System is:

Users should be able to send and receive messages instantly, and the system should also handle offline users, delivery status, read receipts, and message history.

Think of something like WhatsApp, Slack, or in-app chat.

First, the main components would be:

  • Client app
  • API Gateway
  • WebSocket Gateway
  • Messaging Service
  • Message Queue
  • Message Database
  • Presence Service
  • Notification Service
  • Media/File Service
Now coming to the connection part.

For real-time communication, I would use WebSocket.

When a user opens the app, the client creates a WebSocket connection with the WebSocket Gateway.

The gateway keeps the connection alive and tracks something like:

userId -> active connection

If the user is online, we can push the message immediately.

If the user is offline, we store the message and send a push notification.

Now coming to the send message flow.

When User A sends a message to User B:

First, the message goes to the Messaging Service.

The service validates sender, receiver, and conversation permissions.

Then it stores the message in the database with status like SENT.

After that, it publishes an event to Kafka or RabbitMQ.

The delivery worker checks whether User B is online.

If User B is online, it pushes the message through WebSocket.

If User B is offline, it keeps the message in DB and triggers push notification.

Now coming to database design.

We can have a conversations table:

id, type, created_at

Type can be ONE_TO_ONE or GROUP.

Then a conversation_members table:

conversation_id, user_id, role, joined_at

Then a messages table:

id, conversation_id, sender_id, message_type, content, media_url, created_at, status

For delivery and read status, we can have:

message_receipts

with fields like:

message_id, user_id, delivered_at, read_at

This is useful especially for group chats, because each user can have a different read status.

Now coming to message ordering.

Ordering is very important.

Inside one conversation, messages should appear in the correct order.

So we can generate a sequence number per conversation.

For example:

conversation_id + sequence_number

Kafka partitioning can also help here.

If we partition messages by conversation_id, then messages of the same conversation go to the same partition and maintain order.

Now coming to offline delivery.

If the receiver is offline, we don’t lose the message.

The message is already stored in DB.

When the user comes online again, the client can call sync API like:

GET /conversations/{id}/messages?after=lastMessageId

This will fetch missed messages.

So WebSocket is for real-time push, but REST API is still useful for history and recovery.

Now coming to presence.

Presence means whether the user is online, offline, typing, or last seen.

I would store temporary presence state in Redis.

For example:

user:123:status = online

with a TTL.

The WebSocket Gateway updates this status using heartbeat or ping-pong.

If heartbeat stops, the user becomes offline.

Now coming to scalability.

WebSocket connections are long-lived.

So we need multiple WebSocket Gateway instances behind a load balancer.

But one issue is: User B may be connected to a different gateway instance.

So when User A sends a message, the system should know which gateway has User B’s connection.

We can store:

userId -> gatewayId

in Redis.

Then the Messaging Service can route the message to the correct gateway.

For cross-gateway communication, we can use Redis Pub/Sub, Kafka, or internal gRPC.

Now coming to media messages.

For images, videos, and files, we should not send the file through WebSocket.

The client uploads media to object storage like S3 using pre-signed URL.

Then the message only contains the media URL or file ID.

This keeps WebSocket lightweight.

Now coming to idempotency.

Sometimes the client may retry sending the same message because of network issues.

So the client should send a client_message_id.

The server checks this ID before saving.

If the same message was already saved, we return the existing message instead of creating a duplicate.

Now coming to notifications.

If the user is offline, we send push notifications using Firebase/APNS.

But for muted conversations, blocked users, or disabled notifications, we should respect user preferences.

So Notification Service should check preferences before sending.

Now coming to real project concerns.

We should handle:

  • message retry
  • duplicate message prevention
  • read receipts
  • typing indicators
  • blocked users
  • group membership changes
  • message deletion
  • rate limiting
  • encryption if required
  • audit logs for moderation

For storage, at normal scale, PostgreSQL can work.

At very large scale, I would use Cassandra, DynamoDB, or ScyllaDB because messaging data is huge and write-heavy.

For search inside messages, we can use OpenSearch or Elasticsearch separately.

In conclusion, I would design the Real-Time Messaging System with WebSocket for live delivery, database for durable message storage, Redis for presence and connection routing, Kafka for async message delivery, and push notification for offline users.

The most important points are: message durability, correct ordering inside conversation, scalable WebSocket connections, and reliable offline sync.

Design a news feed / timeline

Requirements: each user sees a feed of posts from people they follow, sorted by recency or relevance.

Two strategies:

Pull (fan-out on read) — at read time, query posts from all the user's followees, merge, sort. Simple but slow at scale.

Push (fan-out on write) — when a user posts, write into each follower's pre-computed timeline. Fast reads, but a celebrity with 10M followers triggers a write storm.

Hybrid (used by Twitter, Instagram) — push for normal users, pull for celebrities. At read time, merge precomputed timeline with on-the-fly fetch of celebrity posts.

Components: Posts in a write-optimized store (Cassandra), timeline in Redis sorted sets keyed by userId, ranking service for ML-driven sorting, CDN for media. Use Kafka for fan-out workers.

Design a notification system must

The main idea of a notification system is to send messages to users through different channels like email, SMS, push notification, or in-app notification.

First, I would keep the system event-driven, because notifications should not slow down the main business flow.

For example, when an order is placed, the Order Service should not directly send email or SMS. It should publish an event like:

ORDER_PLACED

Then the Notification System consumes that event and sends the notification.

Now coming to the main components.

We would have:

  • Client or backend services
  • Notification API
  • Message Queue like Kafka or RabbitMQ
  • Notification Service
  • Template Service
  • User Preference Service
  • Provider Integration like Email, SMS, Push
  • Notification DB
  • Retry and DLQ mechanism
Now coming to the flow.

First, some service publishes an event, like order placed or password reset.

Then the notification service consumes that event.

It checks the user’s notification preferences.

For example, maybe the user allowed email but disabled SMS.

Then it picks the correct template.

For example:

“Your order {{orderId}} has been placed.”

Then it fills dynamic values.

After that, it sends the message using the right provider, like SendGrid for email, Twilio for SMS, or Firebase for push notifications.

Finally, it stores the status like SENT, FAILED, or RETRYING.

Now coming to database design.

We can have a notifications table:

id, user_id, channel, template_id, status, created_at, sent_at, retry_count

And a notification_templates table:

id, type, channel, subject, body, language, version

And maybe a user_preferences table:

user_id, email_enabled, sms_enabled, push_enabled

Now coming to scalability.

Notification traffic can be very high, so we should process it asynchronously using Kafka.

We can scale consumers horizontally.

For example, multiple notification workers can consume from the queue and send notifications in parallel.

For high-priority notifications like OTP or password reset, I would use a separate priority queue.

For marketing notifications, we can use a low-priority queue.

Now coming to failure handling.

External providers can fail, so retry is very important.

If sending fails, we retry with exponential backoff.

If it still fails after max retries, we move it to a Dead Letter Queue.

This helps us debug later without losing messages.

Now coming to idempotency.

This is very important.

Sometimes the same event may be consumed twice.

So we should have an event_id or notification_id.

Before sending, we check whether this notification was already sent.

This prevents duplicate SMS or duplicate emails.

Now coming to rate limiting.

We should not spam users or overload providers.

So we can rate limit per user and per channel.

For example, not more than 5 promotional SMS per day.

Now coming to real project usage.

In real projects, I would separate transactional notifications and promotional notifications.

Transactional notifications like OTP, payment success, and password reset should be fast and reliable.

Promotional notifications can be delayed and processed in batches.

So overall, my design would be:

Use an event-driven architecture, Kafka for async processing, Redis for rate limiting and temporary state, PostgreSQL for notification records and templates, and external providers for actual delivery.

The main focus is reliability, retry handling, avoiding duplicate notifications, and not blocking the main application flow.

Design a Payment Processing System must

The main idea of a Payment Processing System is:

We should never treat payment as a simple one-step API call. Payment is a state-based flow where money movement can succeed, fail, timeout, or come later through a webhook.

First, the main components would be:

  • Payment Service
  • Order Service
  • Payment Gateway like Razorpay, Stripe, PayU
  • Database
  • Webhook Handler
  • Message Queue
  • Notification Service
  • Refund Service
  • Reconciliation Job
Now coming to the payment flow.

When a user places an order, Order Service creates the order with status:

PENDING_PAYMENT

Then Payment Service creates a payment request with the gateway.

The gateway returns a payment link, session id, or payment intent.

User completes payment on the gateway page.

After that, the gateway sends a webhook to our system saying payment succeeded or failed.

Then Payment Service updates payment status and publishes an event like:

PAYMENT_SUCCESS

Order Service consumes that event and marks the order as:

CONFIRMED

Now coming to the database design.

We can have a payments table:

id

order_id

user_id

amount

currency

gateway_name

gateway_payment_id

status

idempotency_key

created_at

updated_at

Status can be:

INITIATED, PENDING, SUCCESS, FAILED, CANCELLED, REFUNDED

We can also have a payment_events table to store all webhook events from gateway.

This is useful for audit and debugging.

Now coming to idempotency.

This is very important in payments.

The same payment request may be retried.

The same webhook may come multiple times.

So every create-payment request should have an idempotency_key.

Before creating a new payment, we check whether payment already exists for that key.

For webhooks, we store the gateway event id.

If the same webhook comes again, we ignore it.

This prevents duplicate payments and duplicate order confirmation.

Now coming to webhook handling.

Webhook handling should be secure.

First, verify the gateway signature.

Then store the raw webhook event.

Then process it.

Also, webhook processing should be idempotent.

In real projects, I prefer storing webhook first, then processing asynchronously through a queue.

That way, even if processing fails, we don’t lose the event.

Now coming to consistency with Order Service.

Payment Service and Order Service usually have separate databases.

So we should not use one big distributed transaction.

Instead, I would use event-driven communication.

Payment Service publishes:

PAYMENT_SUCCESS or PAYMENT_FAILED

Order Service consumes it and updates the order.

If event publishing fails, we can use the Outbox Pattern.

So payment update and event save happen in the same DB transaction.

Then a background publisher sends the event to Kafka.

Now coming to refund flow.

Refund should also be state-based.

Refund request comes in.

We create a refund record with status INITIATED.

Then call the payment gateway refund API.

Gateway may return success immediately or later through webhook.

So refund status can be:

INITIATED, PROCESSING, SUCCESS, FAILED

And once refund succeeds, we publish:

REFUND_SUCCESS

Now coming to failure handling.

Payment APIs can timeout.

A timeout does not always mean failure.

Maybe payment succeeded at gateway side but our system didn’t receive response.

So we should not blindly mark it as failed.

We keep it as PENDING and later verify using gateway status API or webhook.

This is very important in real payment systems.

Now coming to reconciliation.

Sometimes webhook may be missed.

So we need a scheduled reconciliation job.

It checks pending payments with the gateway and updates the correct status.

Now coming to security.

order_id

user_id

gateway_payment_id

idempotency_key

For async events, use Kafka or RabbitMQ.

The main idea of an Order Management System is to manage the complete order lifecycle — from order creation, payment, inventory update, shipment, cancellation, and refund.

We can have:

  • Order Service
  • Payment Service
  • Inventory Service
  • Shipment Service
  • Notification Service
  • User Service
  • Product Service

When a user places an order:

First, the Order Service validates the cart.

Then it creates an order with status like CREATED or PENDING_PAYMENT.

Then it calls Payment Service or publishes a payment event.

After that, Shipment Service creates shipment.

orders

Stores order-level data like order id, user id, total amount, payment status, order status, created time.

order_items

Stores product id, quantity, price, discount, tax, and item status.

order_status_history

Stores every status change, because in real projects we need audit tracking.

payments

Stores payment id, order id, amount, payment mode, payment status.

shipments

Stores shipment id, order id, courier partner, tracking id, shipment status.

Now coming to consistency.

This is the most important part.

Order creation touches payment, inventory, and shipment, so one single database transaction across all services is not practical.

In real projects, I would use the Saga pattern.

For example:

Create order

Reserve inventory

Take payment

Confirm order

Create shipment

If payment fails, we release inventory.

If shipment creation fails, we can retry or mark it for manual processing.

Now coming to message queue.

For example:

ORDER_CREATED

PAYMENT_SUCCESS

PAYMENT_FAILED

INVENTORY_RESERVED

ORDER_SHIPPED

This makes the system more reliable and avoids tight dependency between services.

Now coming to idempotency.

This is very important.

So every request should have an idempotency_key or event_id.

Before processing, we check whether it is already processed.

This avoids duplicate orders, duplicate payments, or duplicate stock deduction.

Now coming to inventory handling.

For inventory, I would prefer stock reservation first.

Now coming to scalability.

Important indexes would be:

user_id

order_id

order_status

created_at

For order history, we can also use a read-optimized store or Elasticsearch if search/filtering becomes heavy.

Now coming to real project concerns.

We should also handle:

  • retry mechanism
  • dead letter queue
  • audit logs
  • role-based access for admin operations
  • refund workflow
  • order cancellation rules
  • notification on every important status change

In conclusion, I would design the Order Management System around the Order Service as the central coordinator, use events for communication, use Saga for distributed consistency, and keep payment, inventory, and shipment loosely connected but reliable.

Design an inventory reservation system must

An inventory reservation system holds stock for a customer during checkout, prevents overselling under concurrent demand, and gracefully releases unused holds. The interview expects you to discuss optimistic vs pessimistic locking, Redis-based hot-stock counters with periodic DB reconciliation, and saga compensations when orders cancel.

CORE IDEA Keep authoritative stock in the DB; decrement a Redis hot counter atomically during checkout with a TTL so abandoned carts auto-release; reconcile Redis back to DB periodically and on every order completion. Overselling is solved by an atomic check-and-decrement, not by application-level locks.

Reservation lifecycle:

Cart triggers reserve(sku, qty=2, holdId, ttl=15m)
↓
Redis Lua: if available ≥ qty → decrement + write hold:holdId with TTL
↓
Customer pays → confirm(holdId) → DB row inserted, Redis hold removed
↓
Customer abandons → TTL expires → keyspace notification triggers release back to counter
↓
Order cancel/refund → release(holdId or orderId) → counter incremented
↓
Every N min: reconcile Redis counter ↔ DB authoritative qty
Optimistic locking (DB only)
  • UPDATE stock SET qty=qty-2, ver=ver+1 WHERE sku=? AND ver=? AND qty>=2
  • If rows=0 → retry or fail.
  • Simple, but contention kills throughput on hot SKUs.
  • OK for slow-moving items.
Pessimistic locking (DB row lock)
  • SELECT ... FOR UPDATE then update.
  • Serializes writers — predictable but slow.
  • Risk of long-running tx blocking the DB.
  • Rarely the right answer at scale.
Redis hot counter (recommended)
  • Atomic EVAL Lua: check & decrement in one op.
  • Sub-ms latency, no DB contention on hot SKUs.
  • Periodic reconciliation back to DB.
  • TTL holds auto-release abandoned carts.
Token-bucket per SKU (extreme hot)
  • Pre-allocate N tokens at sale start (Black Friday SKU).
  • Sharded counters per node to remove single-key bottleneck.
  • Sum counters periodically for accurate qty.
  • Accept micro-oversell, compensate via cancellation.

Atomic reservation — Redis Lua:

-- KEYS[1]=stock:sku:S1   KEYS[2]=hold:hold123   ARGV: qty, ttl_sec
local stock = tonumber(redis.call('GET', KEYS[1]) or '0')
local qty   = tonumber(ARGV[1])
if stock < qty then return {0, stock} end
redis.call('DECRBY', KEYS[1], qty)
redis.call('SET', KEYS[2], qty, 'EX', tonumber(ARGV[2]))
return {1, stock - qty}

Common interview gotchas:

  • Check-then-update races — always atomic via Lua / SQL WHERE qty >= ?.
  • Cart abandonment — every reservation needs a TTL or you'll oversell holds.
  • Hot SKU contention — single-key Redis bottlenecks; shard with bucketing or pre-allocated tokens.
  • Reconciliation drift — Redis is faster but lossy; the DB is the source of truth; cap drift via frequent recon.
  • Multi-warehouse — a SKU at multiple locations is per-(sku, warehouse); pick fulfillment location after reserve.
  • Backorders / pre-orders — allow negative qty with an upper cap; emit different event.
  • Saga compensation — order cancel must always release inventory; idempotent by holdId.
  • WMS sync — physical movements (pick/pack) update the DB; events propagate back to Redis.
  • Hot SKU stampede on flash sale — pre-warm counters, queue request waiting room, fall back to lottery.

Interview one-liner: Hold stock in Redis hot counters with an atomic Lua check-and-decrement, write a hold key with TTL so abandoned carts auto-release, and reconcile back to the authoritative DB on every confirmation and periodically. The DB is the source of truth, Redis is the fast lane, and saga compensations release inventory on every cancel/refund. Hot SKU contention is the main scaling challenge — solved by shard-bucketing or pre-allocated token pools.

Design a Distributed Logging/Audit System must

The main idea of a Distributed Logging and Audit System is to collect logs and audit events from many services, store them reliably, and make them searchable for debugging, monitoring, compliance, and security investigation.

First, I would separate logs and audit events, because they have different purposes.

Logs are mainly for debugging, like:

error occurred while calling payment service

Audit events are business or security records, like:

user changed password

admin refunded order

role permission updated

Audit data is more sensitive and usually needs stronger consistency, retention, and immutability.

Now coming to the high-level design.

Each microservice will generate logs or audit events.

Instead of writing directly to the logging database, services will push logs to a collector or agent.

For example:

Application Service

Log Agent or Sidecar

Kafka

Log Processing Service

Storage

Search and Dashboard

In real projects, we can use something like Fluent Bit, Logstash, Kafka, Elasticsearch/OpenSearch, and Kibana/Grafana.

Now coming to the log flow.

First, the application writes logs in structured JSON format.

For example, each log should have:

timestamp

serviceName

traceId

requestId

userId

logLevel

message

metadata

The important part is traceId.

If one request goes through Order Service, Payment Service, and Notification Service, the same traceId helps us search the full request journey across services.

Now coming to audit flow.

Audit events should be explicitly created by the application.

For example, when an admin changes user permissions, the service publishes an audit event like:

USER_ROLE_UPDATED

This event should contain:

actorId

action

resourceType

resourceId

oldValue

newValue

timestamp

ipAddress

For audit, I would store data in an append-only way.

That means we don’t update old audit records. We only insert new records.

This helps with compliance and investigation.

Now coming to storage.

For logs, I would use OpenSearch or Elasticsearch, because logs need fast search and filtering.

For long-term archive, I would move old logs to object storage like S3.

For audit events, I would use PostgreSQL for structured queries, and also archive to S3 or immutable storage for long-term retention.

So practically:

Recent logs: OpenSearch

Old logs: S3

Audit records: PostgreSQL plus S3 archive

Now coming to scalability.

Logging volume can be huge, so we should not let logging slow down business APIs.

That’s why logs should be collected asynchronously.

Kafka helps here because it can absorb high traffic.

Consumers can process logs in batches and write to OpenSearch.

We can partition Kafka topics by service name or tenant id.

For storage, we can create daily indexes like:

logs-order-service-2026-05-17

This makes retention and deletion easier.

Now coming to reliability.

If OpenSearch is down, we should not lose logs.

Kafka can keep logs for some time.

The processing service can retry.

If processing keeps failing, we move bad messages to a Dead Letter Queue.

For audit events, reliability is even more important.

So the service should either write audit data in the same transaction as the business change, or use the Outbox Pattern.

For example, if role update succeeds but audit event fails, that is dangerous.

So I would save the audit event into an outbox table inside the same DB transaction, then a background worker publishes it to Kafka.

Now coming to security.

Logs should not contain sensitive data like passwords, tokens, card numbers, or full personal details.

We should mask sensitive fields before sending logs.

For audit logs, access should be restricted.

Only authorized admins or compliance teams should be able to view them.

Also, audit logs should be tamper-resistant.

We can use append-only storage, encryption, access control, and checksum/hash chaining for stronger integrity.

Now coming to querying and dashboards.

Developers should be able to search logs by:

traceId

serviceName

errorCode

userId

time range

For audit, admins should be able to search by:

actorId

action

resourceId

time range

In real projects, this helps a lot during production issues.

For example, if a payment failed, we search by traceId and see the complete flow across all services.

In conclusion, I would design it as an async, centralized system using structured logs, Kafka, OpenSearch for searchable logs, PostgreSQL or immutable storage for audit events, and strong retention, masking, and access control.

The most important points are: don’t block business APIs, keep logs searchable, keep audit records reliable and tamper-resistant, and use traceId for end-to-end debugging.

Design a Job Scheduling System must

The main idea of a Job Scheduling System is:

We need a system that can run tasks at a specific time, repeatedly, or after some delay.

For example:

send email at 9 AM

generate report every night

retry failed payment after 10 minutes

run cleanup job every Sunday

First, I would separate the system into two parts:

Scheduler and Worker.

Scheduler decides when a job should run.

Worker actually executes the job.

Now coming to the main components.

We would have:

  • API Service
  • Job Metadata Database
  • Scheduler Service
  • Message Queue
  • Worker Service
  • Retry Handler
  • Dead Letter Queue
  • Monitoring Dashboard
Now coming to the job creation flow.

A client creates a job using an API.

For example:

POST /jobs

The request contains:

job_type

payload

schedule_time

cron_expression

priority

retry_policy

Then we store this job in the database with status like:

SCHEDULED

Now coming to database design.

We can have a jobs table:

id

job_type

payload

schedule_time

cron_expression

status

priority

retry_count

max_retries

created_at

updated_at

Status can be:

SCHEDULED, READY, RUNNING, SUCCESS, FAILED, RETRYING, CANCELLED

For recurring jobs, we can also have a job_runs table.

This stores every execution:

job_id

run_id

started_at

finished_at

status

error_message

Now coming to the scheduling flow.

Scheduler service keeps checking the database for jobs where:

schedule_time <= current_time

and status is SCHEDULED.

Then it marks them as READY and pushes them to a queue like Kafka, RabbitMQ, or SQS.

Workers consume from the queue and execute the job.

After execution, workers update the job status as SUCCESS or FAILED.

Now coming to distributed scheduling.

In real projects, we will run multiple scheduler instances.

So we must avoid two schedulers picking the same job.

We can handle this using database row locking.

For example:

SELECT ... FOR UPDATE SKIP LOCKED

This allows multiple schedulers to safely pick different jobs.

Another option is distributed lock using Redis or Zookeeper.

But for many systems, database locking works fine and is simpler.

Now coming to recurring jobs.

For cron jobs like:

every day at midnight

we should not keep running the same record again and again.

Instead, after one execution is triggered, we calculate the next execution time and update next_run_at.

Each run gets its own entry in job_runs.

This gives us proper history and debugging.

Now coming to retry handling.

Jobs can fail because of temporary issues.

For example, external API timeout.

So we need retry with exponential backoff.

If job fails, we increase retry_count and schedule it again after some delay.

For example:

First retry after 1 minute.

Second retry after 5 minutes.

Third retry after 15 minutes.

If it still fails after max retries, we move it to Dead Letter Queue or mark it as permanently failed.

Now coming to idempotency.

This is very important.

A job may run more than once due to retry or worker crash.

So workers should be idempotent.

For example, if the job is “send invoice email,” we should check whether that invoice email was already sent.

We can use job_id or idempotency_key to avoid duplicate processing.

Now coming to worker crash handling.

Suppose worker picks a job and crashes before updating status.

Then the job may remain stuck in RUNNING.

To solve this, we maintain a heartbeat or lock expiry.

If a job stays in RUNNING beyond timeout, scheduler can move it back to SCHEDULED or RETRYING.

Now coming to scalability.

Workers can be scaled horizontally based on queue size.

If there are too many email jobs, we add more email workers.

If report generation is heavy, we can have a separate queue for report jobs.

So practically, we can have:

high-priority queue

normal queue

low-priority queue

This prevents low-priority batch jobs from blocking urgent jobs.

Now coming to real project usage.

In real projects, this kind of system is used for:

  • payment retries
  • email notifications
  • daily reports
  • data cleanup
  • subscription renewal
  • invoice generation
  • background file processing

For technology choices, I would use:

PostgreSQL for job metadata

Redis for locks or quick delay queues

Kafka/RabbitMQ/SQS for job dispatching

Worker services in Spring Boot

Prometheus/Grafana for monitoring

In conclusion, I would design the Job Scheduling System with a persistent job database, scheduler service, queue-based dispatching, horizontally scalable workers, retry handling, idempotency, and proper monitoring.

The most important points are: don’t lose jobs, don’t execute the same job incorrectly, support retries, and make workers scalable.

Design Multi-Tenant SaaS Platform must

The main idea of a Multi-Tenant SaaS Platform is:

One application serves multiple customers, but each customer’s data, configuration, users, billing, and permissions should be isolated.

Here, each customer is called a tenant.

First, we need a way to identify the tenant.

Usually tenant comes from:

tenant1.myapp.com

or from request header:

X-Tenant-Id

or from logged-in user’s JWT token.

In real projects, I prefer tenant identification from the authenticated token, because headers can be spoofed if not controlled properly.

Now coming to tenant data isolation.

There are three common approaches.

First is shared database, shared schema.

All tenants use the same tables, and every table has tenant_id.

Example:

orders(id, tenant_id, user_id, amount)

This is simple and cost-effective, but every query must filter by tenant_id.

Second is shared database, separate schema.

Each tenant gets its own schema.

This gives better isolation, but migrations and operations become harder.

Third is separate database per tenant.

This gives the strongest isolation, useful for enterprise tenants, but it is more expensive and harder to manage.

In most SaaS products, I would start with shared database and tenant_id column, and for large enterprise customers, support separate database as a premium option.

Now coming to authentication and authorization.

A user may belong to one tenant or multiple tenants.

So login should return a token containing:

user_id

tenant_id

roles

permissions

Every API request should validate the tenant from token and make sure the user has access to that tenant.

We should never allow the client to pass any random tenant id and access data.

Now coming to database design.

Important tables would be:

tenants

Stores tenant details like name, domain, plan, status.

tenant_users

Maps users to tenants.

roles and permissions

For tenant-level access control.

Business tables like orders, invoices, projects should have tenant_id.

Also, we need indexes like:

tenant_id + created_at

tenant_id + user_id

tenant_id + status

because most queries will filter by tenant.

Now coming to tenant configuration.

Each tenant may have different settings.

For example:

branding

custom domain

feature flags

Caching invalidation — the "two hard problems"

"There are only two hard things in computer science: cache invalidation and naming things." Three practical approaches:

  • TTL-based — every entry expires after N seconds. Simple, eventual consistency. Pick TTL based on staleness tolerance. Works for 80% of use cases.
  • Write-through invalidation — on every write, delete or update the cached entry. Strong consistency but more code, and race conditions between reader-fills and writer-invalidations need care (use versioning or invalidate twice with a gap).
  • Event-driven invalidation — subscribe to a change stream (Kafka, CDC) and invalidate. Decouples writers from cache, scales across services.

Patterns that bite: cache stampede (use single-flight locks), negative caching (cache "not found" briefly to absorb floods), cache-coherency in clusters (consistent hashing + Redis cluster).
