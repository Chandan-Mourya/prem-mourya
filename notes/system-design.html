How do you approach a system design question? must

My structure for any 45-minute design interview:

  1. Clarify requirements (5 min) — functional (what does it do?) and non-functional (scale, latency, consistency, availability). Don't assume — ask numbers.
  2. Capacity estimation (5 min) — back-of-envelope: DAU, QPS, storage growth, bandwidth. Helps justify decisions later.
  3. API design (5 min) — define the main endpoints / events.
  4. High-level architecture (10 min) — draw boxes: clients, LB, app servers, DB, cache, queue, CDN. State the data flow.
  5. Deep dive (15 min) — pick 1–2 critical components and detail data model, scaling, failure modes. The interviewer guides you here.
  6. Bottlenecks & tradeoffs (5 min) — where it can break, what you'd add next.

The interview is about communication and tradeoffs, not a "correct" answer. Stay structured, think out loud, ask before assuming.

Vertical vs horizontal scaling

Vertical scaling — make one box bigger (more CPU, RAM, faster disks). Simple, no app changes. Limited by single-machine ceiling and downtime to resize. Cost grows non-linearly at the high end.

Horizontal scaling — add more boxes. Scales nearly linearly if your app is stateless and shardable. Requires a load balancer in front and architectural discipline — no in-memory session state, no local file caches.

My defaults: app tier horizontal (stateless services behind LB, auto-scaling in K8s/AWS), cache horizontal (Redis cluster), DB primary vertical first then horizontal (read replicas, then sharding when really needed).

The 12-Factor approach makes horizontal scaling natural — keep services stateless and let the orchestrator scale them.

What is Load Balancing? must

Load balancing is the process of distributing incoming network traffic across multiple servers so that no single server gets overloaded. A load balancer sits in front of a pool of backend servers and decides which one handles each incoming request. It's one of the most fundamental building blocks in any scalable system.

Core Idea — what it gives you
Availability If one server dies, traffic automatically shifts to healthy ones — no downtime.
Scalability Add or remove servers horizontally — the LB picks them up. Handles 10K → 10M users with the same architecture.
Performance No single box is overwhelmed → lower latency, better throughput, faster response times.
1 Why we need it — the simple picture
Without a Load Balancer
  • 10,000 users → 1 server → it dies / slows down
  • Single point of failure
  • Vertical scaling only (bigger box) — expensive & capped
  • Deploys cause downtime — server has to restart
With a Load Balancer
  • 10,000 users → LB → spread across N servers
  • One server dies? LB drains it, others keep serving
  • Horizontal scaling — add cheap commodity servers
  • Rolling deploys — restart one server at a time, zero downtime
2 Architecture — single front door, many backends
┌─────────────┐ │ Users │ (clients, browsers, mobile apps) └──────┬──────┘ │ ▼ ┌─────────────┐ │ LOAD │ ← health checks, routing algorithm │ BALANCER │ └──────┬──────┘ ┌────────┼────────┐ ▼ ▼ ▼ ┌────────┐ ┌────────┐ ┌────────┐ │Server 1│ │Server 2│ │Server 3│ (identical app instances) └────────┘ └────────┘ └────────┘

The LB performs health checks on each server (e.g. ping /health every 5s). Unhealthy ones are drained — no traffic routed to them. This is what turns load balancing from "spread requests" into a real availability mechanism.

3 Common Load-Balancing Algorithms (overview)
AlgorithmHow it works
Round Robin Requests distributed sequentially — server 1, 2, 3, 1, 2, 3, …
Weighted Round Robin Bigger / faster servers get more traffic via weights (e.g. 3:1:1).
Least Connections Routes to the server with the fewest active connections — great for long-lived connections.
IP Hash Hash of client IP → always picks the same server. Used for session stickiness.
Least Response Time Picks the server currently responding fastest.
Geo-based / GeoDNS Routes users to their nearest region or data center.

For full details on when to use each algorithm and the real-world tools, see the "Load balancing — strategies and where they're used" question below.

4 Benefits — at a glance
  • Prevents server overload — work is spread evenly.
  • Improves response time — no single box becomes a bottleneck.
  • High availability — automatic failover when servers go down.
  • Supports horizontal scaling — just spin up more servers, the LB picks them up.
  • Zero-downtime deploys — rolling restart, one server at a time.
  • SSL termination — decrypt HTTPS once at the LB, pass plain HTTP to backends.
  • Security — single ingress point to harden, hide internal IPs.
5 Layer 4 vs Layer 7 (where the LB sits)
L4 — Transport (TCP/UDP)
  • Routes by IP + port — doesn't inspect the payload
  • Extremely fast (line-rate)
  • App-agnostic — works for any TCP/UDP service
  • Examples: AWS NLB, HAProxy (TCP mode), F5
L7 — Application (HTTP)
  • Routes by URL path, headers, cookies, host
  • Can do SSL termination, sticky sessions, content-based routing
  • Slightly slower (inspects payload)
  • Examples: AWS ALB, NGINX, Envoy, Traefik

Interview-friendly answer: Load balancing is the process of distributing incoming user requests across multiple backend servers so that no single server is overloaded. A load balancer sits in front of the server pool and routes requests using algorithms like round-robin, least connections, or IP hash. This gives the system high availability (failover when a server dies), scalability (just add more servers), and better performance (no single bottleneck). For example, an e-commerce site with millions of users uses a load balancer in front of its app servers so that traffic is distributed evenly, and the site stays online even if one server fails. Common tools: NGINX, HAProxy, AWS ALB/NLB, Envoy, Traefik.
Load balancing — strategies and where they're used must

A load balancer sits in front of a pool of servers and distributes incoming requests across them. The whole point is to improve three things at once:

Why we load-balance — 3 goals
Performance No single server gets overwhelmed → lower latency, better throughput.
Scalability Add or remove instances horizontally without app changes.
Availability If one server dies, health checks drain it and traffic shifts to healthy ones.
1 Common Load-Balancing Strategies
StrategyHow it worksBest used when
Round Robin Requests go one-by-one to each server in order. All servers have equal capacity.
Weighted Round Robin More powerful servers get a higher share (e.g. 3:1). Servers have different capacities (mixed instance sizes).
Least Connections Sends request to the server with the fewest active connections. Long-lived connections — WebSockets, chat, DBs.
Weighted Least Connections Combines server weight with current active connections. Mixed capacities + long-lived sessions.
IP Hash Hash of client IP → always picks the same server. Session stickiness needed (no shared session store).
Consistent Hashing Hashes the key onto a ring; adds/removes servers with minimal reshuffle. Cache routing (Redis cluster, CDN edge), shard routing.
Least Response Time Picks the server with the fastest current response. Performance-critical, latency-sensitive systems.
Random Just picks one at random. Simple setups, mostly stateless services.
Geo-based / GeoDNS Routes user to the nearest region or data center. Global apps, CDNs, streaming, multi-region SaaS.
2 L4 vs L7 — at which layer does it balance?
L4 — Transport (TCP/UDP)
  • Routes by: IP + port
  • Speed: very fast — no payload inspection
  • App-aware: no
  • Features: raw TCP/UDP forwarding
  • Examples: AWS NLB, HAProxy (TCP mode), F5 BIG-IP
L7 — Application (HTTP)
  • Routes by: URL path, headers, cookies, host
  • Speed: slower — does payload inspection
  • App-aware: yes
  • Features: SSL termination, sticky sessions, content-based routing, WAF
  • Examples: AWS ALB, NGINX, Envoy, Traefik
3 Where each strategy is used in the real world

Round Robin

  • Small web apps
  • Stateless REST APIs
  • Internal microservice traffic
Tools: NGINX (default), HAProxy, AWS ALB

Least Connections

  • Chat / messaging apps
  • WebSocket servers
  • Database connection proxies
Why: connections stay open for minutes/hours, so "fewest active" matters more than round-robin fairness.

IP Hash / Sticky Sessions

  • Shopping carts (legacy stack)
  • Login / session-on-server apps
  • File-upload sessions
Modern fix: push session to Redis / JWT, then go stateless and drop stickiness.

Geo-based / GeoDNS

  • CDNs (Cloudflare, CloudFront)
  • Video / streaming platforms
  • Global SaaS, multi-region apps
Tools: AWS Route 53 latency routing, Cloudflare, Akamai.

Consistent Hashing

  • Redis Cluster / Memcached pools
  • CDN edge node selection
  • Sharded service routing
Why: adding/removing a node only reshuffles 1/N keys, not all of them.

Least Response Time

  • Latency-critical APIs (trading, fraud)
  • Multi-region failover
Tools: Envoy, F5, some service-mesh setups.

Interview one-liner: Load balancing strategies decide how incoming traffic is distributed across servers. Pick round-robin for equal stateless servers, weighted for mixed sizes, least connections for long-lived connections, IP hash for session stickiness, consistent hashing for caches/shards, and geo-based for global users. In production you usually have multiple layers of balancing — CDN at the edge, an L7 cloud LB (ALB / NGINX), and a service-mesh sidecar for service-to-service — all backed by health checks.
Caching strategies hot

Cache reduces latency and DB load. Patterns:

  • Cache-aside (lazy loading) — app checks cache; on miss, reads DB and populates. Most common. Risk: stale data on writes.
  • Read-through — cache handles DB read on miss transparently.
  • Write-through — every write goes to cache + DB synchronously. Consistent but slow.
  • Write-behind — writes go to cache, async flush to DB. Fast but risky on cache loss.
  • Write-around — writes skip cache; reads populate it. Good when writes aren't read soon.

Layers: browser/CDN for static, API gateway for hot GETs, Redis for app-level, local in-process (Caffeine) for tiny ultra-hot data.

Always set TTLs. Invalidate on write or accept brief staleness. Watch out for cache stampede (single-flight or lock-on-miss) and thundering herd on restarts (pre-warm or use probabilistic refresh).

Consistent Hashing — what, why, and where must

Consistent hashing is the technique distributed systems use to spread data across multiple servers without having to remap almost all the keys whenever a server is added or removed. It's the foundation behind Cassandra, DynamoDB, Redis Cluster, memcached clients, and most CDNs.

Core Idea
Problem hash(key) % N breaks badly when N changes — almost every key gets reassigned.
Solution Place both servers and keys on a circular hash ring. Each key goes to the next server clockwise.
Win When you add/remove a node, only ~K/N keys move (not all K). Smooth rebalance, no thundering-herd cache misses.
1 The Problem — naive modulo hashing breaks on rebalance

With 3 servers and the rule server = hash(key) % 3:

key "user-42" → hash = 17 → 17 % 3 = 2 (server 2) key "user-91" → hash = 25 → 25 % 3 = 1 (server 1)

Now you add a 4th server. The denominator changes from 3 to 4:

key "user-42" → hash = 17 → 17 % 4 = 1 (was 2, now 1 ❌) key "user-91" → hash = 25 → 25 % 4 = 1 (was 1, still 1 ✅ — lucky)

The disaster: roughly (N−1)/N of all keys end up on a different server. For a cache cluster, that's a cold-cache stampede — every request misses, hits the DB, takes the site down.

2 The Solution — the hash ring

Hash both servers and keys onto a circular space (e.g. 0 → 2³² − 1). Each key is owned by the next server clockwise on the ring.

0 / 2³² • [S1]•─ ─ ─ ─ ─ ─•[S2] / \ / key K1 \ • ◀────────── • // K1 goes clockwise → S2 \ / \ / [S4]•─ ─ ─ ─ ─ ─•[S3] •

Rule: for a key with hash h, walk clockwise on the ring until you hit the first server — that's where the key lives.

3 What happens when a server is added or removed?
Add a server
  • New server lands at some point on the ring.
  • It "steals" only the keys in the arc between itself and its clockwise predecessor.
  • Every other key on the ring stays where it was.
  • Average keys moved: K / N (where K = total keys, N = servers).
Remove a server
  • Its keys are inherited by the next clockwise server.
  • No other keys move.
  • Average keys moved: K / N.
  • The cache stays mostly warm — only one arc rebuilds.

Contrast with modulo hashing: there, adding one node moved ~(N−1)/N of all keys. With consistent hashing, you move only 1/N. That's the whole point.

4 Virtual Nodes (vnodes) — fixing uneven distribution

Problem: with just N points on the ring, the spacing can be wildly uneven — one server might end up owning a huge arc and getting hammered while another barely sees traffic.

Fix: each physical server registers many virtual nodes at different hash positions (typically 100–250 per node).

Without vnodes: With vnodes (each server = 4 points): [S1]──────────[S2] [S1]─[S3]─[S2]─[S1] / \ / \ • uneven arcs • • even spread • \ / \ / [S3]──────────[ ] [S2]─[S3]─[S1]─[S2]

Benefits of vnodes:

  • Load is statistically even across servers.
  • Heterogeneous capacity: a 2× bigger server owns 2× the vnodes.
  • When a server dies, its load is spread across all other servers, not just one neighbor.
5 Modulo Hashing vs Consistent Hashing — side by side
Modulo Hashing
  • Rule: hash(key) % N
  • Add/remove node: ~(N−1)/N keys move 💥
  • Effect: cache stampede, DB overload
  • Load balance: usually OK
  • Use when: N is fixed forever
Consistent Hashing
  • Rule: servers + keys on a ring, key → next server clockwise
  • Add/remove node: only ~K/N keys move ✅
  • Effect: graceful rebalance, cache mostly warm
  • Load balance: good — perfect with vnodes
  • Use when: N grows / shrinks dynamically
6 Benefits — at a glance
  • Minimal rehashing — only ~K/N keys move on any topology change.
  • Scalability — add/remove servers without downtime or full rebalance.
  • Even load distribution (with vnodes) — no hotspots.
  • High availability — failure of one node spreads its keys to many others.
  • Predictable routing — the same key always maps to the same server (until topology changes).
  • Cache-friendly — most existing cache entries stay valid after rebalance.
7 Where it's used in the real world

Distributed Databases

  • Apache Cassandra — partitioner places rows on a ring (Murmur3 hash + vnodes by default).
  • Amazon DynamoDB — partition keys mapped via consistent hashing.
  • Riak, ScyllaDB — same model.
Why: add a node → only that node's arc rebuilds, cluster stays online.

Distributed Caches

  • Redis Cluster (16,384 hash slots, similar idea)
  • Memcached via ketama client-side consistent hashing
  • Twitter's Twemproxy / Pelikan
Why: avoid cold-cache stampedes when scaling the cache tier.

CDNs & Edge

  • Akamai — picks the right edge node for each URL
  • Cloudflare, AWS CloudFront edge routing
  • Object storage front-ends
Why: minimal cache disruption when edge nodes come and go.

Load Balancers & Service Meshes

  • Envoy / HAProxy — ring-hash / maglev load balancing
  • gRPC client-side load balancers
  • Session-affinity routing without sticky cookies
Why: stable routing for user/session to backend without server-side state.
Interview one-liner: Consistent hashing maps both servers and keys onto a circular hash ring, and each key is owned by the next server clockwise. When a server is added or removed, only ~K/N keys move (instead of almost all, like with hash(key) % N). Virtual nodes spread each physical server across many ring positions to keep load even. It's the foundation behind Cassandra, DynamoDB, Redis Cluster, memcached, Akamai/CDNs, and ring-hash load balancers — it's what lets a distributed system scale and rebalance gracefully without cold-cache stampedes.
WebSocket vs Server-Sent Events (SSE) — real-time push must

Both WebSocket and Server-Sent Events (SSE) solve the same core problem — pushing real-time updates from a server to a browser without polling — but they differ in direction, protocol, and operational complexity. Picking the right one is a classic system design call.

Core Difference
WebSocket Full-duplex — both client and server can send messages anytime, over a persistent TCP connection.
SSE One-way push (server → client) — client cannot send back over the same channel; uses a long-lived HTTP response.
Rule of thumb If the client just consumes updates → SSE. If the client also sends data → WebSocket.
1 How they work — conceptually
WebSocket
  • Starts as a normal HTTP request with Upgrade: websocket header.
  • Server agrees → connection upgrades to the WebSocket protocol (ws:// / wss://).
  • Now it's a persistent TCP socket — both sides can send frames anytime.
  • Supports binary + text frames.
  • You handle reconnects, heartbeats (ping/pong), and back-pressure yourself.
Server-Sent Events (SSE)
  • Plain HTTP request from client with header Accept: text/event-stream.
  • Server replies with never-ending HTTP response and pushes data lines as events arrive.
  • Stays standard HTTP/HTTPS — works through proxies, load balancers, firewalls.
  • Text only (UTF-8). Use base64 for binary.
  • Browser auto-reconnects on disconnect with Last-Event-ID header.

3 When to use which

Use WebSocket — Chat / Collab

  • Chat apps (Slack, WhatsApp Web)
  • Live collaboration (Google Docs, Figma)
  • Multiplayer games
  • Trading platforms with order placement
Why: client must send data back constantly (typing, edits, moves, orders).

Use SSE — One-way Push

  • Live notifications (in-app toasts)
  • Stock / crypto price tickers
  • News & sports score feeds
  • Progress updates (uploads, jobs)
  • LLM token streaming (ChatGPT-style)
Why: client only consumes — no need to pay the cost & complexity of full-duplex.

Use Polling — Quick fix

  • Low-frequency updates (every 10s+)
  • When proxies/CDNs block long-lived connections
  • Legacy clients
Tip: use long-polling as a fallback when SSE/WebSocket aren't available — same UX, plain HTTP.

Use HTTP/2 Server Push? — No

  • HTTP/2 Server Push is dead — deprecated by Chrome & major browsers.
  • For app-level push: use SSE or WebSocket.
Note: HTTP/2 push was for sub-resources (CSS, JS), never for app data.

6 Operational gotchas
  • Load balancers: WebSocket needs sticky sessions or a stateless message bus (Redis pub/sub, Kafka). Most cloud LBs need explicit WS support enabled (AWS ALB, GCP HTTPS LB).
  • Connection limits: each persistent connection holds an OS file descriptor and JVM thread/goroutine. Plan for ulimit, kernel somaxconn, and connection-per-instance budgets.
  • Heartbeats: WS doesn't auto-detect dead connections — send ping/pong every 20–30s, drop on missed pong.
  • Scaling out: a publish from one instance must reach connections on other instances — use Redis pub/sub, NATS, or Kafka as the fanout layer.
  • Backpressure: slow consumers can OOM your server. Buffer with limits, drop or coalesce when the queue grows.
  • Authentication: JWT in the initial handshake (URL param or first message). Re-auth on token refresh.
  • SSE reconnect: server should honor Last-Event-ID header to replay missed events.
Interview one-liner: Both WebSocket and SSE push real-time updates from server to browser. WebSocket is full-duplex over a persistent TCP socket — use it for chat, collab, games, and trading where the client also sends data. SSE is one-way (server → client) over plain HTTP with automatic reconnect — use it for notifications, live feeds, price tickers, and LLM token streaming. SSE is simpler, scales easier (it's just HTTP), and is great when you only need server push. For anything truly interactive, WebSocket is the right tool — at the cost of more operational complexity (sticky sessions, heartbeats, fanout bus).
Design a URL shortener (bit.ly)

Requirements: shorten a URL, redirect short → long, ~100M new URLs/day, redirect under 100 ms.

Capacity: 100M × 30 days × 5 years ≈ 18B URLs total. 6–7 chars in base62 = 56–62 billion combinations — enough.

API: POST /shorten {long} → {short}. GET /:code → 301 to long.

Architecture:

  • App service generates short codes (counter-based or hash-based) and stores short → long in a KV store (DynamoDB, Cassandra).
  • Counter approach: distributed counter (Redis INCR) → base62 encode. Predictable, no collisions.
  • Cache: Redis caches hot codes (~80% of traffic is recent URLs).
  • CDN in front for global redirect.
  • Analytics events to Kafka for click tracking.

Bottlenecks: counter contention (shard counters per region), CDN cache hit rate, analytics throughput (async). Discuss custom alias support, abuse / spam detection, rate limiting.

Design a rate limiter

Requirements: limit each user/IP/key to N requests per time window. Must work across multiple app instances.

Algorithms: Token bucket is the standard — N tokens, refilled at rate r, each request consumes one. Allows bursts. (See REST & Security topic for full list.)

Architecture:

  • Store counters in Redis — fast, atomic INCR / EXPIRE.
  • Key: rl:<user>:<window>.
  • Implement at the API gateway for global limits; per-service for fine-grained.
  • Distributed atomicity: use Lua scripts or Redis MULTI/EXEC for "check + increment" atomicity.
  • Respond with 429 Too Many Requests + Retry-After.

Tradeoffs: Redis is SPOF — use Redis cluster or local fallback (lossy but available). Network call adds latency — keep Redis close. For very high QPS, sharded counters reduce contention.

Libraries: Bucket4j (Java + Redis), Envoy rate-limit, Kong plugin.

Design a chat application (WhatsApp-lite)

Requirements: 1-to-1 + group chat, online presence, message delivery + read receipts, push notifications.

Architecture:

  • Connection layer — WebSocket gateway servers maintain persistent connections per user. Sticky routing or a session-to-server lookup in Redis.
  • Message service — receives messages, writes to DB, fans out to recipients via WebSocket or push.
  • Database — Cassandra or DynamoDB for messages partitioned by (chatId, timestamp); sharded for write throughput.
  • Queue — Kafka for async fan-out, delivery to offline users via push (APNs/FCM).
  • Presence — Redis with TTL heartbeats from each connected client.
  • Media — uploads to S3 with signed URLs; only metadata in messages.

Tricky parts: exactly-once delivery (idempotent message IDs), ordering across devices, end-to-end encryption (Signal protocol), connection rebalancing during deployments.

Design a news feed / timeline

Requirements: each user sees a feed of posts from people they follow, sorted by recency or relevance.

Two strategies:

Pull (fan-out on read) — at read time, query posts from all the user's followees, merge, sort. Simple but slow at scale.

Push (fan-out on write) — when a user posts, write into each follower's pre-computed timeline. Fast reads, but a celebrity with 10M followers triggers a write storm.

Hybrid (used by Twitter, Instagram) — push for normal users, pull for celebrities. At read time, merge precomputed timeline with on-the-fly fetch of celebrity posts.

Components: Posts in a write-optimized store (Cassandra), timeline in Redis sorted sets keyed by userId, ranking service for ML-driven sorting, CDN for media. Use Kafka for fan-out workers.

Design a notification system

Requirements: deliver notifications across channels (push, email, SMS, in-app); respect user preferences; high throughput.

Architecture:

  • Event ingress — services publish events ("OrderShipped") to Kafka.
  • Notification orchestrator — subscribes to events, applies templates and user preferences, decides channels.
  • Channel workers — separate consumers per channel (push worker, email worker, SMS worker). Each uses provider SDKs (FCM, SendGrid, Twilio).
  • Provider abstraction — swap providers via config.
  • Retry + DLQ per channel — provider hiccups don't lose notifications.
  • Rate limit per user — avoid notification spam.
  • Audit log — what was sent when, for debugging and compliance.

Tradeoffs: real-time push vs digest emails, deduplication (don't send the same notification twice across channels), localization, GDPR/unsubscribe handling. At OneXtel I built a similar SMS notification pipeline.

Caching invalidation — the "two hard problems"

"There are only two hard things in computer science: cache invalidation and naming things." Three practical approaches:

  • TTL-based — every entry expires after N seconds. Simple, eventual consistency. Pick TTL based on staleness tolerance. Works for 80% of use cases.
  • Write-through invalidation — on every write, delete or update the cached entry. Strong consistency but more code, and race conditions between reader-fills and writer-invalidations need care (use versioning or invalidate twice with a gap).
  • Event-driven invalidation — subscribe to a change stream (Kafka, CDC) and invalidate. Decouples writers from cache, scales across services.

Patterns that bite: cache stampede (use single-flight locks), negative caching (cache "not found" briefly to absorb floods), cache-coherency in clusters (consistent hashing + Redis cluster).
