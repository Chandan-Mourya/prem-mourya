JVM & Memory
What is the JDK, JRE, and JVM? must

Three terms that sound similar and are routinely mixed up. They are nested layers of the Java platform — each one contains the one below it.

Core Idea — they nest like Russian dolls
JDK Java Development Kit — to build Java apps.
JRE Java Runtime Environment — to run Java apps.
JVM Java Virtual Machine — the engine that executes bytecode.
JDK javac jdb jlink jshell jmap jstack
JRE java.lang java.util java.io java.net
JVM Class Loader Bytecode Verifier Execution Engine JIT GC
1 JDK — Java Development Kit

The complete package used to develop Java applications.

Contains:

  • JRE (which contains the JVM)
  • Compiler — javac
  • Debugger — jdb
  • Dev utilities — jshell, jlink, jmap, jstack, jdeps

Use case: if you want to write Java code, compile programs, or build applications — you need the JDK.

2 JRE — Java Runtime Environment

Everything needed to run Java applications — but no development tools.

Contains:

  • JVM
  • Core libraries — java.lang, java.util, java.io, java.net, etc.
  • Supporting files — properties, resources, configuration

Does NOT contain: the compiler or any dev tools.

Use case: if you only want to run an existing Java application (a JAR or WAR) — the JRE is enough.

Note: since Java 11 the standalone JRE is no longer shipped — you build a slim custom runtime with jlink instead.

3 JVM — Java Virtual Machine

The engine that actually executes Java programs. When you write Java code, javac compiles it into bytecode (.class files); the JVM reads that bytecode and runs it on your physical machine.

Main responsibilities:

  • Load and verify .class files (class loader, bytecode verifier)
  • Execute bytecode (interpreter + JIT compiler for hot methods)
  • Manage memory (heap, stack, metaspace)
  • Garbage collection
  • Provide platform independence — same bytecode runs on Linux, Windows, macOS, ARM, x86, because each OS has its own JVM implementation

Think of the JVM as "the machine inside your computer that understands Java bytecode."

5 The Relationship — in one line each
JDK = JRE + Development tools (javac, jdb, …)
JRE = JVM + Core libraries
JVM = The bytecode execution engine itself
In practice: as a developer I install the JDK — it gives me everything (compiler, runtime, debugger). Production servers used to ship the JRE only, but since Java 11 we either ship a custom slim runtime built with jlink, or just use a full JDK container image. The JVM is the part that gives Java its famous "Write Once, Run Anywhere" property — same .class file runs on any OS that has a JVM.
Explain the JVM Memory Model hot

At runtime the JVM splits memory into 5 distinct areas. Some are shared across all threads, others are created per-thread. Understanding this is the first step before reading jstat output, analyzing a heap dump, or debugging a memory leak.

The 5 Runtime Memory Areas
Heap Stores all objects and instance variables — shared.
Stack Stores method frames — local vars, partial results, references.
Method Area Class metadata, static variables, bytecode of methods (since Java 8 → Metaspace in native memory).
PC Register Address of the current instruction being executed.
Native Stack For methods written in C/C++ (via JNI).
SHARED BY ALL THREADS
Heap Young Gen (Eden + 2 Survivors) + Old Gen. All objects live here. GC operates here.
Method Area / Metaspace Class metadata, static fields, runtime constant pool, bytecode of methods.
PER-THREAD (one copy per thread)
Stack Method frames — local variables, parameters, references to heap objects. LIFO. Pops on return.
PC Register Holds the address of the next bytecode instruction this thread will execute.
Native Method Stack Separate stack used when a thread calls a native (JNI / C, C++) method.
1 Tree View — at a glance
JVM Memory
│
├── Heap          → Objects, instance vars        (shared, GC'd)
├── Stack         → Method frames, local vars     (per-thread)
├── Method Area   → Class info, static data       (shared)
├── PC Register   → Current instruction address   (per-thread)
└── Native Stack  → JNI / native method calls     (per-thread)
2 Worked Example — where things end up

When you write:

void run() {
    int count = 10;                    // primitive
    Student s = new Student("Alice");  // reference + object
}

What actually happens:

  • count (primitive int) — lives directly in the method's stack frame.
  • s (the reference variable) — lives in the stack frame too. It's just a pointer.
  • new Student("Alice") — the actual Student object is allocated on the Heap.
  • The Student class itself (its bytecode, methods, static fields) lives in the Method Area / Metaspace.
  • When run() returns, its stack frame is popped — count and the reference s vanish. The Student object on the heap will be reclaimed by GC later when nothing else references it.
3 Heap vs Stack — the quick comparison
Heap
  • Stores: objects, arrays, instance variables
  • Scope: shared across all threads
  • Lifetime: until no references → freed by GC
  • Size: large, configurable (-Xms / -Xmx)
  • Errors: OutOfMemoryError: Java heap space
  • Access: slower (cache misses, indirection)
Stack
  • Stores: method frames — local vars, refs, primitives
  • Scope: per-thread (one stack per thread)
  • Lifetime: auto-freed when method returns (LIFO pop)
  • Size: small, fixed per thread (-Xss)
  • Errors: StackOverflowError (e.g. infinite recursion)
  • Access: very fast (just pointer math)
4 Heap Sub-structure — what GC actually walks

The Heap itself is split for generational GC:

  • Young Generation = Eden + 2 Survivor spaces (S0, S1). Most new objects are born in Eden.
  • When Eden fills → Minor GC: survivors move to a Survivor space; long-lived ones get promoted.
  • Old Generation — long-lived objects end up here. Cleaned by a Major / Full GC, which is more expensive.
  • The premise: most objects die young — so collecting Eden frequently and cheaply is a huge win.
5 Key Rules to Remember
  • Heap is shared → needs synchronization when multiple threads mutate the same object.
  • Stack is thread-local → local variables are inherently thread-safe.
  • Garbage Collector works mainly on the Heap, not the Stack.
  • Since Java 8, PermGen is gone → class metadata lives in Metaspace, which grows in native memory.
  • OutOfMemoryError → heap exhausted. StackOverflowError → stack exhausted (usually runaway recursion).
In one line: the JVM has 5 runtime areas — Heap and Method Area are shared across threads; Stack, PC Register, and Native Stack are per-thread. Objects live on the Heap (managed by GC), references and primitives live on the Stack (auto-freed on method return), and class-level info lives in the Method Area (Metaspace since Java 8). That mental model is enough to debug OutOfMemoryError, StackOverflowError, and most heap-dump investigations.
How does garbage collection work? G1 vs ZGC?

GC reclaims memory by identifying unreachable objects starting from GC roots (active stack frames, static fields, JNI references) and freeing the rest. Modern collectors are generational — they exploit the fact that most objects die young, so collecting Eden frequently is cheap, while old-gen collections are rarer but heavier.

G1 (Garbage First), default since Java 9, divides the heap into ~2 MB regions and collects regions with the most garbage first, aiming for predictable pause times (e.g. 200 ms target). ZGC and Shenandoah are concurrent low-latency collectors — pause times under 10 ms even on multi-TB heaps, at a small throughput cost. I default to G1 for normal services; ZGC for latency-sensitive APIs (financial, real-time).

Stack vs Heap — where do primitives live?

The stack is per-thread, LIFO, and holds method frames. Each frame contains local variables, including primitive values (int, long, boolean) and references to objects. The stack is small (default ~512 KB–1 MB) and fast — allocation and deallocation are simply moving the stack pointer.

The heap is shared across all threads and stores objects (including arrays and wrappers like Integer). When you write Integer i = 5, the variable i sits on the stack but the Integer object lives on the heap. Primitives inside an object also live on the heap as part of that object. If recursion goes too deep you get StackOverflowError; if heap fills you get OutOfMemoryError: Java heap space.

What is the String pool and why does it exist?

The String pool (interned strings) is a special area in the heap (since Java 7) where the JVM stores unique string literals. When you write String a = "hello" twice, both variables point to the same pooled instance, saving memory.

Compare: String a = "hi"; String b = "hi"; a == b returns true. But String c = new String("hi"); a == c returns false — new forces a fresh heap object. You can manually intern with c.intern(). Be careful interning user input — it grows the pool and used to leak into PermGen (pre-Java 7). Pool size is configurable via -XX:StringTableSize. The pool is why equals() exists — never use == for string comparison.

Diagnosing a memory leak — your process? hot

My checklist: (1) confirm with jstat -gc <pid> that Old Gen keeps growing across full GCs — that's the signature of a leak versus high allocation. (2) capture a heap dump with jmap -dump:live or set -XX:+HeapDumpOnOutOfMemoryError in production.

(3) open the dump in Eclipse MAT and run the Leak Suspects report — it identifies dominator trees, the largest retained sizes, and likely culprits. (4) Common offenders: static collections that grow unbounded, ThreadLocals not cleared after use (caught one at Indus Net inside a Spring filter), unclosed resources, listener registrations not removed. (5) Once fixed, re-run the load test and verify Old Gen stabilizes after full GCs.

Collections
HashMap internals — how does it work? hot

A HashMap is backed by an array of buckets (default size 16). When you put(key, value): (1) compute hashCode(), (2) apply the hash spreading function (h = hashCode) ^ (h >>> 16), (3) take hash & (capacity - 1) to get the bucket index. Multiple keys can hit the same bucket — that's a collision.

Collisions are stored as a linked list. Since Java 8, if a bucket exceeds 8 entries and the table has at least 64 entries, it's converted to a red-black tree — lookup goes from O(n) to O(log n). When load factor (default 0.75) is hit, the table doubles and entries are rehashed. Average get/put is O(1), worst case O(log n) with tree bins. Important: HashMap is not thread-safe.

HashMap vs ConcurrentHashMap hot

Both HashMap and ConcurrentHashMap are part of the Java Collections Framework and store key–value pairs, but they differ mainly in thread safety, performance, and behavior in concurrent environments.

Core Difference
HashMap Not thread-safe
ConcurrentHashMap Thread-safe — designed for concurrent access
1 Thread Safety
HashMap
  • Not synchronized.
  • Multiple threads modifying it can lead to data corruption or infinite loops (the famous Java 7 resize bug).
ConcurrentHashMap
  • Designed for concurrency.
  • Uses internal locking — segment-based in Java 7, bucket-level + CAS in Java 8+ — to allow safe concurrent updates.
2 Performance
HashMap
  • Faster in single-threaded scenarios.
  • No synchronization overhead.
ConcurrentHashMap
  • Slightly slower than HashMap in single-thread use.
  • Much faster in multi-threaded environments because it allows parallel reads / writes.
3 Synchronization Behavior
HashMap
  • Requires external synchronization in multithreading.
  • Wrap with Collections.synchronizedMap(...) if you need it shared.
ConcurrentHashMap
  • Handles synchronization internally.
  • Multiple threads can read and write simultaneously without blocking the whole map.
4 Null Handling
HashMap
  • Allows one null key.
  • Allows multiple null values.
ConcurrentHashMap
  • Does NOT allow null keys.
  • Does NOT allow null values.
  • Prevents ambiguity between "absent" and "present with null" in concurrent reads.
5 Iteration Behavior
HashMap
  • Fail-fast iterator.
  • Throws ConcurrentModificationException if modified during iteration.
ConcurrentHashMap
  • Fail-safe (weakly consistent) iterator.
  • Never throws CME; reflects some — not necessarily all — changes that happen during iteration.
6 Use Case
HashMap
  • Single-threaded applications.
  • Local maps inside a method or per-request data where synchronization isn't needed.
ConcurrentHashMap
  • Multi-threaded applications.
  • Shared caches, counters, registries — anywhere multiple threads read/write the same map.
Takeaway: use HashMap for thread-local / single-threaded use, and reach for ConcurrentHashMap the moment a map is shared across threads. For atomic compound ops, prefer computeIfAbsent / merge / compute over get+put. Hashtable is the legacy, whole-map-locked predecessor — don't use it in new code.
ArrayList vs LinkedList — when to use which?

Both implement the List interface but have very different internal structures, which makes their performance profiles almost opposite.

Core Difference
ArrayList Backed by a resizable array — fast random access.
LinkedList Backed by a doubly-linked list — fast insert/delete at ends.
1 Time Complexity
ArrayList
  • get(i) — O(1) random access.
  • add(end) — amortized O(1).
  • add/remove(middle) — O(n) due to array shifts.
LinkedList
  • get(i) — O(n) (walks pointers).
  • add/remove(end) — O(1).
  • add/remove(middle) — O(1) if you already have the node reference; O(n) to find it.
2 Memory & Cache
ArrayList
  • Compact contiguous array — excellent CPU cache locality.
  • Iteration is very fast.
LinkedList
  • Each node = value + prev + next pointers — much higher overhead per element.
  • Nodes scattered in heap — poor cache locality.
3 Use Case
ArrayList
  • Default for almost everything: lookups, iteration, random access.
  • API responses, in-memory caches, intermediate data structures.
LinkedList
  • Queue / deque patterns where you only touch the ends.
  • Even then, ArrayDeque is usually faster.
Takeaway: use ArrayList 95% of the time. Reach for LinkedList only if you genuinely need an end-to-end queue/deque — and even then, prefer ArrayDeque. Many senior engineers say they haven't written new LinkedList<>() in years.
HashSet vs TreeSet vs LinkedHashSet

All three implement the Set interface (no duplicates), but differ in ordering, internal data structure, and performance.

Core Difference
HashSet Hash table — no order, fastest.
LinkedHashSet Hash table + linked list — preserves insertion order.
TreeSet Red-Black tree — always sorted.
1 Ordering
HashSet

No guaranteed order. Iteration order may even change as the table grows.

LinkedHashSet & TreeSet
  • LinkedHashSet — iterates in insertion order.
  • TreeSet — iterates in natural / Comparator order.
2 Performance
HashSet / LinkedHashSet
  • add, contains, remove — O(1) average.
  • LinkedHashSet has a tiny overhead from linked-list pointers.
TreeSet
  • add, contains, remove — O(log n).
  • Slower for plain insert/lookup, but gives ordered traversal for free.
3 Extra Features
HashSet / LinkedHashSet
  • Allow one null element.
  • No range queries.
TreeSet
  • Implements NavigableSet: first(), last(), headSet, tailSet, subSet, ceiling, floor.
  • Does not allow null (it needs to compare).
4 Use Case
HashSet
  • Default when you just need uniqueness and don't care about order.
  • De-duplicating IDs, membership checks.
LinkedHashSet / TreeSet
  • LinkedHashSet — predictable iteration order for tests, caches, deterministic output.
  • TreeSet — always-sorted view, range queries, top-N lookups.
Takeaway: the same hierarchy applies to maps — HashMap / LinkedHashMap / TreeMap. Choose by ordering need first, then performance. Most production code defaults to HashSet / HashMap.
What is a Binary Tree? (foundation for BST, Heap, Trie) must

A Binary Tree is a hierarchical data structure where every node has at most two children — a left child and a right child. It's the foundation for many other structures: BST, AVL, Red-Black, Heaps, Tries, expression trees, parse trees.

Core Idea
Structure Each node holds a value + at most 2 child pointers (left, right). One node is the root.
Why Hierarchical relationships, divide-and-conquer, log-n search (when balanced).
Cost Search/insert/delete is O(log n) only when the tree stays balanced — O(n) worst case if it's skewed.
1 Structure — a worked example
10 // root / \ 5 20 // 5 = left child, 20 = right child / \ 2 8 // leaf nodes (no children)

Here 10 is the root, 5 and 20 are children of 10, and 2, 8, 20 are leaves.

2 Key Terminology
TermMeaning
RootTop node of the tree — has no parent.
ParentA node that has at least one child.
ChildA node directly connected below another node.
LeafA node with no children.
SubtreeA node together with all its descendants forms a smaller tree.
HeightNumber of edges on the longest path from a node down to a leaf.
DepthNumber of edges from the root down to that node.
LevelAll nodes at the same depth — root is level 0.
3 Types of Binary Trees
TypeDefinitionUsed for
Full Every node has either 0 or 2 children — never just one. Expression trees, decision trees.
Complete All levels are completely filled except possibly the last, which fills left-to-right. Heaps (PriorityQueue) — enables array-backed storage.
Perfect All internal nodes have 2 children and all leaves are at the same level. Theoretical analysis, segment trees.
Balanced Height of left and right subtrees differs by at most a small constant (usually 1). Guarantees O(log n) — AVL, Red-Black.
Binary Search Tree (BST) Left subtree < node < right subtree — for every node. Ordered lookups, range queries (TreeMap, TreeSet).
Degenerate / Skewed Each parent has only one child — basically a linked list. The worst case you want to avoid.
4 BST — the most useful variant

A Binary Search Tree adds one ordering rule on top of a binary tree: left < root < right. That single rule turns it into an O(log n) lookup structure (when balanced).

15 / \ 10 20 / \ / \ 7 12 17 25 // every left node < parent, every right node > parent

To search for 17: at 15, go right (17 > 15); at 20, go left (17 < 20); found it — 2 comparisons instead of scanning all 7 nodes.

Catch: if you insert sorted data into a plain BST, it degenerates into a skewed chain (O(n)). That's exactly why self-balancing BSTs like AVL and Red-Black trees exist — they keep the tree balanced automatically.

5 Time Complexity
OperationBalancedSkewed (worst)
SearchO(log n)O(n)
InsertO(log n)O(n)
DeleteO(log n)O(n)
Traversal (in/pre/post-order)O(n)O(n)
SpaceO(n)O(n)

The key takeaway: a plain BST can hit O(n) in the worst case. Balanced variants (AVL, Red-Black) guarantee O(log n).

Searching & Indexing

  • TreeMap, TreeSet (Red-Black tree)
  • Database in-memory indexes
  • Range queries (floorKey, ceilingKey)
Why: O(log n) ordered lookups.

Heaps / Priority Queues

  • Java PriorityQueue
  • Dijkstra, A*, Kafka offset tracking
  • Top-K problems
Why: heap = complete binary tree → can be stored in a simple array.

Compilers / Parsers

  • Expression trees ((a+b) * c)
  • Abstract Syntax Trees (AST)
  • Operator precedence
Tools: ANTLR, JavaC, every interpreter.

File Systems & OS

  • Directory hierarchies
  • Process trees
  • Decision trees in ML / rules engines
Why: hierarchical data is naturally a tree.
One-liner: A Binary Tree is a hierarchical structure where each node has at most two children. The most useful specialization is the BST (left < root < right) which enables O(log n) ordered lookups — provided the tree stays balanced. Real-world systems use balanced variants like AVL and Red-Black trees (Java's TreeMap/TreeSet, Linux kernel scheduler), or complete binary trees as the basis for heaps (PriorityQueue).
What is a Min Heap and Max Heap? (the engine behind PriorityQueue) must

A Heap is a special Complete Binary Tree that satisfies one ordering rule between every parent and its children. It gives you O(1) access to the min (or max) element — exactly what you need for priority queues, scheduling, and "top-K" problems. There are two flavors: Min Heap and Max Heap.

Core Idea
Shape Always a complete binary tree — fills left-to-right, no gaps.
Order Min Heap: parent ≤ children. Max Heap: parent ≥ children. (Only parent-child — siblings are unordered.)
Storage Stored as a flat array (no pointers) — index math gives you parent/children in O(1).
1 Min Heap — smallest sits at the root

Rule: every parent ≤ its children. The root is therefore the minimum of the whole heap.

10 // root = smallest / \ 20 30 / \ 40 50

Use case: get the smallest element fast — task with the earliest deadline, shortest distance in Dijkstra, smallest k elements.

PriorityQueue<Integer> minHeap = new PriorityQueue<>();        // default = min heap
minHeap.offer(30); minHeap.offer(10); minHeap.offer(20);
minHeap.peek();   // 10  (O(1))
minHeap.poll();   // 10, then re-heapify (O(log n))
2 Max Heap — largest sits at the root

Rule: every parent ≥ its children. The root is therefore the maximum of the whole heap.

50 // root = largest / \ 30 40 / \ 10 20

Use case: get the largest element fast — top-K largest, highest priority task, largest pending request.

PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());
maxHeap.offer(30); maxHeap.offer(10); maxHeap.offer(50);
maxHeap.peek();   // 50  (O(1))
3 Why array-backed? — The index trick

Because a heap is always a complete tree, we can flatten it into an array with no wasted space and no pointers:

Tree: Array (0-indexed): 10 ┌────┬────┬────┬────┬────┐ / \ │ 10 │ 20 │ 30 │ 40 │ 50 │ 20 30 └────┴────┴────┴────┴────┘ / \ 0 1 2 3 4 40 50

For a node at index i:

Left = 2·i + 1
Right = 2·i + 2
Parent = (i − 1) / 2 // integer division

Verify on the example above: index 1 is 20 → its parent is at (1−1)/2 = 0 which is 10 ✅. Its children are at indices 3 and 4 → 40 and 50 ✅.

This is why heaps are so fast and so cache-friendly — no node objects, no pointer dereferencing, just contiguous memory.

4 How insert & delete actually work
Insert — "sift up"
  • Put the new element at the end of the array (= last leaf, keeps tree complete).
  • Compare with parent; if heap rule is violated, swap with parent.
  • Repeat until the parent is OK or you reach the root.
  • Cost: O(log n) — at most height swaps.
Delete root — "sift down"
  • Return the root (the answer), then move the last leaf to the root slot.
  • Compare with the smaller (min heap) / larger (max heap) child; swap if needed.
  • Repeat going down until heap rule holds.
  • Cost: O(log n).

Min Heap
  • Root: smallest element
  • Rule: parent ≤ children
  • Java: new PriorityQueue<>() (default)
  • Used for: shortest-path (Dijkstra), earliest-deadline scheduling, smallest-K

7 Where Heaps are actually used

Java & JVM

  • PriorityQueue — backed by a binary min-heap
  • DelayQueue, ScheduledThreadPoolExecutor
  • Some GC algorithms internally
Why: O(1) peek + O(log n) insert/delete is exactly what schedulers need.

OS / Schedulers

  • CPU process schedulers (priority queues)
  • Timer / event queues
  • Network packet scheduling (QoS)
Why: always pick the next highest-priority task in log n.

Graph Algorithms

  • Dijkstra — shortest path (min heap on distance)
  • Prim's — minimum spanning tree
  • A* search
Why: repeatedly "extract min" is the hot loop in these algorithms.

Top-K & Streaming

  • Top-K frequent elements (LeetCode classic)
  • Streaming median (two heaps)
  • Heap Sort
  • Fraud / outlier ranking
Why: keeps only the K best — O(n log k) total.
One-liner: A Heap is a complete binary tree stored as an array. Min Heap keeps the smallest at the root, Max Heap keeps the largest. Peek is O(1), insert/delete are O(log n). It's the engine behind Java's PriorityQueue, OS schedulers, Dijkstra/Prim/A*, top-K problems, and Heap Sort. Use a heap whenever you repeatedly need the "best" element from a changing set without re-sorting.
Sorting Algorithms — Bubble, Selection, Insertion, Merge, Quick, Heap (with code) must

Sorting is the bread-and-butter of any DSA interview. The 6 classic algorithms split into two camps — simple O(n²) ones (Bubble, Selection, Insertion) you learn first, and fast O(n log n) ones (Merge, Quick, Heap) you actually use. Each has a sweet spot.

3 properties interviewers will ask about
Stable Equal elements keep their original relative order. Important when sorting by multiple keys.
In-place Uses O(1) or O(log n) extra memory — doesn't allocate a second array.
Comparison-based Decides order by comparing pairs. Lower bound for these is Ω(n log n).
1 Bubble Sort

Repeatedly walk through the array and swap adjacent elements that are out of order. After each pass the largest element bubbles to the end.

[5, 1, 4] → [1, 5, 4] // swap 5 and 1 → [1, 4, 5] // swap 5 and 4
public static void bubbleSort(int[] a) {
    int n = a.length;
    for (int i = 0; i < n - 1; i++) {
        boolean swapped = false;
        for (int j = 0; j < n - 1 - i; j++) {
            if (a[j] > a[j + 1]) {
                int tmp = a[j];
                a[j] = a[j + 1];
                a[j + 1] = tmp;
                swapped = true;
            }
        }
        if (!swapped) return;
    }
}
Best O(n) · Avg O(n²) · Worst O(n²) O(1) space · stable ✅

Use when: teaching, very small inputs, or when you just need the "is it sorted" early-exit on nearly sorted data.

2 Selection Sort

Find the minimum element in the unsorted portion and swap it into the first unsorted slot. Repeat.

[64, 25, 12] → [12, 25, 64] // pick min (12), swap with first
public static void selectionSort(int[] a) {
    int n = a.length;
    for (int i = 0; i < n - 1; i++) {
        int minIdx = i;
        for (int j = i + 1; j < n; j++)
            if (a[j] < a[minIdx]) minIdx = j;
        int tmp = a[i];
        a[i] = a[minIdx];
        a[minIdx] = tmp;
    }
}
Best / Avg / Worst all O(n²) O(1) space · not stable ❌

Use when: memory writes are expensive — Selection does at most n swaps, fewer than Bubble.

3 Insertion Sort

Build the sorted array one element at a time — take the next element and insert it into its right place in the already-sorted prefix (like sorting playing cards in your hand).

[5, 2, 4] → [2, 5, 4] // insert 2 before 5 → [2, 4, 5] // insert 4 between 2 and 5
public static void insertionSort(int[] a) {
    for (int i = 1; i < a.length; i++) {
        int key = a[i];
        int j = i - 1;
        while (j >= 0 && a[j] > key) {
            a[j + 1] = a[j];
            j--;
        }
        a[j + 1] = key;
    }
}
Best O(n) · Avg O(n²) · Worst O(n²) O(1) space · stable ✅

Use when: data is nearly sorted or small (n ≤ ~10). Java's Timsort actually switches to insertion sort for small subarrays for exactly this reason.

4 Merge Sort — Divide & Conquer

Divide the array in half, recursively sort each half, then merge the two sorted halves in O(n). Guaranteed O(n log n) — no matter the input.

[5, 2, 4, 1] ↓ divide [5, 2] [4, 1] ↓ recurse + merge each [2, 5] [1, 4] ↓ merge both [1, 2, 4, 5]
public static void mergeSort(int[] a) {
    if (a.length < 2) return;
    int mid = a.length / 2;
    int[] left  = Arrays.copyOfRange(a, 0, mid);
    int[] right = Arrays.copyOfRange(a, mid, a.length);
    mergeSort(left);
    mergeSort(right);
    merge(a, left, right);
}

private static void merge(int[] a, int[] l, int[] r) {
    int i = 0, j = 0, k = 0;
    while (i < l.length && j < r.length)
        a[k++] = (l[i] <= r[j]) ? l[i++] : r[j++];
    while (i < l.length) a[k++] = l[i++];
    while (j < r.length) a[k++] = r[j++];
}
Best / Avg / Worst all O(n log n) O(n) space · stable ✅

Use when: stability matters (sorting by multiple keys), linked lists, or when you need a guaranteed O(n log n) (no quicksort worst-case risk). Java's Collections.sort() uses Timsort — a hybrid of merge + insertion sort.

5 Quick Sort — Pivot & Partition

Pick a pivot, partition the array so smaller elements go left and larger ones go right, then recursively sort each side. Average O(n log n), but worst O(n²) on already-sorted data with bad pivot choice.

pivot = 5 [8, 2, 5, 1] ↓ partition [2, 1] 5 [8] ↓ recurse on left + right [1, 2] 5 [8] ↓ result [1, 2, 5, 8]
public static void quickSort(int[] a, int lo, int hi) {
    if (lo < hi) {
        int p = partition(a, lo, hi);
        quickSort(a, lo, p - 1);
        quickSort(a, p + 1, hi);
    }
}

private static int partition(int[] a, int lo, int hi) {
    int pivot = a[hi];          // pick last as pivot
    int i = lo - 1;
    for (int j = lo; j < hi; j++) {
        if (a[j] <= pivot) {
            i++;
            int t = a[i]; a[i] = a[j]; a[j] = t;
        }
    }
    int t = a[i + 1]; a[i + 1] = a[hi]; a[hi] = t;
    return i + 1;
}
Best O(n log n) · Avg O(n log n) · Worst O(n²) O(log n) space · not stable ❌

Use when: general-purpose sorting of primitives — it's the fastest in practice due to cache locality. Java's Arrays.sort(int[]) uses Dual-Pivot Quicksort. Random pivot or median-of-three avoids the O(n²) trap.

6 Heap Sort — sort using a heap

Build a max-heap from the array (O(n)), then repeatedly extract the max from the root and put it at the end. After n extractions, the array is sorted.

[4, 10, 3, 5, 1] ↓ heapify (max heap) [10, 5, 3, 4, 1] ↓ extract 10 → last position [5, 4, 3, 1, 10] ↓ extract 5 [4, 1, 3, 5, 10] ↓ ... continues [1, 3, 4, 5, 10]
public static void heapSort(int[] a) {
    int n = a.length;
    for (int i = n / 2 - 1; i >= 0; i--) heapify(a, n, i);   // build max-heap
    for (int i = n - 1; i > 0; i--) {
        int t = a[0]; a[0] = a[i]; a[i] = t;                  // move max to end
        heapify(a, i, 0);                                     // restore heap on [0..i)
    }
}

private static void heapify(int[] a, int n, int i) {
    int largest = i, l = 2 * i + 1, r = 2 * i + 2;
    if (l < n && a[l] > a[largest]) largest = l;
    if (r < n && a[r] > a[largest]) largest = r;
    if (largest != i) {
        int t = a[i]; a[i] = a[largest]; a[largest] = t;
        heapify(a, n, largest);
    }
}
Best / Avg / Worst all O(n log n) O(1) space · not stable ❌

Use when: you need O(n log n) and O(1) extra memory — embedded systems, real-time constraints, top-K extraction.

Small data (n < ~20)

  • Insertion Sort
  • Fewer overhead instructions than n·log n algos
Why: low constant factor beats asymptotic on small n.

Large data, general purpose

  • Quick Sort (primitives) — fastest in practice
  • Merge Sort (objects) — stable, guaranteed n·log n
Java: Arrays.sort(int[]) → Dual-Pivot Quicksort. Collections.sort() → Timsort.

Memory-constrained

  • Heap Sort
  • O(1) extra space, no recursion stack
Why: in-place + O(n log n) worst case — predictable on embedded systems.

Stability required

  • Merge Sort / Timsort
  • Insertion Sort (for small n)

Nearly sorted

  • Insertion Sort — O(n) on nearly sorted
  • Timsort also exploits "runs"
Why: very few swaps when most elements already in place.

Small integer range (k ≪ n)

  • Counting Sort — O(n + k)
  • Radix Sort — for fixed-width integers / strings
Why: beats the O(n log n) lower bound — these aren't comparison-based.
9 What Java actually uses (interview gem)
  • Arrays.sort(int[]) / primitive arrays → Dual-Pivot Quicksort (Vladimir Yaroslavskiy, 2009). Falls back to insertion sort for small partitions.
  • Arrays.sort(Object[]) / Collections.sort() / List.sort() → Timsort — a hybrid of merge sort + insertion sort that exploits "runs" of already-sorted data. Stable, O(n log n) worst case, O(n) best case on sorted input.
  • Stream.sorted() → also Timsort under the hood.
  • parallelSort → Fork/Join parallel merge sort for large arrays.

Mentioning Dual-Pivot Quicksort and Timsort by name in an interview almost always lands well — it shows you've looked under the hood.

Interview one-liner: Sorting algorithms arrange data in order; pick one based on data size, memory, stability, and data characteristics. Bubble / Selection / Insertion are simple O(n²) and only used for tiny or nearly sorted inputs. Merge / Quick / Heap are the O(n log n) workhorses — Quick is fastest in practice but worst-case O(n²); Merge is stable with guaranteed O(n log n); Heap is O(1) memory. Java itself uses Dual-Pivot Quicksort for primitives and Timsort (merge + insertion hybrid) for objects.
What is a Red-Black Tree? (the engine behind TreeMap / TreeSet) must

A Red-Black Tree is a self-balancing Binary Search Tree (BST). It keeps the tree balanced by coloring each node either red or black and enforcing 5 simple rules. The result: every operation (search / insert / delete) is guaranteed O(log n) — never O(n).

Core Idea
What A BST where each node has a color (red / black) and 5 invariants are maintained.
Why Plain BSTs can degenerate into a linked list (O(n)). Coloring + rotations keep height ≈ log n.
Cost Search / Insert / Delete — all O(log n), guaranteed worst case.
1 Why we need it — the skewed-BST problem

If you insert 10, 20, 30, 40 into a plain BST in order, you get a sloped chain — basically a linked list:

10 \ 20 \ 30 \ 40 // search now = O(n), not O(log n)

A Red-Black Tree detects this and auto-rotates as you insert, so the same data stays balanced:

20(B) / \ 10(B) 30(B) \ 40(R)

Same data, but height ≈ log n. Every operation stays fast.

2 The 5 Rules (invariants)
  1. Every node is either Red or Black.
  2. The root is always Black.
  3. A Red node cannot have a Red child (no two reds in a row).
  4. Every path from root to any NULL leaf has the same number of black nodes (this is called the black-height).
  5. NULL leaves are considered Black.

Why these rules work: they mathematically guarantee that the longest path is at most 2× the shortest path. That keeps the tree height bounded by 2·log₂(n+1) — i.e. O(log n).

3 Example — a valid Red-Black Tree
■ Black ■ Red
10(B) / \ 5(R) 20(R) / \ / \ 3(B) 7(B) 15(B) 25(B)

Check the rules: root is black ✅, no red-red pair ✅, every path from root to a NULL leaf passes through the same count of black nodes ✅.

4 Balancing Operations

After every insert/delete the tree checks the 5 rules. If a rule is violated, it fixes itself using:

Recoloring
  • Flip node colors (red ↔ black) without moving any pointers.
  • Used when an uncle node is red — push the "blackness" up the tree.
  • Cheapest fix — no structure change.
Rotations
  • Left rotation — pivots a node down-left, its right child up.
  • Right rotation — mirror of left.
  • Used when uncle is black — physically reshape the tree.
  • At most 2 rotations per insert (and O(log n) recolorings).
5 Time Complexity
OperationAverageWorstNotes
SearchO(log n)O(log n)Same as a balanced BST
InsertO(log n)O(log n)1 walk down + at most 2 rotations
DeleteO(log n)O(log n)More complex — up to 3 rotations
SpaceO(n)O(n)1 bit per node for the color
6 Where Red-Black Trees are actually used

Java Collections

  • TreeMap — sorted map
  • TreeSet — sorted set
  • ConcurrentSkipListMap uses skip lists, not RB — but the API is similar.
Why: guaranteed O(log n) for get, put, firstKey, floorKey, range queries.

Linux Kernel

  • Completely Fair Scheduler (CFS) — picks the next task to run
  • epoll internal data structure
  • Virtual memory area (VMA) tracking
Why: kernel needs predictable worst-case performance — RB tree gives that.

Databases

  • In-memory index structures
  • Some isolation-level lock managers
Note: on-disk indexes typically use B-trees / B+ trees instead — better cache locality for disk I/O.

Language Runtimes

  • C++ STL: std::map, std::set, std::multimap
  • Compiler symbol tables
  • Some garbage-collector free-list implementations
Why: ordered traversal + log-n inserts is the right primitive for these.
7 RB Tree vs AVL Tree (the common follow-up)
Red-Black Tree
  • Balance: loose — longest path ≤ 2× shortest
  • Insert / Delete: faster (fewer rotations)
  • Search: slightly slower (taller tree)
  • Use when: writes are frequent (Java TreeMap, Linux kernel)
AVL Tree
  • Balance: strict — heights differ by at most 1
  • Insert / Delete: slower (more rotations)
  • Search: faster (shorter tree)
  • Use when: reads dominate writes (in-memory DB indexes)
One-liner: A Red-Black Tree is a self-balancing BST that uses red/black coloring and 5 invariants to keep the tree height bounded by O(log n). Every insert/delete may trigger recoloring and at most a couple of rotations to restore the rules. In Java, it's the engine behind TreeMap and TreeSet; in the Linux kernel it powers the CFS scheduler and epoll. Use it when you need a sorted structure with guaranteed O(log n) operations.
fail-fast vs fail-safe iterators

Fail-fast iterators throw ConcurrentModificationException as soon as they detect the underlying collection was modified after the iterator was created (via a modCount counter). All java.util collections (ArrayList, HashMap, HashSet) are fail-fast. The detection is best-effort — it's not a synchronization guarantee, it's a bug-finding aid.

Fail-safe iterators don't throw; they iterate over a snapshot or a thread-safe structure. CopyOnWriteArrayList copies the array on every write, so iteration is on the old snapshot. ConcurrentHashMap uses weakly consistent iterators — they see some but not necessarily all updates that happen during iteration, and never throw CME.

Rule: never modify a fail-fast collection while iterating it (use iterator.remove() or stream filtering).

OOP & Language
equals() and hashCode() — the contract must

The contract has three rules. (1) If a.equals(b) is true, then a.hashCode() == b.hashCode() must be true. (2) If two objects have the same hashCode they are NOT required to be equal. (3) Both methods must be consistent — for the lifetime of an object the results shouldn't change (assuming used fields don't change).

Breaking the contract breaks HashMap/HashSet badly — entries become invisible because they're placed in one bucket but looked up in another. Always override both together. Use IDE-generated or Objects.hash(field1, field2). For mutable objects, be careful — if a field used in equals/hashCode changes after insertion, you'll lose the entry. That's why immutable keys are safest.

Why are Strings immutable in Java?

Four reasons. (1) Security — strings are used for class names, URLs, file paths, DB passwords. If they were mutable, attacker code could change a string after a security check passed but before it was used. (2) Thread safety — immutable objects are inherently thread-safe and can be shared freely.

(3) String pool — pooling and interning are only safe because strings can't change after creation. (4) HashCode caching — String.hashCode() is cached after first call (the hash field), making it cheap to use strings as HashMap keys. The cost is that string mutation creates new objects, hence StringBuilder for heavy concatenation in loops.

How do you build an immutable class?

Five rules. (1) Mark the class final so it can't be subclassed (subclasses could add mutable state). (2) Make all fields private final. (3) No setters; set everything in the constructor. (4) If you hold references to mutable objects (lists, dates), defensively copy in the constructor and getters — otherwise callers can mutate your internal state.

(5) Don't expose anything that lets a subclass or external code mutate. Java 14+ record classes give you immutable value objects almost for free — final fields, accessors, equals/hashCode/toString. I use records for DTOs, Java events, and config snapshots. java.time types (LocalDate, Instant) are great examples of immutable design in the JDK.

final, finally, finalize() — explain all three

final is a modifier. On a variable it means assigned once (effectively constant); on a method it can't be overridden; on a class it can't be extended. It's a tool for safety and intent — I mark all DTO fields and most local variables final.

finally is a block in try/catch/finally that always runs after try, even if an exception was thrown or a return executed — used to release resources. Java 7+ try-with-resources covers most use cases.

finalize() was a callback invoked by GC before reclaiming an object. Deprecated since Java 9, removed in Java 18. It was unreliable, could resurrect objects, and slowed GC. Use Cleaner or try-with-resources / AutoCloseable instead. If you see finalize() in code, treat it as a smell.

Method overloading vs overriding

Both let you have methods with the same name but they live at very different levels — one is a compile-time mechanism, the other is the foundation of runtime polymorphism.

Core Difference
Overloading Same method name, different parameters, in the same class — compile-time polymorphism.
Overriding Subclass replaces a parent method with the same signature — runtime polymorphism.
1 Where it lives
Overloading

Within the same class (or inherited overloads visible together).

Overriding

Between a parent class / interface and a subclass.

2 Resolution
Overloading
  • Picked by the compiler based on the static types of arguments.
  • Also called static binding.
Overriding
  • Picked at runtime based on the actual object's class.
  • Also called dynamic dispatch / virtual call.
3 Signature Rules
Overloading
  • Must differ in parameter list (count or types).
  • Cannot overload by return type alone.
  • Can differ in access modifier and exceptions freely.
Overriding
  • Must have the same signature; return type same or covariant.
  • Cannot reduce visibility (e.g., public → private).
  • Cannot throw broader checked exceptions.
  • Use @Override — the compiler catches typos.
4 Example
// Overloading — same class, different params
class Calc {
    int add(int a, int b)        { return a + b; }
    double add(double a, double b){ return a + b; }
    int add(int a, int b, int c) { return a + b + c; }
}

// Overriding — subclass replaces parent behavior
class Animal { void speak() { System.out.println("..."); } }
class Dog extends Animal {
    @Override
    void speak() { System.out.println("Woof"); }
}
Takeaway: overloading is a convenience for the API author; overriding is what makes polymorphism work — the foundation of interfaces, abstract classes, and most framework hooks like Spring's @Transactional proxies.
Abstract class vs Interface (post Java 8)

Java 8 blurred the line by adding default methods to interfaces. Both let you define abstractions, but they still serve different design goals.

Core Difference
Abstract class Partial implementation + shared state (fields, constructor) — "is-a".
Interface Pure contract / capability — "can-do". Multiple inheritance allowed.
1 Inheritance
Abstract class
  • A class can extend only one abstract class.
  • Uses extends.
Interface
  • A class can implement multiple interfaces.
  • Uses implements.
2 Fields & State
Abstract class
  • Can have instance fields, any access modifier.
  • Can have constructors.
  • Holds shared state used by subclasses.
Interface
  • Fields are implicitly public static final — constants only.
  • No constructors, no instance state.
3 Methods Allowed
Abstract class
  • Abstract + concrete methods.
  • Any access modifier (public, protected, private).
  • Can have static and final methods.
Interface
  • Abstract methods (default).
  • default methods with a body (Java 8+).
  • static methods (Java 8+).
  • private helper methods (Java 9+).
4 Use Case
Abstract class
  • Shared base for closely-related classes (e.g., AbstractList, HttpServlet).
  • When you need common fields, constructors, or template methods.
Interface
  • Cross-cutting capabilities — Runnable, Comparable, Closeable.
  • Public APIs and contracts (Spring's UserDetailsService, JPA's Repository).
  • Functional interfaces for lambdas.
Modern guidance: prefer interfaces with default methods by default — they're more flexible and support multiple inheritance. Reach for abstract classes only when you need shared state or constructor logic.
Checked vs Unchecked exceptions

Both extend Throwable, but the compiler treats them very differently — that single rule changes how you design APIs.

Core Difference
Checked Extends Exception (not RuntimeException). Compiler enforces handling.
Unchecked Extends RuntimeException or Error. No compile-time check.
1 Compiler Enforcement
Checked
  • Must be either caught (try/catch) or declared with throws.
  • Failing to do so → compile error.
Unchecked
  • No requirement to declare or catch.
  • If uncaught, it propagates up and crashes the thread.
2 When They're Raised
Checked
  • Predictable recoverable conditions outside program control.
  • Examples: IOException, SQLException, InterruptedException.
Unchecked
  • Usually programming bugs — bad arguments, missing nulls, illegal state.
  • Examples: NullPointerException, IllegalArgumentException, ArithmeticException.
3 Effect on API Design
Checked
  • Noisy throws clauses propagate up the call chain.
  • Painful with lambdas / streams (they don't allow checked throws).
  • Encourages "wrap-and-rethrow" boilerplate.
Unchecked
  • Clean method signatures.
  • Works naturally with lambdas, Streams, CompletableFuture.
  • What Spring, Hibernate, JPA all use.
Modern practice: lean heavily toward unchecked. Wrap checked into unchecked at the boundary (UncheckedIOException, custom ResourceNotFoundException) and handle them centrally in a Spring @ControllerAdvice. Reserve checked exceptions for genuinely recoverable conditions the caller will react to specifically.
== vs equals() — and the Integer cache trap

Two of the most misunderstood operators in Java. Using the wrong one is a classic source of silent bugs.

Core Difference
== Compares reference identity for objects, values for primitives.
equals() Compares logical equality — whatever the class defines.
1 What they compare
==
  • For primitives (int, long) — pure value comparison.
  • For objects — true only if both references point to the same memory location.
equals()
  • A method on Object, overridable.
  • Default impl in Object is just ==.
  • Overridden in String, Integer, collections, records, etc. for value-based equality.
2 The Integer Cache Trap

Integer.valueOf(n) caches values from -128 to 127, so within that range the same boxed object is reused.

Integer a = 100, b = 100;
Integer c = 200, d = 200;

a == b;             // true  — both point to the cached 100
c == d;             // false — outside cache, two new objects
a.equals(b);        // true
c.equals(d);        // true

This bug bites every junior at some point — and occasionally seniors. Caching exists for Boolean, Byte, Short (-128..127), Character (0..127), and configurable for Integer.

3 Strings — Same Story
String a = "hello";
String b = "hello";
String c = new String("hello");

a == b;             // true  — same pooled literal
a == c;             // false — new String forces a new object
a.equals(c);        // true
Rule: never use == on wrapper types or Strings. Use equals() for value comparison, or null-safe Objects.equals(a, b). Reserve == for primitives and explicit reference identity checks (rare).
Java 8+ Features
Stream API — explain with an example hot

The Stream API (Java 8) provides a functional pipeline for processing collections: source → intermediate operations → terminal operation. Intermediate ops (filter, map, sorted) are lazy — they're only executed when a terminal op (collect, count, forEach) runs.

Map<String, Long> activeByDept = employees.stream()
    .filter(Employee::isActive)
    .collect(Collectors.groupingBy(
         Employee::getDepartment,
         Collectors.counting()));

Benefits: declarative, parallelizable with .parallelStream(), composable. Watch-outs: streams are single-use, don't use parallel streams blindly (overhead and shared-state bugs), and remember they're not collections — calling .stream() twice on the same Stream throws.

Optional — proper usage

Optional<T> represents a value that may or may not be present. It's a container designed for return types — to make the absence of a value explicit instead of returning null and crashing downstream.

Good usage: Optional<User> findById(Long id). Callers can compose: findById(id).map(User::getEmail).orElse("unknown") or .orElseThrow(() -> new NotFoundException()).

Bad usage: don't use Optional as a field, parameter, or in collections. Don't call get() without first checking isPresent() — that's just null with extra steps. Don't return Optional for collections — return an empty list. Treat it as a return-type-only signaling device.

Functional interfaces and lambdas

A functional interface has exactly one abstract method (SAM — Single Abstract Method). Examples: Runnable, Comparator, and the java.util.function family: Function<T,R>, Predicate<T>, Consumer<T>, Supplier<T>. The @FunctionalInterface annotation is optional but lets the compiler enforce the SAM rule.

A lambda is concise syntax for an instance of a functional interface:

Comparator<String> byLength = (a, b) -> a.length() - b.length();
list.forEach(s -> System.out.println(s));
list.sort(Comparator.comparingInt(String::length));

Method references (String::length) are even more concise. Lambdas capture effectively-final local variables — you can't mutate them inside the lambda, but you can read them.

What's new in Java 17 / 21 (LTS)?

Java 17 (LTS) highlights: sealed classes for closed hierarchies, records finalized, pattern matching for instanceof (if (obj instanceof String s) { use(s); }), text blocks (multiline strings), switch expressions.

Java 21 (LTS) brings the big-ticket items: Virtual Threads (Project Loom) — millions of lightweight threads scheduled by the JVM, perfect for I/O-bound microservices; pattern matching for switch (deconstruction); sequenced collections (first/last on any ordered collection); structured concurrency as a preview API.

The biggest practical change: virtual threads replace most reactive code. You can write blocking style code in Spring 6 / Spring Boot 3 on JDK 21 and get reactive-like scalability without the cognitive cost.

Records — what are they and when to use?

Records (Java 16+) are compact syntax for immutable data carriers:

public record User(Long id, String email, Instant createdAt) {}

This single line gives you: a public canonical constructor, private final fields, public accessors (id(), email()), and correct equals/hashCode/toString. You can add validation in a compact constructor and add methods, but state is immutable.

I use records for: DTOs in API layers, event payloads on Kafka, query result projections from JPA, value objects in DDD. Don't use them when you need inheritance (records are final), framework lifecycle hooks, or mutable state. They've removed thousands of lines of getter/setter boilerplate from our codebase.

CompletableFuture — chaining async work

CompletableFuture<T> represents an async computation that you can compose with callbacks — far more flexible than the original Future.

CompletableFuture.supplyAsync(() -> fetchUser(id))
    .thenApply(this::enrichProfile)
    .thenCombine(loadOrders(id), this::merge)
    .exceptionally(ex -> fallback(ex))
    .thenAccept(this::sendResponse);

Key methods: thenApply (map), thenCompose (flatMap), thenCombine (zip), allOf, anyOf. Always pass a custom ThreadPool — the default ForkJoinPool.commonPool is shared with the JVM and small. Also always add exceptionally or handle, otherwise exceptions get swallowed. I use it for fan-out calls to multiple downstreams, like enriching a user with orders + recommendations + recent activity in parallel.

Date/Time API (java.time) — why switch from Date?

The old java.util.Date and Calendar were notoriously bad: mutable (Date is thread-unsafe), poorly designed (months are 0-indexed in Calendar), and missing timezone handling. The new java.time (JSR-310) replaces them cleanly.

Key types: LocalDate (date without time), LocalTime, LocalDateTime (no timezone — risky for cross-region apps), ZonedDateTime (with zone), Instant (UTC instant, used internally), Duration, Period. All are immutable and thread-safe.

Rule for production services: store Instants in UTC, convert to user timezone only at the edge. This avoids the entire class of DST and zone-shift bugs I've debugged at OneXtel.

Try-with-resources and AutoCloseable

Try-with-resources (Java 7+) ensures resources are closed automatically:

try (var conn = ds.getConnection();
     var stmt = conn.prepareStatement(sql);
     var rs = stmt.executeQuery()) {
    while (rs.next()) { ... }
} // close() called in reverse order, even on exception

The resource must implement AutoCloseable. If both the try block and close() throw, the close exception is added as a suppressed exception — you don't lose either, and Throwable.getSuppressed() retrieves it.

This replaces the old try/finally pattern that was easy to get wrong (forgetting null checks in finally, swallowing the original exception with a close failure). I use it for every DB connection, file stream, HTTP client, and Kafka consumer in modern code.

What is type erasure in generics?

Java generics are implemented via type erasure: at compile time the compiler enforces type safety, but at runtime the generic type information is erased — a List<String> and List<Integer> are both just List in bytecode. The compiler inserts casts where needed.

This was a backwards-compatibility decision for Java 5 — generic code had to interoperate with pre-generic code. Consequences:

  • You can't do new T() or T.class — type information isn't there at runtime.
  • You can't have List<String>[] arrays directly.
  • You can't overload methods that differ only in their generic parameter (both erase to the same signature).
  • Workarounds: pass Class<T> clazz as a parameter (Spring, Jackson do this).

Kotlin and reified generics in inline functions get around this; Java doesn't (yet).

Serialization — and why you avoid it now

Java serialization (Serializable marker interface) writes object state to a binary format and reads it back via ObjectInputStream. It powers RMI and was used for session replication, caching, and queue payloads.

Why we avoid it: security holes (deserialization gadgets are a major CVE source — Apache Commons Collections, Log4Shell-class issues), brittle (any class change can break old data — serialVersionUID hell), slow, verbose, Java-only (can't be consumed by Python/Node services).

Modern alternatives I use: JSON (Jackson) for REST and Kafka payloads, Protobuf or Avro with schema registry for high-throughput typed messaging, and UUID/string-based session tokens instead of session replication. The official Java team also wants to remove serialization eventually (JEP 154 / Project Amber).

Reflection — when do you use it?

Reflection (java.lang.reflect) lets you inspect and modify classes, methods, fields at runtime. Class<?> c = obj.getClass(); Method m = c.getMethod("save"); m.invoke(obj); — calling methods by name dynamically.

I rarely use it directly in application code, but it underpins almost every framework I use: Spring autowires beans via reflection, Jackson maps JSON to fields, Hibernate populates entities, Mockito creates mocks, JUnit finds @Test methods. Direct usage is justified for: generic serializers, plugin frameworks, dependency-injection containers, test helpers.

Costs: slower than direct calls (though JIT helps), breaks encapsulation (accesses private fields), and the security manager can block it. Prefer interfaces/strategy pattern when possible.

Annotations — how do they work under the hood?

An annotation is metadata attached to code — classes, methods, fields, parameters. Each has a retention policy: SOURCE (compiler only, like @Override), CLASS (in bytecode but not at runtime), or RUNTIME (available via reflection — what Spring/JPA use).

At runtime, frameworks scan classes via reflection or class-path scanning, find annotations like @Service, @Transactional, @RestController, and act on them — registering beans, wiring proxies for transactions, mapping URLs.

Source-level annotations can be processed by annotation processors at compile time (Lombok, MapStruct generate code this way). I write custom runtime annotations occasionally for cross-cutting concerns — e.g., @AuditLog processed by a Spring AOP aspect to log user actions automatically.

What is the ClassLoader and how does it work?

A ClassLoader loads .class bytecode into the JVM. Java has a hierarchy with delegation — a child loader first asks its parent before loading itself.

Bootstrap loads core classes (java.lang.*) from the JDK. Platform (formerly Extension) loads JDK modules. Application / System loads from the classpath. Apps can define their own — e.g., Tomcat has a per-webapp loader so two apps can use different versions of the same library.

Common interview gotcha: String.class.getClassLoader() returns null because bootstrap is native. ClassNotFoundException means the loader couldn't find a class; NoClassDefFoundError means it found it once but can't now — usually a deployment/classpath issue. Modules in Java 9+ added another layer of class visibility on top.

String vs StringBuilder vs StringBuffer

All three represent character sequences, but they differ in mutability, thread safety, and performance — picking the wrong one in a loop can tank your service.

Core Difference
String Immutable — every change creates a new object.
StringBuilder Mutable, not thread-safe, fast.
StringBuffer Mutable, thread-safe (synchronized), slower.
1 Mutability
String
  • Immutable. s = s + "x" creates a brand-new String each time.
  • O(n) per concat → O(n²) inside a loop.
StringBuilder / StringBuffer
  • Mutable — internal char[] grows as needed.
  • append is amortized O(1).
2 Thread Safety
StringBuilder
  • Not synchronized.
  • Faster — use within a single thread (local variable, method body).
StringBuffer
  • Every method is synchronized.
  • Safer across threads but with synchronization overhead.
3 Performance

For building a string in a loop (10,000 iterations, rough order):

  • String + in loop → very slow (O(n²), heaps of garbage).
  • StringBuilder → fastest. Default choice.
  • StringBuffer → ~10–20% slower than StringBuilder.
StringBuilder sb = new StringBuilder();
for (String s : list) sb.append(s).append(",");
String result = sb.toString();
4 Use Case
String
  • Constants, keys, returned values — anything that won't change.
  • Map keys, equals/hashCode usage.
StringBuilder / Buffer
  • StringBuilder — building strings in loops, log messages, query construction.
  • StringBuffer — almost never used today; legacy code only.
Modern alternative: for joining a collection use String.join(",", list) or list.stream().collect(Collectors.joining(",")) — cleanest and just as fast. Java 9+ compact strings made plain String even cheaper for ASCII text.
How does autoboxing work — and its pitfalls?

Autoboxing automatically wraps primitives into their object types: Integer i = 5 compiles to Integer.valueOf(5). Unboxing is the reverse: int n = i compiles to i.intValue().

Pitfalls: (1) NullPointerException on unboxing a null wrapper — Integer a = null; int b = a; throws NPE at runtime, not a clear "null" error. (2) Performance — using Integer in tight loops or large collections creates millions of boxed objects, hurting both heap and GC. (3) == trap — Integer cache makes Integer.valueOf(100) == Integer.valueOf(100) true but Integer.valueOf(200) == Integer.valueOf(200) false (-128 to 127 cached).

Rule: use primitives in hot paths and inside data structures; reach for wrappers only when you need null or generics.

Comparable vs Comparator

Both define ordering for objects, but one is built into the class and the other lives outside. Picking the right one shapes your API.

Core Difference
Comparable Natural ordering — implemented by the class itself.
Comparator External ordering — separate strategy object.
1 Where it lives
Comparable
  • The class implements Comparable<T> and defines compareTo(T).
  • One ordering per class (the "natural" one).
  • Examples: String (alphabetical), Integer (numeric), LocalDate (chronological).
Comparator
  • A separate object (or lambda) implementing Comparator<T>.
  • Many comparators per class — by name, salary, age, anything.
  • Doesn't require modifying the class being compared.
2 Method
Comparable
class Employee implements Comparable<Employee> {
    public int compareTo(Employee o) {
        return this.id - o.id;
    }
}
Comparator
Comparator<Employee> bySalary =
    Comparator.comparingDouble(Employee::getSalary);

list.sort(bySalary
    .thenComparing(Employee::getName));
3 Use Case
Comparable
  • When there is one obvious "natural" order for the class.
  • Required for keys of TreeMap / TreeSet (unless you supply a Comparator).
Comparator
  • Multiple orderings (by salary, then by name).
  • Sorting a class you don't own.
  • Reversed / case-insensitive / locale-aware sorts.
  • Modern code lives almost entirely on Comparator with method references and .thenComparing.
Contract for both: return negative / zero / positive, be transitive, and ideally consistent with equals (otherwise TreeSet/TreeMap behave oddly). Inconsistent comparisons can even throw IllegalArgumentException from the sort in Java 7+.
What are sealed classes (Java 17)?

Sealed classes/interfaces restrict which classes can extend or implement them — you list the allowed subclasses explicitly:

public sealed interface PaymentResult
    permits Success, Failure, Pending {}

public record Success(String txnId) implements PaymentResult {}
public record Failure(String reason) implements PaymentResult {}
public record Pending(String trackingId) implements PaymentResult {}

Two big wins. (1) Closed hierarchies — the compiler knows the set of subtypes, so pattern matching switches can be exhaustive: forget a case and you get a compile error. (2) Domain modeling — sealed + records is Java's closest equivalent to algebraic data types (Kotlin's sealed classes, Scala's case classes). I use them for command/result hierarchies and domain events where I want strong compile-time guarantees on handled cases.
