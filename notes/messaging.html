Kafka vs RabbitMQ must

Both move messages between services, but they were designed for very different problems — a distributed log versus a smart broker. Picking the right one shapes your architecture.

Core Difference
RabbitMQ Message broker — smart routing, push-based, message deleted after ack.
Kafka Distributed log — durable, append-only, pull-based, replayable.
1 Data Model
RabbitMQ
  • Exchanges → Queues. Smart routing (direct, topic, fanout, headers).
  • Once consumed and acked, the message is gone.
Kafka
  • Topics → Partitions. Each partition is an ordered append-only log.
  • Messages stay for a retention period (days/weeks) — replayable.
2 Delivery Model
RabbitMQ
  • Push — broker pushes to consumers.
  • Per-message ack; redelivers on failure.
  • Supports priorities, per-message TTL, dead-letter exchanges.
Kafka
  • Pull — consumer polls at its own pace.
  • Tracks position via offsets; consumer controls progress.
  • Many consumer groups can read the same topic independently.
3 Throughput & Scale
RabbitMQ
  • Tens of thousands msg/s per node.
  • Scales vertically; cluster mode exists but is complex.
Kafka
  • Millions msg/s on a small cluster.
  • Horizontally scaled by adding partitions and brokers.
  • Built for throughput from day one.
4 Ordering & Replay
RabbitMQ
  • Per-queue ordering only with a single consumer.
  • No native replay — once acked, it's gone.
Kafka
  • Ordering per partition guaranteed.
  • Replay by offset — perfect for event sourcing, debugging, new consumers backfilling history.
5 Use Case
RabbitMQ
  • Work queues — emails, image processing, retry jobs.
  • Request/response, RPC, fan-out to specific routing keys.
  • Priorities, delays, complex routing rules.
Kafka
  • Event streams — every domain event published once, consumed by many.
  • Log aggregation, CDC (Change Data Capture), metrics pipelines.
  • Event sourcing, stream processing (Kafka Streams, Flink).
Rule of thumb: use RabbitMQ for work queues (jobs to be done) and Kafka for event streams (facts to be published once and read by many). At OneXtel I used Kafka for SMS event streams (millions/day, replayable) and RabbitMQ for per-customer notification jobs (priority + per-message TTL).
How does Kafka work under the hood?

A Kafka cluster has brokers. Data is organized into topics, each split into partitions (the unit of parallelism). Each partition is an ordered, immutable log appended to disk.

Producers send messages with a key — Kafka hashes the key to pick a partition, so messages with the same key always land on the same partition (preserving order per key). Each message gets an offset.

Consumers belong to a consumer group. Kafka assigns each partition to exactly one consumer in the group — so n partitions support up to n parallel consumers per group. Consumers commit offsets back to Kafka.

Each partition has a leader replica + follower replicas across brokers for fault tolerance. Producers write to the leader; ISR (in-sync replicas) replicate. If a leader dies, a follower is promoted. Modern Kafka uses KRaft (no Zookeeper) for cluster metadata.

Delivery guarantees — at-most-once, at-least-once, exactly-once hot must

Every messaging system makes a tradeoff between losing messages and delivering them more than once. Kafka exposes this choice through producer/consumer configuration. Knowing which guarantee your pipeline actually delivers is the difference between a correct system and a silent data-corruption bug.

CORE IDEA Three guarantees: at-most-once (may lose), at-least-once (may duplicate, default), exactly-once (Kafka-internal only). End-to-end exactly-once across DB+Kafka+consumer = at-least-once + idempotent consumers.
GuaranteeWhat it meansHow to get itWhen to use
At-most-once Message may be lost but never duplicated. Producer: acks=0. Consumer: commit offset before processing. Metrics, click-stream telemetry — loss is acceptable, duplication is not.
At-least-once Every message delivered ≥ 1 time. Duplicates possible on retry/rebalance. Producer: acks=all + retries. Consumer: commit offset after processing. Default for production pipelines — orders, payments, audits — paired with idempotent consumers.
Exactly-once (EOS) Each message processed once, no loss, no duplicate. Producer: enable.idempotence=true + transactional producer. Consumer: isolation.level=read_committed. Kafka-to-Kafka stream processing (Kafka Streams). End-to-end across DB+Kafka still needs idempotency.
1 Producer-side configuration that drives the guarantee
# at-least-once producer (default for production)
acks=all                          # leader + all in-sync replicas must ack
enable.idempotence=true           # producer dedupes its own retries via PID + sequence
retries=Integer.MAX_VALUE
max.in.flight.requests.per.connection=5
delivery.timeout.ms=120000

# exactly-once producer (Kafka Streams or transactional writes to multiple topics)
transactional.id=order-svc-tx-1   # required for transactions
# in code:
producer.initTransactions();
producer.beginTransaction();
producer.send(record1);
producer.send(record2);
producer.commitTransaction();     // either both visible or neither
2 Consumer-side — where duplicates actually come from
Consumer polls a batch
↓
Processes message (writes to DB / calls API)
↓
Crashes before commit
↓
Rebalance → new consumer reads from last committed offset
↓
The same message is processed again → duplicate

There is no way to make "process + commit offset" atomic across two systems (DB + Kafka). Therefore at-least-once is the practical ceiling — the consumer must be designed to absorb duplicates safely.

3 Idempotent consumer pattern (the real exactly-once)
@KafkaListener(topics = "order.events", groupId = "billing")
@Transactional
public void onOrderCreated(OrderEvent evt, Acknowledgment ack) {
    if (processedRepo.existsByEventId(evt.getEventId())) {
        ack.acknowledge();           // already handled — skip silently
        return;
    }
    processedRepo.save(new ProcessedEvent(evt.getEventId()));   // dedup row
    billingService.charge(evt);                                 // business work
    ack.acknowledge();               // commit offset only after success
}

The DB transaction wraps the dedup-table write and the business write — they commit together. Even if the offset commit is later replayed, the dedup row blocks duplicate processing.

4 What enable.idempotence=true actually does
  • Producer assigns each message a (Producer ID, sequence number). The broker dedupes any retry from the same producer session.
  • It does not protect against: a fresh JVM resending the same business event, the outbox publisher republishing a row, a different producer sending the same event, or consumer-side reprocessing.
  • Therefore: idempotent producer ≠ end-to-end exactly-once. You still need an event_id on every message and dedup logic in the consumer.
5 Common interview gotchas
  • "Exactly-once" in Kafka is a Kafka-internal guarantee (Kafka → Kafka via transactions). It does not extend to your DB or external API calls.
  • acks=1 (leader only) can lose data on leader crash before replication — use acks=all in production.
  • Auto-commit (enable.auto.commit=true) commits on a timer, not after processing — a crash between processing and the next auto-commit causes message loss or duplication depending on order.
  • Setting max.in.flight.requests.per.connection > 1 without enable.idempotence=true can reorder messages within a partition on retry.
  • Transactional producers require a unique transactional.id per producer instance — share it across pods and they fence each other off.
  • End-to-end exactly-once for "consume → process → produce" pipelines requires Kafka transactions + read_committed on the next consumer.
  • Outbox pattern (DB write + outbox row in one tx) gives you exactly-once on the producer side for free; consumers still need idempotency.

Interview one-liner: Kafka offers three delivery guarantees: at-most-once (commit before processing — may lose), at-least-once (commit after processing — may duplicate, the production default), and exactly-once semantics (EOS) via enable.idempotence=true + transactional producer + read_committed consumer — but only Kafka-to-Kafka. End-to-end across DB and Kafka, the practical pattern is at-least-once + idempotent consumers: every event carries an event_id, and consumers dedupe via a processed_events table inside the same transaction as the business write. That gives you effective exactly-once with simple, robust mechanics.

Transactional Outbox Pattern with Kafka — guaranteeing DB + event consistency must

The classic dual-write problem: a service has to update its database and publish a Kafka event about that change. Doing both directly is not atomic — there's always a window where one succeeds and the other fails, leaving the system inconsistent. The Transactional Outbox pattern solves this by turning two unreliable writes into one atomic DB write plus a reliable replay.

Core Idea
Outbox Write the business data and the event in the same DB transaction (an outbox table). A separate publisher relays the outbox to Kafka. The DB transaction is the only thing that needs to be atomic — the publisher just guarantees at-least-once delivery from the outbox.
1 The dual-write problem — what we're solving
Naive dual write
  • Save Order to DB → publish to Kafka. Two separate systems, no shared transaction.
  • Failure A: DB commits, Kafka publish fails → other services never hear about the order.
  • Failure B: Kafka publish succeeds, DB commit fails → other services think an order exists that doesn't.
  • Failure C: Neither is atomic with the other — there's no shared transaction across DB + broker.
Transactional Outbox
  • Save Order + save outbox event in one DB transaction.
  • Both succeed or both rollback — the DB enforces atomicity.
  • A separate relay reads the outbox and publishes to Kafka.
  • Kafka only ever sees events for committed business state.
2 Flow
API request arrives
↓
Begin DB transaction
↓
INSERT into order table
↓
INSERT into outbox table event payload + metadata
↓
Commit transaction atomicity guaranteed by the DB
↓
Background publisher polls outbox for status = 'PENDING' (or Debezium streams the WAL)
↓
Publish to Kafka
↓
Mark outbox row as SENT (or delete / archive it)
3 Outbox table schema
CREATE TABLE outbox (
    id              BIGSERIAL PRIMARY KEY,
    aggregate_id    VARCHAR(64) NOT NULL,     -- e.g. order_id (used as Kafka partition key)
    aggregate_type  VARCHAR(64) NOT NULL,     -- e.g. 'Order'
    event_type      VARCHAR(64) NOT NULL,     -- e.g. 'OrderCreated'
    payload         JSONB        NOT NULL,    -- the event body
    status          VARCHAR(16)  NOT NULL DEFAULT 'PENDING',  -- PENDING | SENT | FAILED
    retry_count     INT          NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ  NOT NULL DEFAULT now(),
    published_at    TIMESTAMPTZ,
    INDEX idx_status_created (status, created_at)
);
4 Spring Boot — write business row + outbox row in one transaction
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository  orders;
    private final OutboxRepository outbox;
    private final ObjectMapper     mapper;

    @Transactional                                    // single DB tx
    public Order create(OrderRequest req) {
        Order saved = orders.save(new Order(req));

        OutboxEvent evt = OutboxEvent.builder()
            .aggregateId(saved.getId().toString())    // partition key
            .aggregateType("Order")
            .eventType("OrderCreated")
            .payload(mapper.valueToTree(saved))
            .status(Status.PENDING)
            .build();
        outbox.save(evt);

        return saved;
    }
}

Both orders.save(...) and outbox.save(...) run inside the same @Transactional boundary. Commit succeeds → both rows exist. Commit rolls back → neither exists. There is never an inconsistent state.

5 Two ways to relay outbox → Kafka
Polling publisher (simple)
  • @Scheduled job every 1–5s.
  • SELECT … WHERE status='PENDING' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 100;
  • Publish each row to Kafka → UPDATE outbox SET status='SENT', published_at=now() WHERE id=?.
  • Pros: easy, no extra infra, works on any DB.
  • Cons: polling latency, constant DB load.
Debezium CDC (production)
  • Debezium reads the DB's WAL / binlog and streams every outbox INSERT to Kafka via Kafka Connect.
  • No application-side publisher at all.
  • Pros: near-real-time, no polling, no DB hot spot on the outbox table.
  • Cons: extra infra (Kafka Connect + Debezium), schema-evolution care, requires CDC-enabled DB (Postgres WAL / MySQL binlog).
6 Polling publisher snippet
@Component
@RequiredArgsConstructor
public class OutboxPublisher {
    private final OutboxRepository outbox;
    private final KafkaTemplate<String, String> kafka;

    @Scheduled(fixedDelay = 1000)                    // poll every 1s
    @Transactional                                    // wraps the SELECT … FOR UPDATE
    public void publishBatch() {
        // FOR UPDATE SKIP LOCKED → multiple publisher pods can run in parallel
        // without picking the same row.
        List<OutboxEvent> batch = outbox.lockPendingBatch(100);

        for (OutboxEvent evt : batch) {
            ProducerRecord<String, String> record = new ProducerRecord<>(
                "order.events",
                evt.getAggregateId(),                 // partition key — preserves per-order ordering
                evt.getPayload().toString()
            );
            kafka.send(record).get();                 // wait for ack
            evt.setStatus(Status.SENT);
            evt.setPublishedAt(Instant.now());
        }
        // tx commit → rows marked SENT atomically with the lock release
    }
}

// Repository query
@Query(value = """
    SELECT * FROM outbox
    WHERE status = 'PENDING'
    ORDER BY id
    FOR UPDATE SKIP LOCKED
    LIMIT :n
    """, nativeQuery = true)
List<OutboxEvent> lockPendingBatch(@Param("n") int n);

FOR UPDATE SKIP LOCKED is the key to running multiple publisher instances safely: each pod locks a disjoint set of rows and skips the ones a peer is already processing. If a publisher crashes mid-batch, its lock is released and another pod picks up those rows → the row stays PENDING until it's actually delivered.

7 Why this works

The DB guarantees atomicity of the business write + outbox write via an ordinary local ACID transaction. Kafka is decoupled — the publisher only has to guarantee at-least-once delivery from the outbox, which is trivial (retry until SENT). There is no distributed transaction across DB + Kafka, and no 2PC anywhere. The pattern transforms a hard problem (distributed atomicity across two heterogeneous systems) into a simple one (atomic write to one DB + reliable replay).

8 Delivery semantics — what you actually get
StageGuaranteeWhy
DB write (order + outbox)Exactly-onceOne ACID transaction — atomic by construction.
Kafka publishing At-least-oncePublisher may crash mid-publish; row stays PENDING → it'll be republished.
End-to-end (producer → consumer)At-least-onceTherefore: consumers MUST be idempotent.
9 Idempotency on the consumer side

Since the end-to-end guarantee is at-least-once, consumers will occasionally see the same event twice (e.g. publisher acked the row but crashed before marking it SENT). The standard fix: dedupe via an event_id stamped on each event, backed by a small processed_events table.

@KafkaListener(topics = "order.events", groupId = "billing")
@Transactional
public void onOrderCreated(OrderCreated evt) {
    if (processedEvents.existsByEventId(evt.getEventId())) {
        return;                                   // duplicate — already handled
    }
    processedEvents.save(new ProcessedEvent(evt.getEventId(), Instant.now()));
    billing.charge(evt);                          // business logic
}

Note: Kafka's enable.idempotence=true only dedupes producer-side in-flight retries (same producer, same session). It does not protect consumers from duplicates caused by republishes from the outbox — you still need a consumer-side dedup key.

13 Common interview gotchas
  • You don't need 2PC — that's the whole point of the pattern.
  • The publisher is at-least-once + consumers must be idempotent — "exactly-once end-to-end" is a myth in real distributed systems.
  • Use FOR UPDATE SKIP LOCKED so multiple publisher pods don't pick the same row.
  • Always partition Kafka by aggregate_id so per-entity ordering is preserved.

The DB transaction gives you exactly-once for the business write; the relay gives you at-least-once for Kafka. End-to-end is at-least-once → consumers must be idempotent (event_id dedup table). Production essentials: idempotent consumers, SKIP LOCKED for parallel publishers, archiving of SENT rows, and observability on outbox lag.

Kafka consumer offsets and rebalancing

Each consumer in a group tracks its current offset per partition — the next message to read. Offsets are committed back to Kafka periodically (auto-commit) or manually (more reliable).

When a consumer joins or leaves the group, Kafka triggers a rebalance — partitions are redistributed. The classic gotcha: if processing is slow and the consumer doesn't poll within max.poll.interval.ms, Kafka assumes it's dead and reassigns its partitions → duplicate processing.

Practices to follow:

  • Manual commit after successful processing — auto-commit can lose messages on crash.
  • Tune max.poll.records and max.poll.interval.ms so a batch finishes well before the timeout.
  • Use Kafka's cooperative rebalancing (incremental) instead of eager stop-the-world.
  • Idempotent processing so reprocessing on rebalance is safe.
What happens if a Kafka consumer crashes after processing but before committing the offset? must

This is the canonical "at-least-once vs exactly-once" interview probe. Understanding the exact failure window — and the only correct mitigation — separates engineers who have run Kafka in production from those who have only read about it.

CORE IDEA The next consumer that picks up the partition starts from the last committed offset, so the message gets processed again. The only correct fix is to make consumer logic idempotent — the offset cannot be committed atomically with an external side effect.
1 The exact sequence of events
Consumer polls offset N from broker
↓
Processes message — writes to DB / calls API / sends downstream event
↓
Pod crashes / OOM kill / network partition offset N never committed
↓
Heartbeat times out — Kafka triggers a rebalance
↓
Partition reassigned to another consumer in the group
↓
New consumer reads from last committed offset (still N)
↓
Same message is processed a second time
2 Why you can't make it exactly-once

The consumer's offset commit goes to Kafka, but the side effect (DB write, external HTTP call) goes somewhere else. There is no shared transaction across two systems. The two writes can never be atomic — at any failure point, one will be applied and the other won't.

Commit orderCrash window outcomeRisk
Commit offset before processingCrash after commit, before DB write → message lostData loss — almost never acceptable
Commit offset after processingCrash after DB write, before commit → message reprocessedDuplicates — solvable with idempotency

Therefore the right design is "process → commit", and rely on idempotent processing.

3 The correct consumer skeleton
# Spring Kafka — disable auto-commit, use manual ack
spring.kafka.consumer.enable-auto-commit=false
spring.kafka.listener.ack-mode=manual_immediate
spring.kafka.consumer.isolation-level=read_committed
spring.kafka.consumer.max-poll-records=50
spring.kafka.consumer.properties.max.poll.interval.ms=300000
@KafkaListener(topics = "payments", groupId = "ledger")
@Transactional
public void onPayment(ConsumerRecord<String, PaymentEvent> rec, Acknowledgment ack) {
    String eventId = rec.value().getEventId();

    if (processedRepo.existsByEventId(eventId)) {     // dedup table inside same DB
        ack.acknowledge();                            // duplicate — skip + commit
        return;
    }
    processedRepo.save(new Processed(eventId));       // dedup row
    ledgerService.post(rec.value());                  // business write

    ack.acknowledge();                                // commit offset only AFTER tx commits
}

The DB transaction makes "dedup row + business write" atomic. The offset commit happens after — if it fails, redelivery hits the dedup check and skips.

4 Why Kafka's transactional producer doesn't fully solve this

Kafka transactions guarantee atomicity for Kafka-only "consume → process → produce" pipelines (used in Kafka Streams). They do not wrap external side effects like DB writes or REST calls. As soon as your processing touches a non-Kafka system, the only durable answer is consumer-side idempotency.

5 Common interview gotchas
  • The window is "between processing and offset commit" — not "between poll and processing".
  • Auto-commit (enable.auto.commit=true) commits on a timer regardless of processing — risk of both loss and duplication depending on timing.
  • Long processing + missed poll() within max.poll.interval.ms triggers a rebalance — same outcome as a crash.
  • Dedup table must be in the same DB as the business write so they share a transaction; a remote dedup store reintroduces the dual-write problem.
  • Use read_committed isolation when consuming from a topic produced by a transactional producer, otherwise you'll see uncommitted records.
  • Cooperative rebalancing (partition.assignment.strategy=CooperativeStickyAssignor) reduces stop-the-world rebalance pauses but doesn't change the duplicate-processing semantics.
  • Pod graceful shutdown should call consumer.close() so in-flight processing finishes and offsets are committed before exit.

Interview one-liner: If a Kafka consumer crashes between processing and committing its offset, the next consumer that owns the partition restarts from the last committed offset — so that message is processed again. There is no way to make external side effects (DB write, HTTP call) atomic with the offset commit, so the only durable answer is at-least-once delivery + idempotent consumers: an event_id on every message and a dedup table inside the same DB transaction as the business write. Manual offset commits, enable.auto.commit=false, and ack-mode=manual_immediate in Spring Kafka are the production defaults.

How do you handle duplicate events in Kafka? must

In Kafka the realistic delivery contract is at-least-once, so consumers will see the same event twice — on retries, rebalances, redeploys, or republishes from an outbox. The fix is to design every consumer as a pure function of the event, even when invoked twice.

CORE IDEA Every event carries an event_id. Every consumer dedupes by writing the event_id to a dedup table in the same DB transaction as the business write — a duplicate hits a unique-key violation and is skipped.

2 Three dedup strategies
Dedup table (most common)
  • Table processed_events(event_id PRIMARY KEY, processed_at).
  • Insert row + business write in one transaction.
  • Duplicate → unique-key violation → skip.
  • Prune rows older than retention window (e.g., 30 days).
Natural-key idempotency
  • The business write is itself idempotent: UPSERT by natural key with version check.
  • Example: INSERT … ON CONFLICT (order_id) DO UPDATE WHERE excluded.version > orders.version.

Idempotent downstream call
  • External API supports Idempotency-Key header (Stripe, PayPal pattern).
  • Pass event_id as the key — provider dedupes.
  • Use when the side effect is at a third party you can't transact with.
3 Idempotent consumer in Spring Kafka
@KafkaListener(topics = "order.events", groupId = "shipping",
               containerFactory = "kafkaListenerContainerFactory")
@Transactional
public void onOrderCreated(OrderCreated evt, Acknowledgment ack) {
    try {
        processedRepo.save(new ProcessedEvent(evt.getEventId(), Instant.now()));
    } catch (DataIntegrityViolationException dup) {
        ack.acknowledge();                          // already processed → skip
        return;
    }
    shipmentService.create(evt);                    // business work
    ack.acknowledge();                              // commit offset after tx commits
}

The event_id is the primary key of the dedup table — a duplicate insert raises a constraint violation, which we catch and acknowledge. The business write only runs for first-time events.

4 What about Redis or an in-memory cache?

Tempting but dangerous. A Redis-backed dedup is fast but reintroduces the dual-write problem — Redis insert and DB write are two systems again. Use it only as an optimization layer in front of a DB-backed dedup, never as the sole source of truth.

5 Common interview gotchas
  • enable.idempotence=true on the producer only dedupes same-session retries, not republishes from a fresh JVM or an outbox relay.
  • The dedup row and the business write must be in the same DB and same transaction, otherwise you have a dual-write race.
  • event_id must be deterministic — UUIDv4 generated at consume time defeats dedup. Generate it at the producer (or use an outbox surrogate id).
  • The dedup table grows forever — partition by date or run a TTL job to drop old rows.
  • Per-event dedup, not per-batch — a partial-batch crash can leave half processed.
  • Replays from a specific offset will hit the dedup table and skip everything — that's correct behavior, not a bug.
  • For pipelines that produce to another Kafka topic, prefer Kafka transactions + read_committed consumer for native exactly-once between topics.

Interview one-liner: Kafka delivery is at-least-once in practice, so duplicates are inevitable on retries, rebalances, and outbox republishes. The fix is to make every consumer idempotent: stamp every event with a stable event_id at production time, and on the consumer side write that id to a processed_events dedup table inside the same DB transaction as the business write. A duplicate hits a unique-key violation and is skipped. For pipelines that write only to Kafka, use transactional producers + read_committed consumers; for anything that touches a DB or external API, idempotency is the only durable answer.

Retry and Dead Letter Queue (DLQ) in Kafka — full pattern must

In a Kafka consumer, errors are inevitable: transient (timeout, 503), recoverable (data not ready yet), or terminal (poison message — bad schema, broken business invariant). Without a strategy, one bad message blocks the partition and the consumer group falls infinitely behind. The standard production fix is bounded retries with backoff followed by a Dead Letter Queue.

CORE IDEA Retry transient errors a few times with backoff; if still failing, publish the message to a DLQ topic with full metadata (original topic, partition, offset, exception, attempt count) and commit the offset so the consumer keeps moving. Operators inspect the DLQ, fix the cause, and replay.
1 Why a "retry forever" loop is a production bug
  • One poison message blocks its partition — every later message in that partition is held up behind it.
  • Consumer lag grows monotonically; SLOs miss; downstream systems starve.
  • The bad message is usually data-related (missing field, wrong format) — retrying changes nothing.
  • Without alerting on DLQ count, the failure stays invisible until customer impact.
2 The retry + DLQ flow
Consumer receives message at offset N

3 Spring Kafka — declarative DLQ
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<String, String> template) {
    // Publish to .DLT with original headers preserved
    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
        template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition())
    );

    // Backoff: 3 attempts at 1s, 2s, 4s, then DLQ
    ExponentialBackOffWithMaxRetries backoff = new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(1_000L);
    backoff.setMultiplier(2.0);
    backoff.setMaxInterval(10_000L);

    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backoff);
    // Don't retry deserialization or business validation failures — straight to DLQ
    handler.addNotRetryableExceptions(
        DeserializationException.class,
        ValidationException.class
    );
    return handler;
}

Spring Kafka's DefaultErrorHandler + DeadLetterPublishingRecoverer handles the full retry-then-DLQ flow. The DLQ topic is conventionally named <original-topic>.DLT.

5 Two retry styles — local vs blocking-retry-topic
In-process retry (default)
  • Backoff between attempts happens in the consumer thread.
  • Simple — one consumer, one DLQ.
  • Risk: long backoffs eat max.poll.interval.ms and cause rebalance.
Non-blocking retry topics

  • Each retry topic has its own delayed consumer.
  • Original consumer is never blocked — retries happen on parallel topics.
  • Use for long backoffs (minutes/hours) or hot partitions.

7 Replay from DLQ

Two patterns for replaying:

  • Operator UI — list DLQ messages, allow manual edit + republish to original topic with a fresh event_id.
  • Bulk replay tool — small CLI / Spring Boot job that reads the DLQ and republishes once the upstream issue is fixed.

Always change the event_id or include a replay_attempt header on replay so consumer-side dedup logic doesn't reject it (assuming you want it reprocessed).

8 Common interview gotchas
  • Don't retry on terminal errors (deserialization, validation, business invariants) — they'll never succeed and you waste capacity.
  • Cap total retry budget so it fits inside max.poll.interval.ms; otherwise rebalance triggers and the same message is reprocessed.
  • Use exponential backoff with jitter to avoid thundering-herd on a downstream that just came back.
  • Always alert on DLQ message count — a silent DLQ is worse than no DLQ.
  • Preserve original message bytes in the DLQ — don't lose context when wrapping.
  • Keep the DLQ schema-compatible with the source topic so replay tools can deserialize.
  • For high-volume topics, partition the DLQ the same way as the source so replay preserves per-key ordering.
  • Don't auto-replay — most poison messages need a human decision.

Interview one-liner: Production Kafka consumers use a bounded-retry + DLQ pattern: retry transient errors a few times with exponential backoff, then publish failed messages to a <topic>.DLT topic with full metadata (original offset, exception, stack trace) and commit the offset so the consumer keeps moving. In Spring Kafka, DefaultErrorHandler + DeadLetterPublishingRecoverer implements blocking retries, while @RetryableTopic implements non-blocking retries via dedicated retry topics. Critical disciplines: skip terminal errors, cap retries inside max.poll.interval.ms, alert on DLQ size, and never auto-replay without a human in the loop.

How does Kafka ensure message ordering? must

Kafka's ordering guarantee is precise but narrow: messages are ordered within a single partition, never across partitions. Production systems achieve "ordered processing per entity" by routing all events for that entity to the same partition via a partition key.

CORE IDEA Order is a property of a partition, not a topic. Send all events for the same entity (same orderId, userId) with the same key — Kafka hashes the key to pick a partition, so they stay in order on the same log.
1 How partitioning works
// All events for the same orderId land on the same partition
producer.send(new ProducerRecord<>("orders", orderId, eventJson));

// Internally:
// partition = murmur2(orderId) % numPartitions

Consumers in a group own disjoint partitions; one partition is read by exactly one consumer at a time. Per-partition reads are sequential, so all events for one orderId are processed in producer order on a single thread.

2 What can break the ordering guarantee
CauseWhy it breaks orderFix
Producer retries with max.in.flight.requests.per.connection > 1 Message N+1 may land before retried N Set enable.idempotence=true (Kafka enforces ordering on retries)
Repartitioning (changing partition count) New partition for the same key Partition count is forever — never decrease, increase only with care
Consumer parallelism inside one partition Multi-thread processing of the same partition Use Spring Kafka's concurrency=1 per partition or a single executor
Retry-then-skip on a poison message Later messages processed before the failed one is recovered DLQ + accept that within an entity, the failed event is "lost" until replayed
Hot key Order is preserved but throughput is bottlenecked on one consumer Sub-key the entity (userId#shard) if business logic allows
3 Producer config to keep order safe
enable.idempotence=true            # required for safe retries with ordering
acks=all                            # leader + ISR replication
max.in.flight.requests.per.connection=5   # safe with idempotence
retries=Integer.MAX_VALUE
delivery.timeout.ms=120000

With enable.idempotence=true, Kafka's broker keeps a per-producer sequence number per partition and only accepts records in order — retries that arrive out of sequence are buffered and reordered.

4 Cross-partition ordering — when you actually need it

Some systems need a global sequence (e.g., a strict ledger). Two options:

  • Single partition — easiest, but caps throughput at one consumer's speed.
  • Application-level reordering — every event carries a monotonic sequence_number per producer; consumer buffers out-of-order events and applies them in sequence. Complex but works at scale.

For 95% of systems, "per-entity ordering on the same partition key" is enough — global ordering is a smell that often points to over-modeling.

5 Common interview gotchas
  • Order is a partition property, not a topic property — saying "Kafka guarantees ordering" is wrong without "per partition".
  • enable.idempotence=true is required if you have max.in.flight > 1 and want ordering on retries.
  • Increasing partition count rebalances keys to new partitions and can split a single entity's stream — pre-size partitions generously.
  • Consumer concurrency > 1 per partition breaks order — Spring Kafka's concurrency is a per-listener thread count, but each partition is still single-threaded within the container.
  • If a poison message is sent to DLQ, later events for the same key are processed — the DLQ replay must merge back carefully or accept out-of-order recovery.
  • Choose the partition key carefully — too coarse (e.g., region) creates hot partitions; too fine (e.g., random) eliminates ordering.
  • For multi-event business flows that need order across keys (rare), use orchestration (Saga) or a single key per workflow id.

Interview one-liner: Kafka guarantees ordering within a single partition — to preserve ordering for one entity, send all its events with the same partition key (e.g., orderId) so they hash to the same partition. Set enable.idempotence=true on the producer so retries with max.in.flight > 1 don't reorder. Per-partition processing is single-threaded by design, so beware hot keys; cross-partition ordering needs application-level sequencing or a single partition (which caps throughput). For 95% of systems, "per-entity ordering on a partition key" is the right design.

How do you design event-driven architecture for high-scale systems? must

Event-Driven Architecture (EDA) is the dominant pattern for systems that must scale independently per service, absorb traffic spikes, and keep producers decoupled from consumers. Done well it gives you horizontal scale and resilience for free; done poorly it produces a distributed monolith with worse debugging and the same coupling, just hidden behind a queue.

CORE IDEA Services publish domain events ("OrderPlaced", "PaymentCaptured") to a durable log (Kafka). Other services subscribe at their own pace. No producer knows who consumes — coupling collapses to the event schema.
1 Why EDA for high-scale
  • Loose coupling — adding a new consumer (analytics, ML pipeline, notification) needs zero changes to producers.
  • Asymmetric scaling — fast producer, slow consumer? Kafka buffers and the consumer scales out independently.
  • Resilience — consumer outage doesn't fail producers; messages backlog and process when the consumer recovers.
  • Replayability — Kafka's retention lets a new consumer replay history to bootstrap state.
  • Multiple read models — one event drives DB updates, search-index sync, analytics, audit, notifications.
2 Reference architecture for a high-scale event-driven platform
Producer service writes business state to its DB + outbox row in one tx
↓
Outbox publisher (or Debezium CDC) → Kafka topic, partitioned by aggregate id
↓
Schema Registry validates Avro/Protobuf schema at produce time
↓
Consumer groups (per service) read independently — billing, shipping, search-indexer, analytics
↓
Each consumer dedupes on event_id + writes its own read model
↓
Failures → retry topics + DLT; observability stack tracks lag and DLQ depth

5 Throughput levers at scale
  • Pre-size partitions generously — partition count caps consumer parallelism per group; you cannot easily reduce.
  • Compression (compression.type=lz4 or zstd) — 2–5× higher effective throughput, modest CPU cost.
  • Batching — linger.ms=10, batch.size=64KB — far higher throughput per producer.
  • Tiered storage for long retention — Kafka 3.6+ supports remote storage; cheap S3 for cold data.
  • Async processing within consumer — fan out to a worker pool when downstream is slow, but preserve per-key order using a key→executor mapping.
  • Multi-DC / cross-region — MirrorMaker 2 or Confluent Replicator with active-passive or aggregate cluster patterns.
6 Reliability disciplines
  • Outbox pattern for the dual-write problem (DB + Kafka).
  • Idempotent consumers with event_id dedup table.
  • Retry topics + DLT for poison messages.
  • Schema compatibility enforced at produce time by Schema Registry.
  • Observability — consumer lag per group, DLT depth, throughput per topic, end-to-end latency from occurred_at to consumer-write.
  • Backpressure — circuit breakers when consumer's downstream (DB / API) is unhealthy.

E-commerce checkout

OrderPlaced drives billing, fulfillment, search-index, recommendations, analytics — all decoupled.

Payment capture

PaymentCaptured updates the ledger, triggers receipt email, releases inventory hold, updates fraud score.

Real-time analytics

All domain events streamed to Kafka → ksqlDB / Flink → real-time dashboards + ML feature store.

Search index sync

CDC events from primary DB → Kafka → Elasticsearch indexer; near-real-time search without dual writes.

7 Common interview gotchas
  • Synchronous request/response over a queue is anti-pattern — if you need a reply, use HTTP/gRPC. Use events for facts that fan out.
  • Don't put commands in event topics — commands are point-to-point and create coupling. Use a separate command bus or direct call.
  • Ignoring schema evolution → consumers break the moment a producer adds a field.
  • Eventual consistency must be designed for — UIs need "processing…" states, idempotent retries, read-after-write strategies.
  • Skipping the outbox pattern → silent dual-write inconsistency you'll discover during a postmortem.
  • Using events for everything → debugging becomes archaeology across N consumer groups; keep synchronous orchestration for tight workflows.
  • Partition count over-allocation costs ZK/KRaft metadata RAM; under-allocation caps consumer scale-out forever.
  • Consumer lag is the most important metric — alert on it before customers feel it.

Interview one-liner: A high-scale event-driven architecture publishes past-tense domain events to Kafka topics partitioned by aggregate id, with a Schema Registry (Avro/Protobuf) enforcing forward/backward compatibility. Producers use the Transactional Outbox pattern to avoid dual-writes; consumers are idempotent via an event_id dedup table; failures route through retry topics and a DLT with operational replay. Throughput levers — partition pre-sizing, compression, batching, tiered storage; reliability comes from outbox + idempotency + observability on consumer lag. Done well, EDA gives loose coupling, asymmetric scaling, replayable history, and effortless addition of new consumers without touching producers.

What is the difference between queue and topic? must

Queue = one consumer per message (point-to-point). Topic = many subscribers can receive the same message (pub-sub).

Now coming to queue.

Work distribution — only one worker processes each payment message.

Now coming to topic.

Broadcast — fraud alert sent to audit, notification, and analytics services.

Now coming to conclusion.

Point-to-point vs publish-subscribe.

Point-to-point (P2P) delivers each message to exactly one consumer via a Queue; publish-subscribe delivers each message to all active subscribers via a Topic.

P2P / Queue

Message remains in queue until exactly one consumer receives and acknowledges it.

Use for: task delegation (process this payment), work distribution across competing consumers.

Pub-Sub / Topic

Every active subscriber receives a copy; durable subscriber retains messages while offline.

Use for: event broadcasting (transaction posted → audit, SMS, and ledger services all receive the event).

Banking choice

Queue: payment processing tasks — each payment processed by one worker. Topic: transaction events — multiple downstream systems notified.

What is message producer and consumer?

A message producer creates and sends messages to a queue/topic; a consumer receives and processes messages — decoupled via the message broker.

JMS API

Producer: Session.createProducer(destination); producer.send(message); — fire and forget.

Consumer: Session.createConsumer(destination); consumer.receive() (blocking) or MessageListener.onMessage(msg) (async).

Banking

Payment service (producer) sends payment request to PAYMENT.QUEUE; payment processor service (consumer) dequeues and executes fund transfer.

Now coming to conclusion.

Decouple producers and consumers — they can scale independently and the broker handles delivery guarantees.

What is durable subscriber?

A durable subscriber on a JMS Topic retains messages while the subscriber is offline — messages are delivered when it reconnects, unlike non-durable which loses messages during disconnection.

Setup

session.createDurableSubscriber(topic, 'subscriptionName') — registered with broker by unique subscription name.

Messages accumulate on the broker while subscriber is down; delivered in order when subscriber reconnects.

Banking use

Audit logging service as durable subscriber on TRANSACTION.TOPIC — never loses transaction events even during maintenance windows.

Now coming to conclusion.

Use durable subscribers for critical downstream systems that must receive every event — audit, GL, reporting.

What is message acknowledgement?

Message acknowledgement confirms to the broker that the consumer successfully processed a message — the broker then removes it from the queue.

Modes

AUTO_ACKNOWLEDGE: broker removes message immediately after consumer receives it — risk of lost message on consumer crash.

CLIENT_ACKNOWLEDGE: consumer calls message.acknowledge() after processing — broker keeps message until ack received.

DUPS_OK_ACKNOWLEDGE: lazy ack; may redeliver — use only for idempotent consumers.

Banking

Use CLIENT_ACKNOWLEDGE for payment processing: ack only after transaction is successfully posted and committed to DB.

Now coming to conclusion.

CLIENT_ACKNOWLEDGE is the safe choice for financial messaging — ensures no message is lost due to consumer failure.

Auto acknowledge vs client acknowledge.

AUTO_ACKNOWLEDGE automatically acks after message receipt; CLIENT_ACKNOWLEDGE requires the consumer to explicitly call acknowledge() after successful processing.

AUTO_ACKNOWLEDGE

Simpler; message removed from queue as soon as consumer receives it.

Risk: consumer receives message, crashes before processing — message is lost (not redelivered).

CLIENT_ACKNOWLEDGE

Consumer processes message, commits DB transaction, then calls msg.acknowledge().

If consumer crashes before ack: broker redelivers — message not lost. Requires idempotent consumer.

Now coming to conclusion.

Banking payment consumers must use CLIENT_ACKNOWLEDGE — losing a payment message is unacceptable.

What is message redelivery?

Message redelivery occurs when a message is not acknowledged within the timeout — the broker redelivers it to the same or another consumer, up to the configured redelivery limit.

Mechanism

Consumer fails to ack (crash, session close, timeout) → broker marks message as unacknowledged → redelivers.

Redelivery count tracked via JMSXDeliveryCount header; after max retries, moved to DLQ.

Consumer requirements

Consumer must be idempotent: processing the same payment message twice must not double-debit.

Idempotency: check if message reference already processed in DB before processing — return success if already done.

Now coming to conclusion.

Assume any message may be redelivered — design all financial message consumers to be idempotent.

Architecture

Proxy Service: inbound endpoint (SOAP, REST, JMS, File) that receives requests from clients.

Business Service: outbound endpoint representing the actual backend service being called.

Pipeline: processing stages between proxy and business service for transformation, routing, validation, error handling.

Banking

OSB mediates between FLEXCUBE and external payment systems — receives SOAP from FLEXCUBE, transforms to ISO 20022 XML, routes to payment gateway.

Now coming to conclusion.

Why use Oracle Service Bus?

Oracle Service Bus is used to decouple service consumers from providers, enabling format transformation, protocol mediation, routing, and centralized error handling without changing either endpoint.

Benefits

Routing: route to different backends based on message content (transaction type, amount, destination bank).

Operational

OSB reduces point-to-point integration web — 10 systems with 90 P2P connections become 10 + OSB with 20 connections.
