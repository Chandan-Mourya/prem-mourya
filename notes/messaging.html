Kafka vs RabbitMQ must

Both move messages between services, but they were designed for very different problems — a distributed log versus a smart broker. Picking the right one shapes your architecture.

Core Difference
RabbitMQ Message broker — smart routing, push-based, message deleted after ack.
Kafka Distributed log — durable, append-only, pull-based, replayable.
1 Data Model
RabbitMQ
  • Exchanges → Queues. Smart routing (direct, topic, fanout, headers).
  • Once consumed and acked, the message is gone.
Kafka
  • Topics → Partitions. Each partition is an ordered append-only log.
  • Messages stay for a retention period (days/weeks) — replayable.
2 Delivery Model
RabbitMQ
  • Push — broker pushes to consumers.
  • Per-message ack; redelivers on failure.
  • Supports priorities, per-message TTL, dead-letter exchanges.
Kafka
  • Pull — consumer polls at its own pace.
  • Tracks position via offsets; consumer controls progress.
  • Many consumer groups can read the same topic independently.
3 Throughput & Scale
RabbitMQ
  • Tens of thousands msg/s per node.
  • Scales vertically; cluster mode exists but is complex.
Kafka
  • Millions msg/s on a small cluster.
  • Horizontally scaled by adding partitions and brokers.
  • Built for throughput from day one.
4 Ordering & Replay
RabbitMQ
  • Per-queue ordering only with a single consumer.
  • No native replay — once acked, it's gone.
Kafka
  • Ordering per partition guaranteed.
  • Replay by offset — perfect for event sourcing, debugging, new consumers backfilling history.
5 Use Case
RabbitMQ
  • Work queues — emails, image processing, retry jobs.
  • Request/response, RPC, fan-out to specific routing keys.
  • Priorities, delays, complex routing rules.
Kafka
  • Event streams — every domain event published once, consumed by many.
  • Log aggregation, CDC (Change Data Capture), metrics pipelines.
  • Event sourcing, stream processing (Kafka Streams, Flink).
Rule of thumb: use RabbitMQ for work queues (jobs to be done) and Kafka for event streams (facts to be published once and read by many). At OneXtel I used Kafka for SMS event streams (millions/day, replayable) and RabbitMQ for per-customer notification jobs (priority + per-message TTL).
How does Kafka work under the hood?

A Kafka cluster has brokers. Data is organized into topics, each split into partitions (the unit of parallelism). Each partition is an ordered, immutable log appended to disk.

Producers send messages with a key — Kafka hashes the key to pick a partition, so messages with the same key always land on the same partition (preserving order per key). Each message gets an offset.

Consumers belong to a consumer group. Kafka assigns each partition to exactly one consumer in the group — so n partitions support up to n parallel consumers per group. Consumers commit offsets back to Kafka.

Each partition has a leader replica + follower replicas across brokers for fault tolerance. Producers write to the leader; ISR (in-sync replicas) replicate. If a leader dies, a follower is promoted. Modern Kafka uses KRaft (no Zookeeper) for cluster metadata.

Delivery guarantees — at-most-once, at-least-once, exactly-once hot

Three levels of guarantee for messaging.

At-most-once — fire-and-forget. Message may be lost but never duplicated. Used for metrics/logs where occasional loss is OK.

At-least-once — every message is delivered, possibly multiple times. The default, and what almost every production pipeline does. Consumers must be idempotent — process the same message twice with the same effect (use natural keys, version checks, or idempotency-key tables).

Exactly-once — every message processed exactly once. Hard. Kafka supports it within Kafka's own boundaries (enable.idempotence=true + transactional producer); end-to-end (Kafka → DB → Kafka) requires care. Stripe's CTO once said: "exactly-once is at-least-once + idempotency on the consumer."

I design for at-least-once + idempotent consumers. Simpler, robust, and gives effective exactly-once semantics in practice.

Kafka consumer offsets and rebalancing

Each consumer in a group tracks its current offset per partition — the next message to read. Offsets are committed back to Kafka periodically (auto-commit) or manually (more reliable).

When a consumer joins or leaves the group, Kafka triggers a rebalance — partitions are redistributed. The classic gotcha: if processing is slow and the consumer doesn't poll within max.poll.interval.ms, Kafka assumes it's dead and reassigns its partitions → duplicate processing.

Practices I follow:

  • Manual commit after successful processing — auto-commit can lose messages on crash.
  • Tune max.poll.records and max.poll.interval.ms so a batch finishes well before the timeout.
  • Use Kafka's cooperative rebalancing (incremental) instead of eager stop-the-world.
  • Idempotent processing so reprocessing on rebalance is safe.
Dead Letter Queue — what and why?

A Dead Letter Queue (DLQ) is a separate queue where you park messages that repeatedly fail to be processed. Without one, a poison message blocks the partition or causes endless retries that waste resources.

Typical pattern: try to process N times with backoff; if still failing, move to topic.DLQ with metadata (original topic, partition, offset, error message, attempt count). Operations can inspect, fix data, and replay from DLQ.

In Spring Kafka, a DefaultErrorHandler + DeadLetterPublishingRecoverer wires this up declaratively. With RabbitMQ, declare a queue with a dead-letter-exchange argument.

At OneXtel we had a DLQ for SMS that failed delivery — operators could see them in a UI, fix the carrier mapping, and replay. Without that, a single bad operator config would have backed up the entire queue.

How do you ensure message ordering?

Kafka guarantees order within a partition, not across partitions. To preserve ordering for a specific entity, send all its messages with the same key — they go to the same partition.

// All events for the same orderId stay in order
producer.send(new ProducerRecord("orders", orderId, event));

Two consequences. (1) Per-partition processing is sequential — if one entity is hot, you can't parallelize its processing. Watch for hot keys. (2) If you need to retry messages, retrying out-of-order breaks ordering — sometimes you must pause the partition during retry or accept brief out-of-order processing.

Cross-partition ordering needs an external sequence in each event (Lamport timestamps, vector clocks) and reordering on the consumer side. Usually not worth the complexity — design so per-entity order in one partition is sufficient.

Event-driven architecture — what's the win?

Event-driven architecture (EDA): services publish domain events ("OrderPlaced", "UserSignedUp") to a stream; other services subscribe and react. No service knows who consumes its events.

Wins:

  • Loose coupling — add a new consumer without touching producers. The Inventory team can build a "track popularity" service from OrderPlaced without coordinating with Checkout.
  • Resilience — consumer outages don't fail producers; events buffer in Kafka.
  • Auditability — events are a permanent record; replay rebuilds state.
  • Multiple read models — same event drives DB updates, ES indexing, analytics, notifications.

Costs: eventual consistency in UI, harder debugging, schema evolution discipline (use a schema registry — Avro/Protobuf with backward-compat rules). On Punctuations.ai we made EDA core — resume changes flow as events into ES, analytics, audit, and notifications.
