String pool — what does this print? 
String a = "hello";
String b = "hello";
String c = new String("hello");
String d = c.intern();

System.out.println(a == b);  // ?
System.out.println(a == c);  // ?
System.out.println(a == d);  // ?
System.out.println(a.equals(c));  // ?

Output: true, false, true, true

Why: Literals "hello" are interned into the String pool, so a and b point to the same object. new String("hello") forces a fresh heap object → different reference (a == c false). c.intern() returns the pooled instance, so a == d is true. equals() compares content, always true here.

Lesson: never use == on Strings. Always .equals().

Integer cache trap hot 
Integer a = 100;
Integer b = 100;
Integer c = 200;
Integer d = 200;

System.out.println(a == b);  // ?
System.out.println(c == d);  // ?
System.out.println(a.equals(b));  // ?
System.out.println(c.equals(d));  // ?

Output: true, false, true, true

Why: Integer.valueOf(n) caches values from -128 to 127. So 100 returns the same cached Integer → a == b true. 200 is outside the cache → new boxed objects each time → reference compare fails. equals() compares values, always true.

Lesson: never use == on wrapper types. Same for Long, Short, Byte, Character.

finally with return — which value wins? 
public static int test() {
    try {
        return 1;
    } finally {
        return 2;   // overrides the try return
    }
}
// What does test() return?

Output: 2

Why: a return in finally always overrides any return (or exception!) from try. The try block's return value is computed and stored, but the finally's return replaces it.

Lesson: never return from finally — it silently swallows exceptions and overrides results. Most IDEs warn about this. Use finally only for cleanup; let the try-catch decide what to return.

finally with mutation — but not return 
public static int test() {
    int x = 1;
    try {
        return x;
    } finally {
        x = 2;   // mutate, but don't return
    }
}

Output: 1

Why: The return value is evaluated and saved before finally runs. Finally can mutate x, but the value to be returned has already been captured.

Contrast this with the previous puzzle — the rule is: finally can override via its own return, but post-evaluation mutations to local variables don't propagate.

Autoboxing in collections — NullPointerException? 
Map<String, Integer> counts = new HashMap<>();
counts.put("a", 1);
int total = counts.get("a") + counts.get("missing");
// What happens?

Output: NullPointerException

Why: counts.get("missing") returns null (Integer). Auto-unboxing null to int throws NPE — and the stack trace doesn't make it obvious which line caused it.

Lesson: guard against this with getOrDefault(key, 0) or check for null. This is one of the most common production NPEs.

Switch on Integer — null hazard 
Integer x = null;
switch (x) {
    case 1: System.out.println("one"); break;
    default: System.out.println("other");
}

Output: NullPointerException

Why: switch on a wrapper auto-unboxes — and unboxing null throws NPE. Same for switch on String with a null reference.

Lesson: always null-check before switching on wrappers/Strings, or use Java 21+ switch patterns that can explicitly handle null with a case null branch.

Static initialization order 
public class A {
    static int x = B.y + 1;
}
public class B {
    static int y = A.x + 1;
}
// What if we load A first?

Output: A.x = 2, B.y = 1 (depends which is loaded first)

Why: Class loading triggers static initialization. If A loads first, A.x evaluation needs B.y — triggers B's initialization. At that point A is being initialized, so A.x is still the default 0. So B.y = 0 + 1 = 1. Then back in A: x = 1 + 1 = 2.

Lesson: circular static dependencies produce hard-to-debug bugs. Avoid them; if you must, document which class is loaded first.

Overriding vs overloading at compile time 
class Animal {
    void eat(Object o) { System.out.println("Animal Object"); }
}
class Dog extends Animal {
    void eat(String s) { System.out.println("Dog String"); }
    @Override
    void eat(Object o) { System.out.println("Dog Object"); }
}

Animal a = new Dog();
a.eat("bone");

Output: Dog Object

Why: Method resolution is compile-time on parameter types (overloading) and runtime on receiver (overriding). The compiler sees a as Animal — Animal only has eat(Object). So at compile time, eat(Object) is selected. At runtime, dynamic dispatch picks Dog's overridden version: "Dog Object". The eat(String) overload in Dog isn't visible through the Animal reference.

HashMap put with mutable key 
class Key {
    int id;
    public int hashCode() { return id; }
    public boolean equals(Object o) { return o instanceof Key && ((Key)o).id == id; }
}

Map<Key, String> map = new HashMap<>();
Key k = new Key();
k.id = 1;
map.put(k, "hello");

k.id = 2;       // mutate the key after insertion
System.out.println(map.get(k));
System.out.println(map.size());

Output: null, 1

Why: the entry was placed in bucket(hash(1)). After mutation, looking up k hashes to bucket(hash(2)) — empty. The entry is still in the map (size = 1) but unreachable.

Lesson: always use immutable keys for HashMap. This is why String, Integer, and records make ideal keys.

Stream — terminal op missing 
List<Integer> nums = List.of(1, 2, 3);
nums.stream()
    .filter(n -> { System.out.println("filtering " + n); return n > 1; })
    .map(n -> { System.out.println("mapping " + n);    return n * 2; });
System.out.println("done");

Output: just "done" — none of the inner prints

Why: Stream intermediate operations (filter, map) are lazy. Without a terminal op (collect, forEach, count, reduce), the pipeline never executes.

Lesson: "my stream isn't doing anything" is almost always a missing terminal operation.

Concurrent modification 
List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4));
for (Integer n : list) {
    if (n == 2) list.remove(n);
}

Output: ConcurrentModificationException (on most JVMs)

Why: The for-each loop uses an iterator. ArrayList's iterator is fail-fast — it checks modCount on each next(). Removing through the list (not the iterator) bumps modCount, so the next iteration throws.

Fixes:

  • Iterator.remove() — the iterator-aware way.
  • list.removeIf(n -> n == 2) — clean, since Java 8.
  • Stream + collect to a new list.
Boolean.parseBoolean vs valueOf 
System.out.println(Boolean.parseBoolean("TRUE"));   // ?
System.out.println(Boolean.parseBoolean("yes"));    // ?
System.out.println(Boolean.valueOf("true").booleanValue());  // ?

Output: true, false, true

Why: parseBoolean is case-insensitive but accepts only "true" or anything-else (which is false). "yes" is anything-else, so false. valueOf("true") follows the same rule and returns Boolean.TRUE.

Lesson: if you parse user input (form, env var), validate explicitly — don't rely on "any other string is false" semantics.

Generic method type inference 
public static <T> List<T> emptyList() {
    return new ArrayList<>();
}

List<String> xs = emptyList();        // OK
Object o = emptyList();               // What type is T inferred to?

Output: Object — but compiles. T is inferred from the target type.

Why: Java's type inference uses the assignment context. For List<String> xs = emptyList(), T is String. For Object o = emptyList(), no list type is specified, so T defaults to Object.

Lesson: if inference is ambiguous, specify explicitly: Collections.<String>emptyList(). Useful when chaining onto a generic factory method.

Equals symmetry trap 
class Point {
    int x, y;
    public boolean equals(Object o) {
        if (!(o instanceof Point)) return false;
        Point p = (Point) o;
        return p.x == x && p.y == y;
    }
}
class ColorPoint extends Point {
    String color;
    public boolean equals(Object o) {
        if (!(o instanceof ColorPoint)) return false;
        return super.equals(o) && ((ColorPoint)o).color.equals(color);
    }
}

Point p = new Point(); p.x = 1; p.y = 2;
ColorPoint cp = new ColorPoint(); cp.x = 1; cp.y = 2; cp.color = "red";

System.out.println(p.equals(cp));   // ?
System.out.println(cp.equals(p));   // ?

Output: true, false — violates symmetry

Why: Point's equals accepts any Point, so it sees cp as a Point and returns true. ColorPoint's equals requires a ColorPoint, so p (plain Point) is rejected.

Lesson: mixing inheritance + equals is hard. Best practices: prefer composition, mark equals classes as final, or use getClass() instead of instanceof. This is exactly why Effective Java item 10 spends pages on equals contracts.

Why this synchronizes nothing 
class Counter {
    private Integer count = 0;
    public synchronized void increment() {
        count++;
    }
}
// Two threads share a Counter and call increment() in a loop.
// Is count thread-safe?

Output: safe within one Counter, but with a subtle issue.

Why: the synchronized method synchronizes on this, so two threads calling on the same Counter are mutually excluded. count++ on Integer creates a new Integer each time (autoboxing), but the increment is still atomic relative to other increment calls.

However: if any non-synchronized reader reads count without synchronization, the JMM doesn't guarantee visibility. Either make the field volatile, synchronize reads, or use AtomicInteger. The puzzle is more about subtle JMM rules than the lock itself.
