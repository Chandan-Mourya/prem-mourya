SOAP vs REST.

SOAP is a protocol with XML envelope, WSDL contract, and WS-Security; REST is an architectural style using HTTP verbs with JSON payloads and no enforced message format.

SOAP

Strict XML Envelope (Header+Body); WSDL defines contract; XSD validates messages; stateful support via WS-Addressing.

Enterprise features: WS-Security (message-level encryption/signing), WS-AtomicTransaction, WS-ReliableMessaging.

REST

Lightweight; JSON or XML; uses HTTP methods semantically; stateless; easy to consume from any client.

No built-in transaction or security standards — layered via OAuth2/mTLS/JWT.

Banking

SOAP: inter-bank integration, SWIFT interfaces, legacy core banking. REST: digital channels, microservices.

Now coming to conclusion.

Choose SOAP when WS-Security or WS-AtomicTransaction is required; REST for all new banking API development.

What is XSD?

An XSD (XML Schema Definition) defines the structure, data types, and constraints for XML documents — used by SOAP services to validate request and response messages.

Structure

Defines: elements (names, types), complex types (nested elements), simple types (restrictions on strings/numbers).

xs:element, xs:complexType, xs:sequence, xs:restriction — core XSD constructs.

SOAP validation

SOAP stack validates incoming XML against XSD before processing — invalid messages rejected with fault response.

XSD version changes require coordinating with all consumers — adding a mandatory element is a breaking change.

Banking

ISO 20022 messages (pacs.008, camt.054) have strict XSD schemas — compliance mandatory for payment system integration.

Now coming to conclusion.

XSD is the contract enforcement mechanism for SOAP — always validate incoming messages against the XSD.

How do you consume SOAP service in Java?

Consume a SOAP service in Java by generating client stubs from the WSDL using wsimport or CXF wsdl2java, then calling the service via the generated proxy.

wsimport / JAX-WS

wsimport -s src -d classes http://service.bank.com/payment?wsdl — generates service and port classes.

PaymentService service = new PaymentService(); PaymentPort port = service.getPaymentPort(); Response r = port.processPayment(req);

Apache CXF

Add CXF to pom.xml; configure wsdl2java plugin; use generated stub. CXF supports interceptors for WS-Security headers.

Spring-WS

WebServiceTemplate.marshalSendAndReceive(uri, request) — marshals Java object to SOAP XML, sends, unmarshals response.

Now coming to conclusion.

Always regenerate stubs when the WSDL changes — stale stubs cause runtime marshaling failures.

How do you secure SOAP service?

SOAP services are secured using WS-Security (message-level) with UsernameToken, X.509 certificate signing/encryption, or transport-level TLS.

WS-Security

UsernameToken: username/password in SOAP header — basic but simple. X.509: sign the SOAP body with private key; encrypt with recipient's public key.

Provides message-level security — protected end-to-end even if intermediaries are present.

Transport level

HTTPS (TLS): encrypts the HTTP channel; simpler but only protects in transit — intermediary can read/modify.

mTLS: client certificate authentication at transport level — used for bank-to-bank SOAP calls.

Now coming to conclusion.

For inter-bank SOAP, use X.509 message-level signing for non-repudiation — transport TLS alone is insufficient.

What is WS-Security?

WS-Security is a SOAP extension standard for message-level security: authentication (UsernameToken, X.509), message integrity (XML signature), and confidentiality (XML encryption).

Components

Security header in SOAP envelope: contains UsernameToken or BinarySecurityToken (X.509 cert) for authentication.

XML Signature: signs SOAP body with sender's private key — receiver verifies with sender's public key.

XML Encryption: encrypts specific SOAP elements with recipient's public key — ensures confidentiality.

Banking use

FLEXCUBE exposes SOAP services secured with WS-Security X.509 — partners must present valid certificate to call.

Now coming to conclusion.

WS-Security provides non-repudiation (signature) and confidentiality (encryption) — both important for financial messages.

What is MTOM?

MTOM (Message Transmission Optimization Mechanism) is a SOAP optimization for transmitting binary data (documents, images) by attaching them as MIME parts instead of base64-encoding in XML.

Problem it solves

Base64-encoding binary data in XML increases size by ~33% and requires expensive parsing.

MTOM: binary data attached as MIME multipart; XML references the attachment — much more efficient.

Banking use

Sending KYC document scans or cheque images via SOAP — MTOM reduces payload size and processing time.

Now coming to conclusion.

Use MTOM for any SOAP service that transmits binary attachments — standard for document-heavy banking integrations.

How do you debug SOAP request/response?

SOAP request/response is debugged by capturing the raw XML using logging interceptors, OSB message logs, or network proxies (Fiddler/Wireshark) to inspect the actual SOAP envelope.

Tools

Apache CXF: add logging interceptor (LoggingInInterceptor, LoggingOutInterceptor) to log full SOAP XML.

OSB pipeline: add Log action in request/response pipeline to log message body to server log.

SoapUI: send test SOAP requests manually; inspect request and response XML side by side.

Validation

Copy captured request XML into xmllint --schema service.xsd — validates against WSDL schema.

Now coming to conclusion.

Always log SOAP request and response with timestamp and correlation ID for post-incident debugging.

How do you handle SOAP timeout?

SOAP timeouts are handled by setting connect/read timeouts on the HTTP binding, implementing retry with exponential backoff, and providing a meaningful fault response on timeout.

Configuration

JAX-WS: ((BindingProvider) port).getRequestContext().put(BindingProviderProperties.REQUEST_TIMEOUT, 30000);

CXF: HTTPConduit conduit = ...; HTTPClientPolicy policy = ...; policy.setReceiveTimeout(30000);

Handling

Catch SOAPFaultException or SocketTimeoutException; log timeout with correlation ID; return error response to caller.

Retry only if the operation is idempotent — SOAP read operations yes; payment operations only with idempotency key.

Now coming to conclusion.

SOAP timeouts without retry leave the caller waiting indefinitely — always set explicit timeouts on all bindings.

How do you expose SOAP service from Java?

Expose a SOAP service from Java using JAX-WS annotations (@WebService, @WebMethod) with a servlet container deployment or Spring-WS with @Endpoint.

JAX-WS

@WebService(serviceName='PaymentService') on class; @WebMethod on each operation.

Deploy to WebLogic as WAR — JAX-WS runtime handles WSDL generation (?wsdl suffix on URL).

Spring-WS

@Endpoint class with @PayloadRoot(namespace='...', localPart='ProcessPaymentRequest') on method.

Configure MessageDispatcherServlet in web.xml; define WSDL bean; Spring-WS handles routing and marshaling.

Now coming to conclusion.

JAX-WS is simpler for straightforward services; Spring-WS for contract-first development with strict XSD control.
